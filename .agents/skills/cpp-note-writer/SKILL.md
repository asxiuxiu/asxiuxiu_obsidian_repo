# C++ 引擎笔记写作 Skill

## 服务定位

本 skill 是 `Notes/C++编程/` 目录下笔记的**专用生产工具**。它不替代 `note-refine`（叙事质量审查），而是与其配合：

- **本 skill**：负责「写什么」和「怎么组织内容」——确定笔记结构、叙述方式与代码表达，生成正文，建立引擎映射
- **`note-refine`**：负责「写得怎么样」——在初稿产出后进行费曼质量审查和叙述优化

产出笔记必须**单点聚焦**：一篇笔记只回答一个核心问题，覆盖一个核心机制。

## 触发场景

当用户表达以下任何一种意图时触发：

- "帮我写/新建一篇 C++ 笔记"
- "写一篇关于 XXX 的 C++ 笔记"
- "重写/整理 C++ 里的 XXX"
- "根据 RoadMap 写笔记"
- "补充 C++ 索引里标记为 ⬜ 的笔记"

## 前置依赖

执行本 skill 前，**必须先读取以下 skill**：

1. **`note-refine`** — 理解费曼叙述规范、写作方法与自检清单
2. **`obsidian-markdown`** — 确保 frontmatter、wikilink、callout、代码块格式正确

## 笔记标题规范

**禁止用「为什么…」作为标题。** 标题应为陈述式或主题式，直接点明笔记要讨论的核心机制。

| ❌ 不推荐 | ✅ 推荐 |
|---------|--------|
| 为什么 `std::move` 不移动任何东西？ | 右值引用与 `std::move` 的本质 |
| 为什么虚函数调用比普通函数慢？ | 虚函数表的底层实现 |
| 为什么 C++ 需要四种类型转换？ | C++ 四种类型转换的分工与边界 |

**标题格式**：
- 不用前缀编号（如 `01-`、`1.`）
- 不用问号、冒号等 Windows 非法字符
- 文件名与笔记 `title` frontmatter 保持一致
- 示例：`C++ 虚函数表的底层实现.md`、`右值引用与移动语义.md`

## 正文叙事规范

画面叙事没有唯一强制写法。**叙述方式随内容自然选择**。核心原则继承自 note-refine：Why 先行、零假定、场景绑定、因果清晰、让零基础读者顺畅理解。可以走机制式、对比式、场景贯穿式，或用演进式（naive → 改进）；演进式只在确有技术演进时选用，不是唯一或首选结构。

### 叙述方式可选角度

不同笔记适合不同切入方式，不强求统一：

- **机制式**：直接讲清语言机制、数据结构、编译行为，配最小代码验证
- **需求式**：从「一个具体需求或缺陷」出发，讲清楚怎么做、为什么这么做能解决
- **对比式**：两种用法的取舍与代价（如传值 vs 传引用、`move` vs 拷贝）
- **场景绑定式**：绑定引擎中的具体使用/故障场景贯穿全篇
- **演进式**：梳理语言特性/概念的演进链条（naive → 缺陷 → 改进），仅在此前有真实演进逻辑时用

无论选哪种，都要求**叙述自洽**：零基础读者能顺着一条线索读到底，而不是看到并列的概念堆砌。

### 通用写作要点（继承自 note-refine）

1. **零假定**：首现术语先用 1~2 句人话解释，再加正式名称/缩写；若 vault 已有讲解，用完整路径 wikilink 指向具体标题
2. **Why 先行**：核心概念第一次出现前，先让读者感到「这问题确实需要解决」，绑定引擎场景说清"不这么做会在什么场景出问题"
3. **代码优先**：能用一小段代码/编译行为说清楚的，就不要用大段文字；每个关键机制配可运行的最小示例
4. **因果清晰**：涉及演进时把「因为…所以…」写清楚，但不强制套固定结构

### 演进式叙述参考（可选）

> 若写到的主题确实存在「朴素做法 → 缺陷 → 改进」的真实演进，可按此组织（否则用前面其它角度即可）：

```
朴素理解：如果不用虚函数，怎么让基类指针调用不同子类的方法？
  → naive：基类放枚举 type + switch-case → 新增子类要改所有 switch
改进：虚函数 + 虚函数表 → 编译器塞 vptr，调用期查表 → 每对象多 8 字节、多两次间接
深入：多重继承时有几个 vptr？this 为什么漂移？→…
```

## C++ 代码示例规范

笔记中的代码块**统一使用 `cpp`** 语言标签，遵循 Run Code 插件规范：

```cpp
// flags: -O0 -g
#include <iostream>

struct Base {
    virtual void foo() { std::cout << "Base\n"; }
};

struct Derived : Base {
    void foo() override { std::cout << "Derived\n"; }
};

int main() {
    Base* b = new Derived();
    b->foo();  // 输出 Derived
    delete b;
    return 0;
}
```

| 规范 | 说明 |
|------|------|
| 编译参数 | 通过 `// flags:` 注释控制，放在代码块顶部 20 行内 |
| 追加参数 | `// flags: -O0 -g` 追加到默认参数之后 |
| 替换参数 | `// flags: override -O3 -DNDEBUG` 完全替换默认参数 |
| 默认参数 | `-std=c++20 -Wall -O2` |

**代码示例的选取原则**：
- 每个关键机制至少有一个可运行的最小示例
- 示例要「小」——删掉一切与当前机制无关的代码
- 示例要「能验证」——运行后能看到明确输出，证明你的结论

## 引擎映射规范

每篇笔记必须在**结尾处**设置一个「引擎映射」小节，明确回答：

> **这个 C++ 机制在 UE / Bevy / chaos 源码中对应什么？**

```markdown
---

## 引擎映射

| 引擎 | 应用场景 | 具体体现 |
|------|---------|---------|
| **UE** | `UObject` 的反射与序列化 | `UProperty` 宏生成的反射表替代了手写的 vtable，支持编辑器实时修改 |
```

## 工作流程

### 第一步：确认主题范围

1. 读取 `Notes/C++编程/索引.md`，确认用户要写的笔记属于哪个主题
2. 明确这篇笔记的**核心问题**（只能有一个）
3. 确认前置知识：列出读者需要已经掌握的概念（用于文末的「相关笔记」链接）

### 第二步：确定叙述方式

1. 先想清楚正文**用什么角度组织**（机制式 / 需求式 / 对比式 / 场景绑定式 / 演进式），选当前主题最自然的一种，不必套固定模板
2. 无论选哪种，都确保覆盖：
   - [ ] 核心机制讲清楚：数据/编译层面长什么样、关键步骤、配最小代码
   - [ ] 有引擎场景绑定，而不是纯概念罗列
   - [ ] 覆盖边界情况和常见陷阱

### 第三步：生成正文

1. 按模板创建文件，填充 frontmatter
2. 按第二步确定的叙述方式撰写正文，每个关键机制配：
   - 场景绑定（这个机制在什么引擎场景下被用到）
   - 机制讲解（用自己的话写，不要复制 cppreference）
   - 代码验证（可运行的 minimal example）
3. 撰写「引擎映射」小节（映射对象为保留的 UE / Bevy / chaos 源码分析）
4. 添加「相关笔记」wikilink

### 第四步：自检（在交付前执行）

对照以下清单自检，确认后再交付：

- [ ] **单点聚焦**：这篇笔记是否只回答了一个核心问题？如果涉及多个并列概念，是否该拆成多篇？
- [ ] **标题合规**：标题是否陈述式/主题式，没有「为什么」开头？
- [ ] **叙述自洽**：正文是否有一条清晰线索让读者顺畅读到底，没有并列概念堆砌？
- [ ] **零假定**：首次出现的术语是否有 1~2 句人话解释？
- [ ] **代码可运行**：每个代码块是否能在 Run Code 插件中编译运行？
- [ ] **引擎映射**：结尾是否有「引擎映射」小节，明确连接 UE / Bevy / chaos 源码分析？
- [ ] **链接完整**：是否通过 wikilink 连接了 vault 中已有的相关笔记？
- [ ] **表格只用于总结**：表格是否只出现在机制讲解之后，而不是用于首次引入概念？

### 第五步：交付与后续

1. 将新笔记路径添加到 `Notes/C++编程/索引.md`，更新状态列
2. 如果笔记质量要求高，触发 `note-refine` 进行深度审查

## 注意事项

- **不要写百科**：拒绝「第一种…第二种…第三种…」的并列罗列。如果发现自己开始罗列，试着换成一种更有线索的叙述（机制式、对比式或演进式）。
- **不要过度引用标准原文**：cppreference 是查细节用的，笔记应该用你自己的话解释机制。只有在精确说明标准行为时才引用标准条款。
- **比喻要贯穿**：如果用了比喻（如「虚函数表就像电话簿」），确保这个比喻在整篇笔记中持续发挥作用，不是开头提一下就扔掉。
- **诚实面对不理解**：如果某个机制你还没想透，不要硬写。写一个「问题笔记」记录当前的理解和待验证假设，比写一篇错误的笔记更有价值。
- **代码优先于文字**：能用 10 行代码说清楚的，不要用 200 字描述。C++ 笔记的核心是「可验证」。

# 动画系统笔记写作 Skill

## 服务定位

本 skill 是 `Notes/动画系统/` 目录下笔记的**专用生产工具**。它不替代 `note-refine`（叙事质量审查），而是与其配合：

- **本 skill**：负责「写什么」和「怎么组织内容」——结合 `Notes/动画系统/索引.md` 的 RoadMap，确定笔记结构、生成正文、插入结构/算法表达、在结尾附参考实现（UE）映射
- **`note-refine`**：负责「写得怎么样」——初稿产出后的费曼质量审查和叙述优化

产出笔记必须**单点聚焦**：一篇笔记只回答一个核心问题，覆盖一个核心机制。动画笔记尤其要求用**数据流**视角写作。

> [!important] 引擎无关立场
> 动画系统的核心概念（关键帧采样、姿势混合、状态机、混合空间、IK、Root Motion）**与引擎无关**——换任何引擎或自研运行时都是同一套东西。笔记正文必须按引擎无关的机制来写，不出现"UE 里怎么做"的主线叙述；UE 源码只在结尾「参考实现（UE）」小节作为工业界落地形态的对照。
>
> **少提 UE，多讲「怎么来的」**：正文只讲通用机制，连"骨骼"这类概念也要先把通用含义讲透；「参考实现（UE）」小节压到一张映射表 + 一两句点评，它是索引不是学习目标；推导要讲清「怎么一步步来的」——这个概念为什么出现、解决了什么缺陷，因果链比结论更重要。
>
> [!warning] UE 类名必须核对源码，不确定就概括描述
> 「参考实现（UE）」小节里的每个 `F...` / `U...` 类名都必须是真实存在的。**凭印象编造类名是硬错误**——读者会照着去查，查不到就是信任崩塌。
> - 不确定时，两种正确做法：① 用通用描述替代（如「脚部落地节点」而不是编一个类名）；② 直接查源码确认（UE 源码根目录见 `.engine-source-config`）：`grep -rl "FSomeName" <UE_SOURCE_ROOT>/Engine/Source/Runtime --include=*.h`
> - 注意引擎版本差异：某些节点/类在特定版本里才存在（或已被移除），不确定时描述成「编辑器工具链里的重定向资产」这类概括说法，比写一个查不到的类名好。

> [!important] 唯一硬标准：把概念讲透
> 衡量一篇笔记好坏的**唯一硬标准是「一个零基础读者能否顺着一条线索把核心概念真正读懂」**。代码、公式、图、可运行验证都只是服务于这个目的、可选的表达手段——概念讲透了，手段哪怕朴素也合格；概念没讲透，手段再花哨（一堆可跑通却与理解无关的代码）也是失败。写作资源优先投向 Why 先行、直观直觉、因果链路、可感的视觉后果。

> [!important] 第二硬标准：实用性过滤——只写「会影响你下手」的知识
> 游戏开发里，很多东西**不需要深究底层原理，知道结论和影响就足够了**。写笔记前必须对每个知识点做一次过滤，问自己：
>
> > **「不知道这条，我在项目里会做出什么错误的决定？」**
> >
> > 答不上来 → 它不该占据正文篇幅。写一句"知道有这回事"即可，或收进折叠区块。
>
> 最典型的反面例子是**四元数的推导**：底层乘法怎么展开、旋转向量为什么是 `qvq*`、半角是怎么凑出来的——这些对调动画、做美术创作**没有任何决策价值**。真正影响下手的是另外几条：乘法顺序写反会导致姿势错位、`q` 与 `-q` 同姿态会让插值绕远路、轴不归一化会让角色"发胖"。**前者是数学家的事，后者才是开发者的事。**
>
> 具体到写作，每个知识点落入以下三类之一，处理方式完全不同：
>
> | 类别 | 判断标准 | 处理方式 |
> | :--- | :--- | :--- |
> | **必须懂** | 不知道就会做出错误决策、写出错误代码、看不出 bug | 用整节篇幅讲透，配场景与视觉后果 |
> | **知道即可** | 知道它存在、知道它解决什么问题就够了，细节由引擎封装 | 一两句说清「是什么 + 什么时候会遇到」，**不推导** |
> | **可以不知道** | 纯内部实现细节，绕开它不影响任何使用 | 折叠区块收纳，或直接不提 |
>
> 判断"必须懂"的硬测试：**它能不能被翻译成一个可视或可感知的后果？** 翻译不出来的，一律降级。同时防两种偏差：**宁缺毋滥**（三个讲透的概念远胜十个各讲一半的）与**别砍过界**（"必须懂"的必须配场景配后果）。
>
> **这就是「实用性过滤」的全部规则，后文只讲怎么执行。**

> [!important] 第三硬标准：每个结论只讲一次（防跨节重复）
> 实用性过滤管的是「**要不要写**这个知识点」，这一条管的是「**写几遍**」。**查重复不能用"单段质量"，只能用"出现次数"**：重复段落删掉任意一处都不影响理解，所以删掉测试、翻译测试对重复天然失效。详细的小节职责表、硬预算与判断方法见下文「小节职责分配」。

当用户表达以下任何一种意图时触发：

- "帮我写/新建一篇动画系统笔记"
- "写一篇关于 XXX 的动画系统笔记"
- "补全动画系统 RoadMap 里标记为 ⬜ 的笔记"
- "根据动画系统索引写笔记"
- "把 `Notes/动画系统/` 某篇骨架笔记填充完整"

## 前置依赖

执行本 skill 前，**必须先读取以下 skill**：

1. **`obsidian-markdown`** — 确保 frontmatter、wikilink、callout、代码块格式正确
2. **`note-refine`** — 理解费曼叙述规范、写作方法与自检清单

## 与 RoadMap 索引的联动

动画系统笔记不是凭空写的，而是**填充 RoadMap**。开始前必须：

1. 读取 `Notes/动画系统/索引.md`，定位用户要写的笔记在哪个块（🔴 必懂 / 🟡 常用 / ⚪ 了解）、哪一篇
2. 该笔记在索引中的「核心问题」即本篇要回答清楚的重点——它决定你选择哪种叙述方式，以及正文要覆盖哪些要点
3. 完成后把索引中对应笔记的状态列从 `⬜` 改为 `✅`

## 优先级与详略

索引把笔记分为三档，**写作深度必须匹配档位**：

| 档位 | 定位 | 写法 |
|------|------|------|
| 🔴 必懂 | 调角色动画时天天打交道的概念 | 逐篇写透：Why 先行、机制推导、典型坑、数值边界一个不少 |
| 🟡 常用 | 项目里定期会遇到 | 讲清机制与典型场景即可，不穷尽边角情形 |
| ⚪ 了解 | 多数项目用不到 | 速览篇：每个话题只回答「它是什么、什么项目才需要它」，不推导机制；末尾指向参考实现供深挖 |

每篇 🔴/🟡 笔记的「为什么需要解决这个问题」小节，必须落到**调动画时的具体场景**，而不是抽象的知识体系定位。

**档位决定「整篇写多深」，实用性过滤决定「篇内每个知识点写多深」——两者叠加，不冲突。** 一篇 🔴 笔记同样可以（也应该）包含"知道即可"的知识点；档位高不等于每个细节都要展开推导。以四元数篇为例，对照 vault 内已完成的 [[Notes/动画系统/旋转与变换基础/四元数的几何意义与运算|四元数的几何意义与运算]]：

| 知识点 | 分类 | 实际写法 |
| :--- | :--- | :--- |
| 乘法顺序写反 → 姿势错位 | 必须懂 | 整节展开，配"先向右转再低头"的对比场景 |
| `q` 与 `-q` 同姿态 → 插值绕远路 | 必须懂 | 整节展开，配"该转 30° 却转了 330°"的视觉后果 |
| 轴必须归一化 → 角色越算越胖 | 必须懂 | 列入「边界与坑」，配可见后果 |
| 半角（为什么打印出来看不懂） | 知道即可 | 只给结论"四个数 = 半角余弦 + 半角正弦×轴"，**明确写出"为什么折半属于内部机制，不知道不影响使用"** |
| 乘法怎么展开（Hamilton 规则） | 可以不知道 | 折叠区块一句带过：「当黑盒即可」 |

## 笔记标题规范

**禁止用「为什么…」作为标题。** 标题应为陈述式或主题式，直接点明笔记要讨论的核心机制。

| ❌ 不推荐 | ✅ 推荐 |
|---------|--------|
| 为什么要用四元数表示旋转？ | 四元数的几何意义与运算 |
| 蒙皮矩阵为什么要乘 Bind 逆矩阵？ | 蒙皮矩阵：从骨骼姿势到顶点变形 |

**标题格式**：
- 不用前缀编号（如 `01-`、`1.`）
- 不用问号、`?` 等 Windows 非法字符；可用中文冒号 `：` 分隔主题与副题
- 文件名与笔记 `title` frontmatter 保持一致
- 示例：`四元数插值：Slerp与归一化.md`、`FABRIK与脚部IK.md`、`Additive动画：叠加与增量姿势.md`
- **必须与索引已有 wikilink 目标完全一致**，避免产生死链（索引中的标题即权威）

## 正文叙事规范

动画笔记没有唯一强制写法。**从哪个角度入手都行，随内容自然选择**：

- **数据流式**：讲一个姿势在系统里「进 → 处理 → 出」，适合采样、混合、蒙皮这类流水线环节（动画笔记最常用）
- **需求式/问题式**：从「一个具体缺陷或需求」出发，讲清楚怎么做、为什么这么做能解决——问题只是切入点，不必编排成固定的「问题 0→1→2」链条
- **机制式**：直接讲清数据结构、公式推导与算法步骤，再补上典型场景与边界
- **对比式**：两种方案的取舍（如 Lerp vs Slerp），讲清各自的代价与适用场景
- **场景绑定式**：用一个具体角色/玩法场景贯穿（如「角色走下坡时怎么收腿」）

无论选哪种，都要求**叙述自洽**：零基础读者读完能顺着一条线索走到底，而不是看到一堆并列的概念堆砌。

### 数据流视角（动画笔记最常用）

动画系统的核心追问是：

> **一份动画姿势（Pose）数据，从资源到屏幕，经过了哪几站？**

写作时反复自问：**当前讲的机制，输入是什么结构、输出是什么结构？在姿势流经的哪一站？**

```mermaid
graph LR
    A[动画资源] --> B[采样引擎]
    B --> C[混合/状态机]
    C --> D[IK/物理后处理]
    D --> E[蒙皮矩阵]
    E --> F[GPU 渲染]
```

### 地基概念必须先钉死，再谈机制（血的教训）

有一类笔记特别容易写坏：**它用了某个词，却从没解释过这个词**。最典型的是「骨骼」——写作者天天用，就默认读者也知道，于是直接写出「每根骨骼都是一个套娃」。读者读到这儿会卡住：**骨骼到底是骨头、是顶点，还是一个坐标系？**

所以**动笔前先列一遍本篇会用到、但读者可能没被交代过的地基词**（骨骼、蒙皮、Bind Pose、姿势、姿势空间、资产……），凡是没交代过的，按下面两条之一处理：

1. **本篇就要用它** → 先花一段讲清「为什么需要这个东西」（从上一个方案的缺陷出发），再给名字，最后才用它讲机制。
2. **它属于另一篇** → 明确告诉读者"这篇不讲，下一篇讲"，并给出 wikilink。**读者带着一个明确的疑问进下一篇，比带着一团模糊的概念进下一篇好得多。**

**「骨骼」这个特例值得单独记：** 现实里的骨头有长度有体积，游戏里的「骨骼」是一个**没有长度的坐标架**——真实骨骼的长度在数据里表现为"子关节相对父关节的偏移量"。这个认知不建立起来，后面关于层级、蒙皮、重定向的讲解都会踩空。它必须先有一篇专门的地基笔记（见 roadMap「角色资产与骨骼基础」块）。

### 基础概念要放进实际场景，不能浮在数学上

纯数学的层级变换（「父变换 × 子变换」）对台灯、对太阳系、对角色都成立——**这恰恰是它的价值，也可能是它的陷阱**：只讲数学，读者学会了公式却不知道该往哪儿用。正确做法是**先建立通用直觉，再落到角色场景**：讲层级先说清"灯罩为什么不会飞到屋子另一头"，再讲"角色的身体天然长成这个形状"；讲世界→局部的反向求解必须绑定用途（武器吸附到手、IK、重定向）。

**判断标准**：讲完一个基础概念后，读者能不能说出"我在什么情况下会用到它"？

### 通用写作要点（继承自 note-refine）

1. **零假定**：首次出现的术语（Pose、Bone、蒙皮、万向锁等）先用 1~2 句人话解释，再给正式名称；若 vault 已有讲解，用完整路径 wikilink 指向具体标题
2. **Why 先行**：任何核心概念第一次出现前，先让读者感到「这问题确实需要解决」。缺陷要用"看得见的表现"描述（模型发胖/扭转、旋转翻转、姿势跳变）
3. **因果清晰**：涉及演进（A 有问题→引入 B）就把链条写清楚，不必套固定结构

**篇幅比例**：写完回头数一遍，"必须懂"的知识点是否占了正文主要篇幅？低于一半说明推导、考据、罗列挤占了空间，砍掉它们。

### 明确该跳过的内容（会拖垮笔记价值的几类）

以下内容**默认不写**，除非它恰好会影响开发决策：

- **纯数学推导链**：半角怎么来的、乘法展开式、`qvq*` 的证明、矩阵元素与三角函数的关系式。→ 收进折叠区块，一句话交代「引擎已封装，当黑盒用」。
- **历史与命名考据**：为什么叫"四元数"、Hamilton 是谁、某个术语的拉丁语词源。
- **教科书式的完备性**：所有退化情况的数学分类、所有变体的形式化定义。→ 只写项目里真会撞上的边界。
- **实现细节的精确参数**：内存布局、某个引擎的内部字段名、逐行源码。→ 归到文末「参考实现」。
- **并列百科罗列**："三种方案分别是……" → 换成因果推导或场景贯穿。

> **反面示例**：❌ "四元数乘法按 Hamilton 规则展开，实部为 ww'−v·v'，虚部为 wv' + w'v + v×v'，因此……" / ✅ "两张处方单相乘就合成为一张，**先做的写在乘号右边**——顺序写反，姿势就错位。"

### 小节职责分配：每个结论只准"讲一次"（防跨节重复）

**这是实测出来的高频故障。** 每一节单独看都合理——开头 tip 预告一遍、Why 段铺垫一遍、核心机制推导一遍、边界与坑罗列一遍、总结再收一遍。五处都"讲得对"，但读者读到第三遍就开始跳行，真正需要展开的机制反而只占一小段。**啰嗦不是写错了，是没有分配职责。** 动笔前先给每个小节派一个唯一职责：

| 小节 | 唯一职责 | 允许写法 |
| :--- | :--- | :--- |
| 开头的 `[!tip] 需要懂多深` | **只列"要会什么"，不解释为什么** | 每条一行，不超过一句；**禁止在这里预演视觉后果**（"顺序反了手会甩出去"属于正文） |
| 为什么需要解决这个问题 | **只负责让读者感到"这问题确实要解决"** | 用**一个**场景把痛感建立起来即可，说完就走 |
| 直观理解 | **只负责建立直觉**（比喻/贯穿场景 + 数据流定位） | 比喻在这里立起来，后面各节**引用**它，不再重新解释它 |
| 核心机制 | **唯一允许展开推导和视觉后果的地方** | 因果链、为什么、看得见的后果，全部在这里一次讲透 |
| 边界与坑 | **只列前面没展开过的**新边界 | 一句话一条；**已推导过的坑不重复解释**，最多写"顺序反了会飞出去（见上文）"式的指针 |
| 一句话总结 | **只做压缩，不复述** | 不引入新名词、不重复正文措辞；读起来应是"收口"而非"重讲" |

**硬预算（写完必须数）：**

1. **同一个结论，全文展开不超过 1 处。** 其余位置只允许"指针式复述"（半句话带过 + 指向上文）。
2. **任何一个"视觉后果"（如"手绕肩膀画大圈"）全文出现不超过 2 次**：核心机制里讲透 1 次，至多在总结里压缩 1 次。
3. **开头 tip 与结尾总结合计不超过正文的 15%**——它们最容易膨胀成"预演 + 复述"两篇小作文。
4. **边界与坑小节里，凡是上文已展开解释过的条目，删到一句话或直接删除。**

**判断重复的方法（不能靠感觉）：** 挑出 3~5 个核心结论，用文本搜索数它们在全文的出现位置。**出现 ≥3 处就是重复**，必须收归到唯一职责位。重点搜索**措辞不同、意思相同**的句子——"绕肩膀画大圈""甩出去""飞到屋子另一头"讲的是同一件事，正则要按语义写。**查重复只能用"出现次数"**：删掉测试、翻译测试都测不出重复，因为重复段落删掉任意一处都不影响理解。

## 代码示例规范

笔记中的代码块**统一使用 `cpp`** 语言标签，遵循 Run Code 插件规范。动画笔记的代码通常是**结构/算法表达**，完整可运行程序不是目标——「把概念讲透」优先于「让代码跑出数值」。**代码不是笔记的必需装饰**：一句话能说清的事，用代码堆出来只会稀释重点。判断某段代码该不该写：

| 代码的作用 | 例子 | 该不该写 |
| :--- | :--- | :--- |
| 表达关键步骤/结构，帮助理解机制 | 矩阵乘法中三个分量出现的顺序、层级遍历的循环骨架 | ✅ 写 |
| 暴露一个会踩的坑 | `if (dot < 0)` 的符号翻转、除零兜底 | ✅ 写 |
| 重复一个已经讲清楚的结论 | 完整可运行的 Slerp 实现、凑一个 `main` 打印数值 | ❌ 不写 |
| 展示引擎内部实现细节 | 逐行复刻 `FQuat::operator*` | ❌ 不写（归到参考实现） |

```cpp
// flags: -O0 -g

// 复合变换：三个分量各自"进去、出来"的顺序
// 关键不在代码长度，而在 T→R→S 这个顺序本身（顺序反了，结果就错）
struct Transform {
    Vec3  Translation;
    Quat  Rotation;
    Vec3  Scale;
};

// 把子节点的局部变换挂到父节点上：先缩放、再旋转、最后平移
Transform Compose(const Transform& parent, const Transform& child) {
    Transform out;
    out.Scale       = parent.Scale * child.Scale;
    // 父的旋转作用在子的位置上（子得先被缩放，才能被父的旋转正确带到父空间）
    out.Translation = parent.Translation
                    + parent.Rotation.Rotate(parent.Scale * child.Translation);
    out.Rotation    = parent.Rotation * child.Rotation;
    return out;
}
```

| 规范 | 说明 |
|------|------|
| 编译参数 | 通过 `// flags:` 注释控制，放在代码块顶部 20 行内（默认 `-std=c++20 -Wall -O2`） |
| 表达优先 | 用代码表达「数据结构 + 关键步骤」，不必追求完整引擎代码 |
| 可视化可选 | 蒙皮、IK 等位置型机制可用 Mermaid 或少量 ASCII 图辅助 |
| 不写证明性代码 | 上表"不写"的两类一律不写 |

代码服务于概念：选最能讲清机制的表达方式，公式或伪代码同样有效。**示例要「小」**——每一行删掉后读者理解都不该受影响。

## 工作流程

### 第一步：定位主题

1. 读取 `Notes/动画系统/索引.md`，确认用户要写的笔记属于哪个阶段、哪一篇
2. 明确**核心问题**（只能有一个）——它已在索引中定义
3. 确认前置知识，用于文末「相关笔记」链接

### 第二步：确定叙述方式与数据流

1. 先想清楚正文**用什么角度组织**（数据流式 / 需求式 / 机制式 / 对比式 / 场景绑定式），选当前主题最自然的一种
2. 位置定位：本篇在动画数据流链路中处理哪一站（输入→机制→输出）
3. **列出本篇的知识点清单，逐个过实用性过滤**（规则见开头第二硬标准）：
   - 把想到的知识点全写下来（别在脑子里筛，写下来才看得清），每个标注 **必须懂 / 知道即可 / 可以不知道** 三档
   - 按「小节职责分配」表给每个结论指定**唯一**展开位置
4. 无论选哪种写法，都确保覆盖：核心机制（数据结构、关键步骤、公式/代码）讲清楚；有具体场景或可视效果绑定；覆盖边界/退化情形（角度为 0、权重为 0、骨骼缺失等）；"可以不知道"的内容收进折叠区块（写法见上文模板）

### 第三步：生成正文

1. 按模板创建/填充文件，frontmatter 与索引链接目标一致
2. 按第二步确定的叙述方式撰写正文，机制配最小代码或公式辅助表达
3. 撰写「参考实现（UE）」小节，映射到具体模块与数据结构
4. 在索引中打勾：把对应笔记状态列改为 `✅`

### 第四步：自检（交付前执行）

- [ ] **实用性过滤**：正文里每个知识点都能回答「不知道这条，读者会做出什么错误决定」吗？
- [ ] **无推导表演**：纯数学推导、历史考据、引擎私有实现细节是否已折叠或删除，并明确告知"不读不影响"？
- [ ] **篇幅比例**：「必须懂」的内容是否占了正文主要部分、且配了场景与后果（而不是只剩一句孤零零的结论）？
- [ ] **单点聚焦**：是否只回答一个核心问题？若涉及多个并列概念，是否该拆篇？
- [ ] **标题合规**：陈述式/主题式，无「为什么」开头，且与索引 wikilink 目标一致
- [ ] **数据流清晰**：是否明确本篇机制的输入输出？读者能否画出它在动画链路的位置？
- [ ] **零假定**：首次出现的术语（如 Pose、Body、Bone、蒙皮）是否有 1~2 句人话解释，并链接 vault 内已有讲解？
- [ ] **数值边界**：是否讨论了退化情形（零角度、零权重、缺失骨骼）？
- [ ] **详略匹配档位**：🔴 篇是否写透（含典型坑与数值边界）？🟡 篇是否克制？⚪ 速览是否只答「是什么、什么时候需要」？
- [ ] **参考实现**：结尾是否落到 UE 的具体模块/数据结构并有 wikilink，且正文保持引擎无关叙述？
- [ ] **代码规范**：代码块用 `cpp` 标签（如有代码）；代码是否都有决策价值，而不是为验证而写？
- [ ] **表格只用于总结**：表格只出现在机制讲解之后，不用于首次引入概念
- [ ] **跨节重复（必查）**：挑 3~5 个核心结论，搜索它们在全文的出现次数——**有任何一个 ≥3 处，就是没分配好小节职责**，按「小节职责分配」表收归到唯一位置，其余改成半句指针。特别注意**措辞不同、意思相同**的句子。
- [ ] **首尾不膨胀**：开头 `[!tip]` 只列"要会什么"、没预演正文的视觉后果；结尾总结是压缩不是复述。两者合计不超过正文 15%。
- [ ] **索引回写**：索引中该笔记状态是否已更新？

> 自检时的三个高频判据：
> 1. **删掉测试**——把某个知识点整段删掉，读者对"必须懂"的内容的理解会受影响吗？不会 → 它本来就不该占篇幅。
> 2. **翻译测试**——这个知识点能翻译成一个可视后果吗？不能 → 它是"知道即可"，别用推导去凑篇幅。
> 3. **次数测试**——这个结论在全文出现几次？≥3 处 → 按小节职责收归一处（唯一能测出重复的判据）。

### 第五步：交付与后续

质量要求高时，触发 `note-refine` 进行费曼叙述深度审查。

## 注意事项

以下几条是上面各处规则之外、只在动手时才想得起来的补充：

- **数据流优先于孤立概念**：每个机制都要交代它的输入/输出，讲清它在姿势链路中连接哪两个环节。
- **公式和代码都是压缩的叙述**：选最自然的一种即可，不必同时给出。
- **诚实面对不理解**：某一环没想透就写「问题笔记」记录当前理解与待验证假设，比硬写一篇错误笔记更有价值。
- **先读索引再动手**：已存在的骨架笔记里已写好核心问题与 `[!todo]`，填充时尽量沿用 为什么需要 → 直观理解 → 核心机制 → 参考实现 的骨架；可适度调整小节，但别偏离索引定义的核心问题与优先级档位。

# 图形学进阶之旅（Graphics Journey）

本 skill 负责将用户的**图形学理论知识**（软渲染器、变换、光栅化、着色模型）转化为**对像素运作机制的深刻理解**和**引擎级渲染架构能力**。

**核心使命**：每篇笔记必须回答一个**本质问题**——"我们想让屏幕上的像素变成什么样？为此每个像素需要什么信息？这些信息如何被组织、传递和计算？"最终让用户理解：API 对象只是答案的一种表达形式，而不是问题本身。

> **关键原则：图形学是像素背后的操作，不是 API 对象的集合。**
>
> 在 AI 可以写代码的今天，**API 细节是最不重要的**。人需要掌握的是**概念知识体系**：每个概念解决什么像素问题、需要哪些信息、这些信息如何组织、不同设计选择之间的 trade-off。API 调用只是这些概念在特定后端上的表达，应该由概念自然推导出来，而不是靠记忆。
>
> 每个概念（VBO/VAO/Shader/Texture/FBO/RenderPass）必须先讲清楚：
> 1. **没有它之前，像素会出什么问题？**
> 2. **每个像素需要什么额外信息才能解决这个问题？**
> 3. **这些信息怎么组织最高效、最正确？**
> 4. **OpenGL / Vulkan / D3D12 / Metal 分别用什么抽象来表达这种组织方式？**
>
> 拒绝"VAO 是一个容器对象，它包含……"这种百科式讲解。拒绝"OpenGL 有 VBO、VAO、EBO、FBO……"这种 API 罗列式开头。

## API 禁言令（最高红线，优先级高于一切写作建议）

这是本 skill 最重要的写作纪律。过往产出最常见的失败模式就是：**推导还没走完，API 名词就已经接管了叙事**——段落里到处是 VBO、VAO、FBO、`gl*` 函数名，读者还没搞懂"要解决什么问题、怎么解决"，就被迫去记 API 了。这是严厉禁止的。

**规则：**

1. **推导区零 API**：从笔记开头，到"像素问题 → 信息需求 → 组织方案"推导全部完成之前，正文**禁止出现任何 API 名称、对象名、函数名**——VBO、VAO、EBO、FBO、Texture、Sampler、RenderPass、PSO、`gl*`、`vk*` 等一律不许出现，**也不许用括号注释夹带**（❌ "需要一份常驻显存的数据（VBO 解决）"）。推导区只能用功能性描述："一份常驻 GPU 显存的顶点数据"、"一张可写的中间画面"、"一份可复用的格式解释"。
2. **API 只在收尾落地**：推导完成、读者已经知道该怎么解决问题之后，才允许在一个独立的收尾小节（如"落地表达"）引入 API，且必须简短、**纯文字、无代码**：
   - 说清楚"为解决这个问题，引入了哪个概念对象"；
   - 一句话点出它在各 backend 的名字和设计差异（"OpenGL 里叫 X；Vulkan 把同一件事拆成 Y + Z，因为它认为……"）；
   - **不逐函数讲解、不给参数列表、不展开调用流程、不放 API 代码片段**。具体代码实现交给 AI 生成，读者不需要记。
3. **占比硬上限**：笔记中所有含 API 名词的内容合计不超过正文 **10%**。
4. **自检标准**：把笔记里所有 API 名词删掉，正文必须仍然完整自洽。如果删掉后逻辑断了，说明概念本身是靠 API 名词撑着的——这部分必须重写。

**为什么这样规定**：读者学会的是"问题 → 方案"的推导能力；API 名字只是方案的邮编，查一下就有，实现可以让 AI 写。笔记里每多一个提前出现的 API 名词，就多一分把读者带回"背 API"老路的风险。

## 2026 学习主线：AI 擅长领域 vs 必须人类深入思考的问题

在 AI 能生成代码的今天，图形学学习的主线必须从"怎么写 Shader / 怎么调 API"转向"**为什么这样组织像素计算**"和"**不同组织方式之间的 trade-off**"以下分类决定笔墨分配：凡是 AI 能靠提示词稳定产出的，人只需要知道"是什么、为什么、边界在哪"；凡是涉及架构判断、数据组织、性能取舍的，人必须深入思考。

### 了解即可（AI 实现，人知道是什么、为什么、边界）

这些领域 AI 已经非常擅长，笔记中**只保留概念解释和工程边界**，不展开具体代码实现与参数调优：

- **具体光照模型的公式实现**（Blinn-Phong、Phong 等）——知道它把反射拆成环境/漫反射/高光三项，知道它是经验模型、参数靠手调、能量不守恒即可。
- **单一后处理效果的卷积核代码**（高斯模糊、Bloom、FXAA 等）——知道它解决什么像素问题、需要什么输入输出、性能量级即可。
- **API 对象创建的具体函数调用**（`glGenBuffers`、`vkCreateBuffer`、`glTexImage2D` 等）——知道这些调用表达什么概念即可，具体签名让 AI 生成。
- **语言语法细节**（GLSL/HLSL 的修饰符、`std140` 具体对齐规则、location 绑定）——只在需要排错时查阅。
- **单一算法的参数调优**（shininess、PCF 核大小、SSAO 半径等）——知道参数影响什么方向，不记具体数值。
- **可复现的数学推导**（法线矩阵、透视投影矩阵、Mipmap 层级公式）——知道结论的几何直觉，不展开逐步推导。

### 必须深入思考（决定架构、正确性与性能）

这些问题的答案无法由 AI 替代，因为它们是**工程判断**而非**代码生成**：

- **每个概念解决什么像素问题？** 没有它之前，像素会怎么错？
- **数据按什么频率更新？** 应该走 Attribute、Uniform、Varying 还是 Constant Buffer / SSBO？
- **计算应该放在管线的哪个阶段？** 顶点、几何、片段还是 Compute Shader？为什么要放在那里？
- **多 Pass 之间如何组织依赖？** 谁读谁、谁写谁、资源生命周期怎么管理？
- **不同方案在性能 / 质量 / 复杂度上的 trade-off** 是什么？（Forward vs Deferred vs Forward+、MSAA vs TAA、烘焙 GI vs 实时 GI）
- **现代引擎为什么这样设计？**（RenderGraph、GPU-Driven、Bindless、PSO 缓存）
- **瓶颈在哪里？** 是带宽、ALU、填充率还是 CPU 提交？如何验证？

### 对产出的影响

- 写笔记时，**了解即可**的内容用 1~2 段大白话 + 一句话结论带过，不占代码篇幅。
- **必须深入思考**的内容要展开因果推导、给出信息变化图、标注 trade-off，并在结尾给出明确推荐。

## 核心方法论：本质问题驱动 + 像素优先

> 笔记叙述质量需符合 `note-refine` skill 的通用规范。本 skill 专注图形学领域的本质问题组织与跨 API 思维模型对照，`note-refine` 提供通用的费曼叙述自检清单。

图形学进阶最大的障碍不是 API 复杂，而是**把 API 对象误当成学习目标**。本 skill 的核心方法是：每篇笔记先锁定一个**本质的像素问题**，再推导需要的信息结构，最后才把 API 作为实现选项引入。

### 本质问题模板（每篇笔记必须先回答）

在写任何内容之前，先写下这个笔记要回答的本质问题：

```
我们想要屏幕上的像素发生什么变化？
↓
每个像素需要哪些输入才能产生这种变化？
（位置、颜色、法线、UV、深度、光源方向、历史颜色、相邻像素……）
↓
这些输入从哪里来？怎么组织？按什么频率更新？
（每顶点、每物体、每材质、每帧、全局常量……）
↓
如果不用现代 GPU API，最 naive 的方案是什么？有什么问题？
↓
（以上推导全程零 API 名词。下面这一步只在收尾小节完成：）
这个组织方案在 OpenGL / Vulkan / D3D12 / Metal 里分别叫什么？
一句话带过设计差异即可，不展开调用细节——实现交给 AI。
```

**每个概念都必须能回答："这个东西让哪个像素变好了？怎么变好的？"**

### 从像素问题到 API 对象的示例重写

**以「顶点数据怎么上 GPU」为例（旧写法 vs 新写法）**：

```
旧写法：
"每次绘制都要重复配置顶点属性指针，代码又臭又长还容易错。
→ 引入 VAO 把属性配置打包。"
（问题还没讲清楚，API 名词先上场了——这就是被禁止的 API 叙事。）

新写法：
"软渲染器里，每个像素的颜色来自 CPU 内存里的顶点数据。
GPU 要并行处理上万个顶点，不能每次绘制都重新从 CPU 读内存。
→ 本质问题：怎么让 GPU 快速、重复地访问同一份顶点数据？
→ 需要一份常驻 GPU 显存的顶点数据。
→ 但 GPU 看到的只是字节流，还要告诉它'前 3 个 float 是位置，后 2 个是 UV'。
→ 如果每次绘制都重新解释格式，太慢且易错，这份'格式解释'也得能打包复用。

（推导到此结束。读者已经知道方案是什么了，下面才落地：）
→ 这套方案在 OpenGL 里落地为两个对象：VBO（常驻显存的数据）和 VAO（可复用的格式解释）；
   Vulkan 里同一件事是 VkBuffer + 顶点输入描述，只是把'数据'和'格式'显式拆开。
   具体怎么创建、怎么绑定，代码交给 AI 写。"
```

**以「给三角形贴图片」为例（旧写法 vs 新写法）**：

```
旧写法：
"PNG 文件怎么变成 GPU 上的纹理对象？用 stb_image 加载，glTexImage2D 上传。"
（直接跳进实现细节，读者不知道为什么要这么做。）

新写法：
"纯色三角形太假。我们想用一张图片控制每个像素的基础颜色。
→ 本质问题：三角形表面每个像素应该取什么颜色？
→ 需要一张 2D 颜色查询表，外加每个顶点到这张表的坐标映射（UV）。
→ 光栅化时，根据插值出的 UV 去查这张表，得到当前像素的颜色。
→ 这张表必须常驻 GPU 显存，且支持高效随机访问；'表里的数据'和'查表的方式'
   （过滤、平铺）是两件事，可以分开决策。

（落地：）
→ OpenGL 把'数据 + 采样方式'打包成一个纹理对象（Texture）；
   Vulkan 则拆成 VkImage（数据）/ VkImageView（怎么看）/ VkSampler（怎么采样），
   因为它认为'存什么'和'怎么读'是两个独立决策。"
```

**以「模糊效果为什么要画两遍」为例（旧写法 vs 新写法）**：

```
旧写法：
"后处理需要先拿到渲染好的画面，但默认帧缓冲是只写的。所以创建 FBO。"

新写法：
"模糊效果需要把每个像素替换成周围像素的加权平均。
→ 本质问题：计算当前像素时，能不能读到已经算好的相邻像素？
→ 不能。当前管线是单向的：顶点 → 光栅化 → 逐像素计算 → 写入画面。
→ 所以需要一个'可读的中间画面'：先把场景画到一张中间画布上，
   再跑第二遍，把这张画布当输入，对每个像素做卷积。

（落地：）
→ OpenGL 用 FBO 表达这个'可写的中间画面'；
   Vulkan 把同一件事拆成 RenderPass（渲染过程描述）+ Framebuffer（具体图像绑定），
   因为它要在录制命令前就知道完整的读写关系。"
```

### 图形学笔记的写作要求（按优先级）

#### 1. 本质问题优先（最高优先级）

- 每篇笔记开头必须写明：**这篇笔记解决什么像素问题？**
- 禁止以 API 对象名称开头。例如禁止：
  - ❌ "VBO 是顶点缓冲对象……"
  - ❌ "OpenGL 的 FBO 由颜色附件和深度附件组成……"
  - ❌ "glTexImage2D 的参数如下……"
- 必须以像素现象开头：
  - ✅ "为什么 10 万个顶点的模型每帧从 CPU 上传到 GPU 会卡？"
  - ✅ "为什么屏幕上的物体会被远处的物体盖住？"
  - ✅ "为什么远处纹理会闪烁？"
  - ✅ "为什么模糊效果不能在一个 Pass 里完成？"

#### 2. 信息结构先于 API（执行 API 禁言令）

在引入任何 API 名词之前，必须先讲清楚：
- **每个像素需要什么信息？**
- **这些信息在 GPU 上怎么组织最高效？**
- **更新频率是什么？**（每帧、每物体、每顶点、全局）
- **为什么这种组织方式能解决像素问题？**

这部分推导**全程禁止出现 API 名词**（见「API 禁言令」）。推导完成后，才在收尾小节用一两句话落地：这个概念对象在 OpenGL 里叫什么、在其他 backend 里叫什么、设计差异是什么。具体的函数调用和代码实现交给 AI 生成，不在正文展开。

#### 3. API 是"实现选项"，不是"学习目标"

- OpenGL 只是**众多后端中最适合学习的一个**，不是图形学的本质。
- 每篇笔记在讲完概念后，必须回答：**如果换成 Vulkan/D3D12/Metal，这个本质问题怎么表达？**
- 现代 API 对照不是"名称映射表"，而是**设计哲学对照**：
  - OpenGL 为什么隐式？（历史兼容性）
  - Vulkan 为什么显式？（多线程、驱动开销）
  - D3D12 为什么用 PSO？（CPU 端预验证）
  - Metal 为什么用 RenderPipelineDescriptor？（Apple 的显式内存模型）

#### 3.5 跨 API 对照：讲"为什么有区别"，不是"每个 API 写一遍"

跨 API 对照是 graphics-journey 的核心方法之一，但**不是为了展示"每个 API 都会做这件事"，而是为了解释"为什么不同 API 对同一件事有不同的控制权划分"**。

**禁止**：
- ❌ 为 OpenGL / Vulkan / D3D12 / Metal 各写一段完整代码，罗列一遍函数调用。
- ❌ 用表格对比 API 对象名称、函数签名、参数列表。
- ❌ 把跨 API 对照当成笔记正文的主体。

**必须**：
- ✅ 先讲清楚**这个概念的像素问题是什么**、**非 API 的知识结构是什么**（例如：顶点数据有静态/动态之分、有常驻/流式之分）。
- ✅ 引入跨 API 对照时，必须回答三个问题：
  1. **这个 API 为什么这样设计？**（历史背景、目标用户、硬件假设）
  2. **它比其他 API 多暴露或隐藏了什么控制权？**
  3. **这个控制权差异，和前面讲的非 API 知识（更新频率、生命周期、信息组织方式）如何一一对应？**
- ✅ 跨 API 对照**纯文字、无代码**：所有 backend 都只用一句话描述其设计选择，不逐 API 给函数名和调用流程；概念对象名只在收尾落地小节出现。

**示例（正确写法）**：

```markdown
OpenGL 把"数据放在哪里"的决策交给驱动猜：你只需要表达"这块数据基本不变"，
驱动决定它最终进 GPU 独占显存、CPU 可见内存、还是共享内存。

Vulkan 把同一个决策拆成"创建缓冲区对象"和"分配并绑定显存"两步：
因为它认为开发者比驱动更清楚这块数据是"静态常驻"还是"动态每帧更新"。
这正好对应前面讲的"数据是否变化"和"是否常驻"两个维度。
```

### 原则 2：Why 先行（像素问题驱动）

```markdown
❌ VBO是顶点缓冲对象，使用glGenBuffers创建，glBindBuffer绑定……
（读者：哦，又一个API对象。跟我有什么关系？）

✅ 软渲染器里，顶点数据存在std::vector里，CPU按顺序访问。
但GPU要同时处理上万个顶点，每次绘制都从CPU内存读数据会变成瓶颈。
更麻烦的是，如果每帧都重新上传，10万个顶点就是几MB的内存拷贝。
所以我们需要一种方式：把顶点数据一次性放到GPU能直接访问的显存里，
并且让GPU知道每个顶点的格式。VBO解决"数据放哪"，VAO解决"格式怎么解释"。
（读者：原来VBO/VAO不是可选优化，而是GPU并行渲染的前提。）
```

### 原则 3：因果推导（演进逻辑）

```markdown
❌ 渲染到纹理需要以下步骤：创建FBO、创建纹理、附加纹理到FBO……
（这是API手册，不是学习笔记。）

✅ 模糊效果需要读取当前像素周围的已渲染颜色。
但当前渲染管线只允许片段着色器输出颜色，不允许它读取帧缓冲。
于是我们引入一个中间步骤：先把场景画到一张"可写的纹理"上，
再用第二个Pass把这张纹理当输入，对每个像素做卷积。
OpenGL里这个"可写的纹理目标"就是FBO；
Vulkan里同一个本质被拆成RenderPass（过程描述）和Framebuffer（图像绑定）。
```

## 精确性与诚实性原则

### 原则 1：操作必须精确到"信息变化图"

图形API操作的是**像素流水线中的信息状态**，但理解状态的目的不是背 API，而是理解**像素流水线中的信息流动**。任何涉及信息组织变化的内容，必须提供操作前后的精确状态对比。

**必须画出来的场景包括**：
- 顶点数据从 CPU → GPU 显存 → 顶点着色器的信息流
- "常驻显存数据 / 格式解释 / 索引复用"三类结构的绑定关系图（哪个信息挂在哪个结构上）
- Shader 的数据流图（每顶点输入 → 顶点处理 → 插值传递 → 逐像素计算 → 输出）
- 纹理作为"2D 查询表"的访问路径（UV → 查表方式 → 表数据 → 像素颜色）
- "可写中间画面"的附件结构（场景颜色、深度信息、模板信息的布局）
- 渲染管线的画面切换（默认画面 → 中间画面 → 默认画面）
- 后处理链中"当前 Pass 读什么、写什么"的信息流

**自问 checklist**：
- 一个谨慎的读者看到这段，会不会问"格式解释和顶点数据是绑在一起还是分开的"？
- 他会不会问"绘制时用的是哪份索引数据"？
- 他会不会问"每帧不变的参数是跟着数据走还是跟着着色程序走"？
- 他会不会问"这个后处理 Pass 读的是上一步的颜色还是原始场景"？
- 如果以上任何一个问题的答案会影响理解，就必须在笔记中主动给出。

### 原则 2：性能与 trade-off 必须诚实

不能为了推崇某个 API 或架构而隐瞒其代价。

**必须包含的要素**：
- **承认代价**：这个抽象消除了什么成本？又引入了什么新成本？
- **对比基准**：和最 naive 的实现相比，在什么场景下更好、什么场景下更差？
- **反例警告**：在什么极端使用方式下，这个方案会失效或表现糟糕？
- **不连续的真相**：如果涉及"GPU并行"或"零拷贝"的宣传，必须明确说明"哪里避免了拷贝、哪里还是有开销"。

**禁止出现的说辞**：
- "VBO完全消除了数据传输开销" → 应该说"首次上传仍有 CPU→GPU 拷贝，但绘制时不再重复传输"
- "Shader让一切可定制" → 应该说"增加了编译链接的复杂度，且不同 GPU 的 Shader 编译器行为有差异"
- "FBO让后处理免费" → 应该说"增加了额外的纹理采样开销和显存占用"

### API 对照的呈现方式（思维模型版）

```markdown
> **参考：OpenGL / Vulkan / D3D12 / Metal 对「离屏渲染目标」这个问题的不同表达**
> 
> 我们在解决的本质问题是：**片段着色器需要读取已经渲染好的画面，但当前管线只能写不能读。**
> 
> 这个本质需求可以拆解为三个子问题：
> 1. 画到哪？（渲染目标）
> 2. 画完的东西怎么被下一步读到？（纹理 vs Renderbuffer）
> 3. 渲染过程本身如何描述？（隐式 vs 显式 RenderPass）
> 
> 各 API 的选择：
> - **OpenGL**：用 FBO 把"渲染目标"和"附件绑定"打包成一个对象。原因：历史兼容，学习曲线平缓。
> - **Vulkan**：拆成 RenderPass（描述子Pass、附件加载/存储、依赖）+ Framebuffer（具体图像视图）。原因：让驱动在录制命令时就能做完整验证，支持多线程。
> - **D3D12**：用 OMSetRenderTargets 绑定 RTV/DSV，用 PSO + ResourceBarrier 描述格式和状态转换。原因：与 D3D12 的显式资源状态模型一致。
> - **Metal**：用 MTLRenderPassDescriptor 描述渲染目标，用 MTLRenderCommandEncoder 执行。原因：与 Apple 的显式命令编码器风格一致。
> 
> **个人项目推荐**：学习阶段用 OpenGL FBO，因为概念最少；向现代 API 迁移时，
> mentally map 为 "FBO ≈ RenderPass + Framebuffer"，重点理解"为什么现代 API 要把描述和绑定分开"。
```

3. **锁定本质问题**：用一句话回答"这篇笔记解决什么像素问题？"
4. **梳理信息结构**：列出从 naive 到工业级需要回答的子问题
   - 简单知识点（如 Uniform vs Attribute）：3~5 个子问题
   - 中等知识点（如纹理系统）：5~8 个子问题
   - 复杂知识点（如引擎渲染管线抽象）：8~12 个或更多子问题
5. **确定跨 API 对照点**：标注哪些子问题能体现 OpenGL/Vulkan/D3D12/Metal 的设计差异
6. **产出问题链大纲**：向用户展示梳理好的本质问题和信息结构，确认方向后再进入下一阶段

**产出**：
- 该模块解决的像素问题（Why）
- 完整的信息结构问题链
- 每个问题对应的 naive 方案轮廓
- 需要引入跨 API 对照的子问题标注
- **前置依赖声明**和**本模块增量**说明

### 阶段二：逐个解决问题（血肉）

**输入**：图形学理论 + 现代 API 文档 + 引擎源码 + 互联网搜索
**步骤**：
1. 按问题链顺序，逐个解决每个子问题
2. 对每个子问题（全程遵守 API 禁言令，只许功能性描述）：
   - **先给 naive 方案**：写出"如果刚学完软渲染器，我会怎么处理这个像素问题"
   - **推演它**：指出具体哪里会出问题（性能、正确性、可扩展性）
   - **提出信息组织方案**：说明需要引入什么抽象结构（只讲结构，不给 API 名字）
   - **标注还遗留哪些问题**
3. **统一收尾落地**：所有子问题推导完成后，在收尾小节一次性引入 API——每个概念对象一句话（名字 + 各 backend 差异），不逐函数讲解，代码交给 AI 生成
4. **搜索互联网**：针对当前正在解决的具体子问题，搜索不同方案的设计差异（重点是设计哲学，不是函数签名）

**产出**：
- 每个子问题的 naive 方案 + 问题分析 + 信息组织方案（零 API 名词）
- 信息结构的完整演进过程
- 收尾落地小节：概念对象名 + 跨 backend 设计差异一句话
- **明确推荐**：在每个需要决策的子问题上，给出"推荐采用哪种方案"的结论

### 阶段三：定型与下一步

**步骤**：
1. 梳理跨模块耦合、性能优化、现代引擎抽象方式
2. **搜索互联网**：确认引擎中该模块的现代抽象方式（bgfx/Sokol/The-Forge/UE/Bevy 等）
3. 输出经过验证的、可迁移的设计清单
4. 在笔记结尾添加**下一步预告**
5. **精确性审查**：检查所有涉及信息结构、数据流、API 像素链路状态的地方
6. **叙事审查**：检查是否符合费曼精神（本质问题先行、因果推导、问题链衔接）
7. **API 禁言审查**：通读正文，确认推导区零 API 名词、含 API 名词的内容合计 ≤10% 且只出现在收尾小节/附录；做"删掉所有 API 名词后正文仍自洽"的自检
8. **最终一致性审查**：检查是否满足"必须有明确推荐"的原则

**产出**：
- 工业级设计清单
- 设计权衡表（表格只用于总结已解释的内容）
- **个人开发推荐路径**：从 naive 理解到现代引擎抽象的具体步骤
- **更新 roadmap/索引文件**，标注该模块已完成并指向下一个推荐模块

## AI 响应承诺

1. **产出物明确**：一篇写入 roadmap 指定目录的费曼学习笔记
2. **知识独立**：笔记自成体系，不依赖外部教程即可读懂（但会推荐延伸阅读）
3. **像素优先**：每篇笔记从"想要什么样的像素"出发，而不是从 API 对象出发
4. **API 禁言令优先**：推导区零 API 名词；API 只在收尾小节落地（一句话一个 backend，不逐函数讲解，代码交 AI 生成）；含 API 名词的内容合计 ≤10%
5. **代码受控**：正文只出现伪代码；真正的 API 代码只放 workspace 或笔记末尾折叠附录，正文零 API 调用，不强求工作区练习
6. **索引维护**：如 roadmap/索引文件已存在，主动提议更新；如不存在，主动创建
7. **顺序连贯**：产出的每篇笔记都明确声明前置依赖、本模块增量和下一步预告
8. **精确且诚实**：涉及信息结构、GPU 数据流、API 像素链路状态时，主动提供信息变化图和 trade-off 分析
9. **本质问题驱动**：笔记的主体是"像素问题 → 信息需求 → 信息组织 → API 实现"的渐进过程
10. **跨 API 思维模型对照**：不只给出名称映射，而是解释不同 API 对同一本质问题的设计差异；必须说明**为什么 API 会有区别、更复杂的 API 多暴露了什么控制权、这与前面非 API 知识的联系**
11. **禁止多 API 代码堆砌**：跨 API 对照纯文字，每个 backend 一句话描述设计选择，不罗列任何 API 的代码
12. **前沿探索**：每篇笔记搜索行业前沿（现代图形API抽象库），探索更优方案
13. **最正确方案**：在每个需要决策的子问题上，必须在可选方案之间给出明确推荐
14. **Roadmap 唯一权威**：所有目录结构、文件名、阶段划分、依赖关系以 roadmap 为准
15. **叙事质量**：笔记必须遵循费曼精神（本质问题先行、因果推导、问题链衔接、场景绑定）
16. **2026 主线意识**：明确区分"AI 擅长领域（了解即可）"与"必须人类深入思考的领域"，笔墨集中在后者

# Shader 调试工具链

## 问题 0：三个故障现场，为什么"改一行看一次"开始失效？

从 3.3 开始，你的 Shader 不再是"输出一个固定颜色"了。光照、法线变换加进来之后，典型故障变成了这三类：

1. **全黑**：窗口清了背景色，但模型完全不见。
2. **颜色错**：模型在，但明暗全反了，或者整个面一片死黑。
3. **物体消失**：换一个相机角度，模型突然没了。

naive 的调试方式你肯定已经试过：改一行 Shader，重新编译，看一眼；不对，再改一行。这个循环在"输出固定颜色"时代还能忍受，但光照 Shader 的嫌疑犯太多了——顶点数据没传对？MVP 矩阵没更新？法线变换错了？光源位置没设？深度测试把像素全杀了？每个嫌疑犯都要改一次代码验证一次，一次循环几分钟。

更要命的是：**有些 bug 你连"改了有没有效果"都判断不了**。模型根本没出现时，你把法线可视化改成红色输出，屏幕还是黑的——因为像素压根没走到片段着色器。

这不是你不够耐心，是调试方法论失效了。要理解为什么，得先看清楚 GPU 这个黑盒到底有多"黑"。

## 问题 1：为什么 printf 和断点在 GPU 上全部失效？

你在 CPU 代码里养成的两件调试武器——打断点、加打印——到了 GPU 侧同时失效。原因不是工具做得差，而是 [[Notes/计算机图形学/GPU编程基础/CPU怎么向GPU发命令|CPU 与 GPU 的协作方式]]本身决定了这一点：

**第一，异步执行。** `glDrawArrays` 只是把一条命令塞进队列就立刻返回，GPU 什么时候真正执行、执行到哪一步，CPU 完全不知道。你在 draw call 下一行打断点，GPU 可能还没开始画，也可能已经画完了三帧。

**第二，数据在显存。** 顶点缓冲、纹理、帧缓冲都在 GPU 自己的内存里，CPU 侧的调试器看不到。你没法像检查 `std::vector` 那样检查"VBO 里现在的第 5 个顶点是什么"。

**第三，上万条并行线程。** 片段着色器对几十万个像素同时执行，没有"那一条执行路径"可以让你单步。你想看 (320, 240) 这个像素的光照计算，但它和周围十万个像素是同一个时刻、同一批硬件一起跑完的。

三条加起来，结论只有一个：**"实时观察 GPU"这条路不存在。**

那还剩什么？把实时观察换成**录制回放**——不在 GPU 运行时看它，而是把一帧里发生的一切完整录下来，事后慢慢解剖。就像飞机的黑匣子：你没法在空难发生的那一秒坐在驾驶舱里看仪表，但你可以事后把飞行数据记录拿出来，一秒一秒地回放。

## 问题 2：抓帧（Frame Capture）录下的到底是什么？

"抓一帧"听起来像截屏，但截屏只给你最终画面，抓帧给你的是**这一帧的完整案发现场**：

```
一次抓帧 = 一帧内 CPU 发给 GPU 的所有东西的快照
├── 每一条命令：draw call、状态切换、纹理绑定……按时间顺序排列
├── 每条命令执行时的管线状态：深度测试开没开、混合模式是什么
├── 每条命令用到的资源：顶点缓冲内容、纹理内容、uniform 的值
└── 每条命令画完后的输出：当时的颜色缓冲、深度缓冲长什么样
```

有了这个快照，你可以**任选一条 draw call，看它执行前和执行后的所有状态**；可以**任选一张中间纹理放大检查**；甚至可以**把某个像素的片段着色器单独拎出来单步执行**。一帧可以反复回放，和你的程序是否还在运行无关。

这个"录制回放"模型是所有 GPU 调试工具的共同内核。[RenderDoc](https://renderdoc.org/) 是其中最适合学习的：免费开源、跨平台、同时支持 OpenGL / Vulkan / D3D。基本流程只有三步：从 RenderDoc 启动你的程序（或注入正在运行的进程）→ 按 F12 抓一帧 → 双击 capture 开始解剖。

> 具体每个按钮在哪、菜单叫什么，RenderDoc 更新频繁，查[官方 Quick Start 文档](https://renderdoc.org/docs/getting_started/quick_start.html)比背笔记可靠。本篇要讲透的是**抓到 capture 之后怎么想**——这部分不随版本变。

## 问题 3：拿到 capture 之后，怎么排查？——四问定位法

初学者打开 RenderDoc 最常见的反应是"信息太多，不知道看哪"。其实排查一个有问题的像素，本质上是沿着管线**自顶向下问四个问题**，每问一次就把怀疑范围砍掉一半：

```
Q1: 这个 draw call 存在吗？
    └── 不存在 → 问题在 CPU 侧：根本没提交（剔除逻辑错、循环漏了、状态没设对）
Q2: 顶点被正确变换了吗？
    └── 不对 → 问题在几何阶段：顶点数据、属性布局、MVP 矩阵
Q3: 像素为什么没出现在画面上？
    └── 被丢弃 → 问题在固定硬件阶段：深度测试、背面剔除、视锥外
Q4: 颜色为什么不对？
    └── 错色 → 问题在着色阶段：uniform 值、纹理采样、光照计算
```

### Q1：这个 draw call 存在吗？

打开事件浏览器（Event Browser），一帧里所有 API 调用按顺序列成一棵树。先找到"本该画出那个模型"的 draw call。

**它不在？** 那 GPU 是无辜的——CPU 压根没发出这条命令。回去查提交逻辑。这一步就能砍掉 GPU 侧的所有嫌疑，而且不用看任何图形状态。

### Q2：顶点被正确变换了吗？

选中 draw call，打开网格查看器（Mesh Viewer）。它给你两张表：

- **VS Input**：顶点着色器实际收到的数据。位置、法线、UV 是不是模型文件里的值？如果这里就错了，问题在顶点缓冲或属性布局——比如 stride 算错导致每个属性错位一个 float。
- **VS Output**：顶点着色器算完的裁剪空间位置。用线框模式看一眼，模型的形状对不对？如果输入对、输出错，问题在顶点着色器内部——十有八九是 MVP 矩阵：uniform 没更新、矩阵乘法顺序反了、或者传的单位矩阵。

### Q3：像素为什么没出现在画面上？

顶点输出正确，但画面上没有像素。这时候看两样东西：

- **输出合并阶段的状态**：深度测试开了吗？深度缓冲里当前存的值是多少？你的片段深度比它大（更远），就被默默杀掉了——这是"物体消失"最常见的原因。
- **剔除与裁剪**：背面剔除开了吗？你的三角形顶点环绕顺序是不是反了，导致所有面都被当成背面？顶点变换后的位置是不是在视锥之外？

"换一个角度模型就消失"的 bug，九成在这一问：顶点环绕顺序在某一面变成了顺时针，背面剔除把它整个丢了。

### Q4：颜色为什么不对？

像素在了，颜色不对。打开管线状态视图（Pipeline State），沿着数据流查：

- **uniform 的值**：光源位置、光源颜色、材质参数，抓帧时的实际值是什么？经常看到 `lightPos` 是 `(0,0,0)`——CPU 侧忘了设置，或者设置在了另一个 Program 上（回忆 [[Notes/计算机图形学/Shader与光照/Shader程序与跨阶段数据约定#问题 8：最常见的错误不是语法错，而是「约定没对好」|uniform 是 Program 私有状态]]）。
- **绑定的纹理**：采样器指向的纹理是空的、还是绑定到了错误的纹理单元？
- **片段着色器本身**：右键像素可以让 RenderDoc 对这个像素**单步执行片段着色器**，逐行看每个变量的值——这是离"在 GPU 里打断点"最近的体验。

走完四问，任何"像素不符合预期"的问题都能定位到一个具体环节。这个流程的本质是**二分定位**：几何阶段还是着色阶段？数据问题还是状态问题？每问一次，嫌疑范围减半。

## 问题 4：Pixel History——"这个像素为什么是黑色"的终极答案

四问定位法覆盖大多数情况，但有一种问题它答起来费劲：**"这个像素被画了好几次，每次画的是谁？"** 比如屏幕上有个奇怪的亮斑，你不知道是哪个三角形画上去的。

这时用 Pixel History：在输出图像上右键一个像素，RenderDoc 列出这个像素**整帧历史上的每一个片段**——每次有图元尝试写这个像素，都是一条记录：

```
像素 (412, 305) 的历史：
  Event #142  三角形A  深度 0.81  → 深度测试失败，被丢弃
  Event #157  三角形B  深度 0.62  → 写入，颜色 (0.2, 0.5, 0.9)
  Event #203  三角形C  深度 0.44  → 写入，颜色 (1.0, 0.1, 0.1)  ← 最终颜色
```

一眼看穿：这个像素先后被三个三角形竞争，前两个一个被深度挡掉、一个被后来者覆盖，最终留下的是 Event #203 的红色三角形。

这个功能把调试从"推理"变成了"看日志"。没有它，你要猜测覆盖关系、脑补深度值；有了它，**像素的一生就是一张表**。排查半透明排序错误、Z-fighting（两个面深度几乎相同导致画面闪烁）、"不知道为什么这里有个斑点"这类问题，Pixel History 是终点站。

## 问题 5：把常见 bug 翻译成"在 RenderDoc 里看什么"

前面四问是方法论，这张表是速查——症状到工具的直达路线：

| 症状 | 最可能的原因 | 在 RenderDoc 里看哪里 |
|------|-------------|----------------------|
| 全黑，模型不出现 | draw call 未提交 / MVP 传了单位矩阵 / 深度测试全灭 | Event Browser 确认 draw call 存在；Mesh Viewer 看 VS Output；管线状态看深度测试 |
| 换角度物体消失 | 顶点环绕顺序反 + 背面剔除 | Mesh Viewer 线框模式；剔除状态 |
| 颜色全错、明暗反 | uniform 没设置 / 法线没 normalize / 法线矩阵错 | Pipeline State 的 uniform 值；Pixel Debug 单步看 `vNormal` |
| 纹理花屏或纯色 | 纹理没绑上 / UV 越界 / 属性布局错位 | Pipeline State 的纹理绑定；Mesh Viewer 的 VS Input |
| 画面某处有怪斑 | 像素被意外图元覆盖 | Pixel History |
| 画面闪烁（Z-fighting） | 两个面深度几乎相同 | Pixel History 看深度值小数位 |

## 问题 6：不同 API 下，这个"录制回放"模型有什么不同？

抓帧工具不是 RenderDoc 一家，但它们全是同一个内核的不同封装：

- **RenderDoc**：免费开源，跨平台，支持 OpenGL / Vulkan / D3D11 / D3D12。学习首选。
- **PIX on Windows**：微软官方，D3D12 专属。和 D3D12 的显式模型深度集成，能看到命令队列和内存堆的细节。
- **Xcode GPU Frame Capture**：Apple 平台，Metal 专属。Metal 的显式命令编码器在 capture 里直接可见。
- **Nsight Graphics**：NVIDIA 官方，在抓帧之外叠加硬件计数器——能看到 SM 占用率、缓存命中率这类芯片级数据。

为什么不同厂商都要各做一个？因为抓帧必须**拦截 API 调用并重建 GPU 状态**，这和每个 API 的对象模型深度耦合：OpenGL 是全局状态机，抓帧工具要替你把当时的状态机整个重建出来；Vulkan 的状态都在 PSO 和命令缓冲里，工具可以直接读对象。所以工具界面不同，但你练的四问定位法**逐字通用**——它们回答的都是同一条管线上的同四个问题。

> 顺带说明：这些工具都能给每个 draw call 计时，所以常被误以为"性能分析工具"。计时只是顺带能力，逐 Pass 性能剖析是[[Notes/计算机图形学/Roadmap#阶段十四：性能分析与帧优化|阶段十四]]的主题。本篇只用它们的**正确性调试**能力。

## 一个诚实的提醒：工具不是万能的

- **shader 单步调试需要调试信息**。Release 编译把变量名和行号优化掉后，单步看到的可能是汇编级的中间表示。调试时保留 debug info。
- **大场景的 capture 很大**。一帧的所有纹理和缓冲都要存下来，开放世界项目一份 capture 可能几个 GB。学习阶段的场景没这个问题。
- **工具看不到"没发生的事"之外的事**。它能告诉你深度测试杀了像素，但"为什么深度缓冲里是那个值"还要你自己往前追——工具给你现场，推理还是你的。

另外别忘了最便宜的一招：在 Pixel Debug 之前，先把中间量直接当颜色输出（比如 `FragColor = vec4(vNormal * 0.5 + 0.5, 1.0)` 可视化法线）。它 30 秒就能排除一类嫌疑，但它有个前提——像素得能走到片段着色器。像素根本没出现时，只有抓帧能告诉你为什么。

## 与 SelfGameEngine 的关系

本篇是引擎 `9.5 性能分析与调优` 的前置技能，但它的价值远不止性能：引擎渲染代码越写越多之后，**每一次渲染 bug 的排查成本都取决于你有没有这套流程**。材质系统参数绑错了、RenderPass 输出没接上、合批后顶点数据错位——这些引擎 bug 在 RenderDoc 里和本篇的四个问题一一对应。可以说，不会抓帧，引擎渲染开发就退回到"改一行看一次"的盲调时代。

## 设计 checklist

| 检查项 | 标准 |
|--------|------|
| 调试策略 | GPU 问题用录制回放，不用实时观察 |
| 排查顺序 | 四问定位法：draw call 存在 → 顶点变换 → 像素存活 → 颜色计算 |
| 首选工具 | RenderDoc（免费、跨平台、GL/VK/D3D 通吃） |
| 终极武器 | 覆盖类、Z-fighting 类问题直接上 Pixel History |
| 廉价前奏 | 先可视化中间量（法线/UV/深度当颜色输出），30 秒排除一类嫌疑 |
| 边界认知 | shader 单步需要 debug info；工具给现场，推理靠自己 |

# Shader 调试工具链

## 问题 0：像素现象——屏幕黑了，嫌疑人有一页纸长

你写完了带光照的渲染代码，运行，窗口里一片黑。

这一个像素现象背后，站着一整页嫌疑人名单：

```
数据侧：
  □ 顶点数据根本没上传成功（内容为空 / 全是零）
  □ 顶点格式解释错了（把法线当位置读）
  □ 常量没传（光源位置是零向量，模型矩阵是单位阵）
  □ 常量传错了（法线矩阵传成了 Model 矩阵——上一篇的坑）
  □ 相机在模型内部 / 朝向反了，所有东西在视野外

计算侧：
  □ 顶点着色器把位置变换到了离谱的地方
  □ 片段着色器里 normalize 了零向量，得到 NaN
  □ N·L 算出来全是负数，被 max(_, 0) 夹成零

流水线侧：
  □ 三角形被背面剔除干掉了（顶点顺序反了）
  □ 所有片段都没通过深度测试
  □ 画是画了，但画到了没被显示的那块缓冲上
  □ 清屏颜色覆盖了一切（绘制的命令根本没执行到）
```

注意这份名单的结构：它**横跨三个完全不同的领域**——CPU 准备的数据、GPU 上的计算、固定硬件的流水线裁决。而它们共享同一个症状。这就是为什么图形调试的第一课不是学工具，而是接受一个事实：

> **"颜色不对"是最没有信息量的症状。你看到的每个错误像素，都是几百步正确计算和一步错误计算的总和。调试的全部工作，就是找到那一步。**

## 问题 1：为什么普通调试器在 GPU 上集体失效

CPU 代码出 bug 时，你的武器库很顺手：断点、单步、看变量、printf 打日志。到了 GPU 这边，四件武器全部报废。原因不是工具厂商不努力，而是三个结构性的障碍。

**障碍一：代码在另一个处理器上跑。** 你的调试器附着在 CPU 进程上，但着色程序在 GPU 里执行。两者之间隔着驱动、命令队列和 PCIe 总线。CPU 侧的断点能停在"发出绘制命令"那一行，但停不到"这个像素正在被着色"那一刻——那一刻对 CPU 来说根本没有对应的时间点，命令是异步执行的。

**障碍二：同一段代码正在被执行一百万份。** 就算技术上能打断点，你要停在哪一份上？一个 1080p 画面有两百万个像素，两百万份片段着色器并发执行。其中一百九十九万九千九百份都算对了，只有角落里一个像素是错的。断点停在"每份"上，等于没有断点。

**障碍三：GPU 没有控制台。** printf 为什么好用？因为程序有一条通向"外面的世界"的输出通道。GPU 着色器的唯一输出通道是**写像素**——它不能往日志文件写东西，不能弹窗，不能发消息。它的全部表达方式，就是把一个数值写进帧缓冲。

把障碍三反过来读，就得到了 GPU 调试的第一性原理：

> **着色器只有一种输出：颜色。所以一切调试信息的获取，归根结底只有两条路——要么把信息编码进颜色里，要么在 GPU 之外架一台"录像机"把内部状态拍下来。**

这两条路，就是问题 2 和问题 4 要分别推导的方案。

## 问题 2：最 naive 的方案——而且它永远不会过时

### 2.1 把中间结果当颜色输出

怀疑法线不对？别猜，把法线直接画出来：

```
片段着色器的调试改造（伪代码）：
  原本：  outColor = 光照计算(N, L, V, ...)
  现在：  outColor = N × 0.5 + 0.5      // 方向 (-1~1) 映射到颜色 (0~1)
```

法线朝上的面变成浅蓝色（N=(0,1,0) → RGB(0.5,1,0.5)），朝右的变粉，朝前的变浅紫。整个模型变成一颗"彩虹球"——**颜色就是方向的地图**。光照怪怪的？先看这张地图：如果彩虹球本身就不对，凶手在数据或顶点阶段，根本不用怀疑光照公式；如果彩虹球完美无瑕，那法线无罪，去查光源方向。

~={green}这个技巧在图形学里有个不成文的地位：**它是每个图形程序员用到退休的兜底招。** 深度不对就把深度灰度化、怀疑插值就把插值前的原始值画出来、怀疑哪个分支走了就给两个分支涂不同颜色。凡是能算出来的中间量，都能变成颜色。=~

### 2.2 它的极限

但这招有三个硬极限：

- **一次只能看一个量。** 一次绘制只输出一份颜色。怀疑对象有五个，就得改代码、重编译、重跑五次。
- **它改变你正在调试的程序。** 你改写了输出，原来的症状消失了——如果 bug 出在输出之后的阶段（深度测试、混合），你反而把现场破坏了。
- **它看不见"没画出来的东西"。** 物体整个消失了——被剔除、被裁剪、顶点全在视野外——屏幕上根本没有它的像素，你把什么画成彩虹色？最经典的黑屏恰恰属于这一类：naive 方案对"画错"有效，对"没画"无能为力。

### 2.3 另一个方向：把 GPU 数据读回 CPU 打印

着色器不能 printf，但 CPU 可以把 GPU 缓冲里的数据拷回来打印。顶点数据、常量、甚至画完的整张画面都能读回来逐字节检查。

这条路同样真实但同样受限：回读是**同步操作**——CPU 要停下来等 GPU 把队列里积压的命令全部执行完，才能把数据拷回来（这就是[[Notes/计算机图形学/GPU编程基础/CPU怎么向GPU发命令|CPU 与 GPU 异步模型]]的反面）。偶尔读一次还行，每帧都读，帧率直接崩。它适合验收式的抽查，不适合逐像素排查。

### 2.4 小结：naive 方案教会我们什么

两招合起来，其实已经把调试的本质暴露了：

> **调试 = 缩小嫌疑范围。** 每一次操作都在回答一个二分问题："凶手在这条线的左边还是右边？" 把法线画出来，是在问"数据对还是计算错"；读回顶点缓冲，是在问"CPU 传的对还是 GPU 用的错"。

naive 方案的问题不是思路错，而是**每次二分都要改代码、重编译、重跑、人工读字节**。如果有一台机器能把一帧的**所有中间状态**一次性全拍下来，让你事后随便翻看——二分就不再需要改代码了。这台机器就是下一个问题的答案。

## 问题 3：关键洞察——GPU 需要的不是调试器，是时间旅行机

回到问题 1 的三个障碍，逐个看有没有绕行方案：

- 代码在另一个处理器上跑？——**那就别实时跟了，录下来。** CPU 发给 GPU 的每条命令、每条命令执行时携带的全部数据和状态，都可以被一个中间层完整截获、存档。
- 一百万份并行执行？——**事后过滤。** 录制下来的东西是静止的，你可以慢慢翻到"角落里的那个像素"，单独问它：你这份计算是怎么回事？
- GPU 没有输出通道？——**录像机不需要它输出。** 中间层能看到命令流里的每一个字节，GPU 自己不需要开口。

这就是**抓帧（Frame Capture）**的思想：在 CPU 和 GPU 之间架一台录像机，把"这一帧里 CPU 下达的每一条命令 + 每条命令执行现场的全部输入数据和配置"完整记录下来。回放时，GPU 把这一帧重新执行一遍——但这次，每一步的中间状态都被展示出来。

> 它等价于调试领域的**时间旅行调试器（time-travel debugger）**：普通调试器让你停在现在、看现在；时间旅行机让你回到过去任意一个时刻，看那一刻的全部状态，还能反复回去。GPU 调试天然适合这条路，因为一帧本来就是"一串确定的命令 + 确定的数据"——确定性重放几乎是免费的。

抓到一帧之后，你手里有什么？

```
一帧的完整档案：
  ├── 命令流水账：这一帧的每一条命令，按顺序排列
  │     （清屏 → 设配置 → 画模型A → 画模型B → ... → 显示）
  ├── 每条命令的现场快照：
  │     ├── 输入：它读了哪份顶点数据、哪些常量、哪张查询表
  │     ├── 配置：深度测试开没开、混合怎么设、剔除朝向
  │     └── 输出：它画完之后的画面长什么样、深度什么样
  └── 所有原始数据本身：每份缓冲的字节、每张纹理的像素
```

**每一条命令都是一个案发现场的完整快照。** 问题 2 里"改代码、重编译、重跑"才能看一眼的中间状态，现在全部躺在档案里，随你翻。

## 问题 4：有了录像怎么用——从终点倒推的标准流程

录像只是原材料。真正值钱的是一套**固定的排查流程**——它把问题 0 那一页嫌疑人名单，变成一个可以在五分钟内走完的二分决策树。

### 第 0 步：先劈成两半——CPU 错了还是 GPU 错了

这是整个流程里最有价值的一刀。打开档案里的顶点缓冲，直接看数字：

- 顶点数据全是零、常量根本没值 → **CPU 侧问题**：上传环节就错了，GPU 是清白的，回去查数据准备代码。
- 顶点数据、常量都符合预期 → **GPU 侧问题**：数据是对的，错在计算或使用，往下走。

这一步为什么排第一？因为它**零成本且收益最大**：图形 bug 里 CPU 侧和 GPU 侧大约各占一半，而看一眼缓冲只要十秒。抓帧工具在这里扮演的是"海关"——CPU 交出去的东西在过关时被原样登记，事后对账，责任立刻分明。

### 第 1 步：在命令流水账里找到出事的命令

一帧可能有几百条命令，但流水账配了**逐步重放的画面**：点中第 37 条命令，画面显示"前 37 条画完后的样子"。在流水账上往后翻，找到**画面第一次出现错误的那一条**——它之前都对，它之后开始错。嫌疑人从"整帧几百条命令"缩到"一条绘制命令"。

如果画面从头到尾都是黑的、哪条命令都没画出东西——那本身就是信息：翻到"本该画出模型"的命令，看它的输出快照是空的，问题就集中在"为什么这条命令的产出为零"，进入第 3 步的输出裁决检查。

### 第 2 步：检查这条命令的输入现场

选中出事的命令，逐一核对它读的三类数据（对照[[Notes/计算机图形学/光照与数据流/数据通道与更新频率|数据通道]]分类）：

- **顶点数据**：以表格形式查看原始字节按格式解释后的数值——位置是不是预期的范围？法线是不是单位长度？（也可以把顶点阶段输出的位置画成颜色，直接在画面上看形状对不对。）
- **每物体/每帧常量**：矩阵、光源位置、材质参数——逐个读数值，和你在 CPU 侧算的预期值对账。上一篇笔记的"法线矩阵传成 Model 矩阵"在这一步一眼现形：法线矩阵的前几个数值和 Model 矩阵一模一样，就是传错了。
- **查询表（纹理等）**：直接看图片内容——加载成功了吗？是不是一张全黑的图？

输入全对？那么数据无罪，进入计算。

### 第 3 步：检查输出裁决——像素是不是被流水线杀了

很多"黑屏"的凶手不在着色器，而在着色器之后的固定硬件裁决。对出事的命令，查它的配置快照：

- **深度测试**：开着吗？比较方向设反了吗？（"越远越通过"和"越近越通过"一字之差，全灭。）
- **剔除**：背面剔除的朝向和顶点绕序匹配吗？
- **写入目标**：这条命令画到哪块缓冲上了？是最终要显示的那块吗？

这里有一个专门对付"像素去哪了"的杀手锏——**像素历史（Pixel History）**：在最终画面上右键任意一个像素，工具会列出**这一帧里所有试图写它的片段**，按顺序排好，并且标注每一次写入的结局——"被深度测试拒绝"、"写入成功，但后来被第 58 条命令覆盖"、"混合后与背景合成"。

```
像素 (640, 360) 的历史档案：
  第 12 条命令：片段(深度 0.8) → 深度测试通过 → 写入红色
  第 37 条命令：片段(深度 0.5) → 深度测试通过 → 写入绿色（覆盖了红色）
  第 58 条命令：片段(深度 0.9) → 深度测试失败 → 丢弃
  最终颜色 = 绿色 ← 第 37 条命令是最后赢家
```

"我的模型明明画了但看不见"这类 bug，到这一步基本结案：要么它的片段全被更早的深度挡住了，要么它画完之后被别的东西盖掉了，要么它根本不在历史名单里——那就是第 1 步的"产出为零"，往回查剔除和变换。

### 第 4 步：还剩计算嫌疑——对着色器做尸检

输入对、配置对，像素还是错，凶手才轮到着色器逻辑本身。两种手段，由轻到重：

- **中间量可视化**：就是问题 2 的彩虹球大法——但现在不用改代码重编译，抓帧工具可以直接把顶点阶段/片段阶段的任意输出量替换显示在画面上。
- **逐行单步**：对指定的那一个像素，工具根据录制好的输入数据，**在记录之上重新模拟执行**这份着色器，让你像普通调试器一样逐行走、看每个变量的值。问题 1 的"一百万份里找一份"在这里被解决：你不是打断点，而是**事后单独提审那一份计算**。

### 流程全景

```
屏幕上的错误像素
   │
   ├─ 第0步：看原始数据 → CPU 侧错？（结案，回去改数据准备代码）
   │
   ├─ 第1步：流水账逐条重放 → 画面从哪条命令开始错的？
   │
   ├─ 第2步：这条命令的输入（顶点/常量/纹理）对账 → 输入错？
   │
   ├─ 第3步：像素历史 → 被深度杀？被覆盖？压根没出现？（剔除/变换错）
   │
   └─ 第4步：中间量可视化 → 逐行单步 → 着色器逻辑错
```

注意这个顺序的设计哲学：**按排查成本从低到高排，按嫌疑概率从高到低排。** 看一眼缓冲十秒，逐行单步十分钟；而实战中前 3 步能解决九成以上的 bug。单步调试是最后手段，不是第一反应——这是和 CPU 调试习惯最大的不同。

## 问题 5：机器贴不了便利贴——着色器 printf 的位置

抓帧是"事后录像"，还有一类需求它覆盖得不好：**趋势性问题**。比如"某个数值在动画第 3 秒附近开始飘"、"一千个顶点里有三个是 NaN，是哪三个"。这类问题需要着色器像普通程序一样**主动开口汇报**，而不是等你抓帧后逐一提审。

思路是把问题 1 的障碍三拆掉一半：给着色器修一条临时的输出通道——着色器里写打印语句，运行时由外部设施把这些文字收集起来，送到日志窗口。它本质上是**验证层帮着色器代笔**：着色器把消息交给一个特殊的监听者，监听者替它写日志。

> 这是一个补充手段，不是替代品。printf 告诉你"发生了"，抓帧告诉你"为什么"。实战中 printf 负责大海捞针（找到那一帧、那几个顶点），抓帧负责验尸（这个顶点为什么算错）。

---

## 问题 6：这套方法论不会过时，工具会

最后值得明说的一层：本篇笔记的保质期分布得很不均匀。

**会过时的部分**：具体工具的名字、界面、按钮位置。抓帧工具三五年一换代，今天的操作截图明年就过时。这部分**了解即可**——知道"有这个东西、能干什么"，具体怎么点，用时查文档、问 AI。

**不会过时的部分**：问题 4 那套排查流程。它不从属于任何工具，它是从流水线结构本身推导出来的：

> 像素颜色 = 数据 × 计算 × 裁决。所以定位顺序永远是：**先对账数据（海关登记），再找到出事的命令（逐条重放），再查流水线裁决（像素历史），最后才验尸计算（单步）。**

十年后工具换成别的样子，这个顺序还是这个顺序——因为流水线还是那条流水线。学这篇笔记的真正收获，是把"改一行看一次"的随机游走，换成一条确定的二分路径。

## 收尾落地：这套方案在各平台/后端的工具版图上怎么表达

推导区说的"录像机"，落地是一类叫**抓帧调试器**的工具，按平台和后端各有一家：

- **RenderDoc**：免费开源的跨平台抓帧调试器，本篇所有概念（命令流水账、逐步重放、缓冲对账、像素历史、着色器单步）它全都覆盖，是学习阶段的标准答案。它的着色器单步是"在录制数据上模拟执行"，与真实硬件可能有微小出入（诚实的代价之一）。
- **NVIDIA Nsight Graphics**：NVIDIA 的官方工具，抓帧之外更偏性能剖析（每条命令的耗时、硬件计数器），阶段十四性能分析时会更深入地用到它。
- **PIX on Windows**：微软阵营的对应物，D3D12 生态的标准抓帧工具。
- **Xcode GPU Frame Capture**：Apple 平台的对应物，深度集成在 Xcode 里，Metal 专用。
- **着色器 printf**：在 Vulkan 里是验证层提供的 `debugPrintfEXT` 扩展（GLSL/HLSL 里写打印语句，RenderDoc 1.14+ 能直接在其事件窗口里显示这些消息）；其他生态多是厂商工具提供的类似通道。
- **驱动自带的错误报告**：大多数后端还有一个"廉价第一招"——打开调试输出开关后，驱动会把"你传了非法参数"、"这份数据没初始化"之类的警告主动推给 CPU 日志。它不能定位像素问题，但能在抓帧之前就拦掉一批低级错误，成本接近零，永远该开着。

设计差异一句话带过：抓帧派（RenderDoc/PIX）赌的是"一帧是确定的，录下来重放最划算"；实时附加派（部分厂商工具）赌的是"直接插在真机执行上看最准确"。学习阶段选抓帧派——它能回答的问题面最宽，且不挑硬件。

> **诚实的代价清单**：抓帧不是全景监控。它只记录"你实际提交的命令和数据"——如果 bug 是"你忘了发某条命令"，档案里同样没有它（但第 1 步的逐条重放会让缺席很显眼）。录制本身有开销，一帧的档案可能上百 MB。着色器单步是模拟执行，和真机浮点行为可能有出入。以及最根本的一条：**抓帧能告诉你 GPU 忠实地执行了什么，但"CPU 为什么提交了错误的数据"还得回到 CPU 侧用普通调试手段查**——第 0 步那一刀的意义正在于此，它告诉你该用哪套工具继续。

## 总结：这篇笔记建立的核心认知

1. **"颜色不对"是零信息症状**——每个错误像素都是几百步计算的终点。调试的全部工作是把嫌疑范围从"整帧"二分到"一步"。
2. **普通调试器在 GPU 上失效是结构性的**：另一个处理器、百万份并行、没有输出通道。所以 GPU 调试只有两条路：把信息编码进颜色，或者在 GPU 之外架录像机。
3. **"把中间量画成颜色"是永远有效的兜底招**，但它一次看一个量、破坏现场、看不见"没画出来的东西"。
4. **抓帧 = GPU 的时间旅行机**：录制一帧的全部命令与中间状态，事后任意慢放提审。它成立的根基是"一帧 = 确定的命令 + 确定的数据"，重放近乎免费。
5. **标准流程按成本升序、概率降序排**：对账原始数据（劈开 CPU/GPU）→ 逐条重放找出事命令 → 输入对账 → 像素历史查裁决 → 单步验尸计算。九成 bug 在前三步结案，单步是最后手段。
6. **工具会换代，方法论不会**——排查顺序是从流水线结构推导出来的，这才是本篇要带走的资产。

# 法线变换的几何直觉

## 问题 0：像素现象——压扁的球，亮斑跑偏了

场景很简单：一个球体模型，一盏正上方的光。你把球的 X 轴缩放设为 0.5，压成一个橄榄球。

```
   光 ↓↓↓（正上方）

   变换前：球              变换后：橄榄球（X 压扁一半）

      ▄▄▄                    ▄▄▄▄▄▄▄
    ▄█亮██▄                ▄▓▓▓▓▓▓▓▄
    ██亮███      →        ▐▓▓▓▓▓▓▓▓▌     ← 顶部被压平，
    ▀█████▀                ▀▓▓▓▓▓▓▓▀        亮斑应该更大、更居中
      ▀▀▀                    ▀▀▀▀▀▀▀
   亮斑在顶部正中 ✅        但实际画面里亮斑歪到了两侧 ❌
```

顶点位置的变换没有任何问题——形状确实是你要的橄榄球。问题出在光照：**每个像素计算 N·L 时用的法线，不再指向真实表面的朝向。** 于是"这个表面有多正对光源"的判断全盘出错，亮斑出现在几何上根本不该亮的位置。

最自然的写法是罪魁祸首：既然顶点位置用 Model 矩阵变换，法线也是顶点数据，那就用同一个矩阵变呗——

```
顶点着色器里的朴素方案：
  worldPos    = M × position    ← 对的
  worldNormal = M × normal      ← 看起来对称、优雅，但是错的
```

这篇笔记就回答三件事：这个朴素方案为什么**有时候**是对的、什么时候会错、错的时候正确的矩阵长什么样、以及为什么是那个样子。

## 问题 1：法线是"方向"不是"位置"——这句话对变换意味着什么

在 [[Notes/计算机图形学/软光栅化与3D数学/3D变换与齐次坐标|3D 变换与齐次坐标]] 里你已经见过：齐次坐标用 w 分量区分点和方向——

```
点（position）：   (x, y, z, 1)   ← 平移对它有效
方向（direction）： (x, y, z, 0)   ← 平移对它无效
```

为什么方向对平移免疫？直觉很清楚：**一支指向北的箭头，不管你把它拿到哪里，它还是指向北。** "方向"描述的是两个点之间的相对关系，和坐标原点在哪无关。齐次坐标里 w=0 正好把 4×4 矩阵的平移列（第四列）乘以零消掉，数学忠实地编码了这个几何事实。

法线是典型的方向——它描述"这个表面面朝哪里"，不描述"表面在哪"。所以第一个结论：

> **法线变换只跟矩阵的 3×3 部分（旋转 + 缩放）有关，平移列完全不参与。** 所有讨论都可以只看 `mat3(M)`。

但"法线是方向"还有一层更深的含义，是这篇笔记的核心伏笔：**法线不是普通的方向，它是"被约束出来的方向"。**

普通方向（比如顶点的运动速度）是"自有方向"——物体怎么变，它跟着怎么变，用和位置一样的规则变换是天经地义的。而法线的定义是**派生的**：它是"垂直于这个点处所有切线的那个方向"。它的存在是为了满足一个约束（垂直），而不是一个独立的几何量。

这两类方向在变换下的行为截然不同——正是这个区别，决定了法线为什么不能跟着顶点用同一个矩阵。先记住这个伏笔，问题 3 会回收它。

## 问题 2：先用朴素方案——它什么时候碰巧是对的？

直接 `worldNormal = mat3(M) × normal`，逐类变换检验：

### 纯旋转：对

旋转矩阵的每一列都是单位向量且互相垂直（正交矩阵）。它改变所有向量的朝向，但**保持所有夹角和长度**。法线和表面原来垂直，旋转 30° 之后，法线和表面还是垂直——因为垂直关系（90° 夹角）本身就是被旋转保持的。

```
旋转前：  表面 ────→    旋转后：  表面 ───→
              ↑ N                        ↗ N'
          （垂直 90°）               （还是垂直 90°）
```

### 均匀缩放：对（靠 normalize 救回来）

三个轴缩放同样倍数 s，所有方向的**朝向不变**，只有长度变成 s 倍。法线变长了，但我们在光照计算前本来就要 `normalize()`——长度被抹掉，方向是对的。

```
缩放前：N = (0, 1, 0)     缩放 ×3 后：N = (0, 3, 0)
        normalize 后 → (0, 1, 0) ✅ 方向没变
```

### 平移：对（w=0 免疫）

前面说过，不参与。

### 结论：这个 bug 藏得很深

只要你的变换是**旋转 + 均匀缩放 + 平移**的任意组合——也就是游戏里最最常见的刚体变换——朴素方案碰巧完全正确。这意味着：

- 你写的第一个旋转立方体 demo，光照是对的；
- 你加载的 OBJ 模型原地打转，光照也是对的；
- **直到有一天**美术给了一个压扁的模型、或者你自己写了 `scale = (0.5, 1.0, 1.0)`，光照突然诡异起来，而你完全有理由怀疑光源、怀疑插值、怀疑一切——除了那个"一直工作正常"的矩阵。

这就是为什么这个 bug 在初学者项目里平均要浪费一个下午。它值得一篇笔记。

## 问题 3：非均匀缩放为什么破坏法线？

### 3.1 先看现象：压扁球上的具体数字

回到问题 0 的场景：X 轴缩放 0.5，Y 轴不变。取球面上 45° 方向的一点，该处法线 `N = (0.707, 0.707, 0)`。

```
                        真正的法线（26.6°）
                       ↙
        球面一点 •
               ↖ N = (0.707, 0.707)，45°
                \
  ────────────────────────→ X（被压扁的轴）
```

X 压扁一半后，用朴素方案变换法线：`M × N = (0.5×0.707, 0.707) = (0.354, 0.707)`，角度变成 **63.4°**——法线倒向了 Y 轴（没被压的那个轴）。

但压扁后的表面在同一点的真实朝向是多少？椭圆上该点的真实法线角度约 **26.6°**——它倒向了 **X 轴**（被压的那个轴）。

**朴素方案偏了 63.4° − 26.6° ≈ 37°，而且偏的方向和真相正好相反。** 这不是误差，这是方向性错误。

### 3.2 几何直觉：压扁哪个轴，真法线就往哪个轴倒

为什么会这样？想一想"压扁"对表面做了什么：

```
压扁前：圆                    压扁后：椭圆（X 方向被压平）

      ↑ N                        ↙ 真法线倒向 X 轴
    __|__                        因为顶部表面被"摊平"了——
   /     \                       越平的面，法线越接近
  |   •   |      →            被压扁的那个轴
   \_____/                  ___________
                           /  _______  \
                          |  /       \  |
                           \ ‾‾‾‾‾‾‾  /
                            ‾‾‾‾‾‾‾‾‾
```

把一个圆在 X 方向压扁，等于把顶部和底部的弧"摊得更平"。面越平，法线越"躺"向被压的方向。这是表面的真实几何——**真法线倒向被压扁的轴。**

而朴素方案 `M × N` 对法线做的事和对位置做的事一样：X 分量也乘以 0.5。法线本来指得挺"横"的，X 分量一缩，它就"竖"起来了——**假法线倒向没被压的轴。**

一个往被压的轴倒，一个往没压的轴倒，南辕北辙。

> 直觉口诀：**表面怎么变，法线反着来。** 把表面往 X 压，法线往 X 倒；想让数学自动给出这个结果，变换法线的矩阵就得包含"缩放的倒数"——X 缩 0.5，法线的 X 分量就要乘 2。这个"倒数"正是逆转置里"逆"字的来源。

### 3.3 切线见证法：为什么必须是逆转置

几何直觉给了方向，但要得到精确的矩阵，需要回到问题 1 埋的伏笔：**法线是被"垂直于切线"这个约束定义出来的。** 那就让切线当见证人。

第一步：**切线跟着顶点用 M 变换是对的。**

切线 = 表面上两个相邻顶点的差，是"自有方向"（和速度向量同类）。顶点位置用 M 变换，它们的差自然也用 M 变换：

```
T' = M × T    ✅ 切线这么变，没有争议
```

第二步：**变换后的法线必须仍然垂直于变换后的切线。**

这是法线的存在意义，在任何变换下都不能破：

```
N' · T' = 0    对所有切线 T 成立
```

第三步：**设变换法线的矩阵是 G，把两个条件拼起来。**

```
N' = G × N
N' · T' = (G·N)ᵀ(M·T) = Nᵀ (GᵀM) T = 0
```

已知变换前 `Nᵀ T = 0`（法线本来就垂直所有切线）。要让上式对**任意** T 成立，唯一的可能是：

```
Gᵀ × M = I        →        G = (M⁻¹)ᵀ = M⁻ᵀ
```

**法线矩阵 = Model 矩阵的逆转置（inverse transpose）。** 这不是某个人发明的技巧，而是"垂直关系必须在变换下保持"这个几何约束的唯一解。

### 3.4 读出逆转置的几何意义：跟着转，反着缩

把任意 Model 矩阵拆成"旋转 × 缩放"（`M = R × S`），看逆转置对每一部分做了什么：

```
M⁻ᵀ = (R × S)⁻ᵀ = R⁻ᵀ × S⁻ᵀ = R × S⁻¹
```

- **旋转部分 R**：正交矩阵的逆转置是它自己（`R⁻ᵀ = R`）。所以法线**跟着旋转走**——和问题 2 里"纯旋转用 M 变换是对的"完美吻合。
- **缩放部分 S**：对角矩阵的逆转置是每个分量取倒数（`S⁻ᵀ = S⁻¹`）。X 缩 0.5，法线的 X 分量就乘 2。这正是问题 3.2 的直觉口诀"表面怎么变、法线反着来"的数学化身。

> **一句话记住法线矩阵：跟着转，反着缩。** 旋转照旧，缩放取倒数。它只在"存在非均匀缩放"时才和 M 有区别——旋转和均匀缩放时两者殊途同归，这就是为什么 bug 只在那一刻现身。

用 3.1 的数字验证：`M⁻ᵀ = diag(2, 1)`，`M⁻ᵀ × N = (2×0.707, 0.707) = (1.414, 0.707)`，角度 **26.6°**——和椭圆上真实法线分毫不差。

## 问题 4：工程上到底怎么做？

推导完了，落地时有四个真实的工程决策。

### 4.1 法线矩阵在哪算：CPU，每物体一次

矩阵求逆涉及除法和伴随矩阵，不便宜。一个物体几千个顶点，如果让每个顶点在着色器里各算一次求逆，是几千倍浪费。

正确做法：**CPU 端每物体算一次 3×3 逆转置矩阵，和 Model 矩阵一起，走每物体常量通道传进来。**

回看 [[Notes/计算机图形学/光照与数据流/数据通道与更新频率|上一篇笔记]] 里引擎参数绑定的分层框架——层 3.5"每物体常量"里已经躺着一行：`法线矩阵（3x3 部分）`。当时它只是个名字，现在你知道它从哪来、为什么必须和 Model 矩阵并列存在：它和 Model 矩阵同频率（每物体）、同体量（36 字节），但它是一份**独立推导的数据**，不是能从 Model 矩阵里免费提取的。

### 4.2 两条快速路径：大部分时候不用真求逆

- **检测到均匀缩放**（|sx| = |sy| = |sz|）：跳过求逆，直接用 `mat3(M)`，反正方向对，最后 normalize 兜底。
- **检测到纯刚体变换**（旋转 + 平移，无缩放）：`M⁻ᵀ = M`（正交性质），直接用。

引擎可以在每帧更新 Model 矩阵时顺手做这两个检测（比较三个缩放分量，一次分支），命中就省下求逆。这是"把通用解做快"的典型工程手法：**通解保证正确，特判保证速度。**

### 4.3 蒙皮动画的特例：为什么骨骼矩阵可以直接用

骨骼动画里，每个顶点被最多 4 根骨骼的矩阵加权混合——不可能为每个顶点预计算逆转置（每顶点 4 次求逆，每个骨骼每帧都在动）。

但骨骼矩阵几乎都是**旋转 + 平移**（关节只做刚体运动，极少带缩放）。正交矩阵的逆转置是自己，所以蒙皮着色器里直接用骨骼矩阵变换法线，恰好是正确的——这正是快速路径 4.2 第二条的大规模应用。

> 这也是为什么"给骨骼加非均匀缩放"在很多引擎里是危险操作：它悄悄打破了"骨骼矩阵正交"这个默认假设，法线立刻出错，而且错得和这篇笔记开头的橄榄球一模一样。工业上的常见对策是**把缩放烘焙进顶点数据**（在导出资产时就把缩放应用到顶点位置和法线上），让运行时矩阵保持刚体。

### 4.4 永远 normalize，没有例外

两条独立的理由，都要归一化：

1. **缩放破坏单位长度**：均匀缩放把法线拉长 s 倍；逆转置里的 `S⁻¹` 也会改变长度。就算方向对了，`N·L` 里的 N 不是单位向量，亮度就整体偏掉。
2. **插值破坏单位长度**：两个单位法线线性插值，中间结果必然短于 1（弦比弧短）。这是光栅化插值的固有性质，和变换无关。

所以在片段着色器里、做光照之前，`normalize(N)` 是雷打不动的第一步。

> **诚实的代价清单**：法线矩阵不是免费的。每物体多传 36 字节常量、CPU 每物体多一次 3×3 求逆（或一次特判）、着色器里多一次 normalize。这些加起来每帧也许几百纳秒——相比它修复的"整个场景的光照正确性"，这是图形学里性价比最高的几笔开销之一。

## 问题 5：这篇笔记没解决完的事（预告）

- **剪切（shear）变换**：比非均匀缩放更罕见的变换（把方块推成平行四边形）。逆转置对它是通解，依然正确——这就是用"切线见证法"推导而不是"举几个例子"的好处：结论对所有线性变换成立，不需要逐类打补丁。

- **法线贴图的切线空间**：阶段四会引入法线贴图——用一张纹理扰动每个像素的法线。那时你会遇到 TBN 矩阵（切线/副切线/法线拼成的坐标架）：切线跟顶点走 M，法线走 M⁻ᵀ，两个矩阵不同导致 TBN 不再严格正交。今天这篇笔记是理解那个坑的地基。

- **非均匀缩放本身该避免吗**：一定程度上，是。很多团队的资产管线规范直接写着"模型不携带非均匀缩放，缩放在导出时烘焙"。但运行时动画、程序化生形、UI 拉伸都绕不开它——所以法线矩阵这个能力必须存在，哪怕你希望自己永远用不上。

## 收尾落地：这套方案在各图形后端中怎么表达

这篇笔记的收尾异乎寻常地短——**因为法线矩阵不是任何图形后端的概念。** 它不是 GPU 对象，不是管线状态，不是资源类型。它只是 CPU 算好的一份 3×3 矩阵，走 [[Notes/计算机图形学/光照与数据流/数据通道与更新频率|上一篇笔记]] 已经讲透的"每物体常量"通道进着色器。

- **OpenGL**：顶点着色器里多声明一个 `uniform mat3`，和 Model 矩阵并列。历史上固定管线时代有内建的 `gl_NormalMatrix` 和自动归一化开关——硬件曾自动帮你做逆转置；可编程管线把这份责任交给了你，这也是为什么现代教程必须讲这件事。
- **Vulkan / D3D12 / Metal**：没有任何对应物——它就是每物体常量缓冲 / 推送常量里多出来的 36 字节，和上一篇笔记的分层框架完全同构。

这恰好是"概念是本质、API 是邮编"的最佳例证：**这篇笔记 90% 的内容是纯几何，任何后端、任何引擎、任何年代都成立。** 学会的是"法线是被垂直约束定义的方向，变换它要保持垂直关系"，而不是某个 API 的某个对象。

---

## 总结：这篇笔记建立的核心认知

1. **法线是"被约束的方向"，不是"自有的方向"**——它由"垂直于所有切线"定义，变换后必须仍然满足这个约束。这是它和位置、切线、速度等普通几何量的本质区别。
2. **朴素方案（`M × N`）在旋转 + 均匀缩放 + 平移下碰巧正确**——所以这个 bug 只在非均匀缩放现身时爆发，且爆发前毫无征兆。
3. **法线矩阵 = M⁻ᵀ 是"垂直关系保持"的唯一解**——切线见证法两步推出，对一切线性变换成立。
4. **几何口诀：跟着转，反着缩。** 旋转的逆转置是自己，缩放的逆转置是倒数——非均匀缩放压扁哪个轴，真法线就倒向哪个轴，朴素方案偏偏倒向另一边。
5. **工程实践**：CPU 每物体算一次走每物体常量；均匀缩放和刚体变换走快速路径；蒙皮动画因骨骼矩阵正交而天然豁免；片段着色器里永远先 normalize。

# 让像素响应光

## 问题 0：为什么画出来的模型是"平的"？

阶段二结束时，你渲染出来的画面大概是这样的：

```
┌──────────────────────┐
│                      │
│       ▲              │
│      ███             │  整个模型只有一种颜色。
│     █████            │  没有高光、没有阴影过渡、
│    ███████           │  没有"立体感"。
│     █████            │
│      ███             │  它是个剪影——轮廓对了，
│       ▼              │  但所有表面朝向都是"哑的"。
│                      │
└──────────────────────┘
```

每一个像素的颜色在片段着色器里直接写死了——`return vec4(1.0, 0.5, 0.3, 1.0)`。不管你从什么角度看、光源在哪、表面朝向哪，所有像素输出同样的 RGB。

现实中的物体完全不是这样。同一个橙色的篮球：
- **正对光源的面**是亮的；
- **背对光源的面**是暗的；
- 在某个特定角度能看到**一块明亮的光斑**（高光）；
- 完全背光的面也不是全黑，而是**被环境散射光微微照亮**。

> **本质问题：每个像素的颜色，应该由"这个像素对应的表面点，收到了多少来自光源的光"来决定。纯色剪影缺少的是这个"收到多少光"的计算。**

---

## 问题 1：一个像素"收到多少光"，取决于什么？

想象你用手电筒照一面墙。墙上某一点的亮度取决于——

### 1.1 决定性因素：表面朝向与光源方向的夹角

你把一本合上的书平着面对手电筒——整页都是亮的。把书侧过来——亮度减半。把书背过去——完全黑的。

用数学表达：**亮度 ≈ 光源强度 × cos(入射线与表面法线的夹角)**

```
光源方向 L
    \
     \  θ
      \
    ─────── 表面
       ↑ 法线 N

亮度 ∝ max(0, cos(θ)) = max(0, N·L)
```

`max(0, ...)` 是因为夹角超过 90° 意味着光从背后照过来，正面收到的光量为零——这在物理上是合理的：光穿不过不透明的表面。

这就是**漫反射**的直觉：光打到一个粗糙表面，向所有方向均匀散射，但入射角越偏，单位面积接收到的光就越少。**Lambert 余弦定律**讲的就是"斜着照到表面的光，能量被摊到了更大的面积上"。

> **演示**：一束手电光垂直照到墙上是一个小而亮的圆斑；倾斜 60° 照，光斑变成椭圆，面积翻倍——但总光量不变，所以每单位面积的亮度减半。`cos(60°) = 0.5`，和直觉完全吻合。

### 1.2 还有高光：不是所有表面都只做漫反射

镜面和金属不是"向所有方向均匀散射"——大部分光沿入射角的反射方向集中射出。

```
光源 → ◎ → 你（眼睛正好在反射方向上，看到刺眼的光斑）
光源 → ◎ → 旁边的人（不在反射方向上，看到的是暗的）
```

这个高光斑叫**镜面反射**（specular reflection）。它的亮度和"你的视线方向与理想反射方向的夹角"有关——越接近反射方向越亮，离得越远越暗。

### 1.3 还有环境光：完全背光的面为什么不是全黑？

即使一个物体完全背对光源，在现实中也**不是纯黑的**——原因是光在环境中多次反弹：光打到地板 → 反弹到天花板 → 反弹到物体的背面。这个"光 bounce"在实时渲染里是个极其昂贵的问题（阶段十一才系统展开）。

最简单的工程近似：**假设所有表面都被一股均匀的环境光微微照亮**。这不是物理正确的，但避免了"暗面全黑"的视觉灾难。

## 问题 2：这三件事总结成一个公式，长什么样？

每一个像素的颜色 = **环境光项 + 漫反射项 + 镜面反射项**。

这就是 Blinn-Phong 反射模型的核心分解。注意它**不是物理定律**——物理上不存在"环境光/漫反射/镜面反射"三个独立的光源，它们是对同一束光在不同表面行为上的**经验拆分**。

```
像素颜色 = ambient_color + diffuse_color + specular_color

每一项的直觉：

ambient  = 材质颜色 × 环境光颜色 × 环境光强度
           "假设有一股无处不在的弱光，最少保证暗面不是纯黑"

diffuse  = 材质颜色 × 光源颜色 × max(0, N·L) × 光源强度
           "表面越正对光源越亮，背对就是黑的"

specular = 光源颜色 × max(0, N·H)^shininess × 光源强度
           "视线方向越接近镜像反射方向越亮，shininess 控制光斑大小"
```

其中 `H` 叫**半程向量**（halfway vector）：`H = normalize(L + V)`，即光源方向和视线方向的中间方向。如果法线 `N` 和半程向量 `H` 重合，说明你的眼睛正好在理想反射方向上——高光最亮。

### 为什么用半程向量而不直接算反射向量？

这是 Blinn-Phong 对 Phong 模型的关键改进。直接算反射向量的事：

```
Phong:    spec = max(0, reflect(-L, N) · V)^shininess
Blinn:    spec = max(0, N · normalize(L + V))^shininess
```

Blinn-Phong 赢在两点：

1. **低 shininess 时更自然**：Phong 在粗糙表面（低 shininess）上，高光边缘会出现一条生硬的截断线——因为反射向量和视线方向的夹角超过 90° 时被 `max(0, ...)` 一刀切断。Blinn-Phong 的 `N·H` 夹角永远不会超过 90°（除非光源到了表面背面），高光自然渐隐，没有截断。

2. **计算更便宜**：`normalize(L+V)` 比 `reflect(-L, N)` 少一步运算，在几十年前这是实打实的性能差距。现在当然无所谓了，但"计算更简单"加上"结果更自然"的双重优势让 Blinn-Phong 成了事实标准。

> **一句话总结 Blinn-Phong**：它是一种**经验模型**——把光在表面的行为人为拆成三笔账，每笔账的公式不是从物理定律推导出来的，而是"试出来看起来对的"。参数（ambient 强度、diffuse 系数、specular 系数、shininess）全凭艺术家手调，没有"一组正确的参数"。正因如此，换个光照环境参数就要重新调，这也是为什么它最终会被 PBR 取代。

## 问题 3：光照计算放在管线的哪个阶段？

到目前为止，我们只知道片段着色器负责输出像素的最终颜色。但光照计算需要法线、光源方向、观察方向等信息——这些信息进入管线的时间不同。一个关键决策出现了：

**光照计算应该放在顶点着色器，还是片段着色器？**

### 方案 A：在顶点着色器里算（逐顶点光照 / Gouraud Shading）

```
每个顶点：
  1. 拿顶点法线（和位置一起作为顶点属性传进来）
  2. 算 N·L 和 N·H
  3. 输出"这个顶点的最终颜色"作为 varying 传给片段着色器
  4. 光栅化自动插值颜色到每个像素
```

**直觉上可行**：三角形只有 3 个顶点，每个三角形只算 3 次光照，极快。

**问题**：高光被插值"摊薄"了。

```
顶点A（高光亮）  ────插值────  顶点B（高光暗）
           ↓
   三角形中心的高光应该很亮，
   但 A→B 之间线性插值后，
   中心的高光亮度变成了 A+B 的一半 —— 比实际暗得多。
```

结果就是：低面数模型（比如一个只有 100 个面的球）上，能看到明显的三角面片轮廓——每条边的光照过渡不平滑。这就是"逐顶点光照"的特征缺陷：高光被困在顶点上，面片中心永远吃不到完整的镜面反射。

### 方案 B：在片段着色器里算（逐像素光照 / Phong Shading）

```
顶点着色器：
  1. 把法线、世界位置等"原始几何信息"作为 varying 传给片段着色器
  2. 不计算光照，只做坐标变换

片段着色器（每个像素）：
  1. 收到光栅化插值后的法线和世界位置
  2. 用插值后的信息重新计算 N·L 和 N·H
  3. 输出"这个像素的最终颜色"
```

**代价**：每个像素都要算一遍光照——一个屏幕上有 200 万个像素，每个像素算一次 Blinn-Phong，这就是 200 万次 dot product 和 pow。**但这就是 GPU 存在的意义**——200 万次简单数学对 GPU 来说不是负担，而是本职工作。

**收益**：每个像素的光照都是用该像素自己的法线方向算出来的，不会出现面片中心的亮度"被周围顶点稀释"的问题。高光圆润、过渡平滑。

### 决策：选方案 B

在现代 GPU 上，**逐像素光照是默认选择**。顶点着色器算光照唯一能赢的场景是"设备极弱（OpenGL ES 1.x 时代）"或"顶点数是片段数的几百倍（极其密集的几何体 + 低分辨率渲染目标）"——这些在现代桌面/移动 GPU 上几乎不存在。

> **记住这句话**：能放在片段着色器里的就不要放在顶点着色器里。顶点的数量量级是千，像素的数量量级是百万——但 GPU 的片段处理器数量远多于顶点处理器，它就是为了"百万像素并行"设计的。

## 问题 4：Blinn-Phong 的每一项，需要什么信息？从哪来？

现在我们把光照公式拆开，看每一项具体需要什么输入：

| 光照项 | 需要的输入 | 从哪来 | 面片之间是否变化 |
|--------|-----------|--------|-----------------|
| 环境光 | 材质颜色、环境光颜色和强度 | 材质参数、场景全局常量 | 不变化 |
| 漫反射 `N·L` | 表面法线、光源方向、材质颜色、光源颜色 | 法线→顶点属性；光源→场景常量 | **法线在面片之间变化** |
| 镜面反射 `N·H` | 法线、光源方向、视线方向、shininess | 法线→顶点属性；光源+视线→场景常量；shininess→材质参数 | **法线在面片之间变化** |

**关键洞察**：Blinn-Phong 看似三项，但每一项都依赖**法线 `N`**。法线是"这个表面面朝哪里"的信息——每个顶点有自己的法线，光栅化时插值到每个像素。没有法线，光照公式的所有项都算不出来。

- 材质颜色、shininess、光源颜色、光源方向——这些是**全局常量**或**每物体常量**，下一笔记会专门讲它们怎么进 GPU。
- 世界位置和视线方向——可以在顶点着色器里从顶点位置和相机位置推导出来，作为 varying 传下去。

## 问题 5：没有法线怎么办？法线怎么和模型一起给到 GPU？

### 5.1 如果模型文件带了法线

OBJ 文件中可以包含 `vn` 行（顶点法线），和 `v` 行（顶点位置）一样是模型自带的属性。把它作为顶点属性的一种，和位置一起存进 GPU 显存、一起在顶点着色器里声明：

```
顶点数据的布局（内存中的字节流）：
[x y z | nx ny nz | ...]
 位置       法线
```

这只是多了一种顶点属性——和颜色、UV 没有任何区别。GPU 不关心这个属性的语义是"颜色"还是"法线"，它只关心"这个 float3 在内存的第几个字节、stride 是多少"。语义是 Shader 里的逻辑赋予的。

### 5.2 如果模型文件没有法线——怎么重建？

很多简单的 OBJ 文件只提供了位置和面片索引，没有法线。但光照必须要法线，怎么办？**从面片信息反推**。

一个三角形的法线 = 其两条边的叉积归一化：

```
法线 = normalize(cross(B - A, C - A))
```

但这给出的是**面法线**——一个三角形所有像素共用一个法线，结果就是"每个三角面片一种颜色"，回到了逐面片绘制的视觉。

**平滑法线**的思路：一个顶点通常属于多个三角形，取所有相邻三角形的面法线，按面积加权平均，就得到这个顶点的"平滑法线"。

```
顶点 P 被三个三角形共用：
三角形1 面积=2.0, 面法线=(0.1, 0.9, 0.0)
三角形2 面积=1.5, 面法线=(0.3, 0.8, 0.1)
三角形3 面积=2.5, 面法线=(0.0, 0.9, 0.2)

P 的平滑法线 = normalize(2.0×(0.1,0.9,0.0) + 1.5×(0.3,0.8,0.1) + 2.5×(0.0,0.9,0.2))
```

按面积加权的原因：大三角形对这个顶点视觉贡献更大，它的朝向应该更有话语权。

> 法线是单位向量（长度为 1），所有运算前/后都必须做归一化。光栅化的线性插值会破坏单位长度——插值后的法线必须 `normalize()`。

### 5.3 法线传给 GPU 后，片段着色器怎么接收？

整体链路：

```
OBJ 文件                                    GPU 显存
┌──────────┐      ┌──────────┐      ┌─────────────────┐
│ v 行(位置) │ ───→ │ CPU 解析  │ ───→ │ 位置 buffer      │
│ vn 行(法线)│ ───→ │ 交错排列  │ ───→ │ 法线 buffer      │  ← 同一次上传，同一个 VAO 描述布局
│ f 行(面片) │ ───→ │ 索引缓冲  │ ───→ │ 索引 buffer      │
└──────────┘      └──────────┘      └─────────────────┘
                                           │
                                           ▼
                                    顶点着色器拿到：位置 + 法线（每个顶点）
                                           │
                                           ▼ 光栅化插值
                                    片段着色器拿到：插值后的位置 + 法线（每个像素）
                                           │
                                           ▼
                                    计算 N·L、N·H → 像素颜色
```

## 问题 6：这个阶段我不知道、但后续会遇到的坑（预告）

在你开始写 Blinn-Phong 之前，有几个坑值得提前知晓——不是现在要解决的，但知道它们存在可以避免以后 debug 时的巨大困惑：

- **法线被非均匀缩放破坏**：用顶点的 `Model` 矩阵变换法线时，如果模型有非均匀缩放（比如 X 轴压扁一半），用同一个矩阵变换法线会得到错误的方向。法线需要专门的**法线矩阵**（Model 矩阵的逆转置）来变换——这是阶段三 3.3 [[Notes/计算机图形学/光照与数据流/法线变换的几何直觉|法线变换的几何直觉]] 的内容。

- **光源位置和材质参数怎么进 Shader**：目前我们只在 Shader 里拿到顶点属性（位置、法线）。光源在哪、材质什么颜色、shininess 是多少——这些"不逐顶点变化"的信息怎么传给 Shader？这是阶段三 3.2 [[Notes/计算机图形学/光照与数据流/数据通道与更新频率|数据通道与更新频率]] 要回答的。

- **能量不守恒**：Blinn-Phong 的 ambient + diffuse + specular 三项独立相加，没有任何机制保证"反射的总光量 ≤ 入射的总光量"。光源强度 1.0 时，三项加起来可能超过 1.0——这在物理上是不可能的，但在 Blinn-Phong 里完全可能。这就是它最终会被 PBR 取代的根本原因之一。

- **Gamma 校正**：你把 Blinn-Phong 算出来的颜色直接写到屏幕上，结果会发现"暗部太暗、亮部太亮"——因为显示器不是线性的。这个问题在阶段七才系统解决，现在先知道现象存在。

## 收尾落地：这些概念在各图形后端中怎么表达

> 以下内容将前面推导的纯概念映射到具体后端的对象/机制。这部分不是学习目标——只是告诉你在各后端中"这个东西在哪"。具体的函数调用和代码实现交给 AI 生成。

### 光照计算的位置：片段着色器

所有后端都在**片段着色器（Pixel Shader）**中完成光照计算——这是逐像素光照的条件。顶点着色器只负责把法线和世界位置作为输出传给光栅化阶段。

- **OpenGL**：顶点着色器用 `out` 声明法线和世界位置，片段着色器用 `in` 接收插值后的值。Shader 用 GLSL 编写。
- **Vulkan**：同样机制，但 Shader 编译成 SPIR-V 字节码，`in`/`out` 通过 `location` 布局限定符匹配。Vulkan 要求你在创建渲染管线时就声明"哪些顶点属性连到哪个 location"。
- **D3D12**：HLSL 中顶点着色器输出用 `SV_Position`（系统值语义）和自定义语义（如 `NORMAL`、`TEXCOORD`），像素着色器用相同语义接收。管线状态对象（PSO）在创建时绑定输入布局和 Shader。
- **Metal**：`[[stage_in]]` 属性索引机制，`[[position]]` 和 `[[user(n)]]` 限定符。Metal Shading Language 基于 C++14。

核心逻辑完全一致，差异只在语法和绑定时机。

### 法线作为顶点属性

- **OpenGL**：法线和位置一起存入 VBO，VAO 用 `glVertexAttribPointer` 声明其布局（location、stride、offset）。法线是"另一种顶点属性"，不是特殊对象。
- **Vulkan**：`VkVertexInputBindingDescription`（数据从哪个 VkBuffer 来、stride 多少）+ `VkVertexInputAttributeDescription`（第几个 location 是法线、什么格式）。比 OpenGL 显式——创建渲染管线时就要填好，不能运行时偷偷改。
- **D3D12**：`D3D12_INPUT_ELEMENT_DESC` 数组，每个元素描述一个顶点属性的语义名、格式、slot。PSO 创建时锁定。
- **Metal**：`MTLVertexDescriptor`，和 Vulkan/D3D12 一样在管线创建时锁定布局，运行时不可变。

### Blinn-Phong 的参数传递

Blinn-Phong 需要三类参数——材质颜色、光源信息、shininess。这些是"全局常量"或"每物体常量"，不走顶点属性通道：
- **OpenGL**：用 uniform 变量传递。调用 `glUniform*` 系列函数在绘制前设置值。
- **Vulkan**：用 Descriptor Set（绑定 uniform buffer），在录制命令缓冲时绑定。比 OpenGL 复杂但支持多线程录制。
- **D3D12**：用 Constant Buffer View（CBV），通过 Root Signature 绑定。和 Vulkan 的 Descriptor Set 思路一致。
- **Metal**：用 `setVertexBytes` / `setFragmentBytes`（小数据直接内联）或 buffer binding（大数据通过 MTLBuffer）。Metal 对"小常量"做了特殊优化——几个 float 可以直接塞进命令编码器，连显存分配都不需要。

> **下一笔记会专门展开 uniform 及其各后端的对应**——这是阶段三最核心的概念，决定了引擎材质系统"参数绑定"那一层的设计。

## 从 Blinn-Phong 到 PBR：这条路的终点在哪

Blinn-Phong 是一个**经验模型**——它把光的行为拆成三项，每项的公式是靠"调参数试出来的"：

| 问题 | Blinn-Phong 的表现 | PBR 如何解决 |
|------|-------------------|-------------|
| 能量守恒 | ambient+diffuse+specular 可能 > 入射光 | BRDF 强制 `∫反射 ≤ ∫入射` |
| 参数不直观 | shininess=32 这个数字代表什么？不知道，调调看 | roughness=0.3 直接对应"表面微观粗糙程度" |
| 金属 vs 非金属 | 用 specular 颜色手动模拟 | metallic=1 时镜面反射=材质颜色，metallic=0 时镜面反射=白色（电介质反射率~4%） |
| 环境光 | 一个常数值，与场景无关 | IBL：用环境 Cubemap 积分出真实的半球光照 |

> 阶段九（PBR）会完整展开。现在你只需要知道：Blinn-Phong 是通往 PBR 的那座桥——走过它，你才理解 PBR 在解决什么；而不是直接背 Cook-Torrance 公式。

## 总结：这篇笔记留下的问题

这篇笔记说的是：

1. **纯色剪影缺什么**：每个像素需要"这个表面被光照到多少"的计算，而这个计算的核心是法线。
2. **法线从哪里来**：OBJ 文件的 `vn` 行，或者从面片叉积+平滑重建。
3. **光照怎么算**：Blinn-Phong 是一个经验分解——环境光（防止全黑）+ 漫反射（`N·L`，表面越正对光源越亮）+ 镜面反射（`N·H`，越接近镜像反射越亮）。
4. **在哪里算**：片段着色器——GPU 就是为"百万像素并行"设计的。
5. **Blinn-Phong 的局限**：能量不守恒、参数不直观、环境光是假的。

但留下一个巨大的缺口：**材质颜色、光源位置、shininess 这些"不逐顶点变化"的信息，怎么传进 Shader？**

法线是每顶点一份，作为顶点属性传进来了。但光源方向每帧一个值，材质颜色每个模型一个值——如果把它们也塞进每个顶点的属性里，10 万个顶点重复存同一个光源位置，纯属浪费。**GPU 需要一种"一份数据，所有顶点/像素共享"的机制。**

这就是下一篇笔记要回答的——[[Notes/计算机图形学/光照与数据流/数据通道与更新频率|数据通道与更新频率]]。

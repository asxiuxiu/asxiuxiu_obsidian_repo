# 数据通道与更新频率

## 问题 0：Blinn-Phong 需要的信息，更新频率差了几个量级

回顾 Blinn-Phong 光照公式需要的所有输入：

| 需要的信息 | 来源 | 更新时机 | 更新频率 |
|-----------|------|---------|---------|
| 顶点位置 | OBJ / 模型数据 | 模型加载后不变 | 几乎从不更新 |
| 顶点法线 | OBJ / 模型数据 | 模型加载后不变 | 几乎从不更新 |
| MVP 矩阵 | CPU 每帧计算 | 相机或物体动了就变 | 每物体每帧 |
| 光源位置 / 方向 | 场景逻辑 | 光源移动时变 | 每帧 |
| 光源颜色 / 强度 | 场景逻辑 | 光源属性变化时变 | 每场景 / 偶尔 |
| 材质颜色 (albedo) | 材质定义 | 切换材质时变 | 每材质 |
| shininess | 材质定义 | 切换材质时变 | 每材质 |
| 相机位置 | 每帧计算 | 相机动了就变 | 每帧 |
| 环境光强度 | 场景设置 | 切换场景时变 | 全局不变 |

这些数据**不是在同一个时间尺度上变化的**。如果把它们全塞进同一个通道，必然有严重浪费：

### 场景 A：全塞进顶点属性（每个顶点存一份）

```
每个顶点 = [位置 | 法线 | MVP矩阵(64字节) | 光源位置(12字节) | 光源颜色(12字节) | 
            albedo(12字节) | shininess(4字节) | 相机位置(12字节) | 环境光(4字节)]
```

问题显而易见：一个 10 万顶点的模型，MVP 矩阵被重复存储 10 万份——64 字节 × 10 万 = 6.4 MB 白费。更严重的是，**如果光源移动了一点点，你必须更新 10 万个顶点的数据**——这意味着每帧要把整个顶点缓冲重新上传一遍。

### 场景 B：全塞进全局常量（每次绘制前设置）

```
每个物体：
  1. 设置"全局常量" = {MVP, 光源位置, albedo, shininess, ...}
  2. 绑定顶点缓冲（位置 + 法线）
  3. 发绘制命令
```

问题：10 个物体要画，每个物体的 MVP 和 albedo 不同——你得在画每个物体之前重新设置所有常量。**10 个物体 = 10 次全量常量切换。** 如果 1000 个物体，CPU 每帧光是"往 GPU 写常量"就能把一个核心吃满。

### 真正的问题不是"选哪个通道"，而是"不同频率的数据应该走不同的通道"

GPU 硬件提供了**好几种不同速度、不同粒度、不同容量的数据通道**，它们的设计目标就是让你把不同频率的数据分开：

- 有些通道"一个 GPU 线程一个值"（每顶点，同时被几千个线程并行读）
- 有些通道"整个绘制命令一个值"（所有线程看到同一份，非常适合光源位置这种）
- 有些通道"整个 BATCH 一个值"（多个绘制命令之间不用重新设置）

理解这些通道的本质区别，就是理解了 GPU 数据分发的硬件哲学。

## 问题 1：如果我们按"更新频率"给数据分层，应该怎么分？

抛开所有 API 名字，从"这份数据在什么时候会变"的角度，只有五种更新频率：

```
频率层级（从快到慢）：

层级 5：每像素不同 —— 由硬件自动插值产生，不需要 CPU 关心
层级 4：每顶点不同 —— 模型自带，加载后几乎不变
层级 3：每绘制命令不同 —— 每画一个物体切换一次
层级 2：每帧 / 每批次不同 —— 多帧之间更新一次
层级 1：全局不变 —— 程序启动后基本不动
```

这是一个从"数据变化最勤"到"数据变化最懒"的频谱。频率层级越高，数据应该离 GPU 核心越近、访问延迟越低（因为会被更频繁地使用）；频率层级越低，数据位置可以更"远"（因为读一次用很久，开销摊薄了）。

### 层级 4：每顶点不同的数据 → 走"顶点属性"通道

本质：**这份数据的值因顶点而异；如果所有顶点共用同一份，画出来的东西就错了。**

比如法线——方块的六个面法线各不相同，绝对不能全局只有一份。而位置——每个顶点位置不同，更不能共用。

这类数据的特征是：
- 数量 = 顶点数（可能上万、上十万）
- 加载后极少改变（除非做形变动画）
- GPU 必须按顶点索引随机访问

适合走的通道：**从显存中的顶点缓冲直接读取，每个 GPU 线程按自己的顶点索引取对应条目。** 这是硬件高度优化的路径——顶点着色器被并行发射几千份，每个线程自带的"我是第几个顶点"的标识自动对应正确的内存偏移。

### 层级 3：每绘制命令不同的数据 → 走"单绘制命令常量"通道

本质：**这份数据在同一个绘制命令的所有顶点/像素之间完全一样。存一份就够。**

比如 MVP 矩阵——画一个物体时，该物体的所有顶点共享同一个 MVP。光源位置——画一个场景时，所有物体的所有顶点都对着同一个光源。

这类数据的特征是：
- 每个绘制命令只有一份（几百字节以内）
- 同一绘制命令内所有 GPU 线程同时读取
- 可能每帧都变（如相机移动导致 MVP 刷新）

适合走的通道：**一份"附着在绘制命令上的常量块"**，在发出绘制命令时一次性推给 GPU，GPU 把它广播给该绘制命令触发的所有线程。这份常量不占顶点缓冲的位置，不会被每个顶点重复存储。

> **为什么这个通道有大小限制？**
>
> 这类数据在硬件上通常存在一块叫"常量缓存"（constant cache）的专用区域——它不是普通显存，而是专门设计成"一个线程读、所有线程同时拿到"的广播机制。这块区域物理上很小（几十到几百字节，因硬件而异），因为它的设计假设是"常量本来就应该少"——如果你每个绘制命令有 10 KB 的"常量"，说明你把不该是常量的数据也塞进来了。

### 层级 2：每帧 / 每批次不同的数据 → 走"批量常量"通道

本质：**这份数据比"每个绘制命令换一次"更稳定——它在多个绘制命令之间不变。把它跟层级 3 的数据混在一起，会导致不必要的重复上传。**

比如：
- 相机位置：画场景里 100 个物体，光源方向对每个物体都一样——不需要每个物体重新传一遍。
- 环境光参数：整个场景一个值，更不需要每物体重复。
- 投影矩阵：所有物体共享同一个投影，只有视图矩阵随相机变化。

这类数据的特征是：
- 多个绘制命令共享同一份
- 更新频率低于"每绘制命令"但高于"程序启动后不变"
- 适合"设置一次，后面几十个绘制命令复用"

适合走的通道：**一块常驻显存的缓冲区**，CPU 每帧更新一次，然后所有的绘制命令都引用同一块缓冲区。GPU 在绘制命令之间不需要"重新加载"——因为它一直在那里。

### 层级 1：全局不变的数据 → 跟层级 2 放一起即可

比如总环境光强度、色调映射参数等，可以在程序启动时设置一次，之后永远不碰。它们和层级 2 走同样的通道，只是生命周期更长而已——不需要单独的通道，因为"设置一次永久复用"和"每帧设置一次"在硬件视角下没有本质区别。

### 总结：数据频率分层模型

```
数据变化频率              通道选择                举例
────────────────────────────────────────────────────────────
每顶点不同       →   顶点属性通道（来自顶点缓冲）   位置、法线、UV
每绘制命令不同   →   单绘制命令常量块                MVP 矩阵、材质参数
每帧 / 每批次   →   常驻显存批量常量缓冲             光源位置、相机位置、投影矩阵
全局不变        →   同上（只是更新频率更低）         环境光强度
每像素不同       →   不需要通道——硬件自动插值        插值后的法线、UV、世界位置
```

> **"每像素不同"为什么不需要通道？**
>
> 光栅化器是固定硬件，它在生成每个像素时自动根据重心坐标插值顶点着色器的输出。CPU 不需要为"每像素不同"的数据做任何事——这也是 GPU 流水线最精巧的设计之一：CPU 只处理"每顶点"和"每绘制命令"的信息，GPU 自动把它们展开成"每像素"。

## 问题 2：单绘制命令常量有大小限制——如果数据装不下了怎么办？

前面提到，附着在绘制命令上的常量只有几十到几百字节。但有些场景确实需要在一个绘制命令里携带更多数据——比如 PBR 材质可能带 5 种纹理的采样参数、颜色因子、金属/粗糙度值，加起来可能轻松超过 128 字节。

解决方案很简单：**把"装不下的那部分"升一层，放到批量常量缓冲里。**

```
更细致的频谱：

数据变化频率        数据量        通道
───────────────────────────────────────────
每绘制命令，但很小   ≤128B     单绘制命令常量块（最快，每次绘制重新传）
每绘制命令，但较大   >128B     常驻显存缓冲 + 每次绘制切换偏移量
每帧 / 每批次       任意      常驻显存缓冲（每帧更新一次）
```

第二条的意思是：你可以把所有物体的"每物体常量"存在同一块大缓冲里——物体 A 的 MVP 在偏移 0，物体 B 的 MVP 在偏移 64，物体 C 的 MVP 在偏移 128……绘制时只要切换一个"偏移量"而不是重新传整个缓冲。

这是现代 GPU 编程中最重要的性能优化之一：**"切换"比"上传"快几个数量级。** 更新显存缓冲区需要 CPU→GPU 的数据传输（PCIe 带宽有限）；切换一个偏移量只需要改一个指针。

## 问题 3：那"每像素不同但来自插值"的数据呢？它算不算一种通道？

这是一个很好的问题。在阶段二的 Shader 笔记里，你已经见过这个机制：顶点着色器用 `out` 声明输出，片段着色器用 `in` 声明输入，中间的插值由固定硬件完成。

它的本质是：**"把逐顶点数据自动变成逐像素数据"。**

这个通道和前面四种的本质区别是：

| | 顶点属性通道 | 单命令常量 | 批量常量缓冲 | 插值通道 |
|---|---|---|---|---|
| 谁设置 | CPU：模型文件加载时上传一次 | CPU：每次绘制命令前设置 | CPU：每帧更新一次 | 固定硬件：自动完成 |
| 谁消费 | 顶点着色器 | 所有着色器阶段 | 所有着色器阶段 | 顶点着色器 → 片段着色器 |
| 变化粒度 | 每顶点不同 | 整个绘制命令共享 | 多个绘制命令共享 | 每像素不同（硬件自动生成） |

插值通道不需要 CPU 参与，但它确实在管线中传输数据。从"信息流动"的角度看，它让顶点着色器的计算结果（如世界空间法线、世界空间位置）流向片段着色器——省去了片段着色器自己去顶点缓冲里查的麻烦。

> **为什么不让片段着色器直接读顶点缓冲？**
>
> 因为片段着色器不知道"我是哪个三角形的哪个像素"——这个信息在光栅化阶段就已经丢失了。片段着色器收到的是一组已经插值好的数值和屏幕坐标，它不关心这些值是从哪个三角形的哪几个顶点插出来的。让片段着色器去顶点缓冲里回溯原始数据，需要占用额外的带宽和索引逻辑。而"插值后传过去"利用了固定硬件的速度优势——光栅化器本来就是这块的专家。

## 问题 4：把这个频率分层模型放进引擎材质系统，长什么样？

现在我们不是在讨论"一篇 Starcraft 里的 Shader 怎么写"，而是在讨论"引擎渲染管线的参数绑定架构怎么设计"。一个引擎可能要支持上百种材质，每种材质有不同的纹理组合和参数。如果每个材质的参数绑定都手工写，维护成本会失控。

按频率分层的模型直接给出了引擎参数绑定的设计框架：

```
引擎材质系统参数绑定分层：

┌─────────────────────────────────────────────────────┐
│ 层 1：全局常量（程序启动设置，永远不换）            │
│       · 环境光强度                                  │
│       · 色调映射参数                                │
│       →绑定到"批量常量缓冲插槽 0"，只绑定一次        │
├─────────────────────────────────────────────────────┤
│ 层 2：每帧常量（每帧更新一次，所有物体共享）         │
│       · 相机位置                                    │
│       · 投影矩阵                                    │
│       · 光源数组                                    │
│       · 时间                                        │
│       →绑定到"批量常量缓冲插槽 1"，每帧 map/unmap    │
├─────────────────────────────────────────────────────┤
│ 层 3：每材质常量（切换材质时更新）                  │
│       · albedo 颜色因子                             │
│       · metallic / roughness 值                     │
│       · 纹理存在标志（哪些贴图槽位有绑定）           │
│       · 如果有大量材质→存大缓冲，每次绘制只切换偏移  │
│       →绑定到"批量常量缓冲插槽 2"                    │
├─────────────────────────────────────────────────────┤
│ 层 3.5：每物体常量（画每个物体时切换）               │
│       · Model 矩阵                                  │
│       · 法线矩阵（3x3 部分）                        │
│       · 包围盒信息（用于剔除）                       │
│       →如果不大（≤128B）→附着在绘制命令上            │
│       →如果较大→和层 3 合并在同一缓冲，切换偏移量    │
├─────────────────────────────────────────────────────┤
│ 层 4：每顶点数据（模型加载时上传一次）               │
│       · 位置、法线、UV、切线                        │
│       →顶点缓冲，加载后极少改动                      │
└─────────────────────────────────────────────────────┘
```

这套分层的核心原则只有一句话：**"一层一变"——每个数据只能属于一个层级，因为它只在一个频率上变化。** 如果你发现某份数据"有时候 A 频率变、有时候 B 频率变"，说明你把两个不同语义的数据混在一起了——把它们拆成两份。

## 问题 5：除了前面说的"常量"，还有没有别的数据要传？

有。到目前为止我们讨论的都是**绘制命令发出之前，CPU 要设置什么**。但还有一类数据是**在绘制命令内部由 GPU 自己产生的**——比如粒子模拟里的粒子位置、Compute Shader 的输出缓冲。这些不走前面四种通道，它们走的是另一条路：**"GPU 可读写的通用缓冲"**。

通用缓冲和常量的本质区别：

| | 常量（前面讨论的） | 通用缓冲 |
|---|---|---|
| Shader 能写吗？ | 不能（只读） | 能（读写） |
| 容量 | 很小（KB 级） | 很大（MB 甚至 GB 级） |
| 访问速度 | 极快（常量缓存） | 较慢（全局显存） |
| 典型用途 | MVP、光源、材质参数 | 粒子位置、骨骼矩阵、遮挡查询结果 |

通用缓冲不是本阶段的主角——它是阶段十三（Compute Shader）才展开的内容。但你需要现在就知道它存在，因为你在设计引擎参数绑定时，要预留一个"插槽"给未来的通用缓冲。如果在层 2/3 里把缓冲绑定插槽全占满了，到时候就得重构。

## 收尾落地：这套分层规则在各图形后端中怎么表达

> 以下内容将前面推导的纯概念映射到具体后端的机制。这不是学习目标——只是告诉你在各后端中"这个通道叫什么名字"以及"为什么这样设计"。具体的函数调用和代码实现交给 AI 生成。

### 顶点属性通道（层 4：每顶点不同）

所有现代 API 的处理方式基本一致：创建一块 GPU 可访问的缓冲，存顶点数据；然后声明一份"顶点格式描述"（哪些字节是位置、哪些是法线、stride 是多少）；最后在创建渲染管线状态时把这份描述绑定进去。

- **OpenGL**：数据存进 VBO，格式描述由 VAO 记录（`glVertexAttribPointer`）。注意 OpenGL 把格式描述和数据绑定在绘制时才关联——Vulkan/D3D12/Metal 认为这太晚了，驱动没法提前优化。

- **Vulkan**：`VkBuffer` + `VkVertexInputBindingDescription`（数据从哪来、stride 多少）+ `VkVertexInputAttributeDescription`（哪个 location 是什么格式）。在创建 `VkPipeline` 时就锁定，运行时不能改。这是"提前验证"哲学的体现：驱动在 PSO 创建时就知道完整的顶点格式，可以预编译最优的顶点读取路径。

- **D3D12**：和 Vulkan 思路一致——`ID3D12Resource`（缓冲）+ `D3D12_INPUT_ELEMENT_DESC`（每个属性的语义、格式、slot），在 PSO 创建时锁定。

- **Metal**：`MTLBuffer` + `MTLVertexDescriptor`，同样在 `MTLRenderPipelineState` 创建时锁定。

**一句话差异**：OpenGL 允许在绘制时改格式解释（灵活但驱动不能优化），现代 API 要求管线创建时锁定（限制灵活性换取性能可预测性）。

### 单绘制命令常量（层 3.5：每物体，很小）

这个通道在各 API 中"最轻量"——不需要显存分配，不需要缓冲对象，直接塞在绘制命令里。

- **OpenGL**：经典 `uniform` 变量 + `glUniform*` 调用。直接设置，不需要创建缓冲对象。但每次绘制前都要逐个 uniform 调用，1000 个物体 = 几千次 `glUniform*` 调用。这是 OpenGL 传统 uniform 路径最大的性能问题。

- **Vulkan**：Push Constants。每个 `vkCmdPushConstants` 把一小块数据（最少保证 128 字节，通常 128~256 字节）直接写进命令缓冲——不经过描述符、不分配显存缓冲。这是 Vulkan 里最快的数据通道，因为数据跟着命令缓冲走，GPU 执行到这里时直接可用。

- **D3D12**：Root Constants（32 位常量直接嵌在 Root Signature 里，每个占 1 个 DWORD）+ Root CBV（64 位 GPU 虚拟地址，每个占 2 个 DWORD，指向一块常驻缓冲）。Root Signature 总共 64 DWORD 预算——决定了你能用 root constants 传多少数据。D3D12 的设计很诚实：**每个通道的物理容量都是明码标价的。**

- **Metal**：`setVertexBytes:length:atIndex:` / `setFragmentBytes:length:atIndex:`（≤4KB 数据直接内联在命令编码器里）。Metal 和 Vulkan 的 Push Constants 思路一致——小块数据就地塞进命令流，零分配。大于 4KB 自动回退到显存缓冲。

**一句话差异**：OpenGL 把"小常量"和"大缓冲常量"混在一个 uniform 接口里（灵活但慢）；现代 API 把小常量（Push Constants / Root Constants / setVertexBytes）和大缓冲常量（Descriptor Set / Root CBV / MTLBuffer）拆成两条物理上完全不同的路径——因为它们本质上是两种数据。

### 批量常量缓冲（层 2/3：每帧 / 每材质 / 每物体但数据 > 128B）

这个通道承载的是"多个绘制命令共享、不需要每绘制命令重新传"的数据——也就是引擎参数绑定里层 2 和层 3 的核心通道。

- **OpenGL**：Uniform Buffer Object (UBO)。`glBindBuffer(GL_UNIFORM_BUFFER, ...)` 绑定一块缓冲到某个 binding point，Shader 里通过 `layout(std140) uniform` 读取。相比传统 uniform，UBO 的好处是：一次 `glBufferSubData` 更新整帧数据，之后所有物体直接引用，不需要每物体重新设置。

- **Vulkan**：Descriptor Set + `VkBuffer`。这是 Vulkan 设计哲学最集中的体现——你按频率创建多组 Descriptor Set（Set 0 = 每帧数据如相机和光源；Set 1 = 每材质数据如纹理和参数；Set 2 = 每物体数据如 Model 矩阵）。内层循环只切换 Set 2（最便宜），Set 0 和 Set 1 保持不动。Vulkan 为什么要这样拆？因为它认为"描述数据变化频率"是 CPU 端最重要的性能决策——拆得越细，驱动越能规划缓存策略。

- **D3D12**：Constant Buffer View (CBV) 放在 Descriptor Heap 中。和 Vulkan 同思路但实现不同——D3D12 的 Root Signature 直接声明"我的管线有哪些常量缓冲、每个缓冲在哪"，而不是 Vulkan 那样通过 Descriptor Set 间接绑定。D3D12 认为"管线状态"和"资源绑定"的耦合度应该由开发者决定，Root Signature 就是这个决策的载体。

- **Metal**：`MTLBuffer` 绑定到 `setVertexBuffer:offset:atIndex:` 或 `setFragmentBuffer:offset:atIndex:`。Metal 的做法和 Vulkan/D3D12 在哲学上一致（按频率分层绑定），但 API 表面更简洁——没有 Descriptor Set 和 Root Signature 这些独立的概念层，而是直接在 Command Encoder 上设 buffer 和 offset。

**一句话差异**：OpenGL 把 uniform、UBO 混在一个概念空间里；Vulkan 把"数据按什么频率变"提升为一级设计决策（Descriptor Set 频率分层）；D3D12 让你自己设计 Root Signature 表达管线要什么；Metal 在保持频率分层的同时提供了最简单的 API 表面。

### 插值通道（顶点输出 → 片段输入）

所有 API 完全不做差异化设计——因为这是固定硬件，硬件怎么干、API 就怎么暴露：

- **GLSL (OpenGL/Vulkan)**：顶点着色器 `out` → 光栅化插值 → 片段着色器 `in`
- **HLSL (D3D12)**：顶点着色器 `out` 带语义（如 `TEXCOORD0`）→ 光栅化插值 → 像素着色器 `in` 同语义
- **MSL (Metal)**：`[[stage_in]]` 接收插值结果，顶点输出用 `[[user(n)]]` 标记

没有任何 API 在这里做"设计创新"——因为光栅化插值是固定的物理硬件，上层只是在描述它。

## 问题 6：为什么现代 API 要把单绘制命令常量和批量常量拆成两个机制？

这是一个读者应该问但很少被回答的问题。说穿了很简单：**它们物理上是两条不同的硬件路径。**

单绘制命令常量（Push Constants / Root Constants）在 GPU 上的物理位置是**命令处理器附近的一小块 SRAM**——容量极小（几十到几百字节），但延迟接近零（不需要经过显存总线）。GPU 命令处理器看到绘制命令时，直接把这块数据推送进所有 Shader 线程——不需要任何"读取显存"的步骤。

批量常量缓冲（UBO / Constant Buffer / Descriptor Set）走的是**显存 → L2 缓存 → 常量缓存**的路径。它比单命令常量慢，但容量大得多（KB 到 MB 级），适合存几十个光源、一整组材质参数。

如果把 4 字节的 shininess 放进批量常量缓冲，GPU 要去显存读一整条 cache line（通常 64 或 128 字节）才能取回 4 字节有用数据——带宽浪费 95%+。但如果整个绘制命令只传 4 字节 push constant，不需要显存访问，延迟为零。

**反过来**，如果你想把 1KB 的 PBR 材质参数全塞进 push constants——装不下。Push constants 有硬上限（Vulkan 保证 128 字节，D3D12 Root Constants 最多 64 个 DWORD = 256 字节）。超过上限的数据必须走批量缓冲。

这就是"按数据量和更新频率双层匹配"的本意：**小块高热数据走命令级常量（延迟最低），大块低频数据走显存缓冲（容量最大）。** 不是在两种 API 之间选一个，而是两种都需要——区别只是现代 API 把它们拆开让你分别控制，OpenGL 则把两者包装成同一个 uniform 概念（驱动在内部帮你选，但选得不一定好）。

## 总结：这篇笔记建立的核心认知

1. **数据通道的选择问题 = "这份数据在什么频率上变化"**
   - 每顶点 → 顶点缓冲（加载后几乎不变）
   - 每绘制命令 + 很小 → 命令级常量（最快的 GPU 广播路径）
   - 每绘制命令 + 较大 / 每帧 / 每材质 → 常驻显存常量缓冲（按偏移量切换而非重新上传）
   - 每像素 → 固定硬件插值，不需要 CPU 管

2. **"切换"比"上传"快几个数量级**
   - 切换一个缓冲偏移量 = 改一个指针
   - 上传一份数据到显存 = PCIe 总线传输
   - 引擎参数绑定的核心优化方向就是"尽量减少每帧上传的数据量"

3. **现代 API 比以前更"啰嗦"不是坏事——它们是在把"设计决策"还给你**
   - OpenGL 替你在内部做频率分层（但猜得不一定对）
   - Vulkan/D3D12/Metal 要求你显式声明频率分层（因为只有你知道数据的使用模式）
   - "啰嗦" = 控制权。你的引擎需要这种控制权。

4. **这套模型直接决定引擎材质系统的参数绑定架构**
   - 层 1 全局常量 → 程序启动绑定，不动
   - 层 2 每帧常量 → 每帧 map/unmap 一次
   - 层 3 每材质常量 → 存大缓冲 + 按偏移切换
   - 层 3.5 每物体常量 → 命令级常量（数据小）或层 3 缓冲 + 偏移切换（数据大）
   - 每层一个"绑定插槽"，不交叉、不混用。

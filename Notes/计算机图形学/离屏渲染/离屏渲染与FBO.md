# 离屏渲染与 FBO

## 开场：OIT 摸到了门把手，这门到底怎么开？

5.3 结尾抛出一句话：深度剥离要存每一层的剥离结果，加权平均要存累积图——两种方案，无一例外都要"把中间结果存下来再读"，这是幕一和幕二的分水岭，也是本阶段的总开关。

但 5.3 只是摸到了门把手：我们用了这个能力，却没拆开它。当时你大概默认"存下来"就是"写进一张图"——可只要细想一步，问题就来了：**写进哪张图？为什么不能写进屏幕本身？** 一个模糊效果就足以把这层窗户纸捅破。

## 问题 1：算好的画面去哪儿了？——为什么"就地加工"做不到

想要模糊，每个新像素必须读它周围一圈邻居的颜色，算个加权平均。把"模糊"想象成一段流水线：

```
第一遍：场景逐像素着色 → 结果写到哪？
第二遍（要做模糊）：读第一遍的成果，算加权平均 → 结果写到哪？
```

直觉答案是：第一遍写进屏幕，第二遍从屏幕读。但这条直觉毁在管线的两个事实上。

**事实一：给屏幕看的那块画面"只写不读"。** 它由窗口系统管理，GPU 画完就送去显示器、下一帧整体重画。它不是一份可以反复读、慢慢加工的数据，而是一个"递出去就收不回"的结果。

**事实二：就算读得到，也读不到邻居的"正确值"。** 光栅化是并行的——上万个像素同时着色、谁也不等谁（[[Notes/计算机图形学/GPU编程基础/GPU的并行执行模型|GPU 的并行执行模型]]里见过这种"同时跑"的实况）。如果你的着色程序说"读一下右边的邻居"，右边的邻居此刻可能还没算完。让仍在被写入的画面被并发读取，等于让住户边装修边入住——谁搬进去都可能踩到刚涂的漆。

> 所以问题不是"算法难"或"缺技巧"，而是**画面的存放位置从一开始就错了**：它停在"输出终点"，而不是"可读数据"。要让像素读到别人的成果，画面必须换个地方放。

## 问题 2：把画面换个地方放——先画到一张"能读的图"上

阶段四我们建立过一个概念：一张图片查询表——显存里一块 2D 数据，任何着色程序都能按坐标采样它。当时它是**输入**：图片 → 查表 → 得颜色。

现在把它倒过来用：**让光栅化往这张表里写**。场景照常逐像素着色，但输出目标从"交给屏幕"改成"写入这张表"。写完之后，这张表就是一块普通数据——下一遍着色程序可以像读图片一样读它。输入和输出，从此打通。

```
改进后的两遍流水线：

第一遍：场景逐像素着色 → 写入"可读画布"C（一块 2D 数据表，不上屏）
第二遍：对屏幕每个像素，从画布 C 采样周围一圈邻居的颜色
        → 加权平均 → 写入最终屏幕画面
```

第一遍结束时，画布 C 里就是"已经算好的画面"；第二遍的模糊程序对每个像素读 C 的邻居，谁也读得到谁——因为第一遍已经全部写完，不再有"边写边读"的竞争。

> 这个"先画到中间画布、再拿它当输入"的骨架，就是幕二所有技术的共同形状，它叫**多 Pass**：一个 Pass 负责画，下一个 Pass 负责读。默认画面只有一块，这样的画布你想要多少张都可以。

这里有个值得记住的转变：**同样是这张表，从"图片当输入"到"画面当输出"，变的只是"谁往里面写、写完后谁能读"。** 表的本质没变——它始终是一块可寻址的 2D 显存数据。

**先打消一个会冒出来的疑问：画布和屏幕，是不是完全不同的两种东西？** 不是。屏幕本身就是一块 2D 显存，只不过交给窗口系统管理、画完就送去显示器；"画布"是你在显存里自己开辟的另一块 2D 数据，用法一模一样——都是逐像素写、按坐标寻址。两者的真正差别只有一个：**屏幕的像素结构是固定的，画布的像素结构可以由你自己挑。**

每个像素存几组数据、每组几个通道、每通道占几位——这一整套参数统称**像素格式**。屏幕没得选，永远就是"最终要展示给人的颜色"；画布由你定：可以是颜色、可以是深度、甚至可以是一次画四张颜色图。**画布究竟存什么、存成什么格式，取决于一个大问题——这份数据之后要被谁读。** 这句"格式由消费者决定"是本章的眼睛，后面所有判断都从它长出来。

## 问题 3：一张画布够吗？——画布组绑定的不是"一个 Pass"，而是一次完整绘制

画布 C 只想着颜色，但场景渲染从来不只是颜色。回想[[Notes/计算机图形学/软光栅化与3D数学/3D光栅化与深度缓冲|阶段一的深度缓冲]]：物体互相比深度、远的被近的盖住，靠的是每像素一个"当前最近深度"的存储。屏幕能正确遮挡，是因为那块最终画面**附带**了一块深度存储。

现在把场景画到画布 C，遮挡逻辑不能丢——可画布 C 如果只管颜色，它就不知道自己谁在前谁在后。**深度存储必须跟着场景一起画到画布上。**

所以"画布"不是一个东西，而是一组挂载的层：

```
画布组 C
├── 颜色层：每个像素最终算出的颜色     → 被"下一个 Pass"读来做模糊、合成
└── 深度层：每个像素当前的最近深度     → 画布内部做遮挡测试时读
```

挂在画布上的每一层内容，起个名，叫**附件**：颜色附件存颜色，深度附件存深度。一棵画布 = 一个颜色附件 + 一个深度附件（以后还会有别的附件，先记住这两个）。

**这里最容易误解的，是"画布组"和"Pass"到底什么关系——一定要厘清。** 一个画布组**不是**一个 Pass，它绑定的是一**次完整绘制**；而一次完整绘制内部往往包含多个 Pass，这些 Pass 共享同一组附件、往同一组附件上反复写。

```
一次完整绘制（内部 2 个 Pass，共享同一组附件）：
  Pass A：先把不透明物体画进去 → 写颜色层 + 写深度层
  Pass B：再画透明物体           → 继续往颜色层、深度层写（深度测试更严）
  → 结束后，画布组里留存的，是这一次绘制最终沉淀的数据
```

深度的存在也正好印证了这一点：深度不是"哪个 Pass 自己的产物"，而是**这次完整绘制过程中持续存在、每个像素都要用的伴随状态**。它脱离"这次场景绘制"这个整体就无法独立存活——所以它必须跟颜色绑定成一组，而不是跟着某个具体的 Pass 走。这就是为什么抽象成"画布组"而非"每个 Pass 各自组织"：分开组织，Pass B 就看不到 Pass A 留下的深度，整次绘制就断了。

（现实中确实会出现多块画布同时存在——但那时的语义是"上一块是已画完、正被当输入读的旧画布，下一块是正在被写的新画布"，而不是"一个 Pass 一块画布"。）

两个附件的消费者完全不同：

- **颜色附件**：被后面的 Pass 当查询表采样——模糊要读它，合成要读它。
- **深度附件**：被"本画布绘制过程中的遮挡测试"消费——测试是固定硬件，它读深度附件判断当前片段该不该画，读完直接判断，通常不需要把内容再交给谁。

### 追问：深度层该用什么材料做？——"能读回来吗"由消费者决定

既然颜色和深度用途不同，该用什么格式来装？这条决策正好落在问题 2 那句"格式由消费者决定"上。颜色附件必须能被采样，这是它存在的使命，所以它用**可采样的图片格式**（RGBA8 之类，每像素四个通道、每通道 8 位）。深度附件呢？按上面的分工，遮挡测试消费完它之后，就没什么人需要碰它了——那它可以有更省的活法：

- **做法 A：用一张普通图片当深度附件**（颜色层那种可采样格式）。代价：占用与图片相当的存储与带宽，且任何着色程序都能读它。
- **做法 B：用一块专用的深度空间**——只干一件事：写深度、做测试，画完就完。它默认不能被着色程序采样，但更省。

选哪个，只有一个判据：**今后有没有效果需要"读"深度？** 你看，这里完全没有"混乱"的余地——每一份附件存成什么，都被"这份数据之后要被谁读"这一条要求死死钉住：要被采样 → 用图片（可采样格式）；只做内部测试 → 用专用空间。格式的种类虽然多，但选择路径只有这一条，不是拍脑袋。

- 暂时没有 → 做法 B，省。
- 迟早有——景深模糊要按距离虚化、雾要看距离、阴影里要比较谁更远——深度就必须换成可读的图片形式。

> 这是本章第一个重要的工程判断，先记住结论：**深度层默认用专用空间，等到"读深度"的需求真出现时，再把它换成图片。** 不要一开始就无脑全用图片——那是拿带宽换一个暂时用不上的能力。

> 一句话：画布组装了两样东西——**颜色是给别人看的，深度是给自己用的**；也因此颜色用可采样图片、深度默认用专用空间。而"画布组绑定一次完整绘制"这件事，自然引出一个更大的问题：一帧里，到底会有多少块这样的画布组？

## 问题 4：一帧里到底有几个完整绘制？画布组是怎么流转的？——一张"一帧透视图"

这是本章真正想让你建立的一双眼睛。把镜头从"单张画布"拉远到"一整帧"，你会看见：

```
一帧 = 一串完整绘制流程，每个流程画到自己的画布组上：

流程甲（画主场景）         流程乙（加工）           流程丙（拼成最终画面）
  画布组1                    画布组2                   画布组3
  ├─ 写：颜色               ├─ 读：画布组1的颜色       ├─ 读：画布组1、画布组2
  ├─ 写：深度               └─ 写：颜色                └─ 写：颜色
   ↓ 画完，定格为可读数据      ↓ 画完，定格为可读数据      ↓ 画完，交给屏幕
```

**一帧，不是"一次完整绘制"，而是一长串完整绘制。** 默认画面只是最后一块画布组"见光"的结果——前面还有好几块画布组，把场景一步步加工过去。你想要的模糊是一个流程；但真实一帧里，这样的流程常常一串接一串。

**画布组之间的流转规则，就是问题 2 那句话的放大：上一个流程画完，它的画布组就定格成"可读数据"；下一个流程声明"我读它、我写到我的新画布组"——读和写在时间上错开，所以永远没有"边写边读"的竞争。**

这里有个容易再次误解的点，顺手澄清：多个 Pass 是**分工互补**的，不是重复画整个场景。回想问题 3 的例子——Pass A 画不透明物体、Pass B 画透明物体，B 不会把 A 画过的再画一遍。它们各自处理场景的一小部分，拼起来才是完整画面。**"一个完整绘制里套多个 Pass"不等于"整个场景被重画好几遍"。**

那什么时候才真会"重复绘制"整个场景？那通常是极少数、且有别的动机——比如为了让光照的遮挡判断正确，需要从"光的视角"把场景额外画一遍深度；或者要从"水面、镜子的视角"再看一遍正常视角看不到的东西。这类重复绘制是少数派，而且它们往往有省招：只画深度、不画颜色、不上材质，成本被压得比普通绘制低得多。这些具体技术后面阶段会逐个展开，现在你只需要记住一条结构事实：**一帧是分工互补的一串流程，而不是反复重涂一整张画。**

## 问题 5：画这么多，性能会爆炸吗？——代价的真相

顺着上面想，一个胆小的直觉自然跳出来：一帧串这么多流程，GPU 岂不是被榨干？——这个疑问值得正面回答，因为它决定了你后半段所有选型的思维底子。

**代价模型的第一句话：多 Pass 大多不"重复几何"，所以常常比你以为的便宜。** 画一个三角形场景，最贵的是"光栅化几何"——把三角形扫成像素、逐像素着色。而问题 3 里那种分工互补的 Pass，各自只画少量物体；真正会"把整个场景再扫描一遍"的，往往不是靠重新光栅化三角形，而是靠**全屏扫上一张成品图**。

**于是代价被分成两档，量级天差地别：**

- **几何级代价**：重新走一遍"顶点 → 光栅化 → 逐像素"，贵在三角形太多、每个三角形都要重新算。让整个场景从不同视角各画一遍，走的是这一档。
- **像素级代价**：只是把上一张画布当图片，对每个像素快速采样计算。不碰三角形，只在二维平面上"再刷一遍"，便宜得多。模糊、合成、画面加工，大多走这一档。

> 一句话直觉：**几何是贵的一档，像素是便宜的一档；多 Pass 世界里，很多"看起来画了很多遍"的操作其实是在便宜的那一档里刷像素，而不是在贵的那一档里重扫三角。**

**那真正的开销从哪来、怎么控？** 三条直觉就给够，够你撑到后面的定量分析：

1. **只在需要时多画**：阴影那种"从光源视角再画一遍"确实贵，但通常灯光少、且只画深度不画颜色，成本被压住。
2. **能把"重画"从几何级搬到像素级就搬**：画面加工这类操作，用"扫上一张成品图"代替"重新光栅化场景"，便宜得多。
3. **切换画布要抱团**：一帧里多次在画布组之间切换本身有成本（下一节展开），所以同一块画布上用到的绘制一次画完再切走。

> **边界诚实**：这里说的是直觉量级，不承诺具体数字。量化"这帧到底贵在哪一档、能压到多少"是幕三（阶段十四）与 6.2 的正式主题；本笔记先把"几何级 / 像素级"这把尺子给你，它会让后面的性能分析有锚点。

## 问题 6：画布组准备好了，怎么让它们派上用场？——切换"当前目标"

画布组造好了，但 GPU 并不知道今天要画到它上面——绘制命令的默认输出目标还是"屏幕画面"。需要一个动作：**把"当前输出目标"从屏幕切换到这组画布**。

```
renderScene(target = 屏幕画面)                      // 之前：直接给屏幕
renderScene(target = 画布组 C)                      // 现在：先画到中间画布
加工(输入 = 画布组 C 的颜色层, 输出 = 屏幕画面)      // 再拿它当输入
```

画完切回屏幕画面，继续画 UI 之类的最终内容。

这个"切换"不是免费的：GPU 会按"当前目标"组织整批绘制任务，一切换，批被拆断——之前的尾款要结清，下一批重新开场。在移动端芯片上尤其明显：它把画面暂存在芯片内的高速小内存里，一切换目标，整片内容就得倒腾回大显存。所以工程上有一条不成文的规矩：**~={red}别在一帧里频繁来回切换画布；同一块画布上用到的绘制一次画完，再切走=~。** 这跟问题 5 说的"几何级 vs 像素级"是一体两面——切换和重画一样，都有成本，懂得抱团就能省。（移动端厂商的官方优化指南里也写着同样的建议，连"不要在一个帧里对同一块画布反复进出"这种细节都点名了。）

## 问题 7：这组画布组装对了吗？——画之前的体检

画布组是你拼起来的：颜色层是一张 1920×1080 的图，深度层是另一块 1280×720 的空间，格式自己定义、尺寸自己填。拼错了会怎样？最轻的是画面全黑，最重的是驱动直接拒绝执行——而这多半发生在你调试了两小时之后。

错误五花八门：深度层和颜色层尺寸对不上（遮挡测试在每像素上对不齐）、颜色层用的格式驱动不支持、只挂了深度忘了挂颜色（画了也看不见）。所以画布组被使用前，必须有一道**体检**：检查各附件尺寸是否一致、格式是否兼容、是否至少有一个颜色附件——通过才允许开始画，不通过就明确报出是哪一项不合格。

```
体检(画布组 C):
  每个附件的尺寸 == 画布预定尺寸?
  每个附件的格式 与画布声明兼容?
  至少有一个颜色附件?
  全部通过 → 允许绘制；否则 → 给出不合格项
```

这道体检叫**完整性检查**。它不是每帧都跑——画布组结构稳定时，组装完、第一次使用前跑一次就够了。它的意义是把"哪里拼错了"从玄学变回明示：与其画出来黑屏让你猜，不如第一次就告诉你哪一层不对。

## 落地表达：这个方案在各图形后端里叫什么

推导到这里，方案已经完整：**把输出目标从屏幕换成一组"颜色层 + 深度层"的可读画布，画完当数据读回来；一帧里串一串这样的画布组，上一个画组的成果给下一个画组当输入；切换有成本所以要抱团；组装要体检。** 各后端对这个"离屏渲染目标"的表达：

- **OpenGL**：一个叫**帧缓冲对象（Framebuffer Object，FBO）**的对象，把"画到哪 + 挂哪些附件"打包在一起；颜色/深度附件各可选"可采样的图片"或"专用空间"两种形式。默认那块屏幕画面本来叫默认帧缓冲——现在你有了自己的。它把概念压缩成单一对象，最适合学习。
- **Vulkan**：拆成"渲染过程（描述这个 Pass 如何对待每个附件：开始清不清、结束存不存）"和"帧缓冲（把具体某张图绑到哪个附件位）"两部分，并显式声明附件间的读写依赖——它要在录制命令时就掌握完整读写关系，好提前安排片上存储与同步。
- **D3D12**：把"哪张图当颜色目标、哪张当深度目标"以视图形式绑到输出阶段，用显式资源状态转换声明"这张图从可写变为可读"——与其全程显式的资源模型一致。
- **Metal**：用一个渲染过程描述对象一次声明"画到哪、每个附件怎么处理"，命令编码器照章执行。

**为什么现代 API 要把这件事拆开**：OpenGL 打包成对象、细节让驱动临场兜底；Vulkan/D3D12/Metal 要求你在开始画之前把"这组画布怎么被使用"完整交代——因为多 Pass 世界的性能关键（片上存储、同步、屏障）全藏在这些声明里，它们不愿让驱动猜。

**个人项目推荐**：学习阶段用 OpenGL 的打包对象，概念最少；读懂后把它心智地图为"现代 API 的'渲染过程 + 图像绑定'"——拆出来的每一块，都对应本笔记推导里的一个决策：怎么对待附件（渲染过程）、用哪张具体图（帧缓冲）、读写按什么顺序（依赖）。理解"为什么拆"，比背函数名重要得多。

## 明确推荐：一张决策清单

| 决策点 | 推荐 | 理由 |
|--------|------|------|
| 场景还不是最终画面时 | 先画到可读画布，再读它加工 | 像素要读"已画好的画面"，这是唯一来源 |
| 画布和屏幕的关系 | 同一类 2D 显存，差别只在像素格式可不可自定义 | 消除"画布是全新概念"的误解 |
| 画布组和 Pass 的关系 | 画布组绑定一次完整绘制；多 Pass 共享同一组附件 | 深度是整次绘制的伴随状态，拆开就断了 |
| 看待一整帧 | 一帧 = 一串完整绘制流程、每个流程一块画布组，串联而成 | 上一个流程的成果给下一个流程当输入 |
| 多 Pass 会爆炸吗 | 大多分工互补、不重复几何；真重复几何的少数且常被压低 | 代价分"几何级（贵）/像素级（便宜）"两档 |
| 每份附件用什么格式 | 看"这份数据之后要被谁读" | 要被采样→可采样图片；只做内部测试→专用空间 |
| 颜色层用什么形式 | 可采样的图片 | 下一个 Pass 要采样它，这就是它的使命 |
| 深度层用什么形式 | 专用空间（默认）；第一次出现"要读深度"的效果时换图片 | 省带宽；判据是"有没有效果需要读深度" |
| 画布切换 | 同块画布上的绘制一次画完，别来回横跳 | 切换拆散硬件批次，移动端尤其贵 |
| 完整性检查 | 组装后、首次使用前跑一次 | 把拼装错误从"黑屏猜谜"变成"明示哪层不对" |

**落到引擎**：自研引擎的后处理栈正是生长在这套"画布组"上的——引擎侧把它抽象为统一维护的"场景纹理集合"（颜色、深度等画布由管线统一生成、各效果声明读取），见 [[Notes/SelfGameEngine/渲染管线与画面/后处理栈架构|后处理栈架构]]。你在这篇笔记里掌握的"一帧 = 一串画布组"，就是它最底层的那块砖。

# 纹理映射与UV坐标

## 问题 0：光照有了，模型为什么还是像塑料玩具？

阶段三结束时，你的模型长这样：受光面亮、背光面暗、有高光——体积感有了。但凑近看，每一块表面的"基础颜色"都是均匀的。一堵墙是纯粹的一种灰红色，没有砖缝；一个人脸是均匀的肉色，没有毛孔和胡茬。

现实世界的表面细节，尺度远小于三角形：一道划痕可能只有零点几毫米宽，而它所在的三角形有几厘米大。

### 最 naive 的方案：把细节画进顶点

你已经有"顶点颜色"这个机制了——每个顶点带一个颜色，光栅化插值出每个像素的颜色。把砖缝画进顶点颜色行不行？

```
naive 方案（顶点颜色）：

顶点A(红) ────── 顶点B(红)
      中间的砖缝呢？
      插值只能产生 A→B 的渐变，
      画不出"红-深灰缝-红"这种细节。

像素颜色 = 重心插值(v0.color, v1.color, v2.color)
          ↑ 细节的精细程度被顶点密度锁死
```

要在墙面上画出砖缝，就得在砖缝的位置放顶点——一堵 10m×3m 的墙，砖缝毫米级，需要千万级顶点。几何量爆炸，只为表达一张图片就能表达的东西。**这条路在工程上是死的。**

### 换个思路：不算颜色，"查"颜色

表面细节的特点：**它不遵循任何公式，但它是确定的、不变的**。砖缝在哪、锈迹长什么样——艺术家早就画好了。既然算不出来，那就**存起来，用的时候查**。

> **本质问题：每个像素需要一个独立的"基础颜色"，这个颜色无法由公式计算，必须由一张预先准备好的"查询表"提供。**

---

## 问题 1：给每个像素一个独立颜色——需要一张"2D 查询表"

思路反转后，方案的核心结构只有三样东西：

1. **一张表**：一张 2D 的颜色数组（艺术家画的表面细节图）。给它两个坐标，它返回一个颜色。
2. **一个坐标**：每个像素拿到两个数（习惯叫 u、v），表示"查表里的哪个位置"。
3. **一次查询**：像素颜色 = 表[u, v]。

这张表——连同"拿坐标去查它"这套用法——就是**纹理（texture）**。注意这个定义有两半：**数据**和**查法**。数据这一半，在你的第一个实验里就是一张 PNG 图片解码后的颜色数组——图片并没有被排除在纹理之外，它就是表的内容；"查法"这一半，才是纹理在渲染管线里的身份：给它一个 (u, v)，它返回一个值。之所以强调后一半，是因为数据的来源可以换：同样的表可以程序生成、可以装法线、装粗糙度、甚至装"上一帧算好的画面"——来源千变万化，查表机制不变。

```
查询表方案：

顶点A(uv=(0,0)) ────── 顶点B(uv=(1,0))
        光栅化插值，每个像素得到一个 uv

像素基础颜色 = 表查询(细节图, uv)
              ↑ 细节的精细程度 = 表的分辨率，
                与顶点数量完全无关
```

和 naive 方案对比，信息结构的变化是本质性的：

| | 细节从哪来 | 细节精度上限 | 代价 |
|---|---|---|---|
| 顶点颜色 | 顶点属性插值 | 顶点密度 | 顶点数爆炸 |
| 查询表 | 独立的一张表 | 表的分辨率 | 一份显存里的表数据 |

光照公式也因此升级了：阶段三里"材质颜色"是一个全局常量，现在它变成了**逐像素查表的结果**。`N·L` 决定"被照亮多少"，查表结果决定"这个点本来是什么颜色"——两者相乘，像素第一次同时有了明暗和细节。

## 问题 2：查询坐标从哪来？——UV 与插值

每个像素都要一对 (u, v)，但表查询是在逐像素阶段发生的，顶点数据才是我们能输入的东西。老办法：**坐标存在顶点上，插值到像素。**

每个顶点除了位置、法线，再多带一份 2D 坐标，习惯用字母 u、v（避免和空间坐标 x、y、z 混淆），合称 **UV 坐标**。它就是"又一种顶点属性"——GPU 不关心它的语义，和法线、颜色没有任何机制上的区别，语义由查表这个操作赋予。

```
顶点属性的布局（内存中的字节流）：
[ x y z | nx ny nz | u v ]
  位置      法线       UV ← 新增：这个顶点对应表里的哪个位置
```

光栅化时，UV 和法线一样走插值通道：三个顶点的 UV 按[[Notes/计算机图形学/软光栅化与3D数学/光栅化：从直线到三角形#重心坐标：三角形内部的"位置坐标"|重心坐标]]加权，得到每个像素的 UV。

### 一个必须记住的坑：透视校正

UV 是 3D 世界里的属性，不是屏幕属性。如果你在屏幕空间直接线性插值 UV，斜着看的地面纹理会"弯"——近处的格子被压扁、本该笔直的纹理边界发生折弯。原因在[[Notes/计算机图形学/软光栅化与3D数学/3D光栅化与深度缓冲#区别 2：透视校正插值|透视校正插值]]里讲过：屏幕上相等的像素步长，对应 3D 里不等的距离；所有逐顶点属性（颜色、法线、UV）在屏幕空间都必须先除以深度再插值。GPU 硬件默认对顶点输出做透视校正插值，但在你自己的软渲染器里，这一步要自己写——漏掉它的典型症状就是"正对相机没问题，一转视角纹理就扭"。

### 为什么 UV 用 0~1 而不是像素坐标

UV 的取值范围约定为 [0, 1]：(0, 0) 是表的一个角，(1, 1) 是对角，与表的实际分辨率无关。这是一个刻意的设计：**同一份 UV，换一张更高清的表依然有效**。美术把 512×512 的表升级成 4096×4096，模型文件一个字节都不用改——坐标描述的是"表里的相对位置"，不是"第几个格子"。

## 问题 3：谁规定"脸上哪个位置查表的哪个位置"？——UV 展开

顶点上的 UV 值是哪来的？不是算出来的，是**美术在 DCC 工具（Blender/Maya 等建模软件）里手工安排的**。这个安排过程叫 **UV 展开（UV unwrapping）**：把 3D 表面"剪开、摊平"到 2D 平面上。

```
        3D 表面                     2D 平面（表的坐标系）
       ╭──────╮                  ┌──────────────┐
      ╱ 脸部   ╲    剪开、摊平    │  脸  │耳朵│后颈 │
     │  的网格  │   ─────────→  │──────────────│
      ╲       ╱                 │   手臂 │ 躯干  │
       ╰──────╯                  └──────────────┘
```

摊开一张纸没问题，但摊开一颗球必然要剪开——就像地球仪没法不撕破地压成地图。这件事带来三个工程现实，每一个都直接影响最终像素质量：

### 接缝（seam）

剪开的边界两侧，在 3D 上是相邻的点，在表里却隔得很远。~={red}如果表的颜色在接缝两边不连续，渲染出来就是一条肉眼可见的"裂缝"。=~美术的对策有两条：把接缝藏在视线少到的地方（发际线、衣服侧缝、掌心），以及画表的时候让接缝两侧的颜色尽量衔接。**接缝无法消灭，只能藏。**

### 拉伸（distortion）

摊平必然有区域被拉大。被拉大的区域，同样数量的表格子覆盖了更大的表面积——那块区域的细节就被"摊薄"了，呈现为局部模糊。

"必然"两个字值得停下来想明白：为什么摊平就一定会拉伸？

**直觉实验：橘子皮。** 剥下一整块橘子皮，试着把它按平在桌面上。中心按住了，边缘就翘起来；强行把边缘压下去，皮就裂开——或者如果你不让它裂，那一定是某个方向的纤维被扯长了。**"裂开"对应上一节的接缝，"扯长"对应这里的拉伸。**橘子皮不想平，因为它生来就是弯的。

这是图形学里少有的几条"想靠算法变通也无解"的约束之一。原因是几何上的铁律：**"弯的"表面和"平的"表面，本质上是两种不同的几何，硬要摊平必然扭曲。** 一张纸卷成圆筒还能再摊平回长方形（因为卷起来只是摆放方式变了，纸本身没被扯长）；但一颗球的表面怎么都摊不平——它哪处都是弯的，一压就裂或扯。 

> 一句话记住结论即可，不用懂那套数学：**有"拉伸"是逃不掉的物理事实，你只能决定它出现在哪、以什么形式出现。**

展开算法能做的，只有两件事：

1. **让拉伸尽量均匀**，别让某一块被压得特别扁、另一块拉得特别大——把误差平摊开，整体观感就正常；
2. **用"多剪几刀"来换更轻的拉伸**。把球面剪成很多小片再摊平，每片要摊平的"弯"就少了，拉伸更轻微——但代价是接缝更多。这就是 UV 展开的经典权衡：**接缝越多 → 每块拉伸越小但裂缝越多；接缝越少 → 表面越连贯但拉伸越明显。**求接缝和求拉伸，只能两害取其轻。

（现实里展开工具还提供"保角优先"或"保面积优先"这类的偏好——一个保角度不变、一个保面积不变，两者不可兼得——但那是美术在工具里调的档位，你只需知道"拉伸不可避免、可以分档权衡"即可，不必深入。）

### 纹素密度（texel density）

表里一个格子叫**纹素（texel）**。纹素密度 = 单位表面积分到多少纹素，它直接决定这块表面的细节上限。主角的脸和远景的石头不该用同样的密度——脸占屏幕几百像素，值得高密度；石头占几个像素，给高密度纯属浪费表空间。工程上要求同一个场景里"重要程度相近的表面，纹素密度相近"，否则站在一起的两个物体一个清晰一个糊，违和感立刻出现。

> **关键认知：UV 展开是资产创作问题，不是运行时问题。** 模型文件（比如 OBJ 的 `vt` 行）把美术安排好的 UV 带给你，运行时你唯一做的事就是查表。渲染管线不信任、也不修改这个映射——它正确与否，在建模软件里就已经注定了。

## 问题 4：坐标落在格子之间，怎么办？——放大的模糊与缩小的闪烁

表是离散的格子阵，UV 是连续的浮点坐标。查表时 UV 几乎从不会正好落在格子中心。这引出两个方向相反的像素问题：

### 放大：一个纹素盖住好几个像素

镜头贴近表面时，一个纹素要负责一片像素。两种取法：

- **取最近的一格**：一片相邻像素查到同一个颜色 → 屏幕上出现"马赛克方块"。
- **取周围 4 格按距离加权**：颜色在格子间平滑过渡 → 糊，但至少连续。

放大场景的结论：**只能二选一——要么方块，要么糊**。细节的上限就是表的分辨率，这是硬约束。

### 缩小：一个像素盖住几十个纹素

镜头拉远，一个像素的"脚印"覆盖了表里几十个格子，但你只能查一个点。这正是[[Notes/计算机图形学/软光栅化与3D数学/3D光栅化与深度缓冲#走样的本质：采样率不足|走样]]讲过的采样率不足——你在对高频信号做低频采样。

后果不只是"糊一点"，而是**闪烁**：物体或相机微动一帧，采样点落到了完全不同的纹素上，远处表面的颜色在帧与帧之间随机跳变，看上去像一片噪点在抖动。棋盘格地面延伸到远处时，还会出现一圈圈干涉条纹（摩尔纹）。

1.6 里对抗走样的原则是**先滤波，再采样**：一个像素覆盖几十个纹素时，它该得到的是这几十个纹素的平均颜色，而不是随机一个。但逐像素实时算"几十个格子的平均"，每个像素几十次读表——太贵了。

## 问题 5：Mipmap——把"滤波"提前算好（概念预告）

缩小场景的洞察是：**"几十个纹素的平均"这个结果与相机无关，可以提前算好存起来。**

把原图逐级缩小一半，每一级都是上一级 2×2 格子的平均——得到一座"分辨率金字塔"：

```
LOD0:  512×512   原图，一个像素盖不到一个纹素时用它
LOD1:  256×256   每个格子 = 原图 2×2 的平均
LOD2:  128×128   每个格子 = 原图 4×4 的平均
  ...
LOD9:  1×1       整张图的平均颜色
```

渲染时先估算"这个像素的脚印大约盖几个纹素"，选最接近的那一层去查。像素盖 4 个纹素就查 LOD2，盖 16 个就查 LOD4——**一次查询就拿到了近似正确的平均值**，采样率不足从根上消失了，闪烁随之消失。

这座金字塔叫 **Mipmap**。它的代价出奇地小：各层加起来只比原图多约 1/3 显存（等比数列 1 + 1/4 + 1/16 + … ≈ 4/3），还附带一个性能红利——远处像素查的是小图，小图更贴合缓存，读得更快。

> 这里只建立概念：**"远处闪烁"是采样问题，Mipmap 用预过滤的金字塔解决它**。层级之间怎么平滑过渡（两层之间突变会形成一圈可见的界线）、斜着看的表面为什么需要各向异性——这些是 [[Notes/计算机图形学/纹理系统/Mipmap与纹理过滤|Mipmap 与纹理过滤]]的内容，现在不用展开。

## 问题 6：在数据通道分层里，纹理站在哪一层？

回到[[Notes/计算机图形学/光照与数据流/数据通道与更新频率#总结：数据频率分层模型|数据频率分层模型]]，给纹理找位置：

| 通道 | 更新频率 | 数据量级 | 纹理符合吗 |
|---|---|---|---|
| 顶点属性 | 每顶点不同 | 每顶点几 float | ❌ 表是整体一份，不逐顶点 |
| 常量 | 每物体/每帧 | 几十到几百字节 | ❌ 一张 1024² 的表是 4MB，远超常量容量 |
| 插值通道 | 每像素（来自顶点） | — | ❌ 这是 UV 走的通道，不是表本身 |

纹理是一类**新数据**：一份数据量很大（MB 级）、所有像素共享、每个像素随机访问其中一个点、通常很多帧甚至整个游戏过程都不变。它住不进顶点缓冲，也住不进常量缓冲——它需要**一种独立的"只读 2D 查询表"存储**，随数据一起的还要有一份"查表方式"的说明（落在格子之间怎么取值、坐标越界怎么办）。

注意这里的一个结构洞察：**"表里的数据"和"查表的方式"是两个独立的决策**。同一张表，近处想平滑取、远处想走金字塔；同一套查法，可以服务任意多张表。这个"数据与查法可分"的事实，等下看各后端的落地方式时会发现：有的后端把两者打包，有的刻意拆开——分歧的根源就在这。

## 收尾落地：这些概念在各图形后端中怎么表达

> 推导到此结束——你已经知道：需要一份常驻 GPU 的"只读 2D 查询表"（数据），外加一份"查表方式"的说明（过滤、越界处理）。下面是这套方案在各后端的落地，纯文字、无代码，具体实现交给 AI 生成。

- **OpenGL**：把"表数据 + 查表方式"**打包成一个纹理对象（Texture）**。创建一次、设置好过滤参数，绘制前把它绑到一个"纹理单元"插槽上，着色器里通过对应插槽的 sampler 变量查表。金字塔层级可以一条调用自动生成。
- **Vulkan**：刻意拆成三个对象——`VkImage`（表数据本身）、`VkImageView`（把这份数据"看成什么"，2D 还是数组、看哪几层）、`VkSampler`（查表方式）。拆开的理由：它认为"存什么"和"怎么读"是独立决策，同一份数据可能要被多种方式读——比如既当查询表、又当渲染输出目标（这是幕二的事）。
- **D3D12**：数据是 Texture 资源加一个 SRV 描述符（"怎么看这份数据"），查表方式是独立的 Sampler 描述符。思路和 Vulkan 一致——描述和绑定分离，方便 CPU 端提前验证。
- **Metal**：`MTLTexture`（数据）+ `MTLSamplerState`（查法），同样是分离设计。

一句话对照：**OpenGL 打包求简单，现代 API 拆开求控制权**。你现在只需要查表，OpenGL 的打包方式概念最少；但当"一份数据多种读法"的需求出现时（后处理、阴影），拆开的价值就显现了。

## 总结：这篇笔记建立的核心认知

1. **纹理 = 一份 2D 数据 + 一套查表机制。** 数据通常就是一张图片解码后的颜色数组——图片是表的内容，不是被排除的东西；机制是"给坐标、返回颜色"。~={green}用"查询表"而不是"图片"来定义它，是因为数据的来源可以换（程序生成、法线、上一帧的画面）=~，而查表机制不变。像素拿坐标查表得到基础颜色——~={green}细节精度与顶点数量解耦，这是它存在的全部理由=~。
2. **UV 是逐顶点的查询坐标**，靠光栅化插值到每个像素（必须透视校正），用 0~1 的相对坐标换来分辨率无关。
3. **UV 展开是资产创作问题**：接缝要藏、拉伸要匀、纹素密度要匹配重要程度。运行时只是查表。
4. **查表有两个方向相反的走样**：放大时"方块 vs 糊"二选一；缩小时采样率不足导致远处闪烁。
5. **Mipmap 用预过滤金字塔解决缩小走样**：把"滤波"从运行时挪到离线，代价只有 1/3 显存。
6. **纹理在数据通道分层里是独立的一类**：大数据、共享、随机读、长期不变；"表数据"和"查表方式"是两个独立决策。

留下一个最实际的缺口：**理论全通了，但一张 PNG 文件躺在磁盘上——它怎么解码、怎么上传到 GPU、怎么变成那张能查的表？** 这就是下一篇——[[Notes/计算机图形学/纹理系统/纹理对象与加载|纹理对象与加载]]。

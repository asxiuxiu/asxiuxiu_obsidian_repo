# 多重纹理与材质

## 问题 0：一张表只给了一个颜色——但像素的外观不只有颜色

阶段四前四篇都在回答一个问题：每个像素的基础颜色从哪来。答案是"查一张 2D 颜色表"——砖墙的花纹、木箱的纹路、皮肤的底色，全是一张表搞定。到这个节点，纹理系统在单表模式下的全部机制都已就绪：表数据在显存里、查表方式四个维度（过滤/选层/层间/寻址）配好了、shader 拿着 UV 一查，像素颜色就有了。

但把这个"一张表给颜色"的模型放到真实材质面前，立刻露出两个缺口：

**缺口一：像素的外观不只有"基础颜色"这一个维度。** 阶段三的光照公式把最终颜色拆成三块：环境光（写死的低亮度）、漫反射（`N·L`）、高光（`N·H` 的幂）。漫反射和高光都依赖"这个像素看向哪个方向"——也就是法线方向。而法线来自顶点，光栅化插值到像素。一面砖墙有 100 万个像素，法线只来自几百个顶点——每个顶点一条法线，相邻顶点之间全是平滑插值。结果就是：**整面墙的法线是光滑的，灰泥缝和砖面的光照方向完全一样，没有凹凸感。**

想要灰泥缝暗一点、砖面亮一点，需要法线在**像素级**有变化——而顶点法线做不到像素级变化，正如 4.1 所说：细节的尺度远小于三角形时，顶点属性力不从心。但是，这恰恰和"基础颜色"是同构的问题——4.1 的解法是用一张表存每个像素的颜色，那**能不能也用一个表存每个像素的法线方向？**

**缺口二：~={green}一旦不止一张表了，"材质"本身变成了一个新东西。** 砖墙需要一张颜色表 + 一张法线方向表；金属可能再加一张"哪里更光滑"的表；皮肤甚至需要一张"哪里透光"的表。多张表同时参与同一个像素的计算，它们共享同一组 UV、住在不同的插槽上、被同一段逐像素计算同时查询。~={red}**"这些表是一个整体"这件事本身，需要一个名字——这个名字就是材质**=~=~。

> **本质问题：一个像素的外观由多个独立属性（颜色、法线方向、光滑度、金属度……）共同决定。每个属性都需要自己的一张表；多张表要同时挂在 GPU 上、被同一段逐像素计算、按同一组 UV 同时查询。这多张表怎么组织？每张表里的数据怎么被正确解读？这些表 + 参数 + 着色程序合在一起，形成的那个"概念对象"是什么？**

## 问题 1：两张表同时上——插槽编号是桥梁

4.2 已经建立了"一张表怎么挂在插槽上"的机制：绘制前把表挂到插槽 N，shader 里声明一个编号为 N 的"查表器"，逐像素阶段通过编号找到插槽上的表来查。这层间接引用的设计，当初的理由是"同一份 shader 服务任意多张表"——砖墙和木箱用同一段逐像素程序，区别只在挂哪张表。

现在需求升级成"同一段 shader **同时**服务多张表"——砖墙的一次逐像素计算，既要查颜色表（得到砖的红褐色），又要查法线方向表（知道这个像素的微表面朝哪个方向）。按同一套机制，无非是：**多占几个插槽。**

```
绘制前（CPU 侧）:
  插槽0 ← 挂上"砖墙颜色表"
  插槽1 ← 挂上"砖墙法线方向表"

逐像素阶段（GPU 侧）:
  查表器0 = 0（只是个编号）
  查表器1 = 1（只是个编号）

  基础颜色 = 查(插槽[0]上的表, uv)
  法线方向 = 查(插槽[1]上的表, uv)
```

机制上没有新东西——就是 4.2 的插槽模型做了个"乘以 N"。两组 UV 完全一样（所有表贴在同一个表面上，当然用同一组 UV），区别只在查出来的值**语义不同**：插槽 0 的值进"基础颜色"那一项，插槽 1 的值进"法线方向"那一项。

但这立刻引出一个硬约束：**插槽不是无限的。** 每个图形后端都有一个"最多同时挂多少张表"的上限。这个数量通常不大——16 到 32 个。为什么这么少？因为每个插槽背后是一整套"查表方式"的配套状态——过滤模式、寻址模式、金字塔参数——这些状态每个插槽独立维护，硬件上每一套都要占寄存器。16 个插槽意味着 16 套独立的查表方式参数常驻在逐像素阶段的硬件状态里，再多硬件成本就撑不住了。

这个上限在单表时代离你很远——你最多只用过一个插槽。但到了多表时代，它是第一个要面对的工程约束：**一个材质能用的表的张数，不能超过硬件插槽数。** 一个简单的漫反射材质用 1 张表，带了法线贴图就 2 张，PBR 材质（阶段九）轻松 5 张起步——5 张在 16 个插槽里当然够，但场景里如果有几十种材质，每种都要同时绑定自己的表组，就得频繁换挂插槽上的表。换挂本身有开销——这不是本模块的重点，但它是~={green}引擎渲染队列排序（5.6）的种子：按材质分组绘制，就是为了减少"换挂表"的次数=~。

## 问题 2：法线贴图——存的是方向，不是颜色

第二张表的需求说清楚了：我们需要一份"逐像素的法线方向"。但是，怎么把"方向"存进一张表里？

### naive 思路：直接存世界空间法线

最直接的方案：表里的每个纹素，存那个像素在世界空间里的法线方向——就像顶点法线一样，只是精度从"每顶点"升级到了"每纹素"。表里 (x, y, z) 三个分量各占一个通道。

这个方案在逻辑上完全正确。但有一个致命缺陷：**这张表绑定到了模型在空间中的具体朝向。** 一堵墙的砖面法线，如果存的是世界空间方向，那么墙转 90 度，所有法线方向全部作废——表里说的"朝北"此刻是"朝东"了。换一个场景、换一个朝向，就要换一张法线表。这和 UV 映射的核心设计（"同一份 UV 换一张表依然有效"）背道而驰。

### 正确的做法：存"相对于表面"的方向

解法是换一个参照系：

> **法线不存"在世界空间里朝哪"，而存"在这个表面自己的坐标系里朝哪"。**

这个坐标系以表面为基准：法线方向是"朝外"、贴着表面往右是 u 方向、贴着表面往上是 v 方向。在这个坐标系里，一张完全平坦的表面的所有点，法线方向都是"朝外"——也就是 (0, 0, 1)。凹凸信息要存的其实是 **"这个点偏离了平坦表面多少"**——往左偏、往右偏、往上偏、往下偏，分别改动了方向的两个横向分量；第三个分量始终接近 1（绝大多数表面的法线不会反过来指向内部）。

这个坐标系最重要的性质是：**它跟着表面走。** 模型旋转、缩放、变形，坐标系自动跟着转。所以同一张法线贴图能用在一片任意朝向的砖墙上——墙平放、竖立、还是弯成隧道，法线"相对于表面"的解释不变。这是法线贴图能成为通用资产的根。

（这个"跟着表面走的局部坐标系"有个正式名字，叫**切线空间（tangent space）**。名字来自它的三根轴——一根垂直于表面、两根贴着表面——你只需要把它记成"以这个点的表面为基准的局部坐标系"即可，名字不改变上面这段话的意思。）

### 为什么法线贴图是蓝色的

这就解释了一个经典现象：法线贴图看上去是**蓝紫色**的。绝大多数纹素里，法线接近"朝外"——在切线空间里就是 (0, 0, 1)。把方向编码进 RGB：(0, 0, 1) 归一化到 [0,1] 再按三通道存，结果就是纯蓝色 (0.5, 0.5, 1.0)。凹凸信息让法线轻微偏离朝外：偏一个方向让 R 通道偏离中间值，偏另一个方向让 G 通道偏离——于是蓝色基底上泛出紫红和青绿。

```
朝外法线 (0, 0, 1)      → RGB (0.5, 0.5, 1.0)    → 蓝紫色（占绝大多数）
轻微偏右 (0.3, 0, 0.95) → RGB (0.65, 0.5, 0.975) → 偏红紫
轻微偏上 (−0.2, 0.1, 0.97) → RGB (0.4, 0.55, 0.985) → 偏青绿
```

这和三通道各占 8 位的"归一化存储"是同一套约定——4.2 的格式声明在这里只是把语义从"颜色"换成了"方向"。它也继承了同样的坑（见问题 6）：压缩和金字塔对这种"存的不是颜色"的表，都要另眼相看。

## 问题 3：切线空间里的方向，怎么拿去和世界空间的光比？——TBN 变换

法线存在切线空间（表面自己的坐标系）里了。但光照计算里，光源方向和视线方向是在世界空间（或相机空间）里的。**两个不同坐标系里的方向，不能直接比较。** 你得先把查出来的法线方向，转到和光源同属一个坐标系里，再做光照点积。

一个直观的画面：法线贴图告诉你"这个点朝右上方偏了一点"，但"右上方"是世界空间里的右上方（比如是偏东、还是偏上），得靠"这个表面此刻朝哪"来换算。换算需要三样东西——下面逐个说。

### 换算需要的三件套

**第一件：表面朝哪个方向？** 就是每个顶点的法线 N。它已经从顶点带上来了，经过 3.3 讲的法线变换后，方向是世界空间里的。这是纯粹的几何：表面贴着哪个方向。

**第二件：贴图的"右"和"上"在 3D 里各朝哪？** 法线 N 只告诉你表面朝哪，没告诉你贴图怎么摊在表面上。贴图的 u 方向（水平）在 3D 里朝哪、v 方向（垂直）朝哪，得有个东西来描述——这个就叫**切线 T**（对应 u 方向）。它不纯是几何：**同一个表面，换个 UV 展开方式，T 就变了**（后面单独讲）。

**第三件：第三个方向。** 有了 N（朝外）和 T（贴图水平方向），垂直的第三根轴 B 就能由前面两个算出来——不用存，逐像素阶段当场算。

这三件套 N、T、B 合起来，就是**TBN 矩阵**——它做的事一句话：**把切线空间里查出来的法线，转成世界空间能用的方向。**

```
[世界空间法线] = TBN × [切线空间法线]
                       （贴图里查出来的）
```

有了它，法线贴图的值就转成了世界空间方向，可以光明正大地和光源方向、视线方向做点积，光照公式照旧。

### T 是特殊的那一个——它由 UV 展开决定

把三个向量放一起看，能看出谁是异类：

| 向量 | 语义 | 是不是纯几何 |
|------|------|------|
| **N** 法线 | 表面朝外 | 是（建模就带） |
| **T** 切线 | 贴图的 u 方向在 3D 里朝哪 | **不是——绑定 UV 展开** |
| **B** 副切线 | 补成第三根轴 | 逐像素现算，不存 |

N 是纯几何，建模型就知道；**T 不是**。它回答的是："当法线贴图说'朝某个方向凹凸'时，它说的"右"到底对齐到模型表面的哪条线。"——记住一件事即可：**同一个几何点，换一种 UV 展开，T 就完全不同**，所以它是"几何 + 贴图映射"的产物，要逐顶点存储（建模软件从顶点的位置差和 UV 差反解出来，导出时带上）。

一句话总结 T 的语义：**T = "贴图的 u 方向在 3D 表面局部朝向哪"，由 UV 展开决定、逐顶点存储，和法线 N 一起构成 TBN，让法线贴图里每个方向能转到世界空间参与光照。**

> 本模块只要求懂到"切线空间 = 表面的局部坐标系、TBN = 把它对齐到世界空间的变换"这一步。至于"在顶点阶段算还是在像素阶段算"的两种写法，是性能取舍不是概念差异，用到时查参考即可——TBN 的数学推导（叉积、施密特正交化）也放在参考资源里，本项目只需可用，不背公式。

## 问题 4：当表多了，"材质"这个概念就浮出水面了

两张表的需求跑通了：插槽编号隔开，同一份 shader 同时查两张表，颜色给漫反射、法线给光照方向。但如果再往上加——粗糙度贴图（哪里光滑哪里粗糙）、金属度贴图（哪里是金属哪里是电介质）、环境光遮蔽贴图（哪里天生就暗）——shader 里会多出一堆"查表器"变量。每种材质需要的表的组合不同：砖墙要颜色 + 法线，生锈铁板要颜色 + 法线 + 粗糙度 + 金属度，发光广告牌只要颜色 + 自发光强度。

于是出现了一个概念对象：**材质（Material）**。它不是某一张表、也不是某一段着色程序，而是**"一组表的组合 + 一组常量的组合 + 一段着色程序"的合体**。

```
材质 "砖墙" = {
  表组:   插槽0 ← 砖墙颜色表
          插槽1 ← 砖墙法线方向表
  常量组: 粗糙度 = 0.9（粗糙）
          金属度 = 0.0（非金属）
  着色程序: StandardLit（标准光照）
}

材质 "生锈铁板" = {
  表组:   插槽0 ← 铁锈颜色表
          插槽1 ← 铁锈法线方向表
          插槽2 ← 粗糙度变化表
          插槽3 ← 金属度变化表
  常量组: （无——这些属性全由表提供，逐像素变化）
  着色程序: StandardLit
}
```

注意"粗糙度"在两个材质里以不同形式出现：砖墙里它是一个全局常量（整面墙都粗糙），铁锈里它是一张表（有的地方锈得粗糙、有的地方还光滑）。这就是 3.2 的频率分层模型在材质定义里的应用：**同一个语义属性，更新频率可以不同**。"全局常量"适合均匀材质；"查表"适合空间变化的材质。材质系统要同时支持两种，而且允许它们无缝替换——"这个槽位要么给一张表、要么给一个常量"是引擎材质系统的基本能力。

### 表的可选性

并非每种材质都需要填满所有语义槽。没有法线贴图的材质，shader 里就拿顶点插值法线来算——光照公式不变，只是法线的来源从"逐像素查表"降级为"逐顶点插值"。同样，没有粗糙度贴图就用常量粗糙度。材质的每个表槽都是**可选的**，缺省时回退到一个合理的常数值。

这意味着：同一段着色程序，要能正确处理"某张表有、某张表没有"的情况。这是着色器变体（shader variant）问题的起点——"是否有法线贴图"这个布尔条件决定了编译时是否包含查法线表的代码。这个问题的工程解法（宏定义变体、Uber Shader、运行时编译缓存）是阶段十二的内容，此刻只需建立直觉：**多表材质制造了着色程序的分叉，分叉需要管理。**

### 材质 + 表组 + 着色程序 = 三元模型

总结本模块建立的材质概念：

```
材质
├── 着色程序 ── 决定"怎么算"（光照模型、BRDF）
├── 表组     ── 决定"每个像素的各个属性是多少"（颜色/法线/粗糙度/金属度...）
└── 常量组   ── 决定"所有像素共享的参数是多少"（全局粗糙度、颜色常量...）
```

这三个组成部分各自独立变化：同一段着色程序（标准光照）可以搭配完全不同的表组+常量组（砖墙、铁锈、皮肤）；同一张颜色表也可以搭配不同的着色程序（Blinn-Phong 和 PBR 算出来的画面不同，但底图是同一张）。**表组负责采样的"是什么"、着色程序负责采样的"怎么算"、常量组负责采样的"统一修正"**——三者解耦是引擎材质系统的第一条设计原则。

## 问题 5：回顾——材质 "表组" 里的几张表在数据通道分层中的位置

3.2 建立了数据通道的频率分层模型，4.2 往里加了"查询表"这一行：

| 通道 | 更新频率 | 数据量级 | 代表数据 |
|---|---|---|---|
| 顶点属性 | 每顶点 | 每顶点几 float | 位置、法线、UV、**切线 T** ← 新增 |
| 插值传递 | 每像素（来自顶点） | — | 插值后的 UV、法线、**T、B** ← 新增 |
| 常量 | 每物体/每帧 | 几十~几百字节 | MVP、光源参数、**材质常量（粗糙度、金属度等）** ← 新增 |
| 查询表 | 资源级（几乎不变） | MB 级，插槽间接引用 | 颜色表、**法线方向表、粗糙度表、金属度表……** ← 新增 |

变化有三处：
1. 顶点属性多了一个 T（切线方向），它是 TBN 矩阵所需的逐顶点数据；
2. 插值通道多了 T 和 B（B = N × T 在逐像素阶段现算），它们和法线一起构成每个像素的 TBN 矩阵；
3. 查询表和常量各自多了语义槽位——查询表从"一张颜色表"变成"一组多张语义表"，常量从"MVP + 光源"变成"MVP + 光源 + 材质参数"。

这些变化都是"加了新数据"而非"改了旧机制"——插槽模型、频率分层、独立决策，全部复用阶段二~四已建立的框架。

## 问题 6：法线贴图的 Mipmap 陷阱——为什么 4.3 说过"金字塔的正确性依赖表里是颜色"

法线贴图也需要金字塔——远处的表面同样有法线走样的问题。但 4.3 明确警告过：**金字塔假设"平均是有意义的"**，而法线是方向——把两个方向"平均"出来的第三个方向，长度不再等于 1。

```
两个法线的算术平均：
  (0.7, 0, 0.7) 平均 (0, 0.7, 0.7) = (0.35, 0.35, 0.7)
  长度 ≈ 0.87 ≠ 1.0

在光照公式 N·L 里，N 的长度直接影响结果亮度——
  一个"变短"的法线让光照比正常情况更暗。
```

这是法线贴图 + 金字塔的已知"近似"——几乎所有实时渲染都接受它，因为视觉差异通常被漫反射和高光的其他因素掩盖。需要精确结果的场景（比如汽车漆面），可以在生成金字塔后对每一层的每个纹素**重新归一化**法线。这个操作的代价在离线烘焙时支付，不影响运行时性能——这是 4.6 压缩纹理管线里会再见面的话题。

还有一种选择：不用金字塔，但这样远处表面的法线走样（闪烁）会回来。两害相权：略微暗淡的间接光照 << 可见闪烁。工程结论是：**法线贴图一样开金字塔，接受微小的间接光照误差。**

## 收尾落地：多表绑定与材质在各图形后端中怎么表达

> 推导到此结束——你已经知道：多张表通过多占插槽同时挂载，shader 通过多个查表器变量引用不同编号的插槽；法线贴图存的是切线空间里的方向而非颜色，TBN 矩阵负责把切线空间法线转到光照空间；材质 = 表组 + 常量组 + 着色程序的三元合体。下面是各后端的落地，纯文字、无代码，具体实现交给 AI 生成。

- **OpenGL**：插槽在 OpenGL 里叫"纹理单元"，硬件保证至少 16 个，现代硬件通常 32~80 个，可按需查询上限。绑定流程是：激活插槽 N → 把表挂上去 → 给 shader 里的查表器变量赋值编号 N。这套 API 的"激活-绑定-赋值"三步恰好对应 4.2 的"插槽编号是桥梁"的模型。法线贴图没有专门的 API 对象——它就是一张普通的 2D 表，存在普通纹理对象里；TBN 矩阵没有专门的 API 对象——T 是一个普通的顶点属性，N 也是，逐像素的 B = cross(N, T) 在 shader 里手写一行。材质在 OpenGL 里没有原生概念——表组、常量组、着色程序三者全靠你的代码组织。

- **Vulkan**：插槽在 Vulkan 里通过"描述符集"来表达——一个描述符集是一次绑定的"一批资源"（几张表 + 几块常量缓冲），一个材质就是一个或一组描述符集。设计意图是：把"一组表的组合 + 一组常量的组合"做成一个显式对象，绑定一次就全部到位——这和本模块的"材质 = 表组 + 常量组"模型完全一致。插槽上限是物理硬件的限制，在 Vulkan 里对应的上限更高更灵活（描述符集可以很大，也有无绑定扩展来规避上限）。TBN 同样没有专门对象，T 是顶点属性、N 是顶点属性、B 在 shader 里算——和 OpenGL 一样。

- **D3D12**：与 Vulkan 同路——描述符表绑定一批资源（SRV 描述符指向表、CBV 描述符指向常量缓冲），材质 = 一套描述符表的组合。根签名定义了"shader 期望哪些槽位"，相当于"材质的插槽模板"。

- **Metal**：纹理通过参数缓冲区或逐个绑定到着色器参数上，材质的概念在 Metal 里对应"参数缓冲区 + 渲染管线状态 + 一组纹理"的组合——和三元模型结构一致。

一句话对照：**"多张表 + 多常量 + 着色程序"在概念上是同一个东西（材质），但 OpenGL 把它们分散在三个独立的 API 对象里靠代码逻辑组合，现代 API 用描述符集/描述符表把它们显式打包——打包的理由和"渲染状态一次验证"一样：CPU 预验证、批量绑定、减少驱动内部的状态散落。**TBN 矩阵没有一个 API 有专门对象——它太基础了，就是三个顶点属性 + 一个逐像素向量叉积，不值得一个 API 抽象。

## 总结：这篇笔记建立的核心认知

1. **多表同时上的机制就是"多占几个插槽"**——机制上没有新东西，但引出第一个硬约束：插槽有数量上限。一个材质能用的表的张数不能超过硬件上限；场景中的几十种材质需要按材质分组绘制以减少"换挂插槽"的开销。

2. **法线贴图存的是切线空间里的方向，不是颜色**——切线空间就是把法线定义在"表面自己的坐标系"里，这样同一张法线贴图可以用在任意朝向的表面上。法线贴图普遍呈蓝色的原因是：切线空间里的"朝外"方向 (0,0,1) 编码到 RGB 就是 (0.5, 0.5, 1.0)。

3. **TBN 矩阵就是把切线空间的方向转到光照空间的变换矩阵**——三个基向量：T 沿 UV 的 u 方向、B 沿 UV 的 v 方向（B = N × T）、N 垂直于表面。其中 **T 不是纯几何向量，而是"几何 × UV 映射"的产物**——它由顶点的位置差和 UV 展开反解出来，语义是"贴图的 u 方向在 3D 表面局部指向哪"，同一个几何点换个 UV 展开 T 就不同；B 在逐像素阶段当场算。切线空间法线 × TBN = 可以参与光照计算的法线。

4. **材质 = 表组 + 常量组 + 着色程序的三元合体**——表组决定"每个像素各个属性的值"，常量组决定"所有像素共享的参数"，着色程序决定"怎么算"。三元独立变化、彼此解耦。

5. **法线贴图的金字塔可以开，接受微小误差**——把两个法线平均会缩短结果向量，导致间接光照略微变暗；但在所有工程场景里，这个误差远小于关掉金字塔带来的法线走样（闪烁）。

6. **本模块是阶段四"查表方式"四维度的总回收终点**——从 4.1 提出"数据和查法可分"，到 4.3/4.4 说清"查法"的三个开关和一个寻址维度，到本模块说清"多张表一起上的组织方式"——纹理系统在单 Pass 世界里的全部机制到此齐备。后面两篇（4.6 压缩格式、4.7 Cubemap/纹理数组）是"成组的纹理"在工程资源管线和特殊使用场景（天空盒、粒子）里的展开，不改变本模块建立的"材质 = 表组 + 参数组 + 着色程序"的核心结构。

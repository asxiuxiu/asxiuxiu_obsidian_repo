# 纹理对象与加载

## 问题 0：理论全通了，可表还躺在磁盘上

4.1 结束时，理论上的一切都已就绪：纹理是一份 2D 数据加一套查表机制，UV 从顶点插值到像素，逐像素计算拿 UV 查表得到基础颜色。但真正动手时你会撞上一个朴素的事实：你的"表"此刻只是磁盘上的一个 `brick.png`，而查表发生在 GPU 的逐像素阶段——两者之间隔着一整个旅程。

这段旅程只有三步，但每一步都有一种经典翻车方式，而且翻车症状全是"画面错了但程序不崩"：

```
磁盘:  brick.png（压缩字节流，几百 KB）
  │  ① 解码：存储形态 → 查询形态（CPU，一次性）
  ▼
CPU 内存:  宽×高×通道 的连续字节数组（1024²×4 = 4MB）
  │  ② 上传：CPU → GPU 显存，附带内部格式声明（一次性）
  ▼
GPU 显存:  一张只读 2D 查询表（附格式解释）
  │  ③ 挂载：绘制前把表挂到"查表插槽"上
  ▼
逐像素:  uv → 查表 → 基础颜色
```

> **本质问题：逐像素计算要查的那张表，必须由磁盘上的压缩文件，经过一次解码、一次上传、一次挂载，才变成 GPU 显存里"格式明确、随时可查"的查询表。**

这三步里没有一步在算法上高深，但每一步都埋着"不报错只错图"的坑。下面逐个走。

---

## 问题 1：PNG 为什么不能直接查？——存储形态 vs 查询形态

先做最 naive 的思维实验：把 PNG 文件原样读进内存，原样交给 GPU，让逐像素计算直接查文件字节。行不行？

不行，而且失败的原因值得想清楚。PNG/JPEG 是**为存储优化的变长编码**：它们的第一目标是"文件尽量小"，为此不惜让数据难以访问——PNG 的压缩必须顺序解码，每一行还带有依赖前一行的过滤器；JPEG 更极端，颜色根本不存在像素域里，而是存在频域系数中，取一个像素要做一堆乘加。在这类编码里，"第 (u, v) 个纹素在第几个字节"这个问题**没有 O(1) 的答案**。

而查询表的命脉恰恰是**随机访问**：每个像素拿着任意 (u, v) 过来，都要求立刻返回颜色——一帧里这样的查询发生几百万次，且彼此没有顺序。

```
存储形态（PNG 文件）        查询形态（解码后的数组）
目标：体积最小              目标：给定 (u,v)，O(1) 返回颜色
编码：变长、行内有依赖       布局：定长，位置 = (y×宽+x)×通道数
访问方式：整图顺序解码一次    访问方式：任意点随机读，读无数次
```

两种形态的目标根本相反，所以中间必须有一次翻译。**解码就是这次翻译：把"存储形态"一次性地转成"查询形态"。**它有三个特征：发生在 CPU 上、只发生一次（加载时）、产物是一份"宽 × 高 × 通道数"的连续字节数组，外加宽、高、通道数三个元数据。

"通道数"是这里第一次出现的概念，先说清它是什么。**一个像素的颜色不是一个数，而是几个数的组合**——最常见的是红、绿、蓝三个分量，每个分量占一个 8 位字节（取值 0~255），~={green}每个分量就叫一个**通道（channel）**=~。一张图是灰度图（每像素 1 个数）、RGB 图（3 个数）还是 RGBA 图（4 个数，多出来的 A 是 alpha，表示这个像素有多"不透明"，它要到阶段五才派上用场），决定了每个像素占几个字节。所以通道数的本质就是**每个像素的字节数**：解码产物的总长度 = 宽 × 高 × 通道数，数组里第 (x, y) 个像素从第 (y×宽+x)×通道数 个字节开始。它是图片的基本属性，不是附加信息——解码库必须把它告诉你，否则你连这段数组有多长都算不出来，后面陷阱一的错位也正是从"以为的通道数"和"实际的通道数"不一致开始的。

至于解码器内部（熵编码、过滤器重建、频域反变换……），规则繁琐但思想平庸，是典型的"了解即可"领域——工程上没人手写，直接用现成的单文件解码库，具体调用交给 AI 生成。你需要钉死的是它的**产物契约**：它给你一段字节和三个整数，你欠它一次释放。

拿到这份数组，是不是就能直接上传了？能，但从这里到"画面正确"之间，还隔着三个专门咬人的陷阱。

## 问题 2：字节对了，解释错了——加载期三大陷阱

解码产物本身没有问题，问题出在"你怎么向 GPU 描述这段字节"。你在[[Notes/计算机图形学/GPU编程基础/告诉GPU顶点数据长什么样|告诉 GPU 顶点数据长什么样]]里已经领教过这条规律：**数据是一回事，对数据的解释是另一回事**。纹理加载是这条规律的第二次现身——三个陷阱，每一个都是"解释不一致"。

### 陷阱一：通道数不统一

图片文件有三种常见形态：灰度（1 通道）、RGB（3 通道）、RGBA（4 通道）。同一个素材文件夹里，三种都可能有。如果你上传时假设"全是 4 通道"，而某张图实际解出 3 通道，那么从第二个纹素开始，每个纹素读到的字节就整体错位了——画面花掉，但没有任何报错。

工程惯例：**解码时统一转成 4 通道**。代价是多占 1/3 内存，换来"全项目只有一种布局"。这是一笔稳赚的交易，而且透明度通道很快就有用武之地（4.1 结尾预告过：像素不只有颜色，还有不透明度——这是阶段五的入口）。主流解码库都有"强制按 N 通道解码"的选项，就是为这个惯例准备的。

### 陷阱二：行对齐

GPU 读你的 CPU 数组时，默认假设**每行的字节数是 4 的倍数**。这个假设一旦不成立，读取就会逐行错位：

```
一张 3×2 的 RGB 图，每行 3 像素 × 3 字节 = 9 字节（不是 4 的倍数）

你的内存（18 字节，完全正确）：
行0:  R G B | R G B | R G B
行1:  R G B | R G B | R G B

GPU 以为每行 12 字节（向上凑到 4 的倍数）来读：
"行0":  R G B | R G B | R G B | R G B   ← 把行1的头3字节当成行0的尾巴
"行1":  G B | R G B | R G B | ?? ??     ← 从此全部错位

画面症状：颜色整体斜移，出现对角线条纹
```

对策有两条：统一成 4 通道后，行字节数 = 宽 × 4，天然是 4 的倍数（陷阱一的解法顺手把陷阱二也解了，这是"统一 RGBA"惯例的第二个理由）；~={green}或者显式告诉 GPU"这张图按 1 字节对齐读"。后者更省内存=~，前者更省心——学习阶段选前者。

### 陷阱三：原点方向

几乎所有图片格式的原点在**左上角**，解码数组的第一行是图片最上面一行；而 UV 坐标约定 v=0 在**底部**（4.1 的约定）。两边都不"错"，但直接对接的结果就是：贴上去的画面上下颠倒。

对策同样是两条：解码时把数组垂直翻转（解码库通常有现成开关），或者在 UV 上做 v → 1−v 的翻转。选哪条都行，真正的坑在于**全项目必须统一**——一半模型走翻转、一半不走，结果就是有的正有的倒，排查时你会先怀疑 UV 展开、再怀疑模型导出，最后才发现是加载层的约定不一致。

三个陷阱合起来是一条教训：

> ~={red}加载阶段的 bug 几乎从不来自"数据错了"，而来自"你对数据的解释和 GPU 对数据的解释不一致"。=~遇到贴图发花、斜纹、颠倒，先怀疑解释层，别怀疑图片本身。这也是 3.4 那把"显微镜"（RenderDoc）的第一批用武之地：抓一帧，直接看 GPU 显存里那张表长什么样，错位一目了然。

## 问题 3：CPU 数组怎么变成 GPU 查询表？——上传与格式声明

解释层理顺了，正式上传。这一步你在[[Notes/计算机图形学/GPU编程基础/把几何数据放到GPU能访问的地方|2.4]] 已经走通过一次：数据要常驻 GPU 显存，上传是一次性的 CPU→GPU 拷贝。纹理完全同构，而且更新频率比顶点数据更低——顶点数据好歹可能逐帧变化（动画、粒子），纹理通常**整个游戏过程不变**：~={green}上传一次，被查几百万次。这是"常驻显存"这套机制最纯粹的受益者=~。

但纹理上传比顶点上传多一件事：**声明纹素的内部格式**。顶点格式解释回答的是"字节流怎么切分成属性"；纹理的格式声明回答的是"每个纹素几个通道、每通道几位、查表读出来时怎么换算"。最常见的约定是：4 通道 × 8 位无符号整数，读出时由硬件自动归一化到 [0.0, 1.0] 浮点——文件里的 255，到逐像素计算手里就是 1.0。

为什么要归一化？因为逐像素计算是浮点世界：阶段三的光照公式里，`N·L` 的结果在 [0, 1]，材质颜色也必须在 [0, 1]，两者相乘才有意义。让硬件在查表时顺手完成"255 → 1.0"的换算，比在 shader 里给每个像素手写一次除法便宜得多——这是"把固定不变的换算固化进硬件"的典型例子，也是格式声明这个设计的存在理由。

上传这一步的信息变化：

```
上传前（CPU 侧）:  一段字节 + 你脑子里的口头约定"RGBA、每通道 8 位"
上传时声明:        尺寸 1024×1024、内部格式"RGBA8 归一化"、数据指针
上传后（GPU 侧）:  一张只读 2D 查询表
                   查 (u,v) → 返回 4 个 [0,1] 浮点
```

注意"上传后"那一行：GPU 拿到的是它自己的副本。这意味着 **CPU 那份解码数组通常可以立即释放**——除非你打算运行时修改这张表。别小看这件事：一张 4K RGBA 图解码后是 64MB，一个场景几百张图，不释放的话 CPU 内存先爆。"解码产物是临时工，显存里的表才是正式员工"——这个生命周期意识是后面资源管理的伏笔。

## 问题 4：逐像素计算怎么找到这张表？——插槽与查表器

表在显存里了，还剩最后一环。4.1 说"像素颜色 = 表查询(表, uv)"——这个"表"参数，怎么传进逐像素计算？

naive 思路：把表当常量数据传给 shader。[[Notes/计算机图形学/光照与数据流/数据通道与更新频率|3.2 的通道分层]]已经排除了这条路：常量通道的容量是几十到几百字节级，而一张 1024² 的表是 4MB——差了四个数量级，根本塞不进去。

真实的机制引入了一层间接：**插槽**。GPU 提供若干个"查表插槽"，绘制前你把表挂到某个插槽上；shader 里声明一个"查表器"变量，它存的**不是表本身，而是插槽编号**。逐像素计算执行时的完整链路是：读变量里的编号 → 找到对应插槽 → 找到插槽上挂着的那张表 → 用 uv 去查。

```
绘制前（CPU 侧）:            逐像素阶段（GPU 侧）:
插槽0 ← 挂上"砖墙表"          查表器变量 = 0（只是个编号）
                             基础颜色 = 查(插槽[0]上的表, uv)
```

为什么要绕这一层？因为**同一段逐像素计算要服务任意多张表**。砖墙和木箱用同一份 shader，区别只在挂哪张表——表是"每材质的数据"，不是 shader 逻辑的一部分。这和 3.2 里"常量存每物体的参数、shader 只写一次"是同一种解耦思想，只是数据体量大了四个数量级之后，"把数据拷给 shader"不再可行，必须改成"把数据放在原地、给 shader 一个能找到它的编号"。

于是绘制 N 个不同材质物体的流程变成：~={green}每画一个，换挂插槽上的表（顺带换常量），shader 一行不动=~。多张贴图同时参与一个像素的计算（一张表管颜色、一张表管法线方向）时，就是多占用几个插槽——那是[[Notes/计算机图形学/纹理系统/索引|本模块]]第 5 篇的内容，现在只需要理解"一个插槽挂一张表"这个最小机制。

## 问题 5：加载在帧循环里的位置——资源级事件

最后把加载放回整体节奏里看。3.2 建立了更新频率分层：每顶点、每物体、每帧、全局不变。纹理加载甚至不在"全局不变"那一层——它~={green}更低频=~，是一类新东西：~={green}**资源级事件**，只在关卡切换、场景流式加载时发生=~。

这个频率特征带来两个工程事实：

1. **它很慢，但慢得起。**解码一张 4K PNG 要~={green}几十到几百毫秒=~，放在帧循环里必然卡帧；放在加载画面期间或后台线程里就无所谓。这正是引擎"异步加载管线"存在的理由：磁盘读取和解码放工作线程慢慢做，只有最后一步"上传到 GPU"需要回到图形线程。你的引擎 `5.9 异步加载管线`做的就是这个拆分，这里只需建立直觉：**加载天然该异步，因为慢的解码和快的上传是可分离的两步。**
2. **它是显存管理的前线。**纹理是游戏显存占用的大头。~={green}"什么时候解码、什么时候上传、CPU 副本什么时候释放、不用的表什么时候卸载"——这四个决策合起来，就是引擎资源生命周期管理的雏形=~。问题 3 末尾那句"解码产物是临时工"，在这里升级为一条管理原则。

至此，[[Notes/计算机图形学/纹理系统/纹理映射与UV坐标#问题 6：在数据通道分层里，纹理站在哪一层？|4.1 留下的数据通道分层表]]可以正式补上纹理这一行：

| 通道 | 更新频率 | 数据量级 | 代表数据 |
|---|---|---|---|
| 顶点属性 | 每顶点 | 每顶点几 float | 位置、法线、UV |
| 插值传递 | 每像素（来自顶点） | — | 插值后的 UV、法线 |
| 常量 | 每物体/每帧 | 几十~几百字节 | MVP、光源参数 |
| 查询表 | 资源级（几乎不变） | MB 级，插槽间接引用 | 纹理 |

## 收尾落地：这套流程在各图形后端中怎么表达

> 推导到此结束——你已经知道：加载 = 解码（形态翻译）+ 上传（CPU→GPU，附内部格式声明）+ 挂载（插槽与编号）。下面是这套方案在各后端的落地，纯文字、无代码，具体实现交给 AI 生成。

- **解码层**：与图形后端无关，事实标准是 stb_image 这类单头文件库——一行调用返回字节数组加宽/高/通道数，并且自带"强制 N 通道"和"垂直翻转"两个开关，问题 2 的三个陷阱它都预留了出口。
- **OpenGL**：纹理对象把"表数据 + 内部格式 + 查表方式"打包在一起。流程是：生成对象 → 绑定 → 一条调用同时完成"声明尺寸与内部格式"和"把字节拷进显存"。行对齐有专门的像素存储设置，默认值是 4 字节对齐——陷阱二正是这个默认值造成的。上传时的同步由驱动隐式处理，你察觉不到。
- **Vulkan**：同一件事被拆成显式的几步——创建图像对象、为它分配显存、经一块 CPU 可写的"中转缓冲"把数据搬进去、再做一次布局转换，声明这份数据从"待写入"变成"可被采样"。繁琐的理由：它把"CPU 拷贝"与"GPU 采样"之间的时间关系交给你管理，换来异步上传和多线程加载的能力——这正是问题 5 说的"加载天然该异步"在 API 层的兑现。
- **D3D12**：思路与 Vulkan 一致——数据放默认堆、上传堆做中转、用资源状态屏障表达"从拷贝目标变成着色器可读"。
- **Metal**：纹理对象可以直接从字节创建，也可以走显式的拷贝命令；显式程度介于 OpenGL 和 Vulkan 之间。

一句话对照：**OpenGL 替你安排上传的一切细节（包括同步和对齐的默认假设），现代 API 把安排权交给你，连同异步加载的能力一起给你。**学概念时 OpenGL 最省事；当你的引擎要做流式加载、多线程资源管线时，Vulkan/D3D12 的显式模型就是"那件事本身"。

## 总结：这篇笔记建立的核心认知

1. **纹理加载 = 三段旅程**：解码（存储形态 → 查询形态）、上传（CPU → GPU 显存，附内部格式声明）、挂载（表挂到插槽，shader 拿编号查）。每步各解决一个问题，缺一不可。
2. **PNG/JPEG 不能直接查**，因为它们是变长、顺序依赖的存储编码，而查询表要求 O(1) 随机访问。解码的本质是**一次性的形态翻译**，发生在 CPU、只发生一次。
3. **加载期 bug 的三大来源全是"解释不一致"**：通道数不统一、行对齐假设、原点方向。数据对了而解释错了，症状是画面错但程序不崩——先怀疑解释层。统一 RGBA 一个决策能同时拆掉前两个陷阱。
4. **上传必须声明内部格式**；"8 位整数读出时归一化到 [0,1]"让查表结果直接进入浮点光照公式，换算是硬件顺手做的。
5. **shader 不持有表，持有插槽编号**——这是"同一份 shader 服务任意多材质"的解耦设计，也是纹理数据体量超过常量通道四个数量级后的必然选择。
6. **加载是资源级事件**：慢得起、天然该异步（解码与上传可分离）、是显存管理的前线。这四个判断是引擎资源管线的种子。

留下的缺口：表已经能查了，但 4.1 埋下的那个采样问题还没真正落地——远处闪烁要靠金字塔解决，而金字塔怎么生成、层级之间怎么选、坐标落在格子之间怎么取值，这些"查表方式"的细节还全是空白。这就是下一篇——[[Notes/计算机图形学/纹理系统/Mipmap与纹理过滤|Mipmap与纹理过滤]]。

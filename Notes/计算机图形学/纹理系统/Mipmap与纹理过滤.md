# Mipmap与纹理过滤

## 问题 0：概念轮廓变不成像素

4.1 结尾给了金字塔的概念轮廓：把原图逐级缩小一半，渲染时选合适的一层查，远处闪烁就消失了。4.2 把表送上了 GPU。但真正动手时，概念轮廓会立刻碎成三个具体问题：

1. 金字塔的每一层，颜色具体怎么算出来？谁算、什么时候算？
2. 渲染时，每个像素怎么知道"自己该查哪一层"？
3. 选好了层，UV 落在格子之间又怎么取值？层号算出来是 2.8 这种小数又怎么办？

这三个问题合起来，就是 4.1 说的"查表方式"那半个决策的全部内容。逐个走。

---

## 问题 1：金字塔的每一层是怎么算出来的？——预滤波是一次性事件

先回到走样的总原则：一个像素覆盖了表里几十个纹素时，它该得到的是这几十个纹素的**平均颜色**，而不是随机踩中的一个。金字塔第 k 层的一个格子，存的恰好就是原图 2ᵏ×2ᵏ 个纹素的平均——所以造金字塔的办法直接就是定义本身：

```
LOD0 → LOD1:  每 2×2 格子取平均，合成 1 格，尺寸减半
LOD1 → LOD2:  对 LOD1 重复同样的操作
  ...          直到 1×1（整张图的总平均）
```

每层的每个格子 = 上一层 2×2 的平均，递归到底。这个 2×2 平均有个正式名字：**盒式滤波（box filter）**——用一个小方框盖住 4 个纹素，框内取均值。它不是理论上最好的滤波核（有更平滑的选择，能更好地保留细节），但它便宜、结果足够好，是几乎所有实时渲染的默认。滤波核的选择属于"了解即可"领域，你知道"预滤波的质量影响远处的观感"就够了。

真正重要的是生成的**时机**。注意这个计算的两个特征：

- 它只依赖表本身，跟相机、场景、光照**完全无关**；
- 表在游戏的整个生命周期里基本不变（4.2 的"资源级事件"）。

两个特征合起来意味着：**金字塔的生成可以、也应该是一次性事件，和运行时彻底解耦。**要么在加载时跟着上传一起做一次，要么更彻底——离线由资源管线提前算好，把整条金字塔直接烘进资源文件，运行时连生成这一步都省掉（这条路线在 4.6 讲压缩格式时还会回来）。

```
运行时每个像素的开销：
  无金字塔:  想正确就要现场平均几十个纹素 → 每像素几十次读表，太贵
  有金字塔:  选一层，查一次 → 滤波成本已在离线付清
```

这就是 Mipmap 的全部思想：**把"滤波"从每像素每帧的运行时，挪到每张表一次的离线期。**~={green}用 1/3 的额外显存（4.1 算过这笔账），买断整个运行时的滤波开销=~。

层造好了。接下来的问题是：渲染时每个像素面对这座金字塔，该伸手查哪一层？

## 问题 2：渲染时怎么知道该查哪一层？——像素脚印与它的硬件来源

### naive 思路：按距离选层

第一反应大概是：物体离相机越远，查越低的层。算算距离不就行了？

不行，而且错得有教益。同样距离的两块表面，一块正对着你、一块斜放成 60°——斜放的那块在屏幕上被透视压缩了，一个像素盖的纹素多得多。**决定该查哪一层的不是"离你多远"，而是"你的一个像素在表里盖了多大一片"**。距离只是影响脚印大小的因素之一，角度同样重要。按距离选层，斜面全部选错。

### 正确的量：像素脚印

~={green}把像素想象成一枚印章，透过屏幕"盖"到纹理表面上，盖出来的那片区域就是**像素脚印（pixel footprint）**=~。脚印盖几个纹素，就该查"一格等于几个纹素"的那一层：

```
脚印边长 ≈ 1 个纹素   → 查 LOD0（原图，一对一直接查）
脚印边长 ≈ 4 个纹素   → 查 LOD2（每格 = 原图 4×4 的平均）
脚印边长 ≈ 16 个纹素  → 查 LOD4

层号 = log2(脚印边长)
```

问题变成：渲染中的这个像素，怎么测量自己的脚印边长？它不知道自己在哪个三角形上，不知道表面的朝向——逐像素计算的世界里，这些信息它都拿不到。

### 关键洞察：脚印藏在"邻居的 UV"里

换一个问题问自己：横向相邻的两个像素，它们的 UV 差多少？

如果屏幕上每往右挪一个像素，UV 就移动 0.01，而表是 1024 宽——那一个像素就对应表里 0.01 × 1024 ≈ 10 个纹素。**脚印宽度根本不需要"测量"，它就是相邻像素的 UV 差值。**横向、纵向各算一次差值，脚印的大小就有了。

```
屏幕:   像素(x,y)    像素(x+1,y)
UV:     (0.500, 0.3)  (0.510, 0.3)  ← 横向差 0.01
表:     1024×1024 → 横向脚印 = 0.01 × 1024 ≈ 10 个纹素
                    → 该查大约 LOD3（一格 = 8 纹素）
```

这个洞察漂亮在：**它把"选层"从 3D 几何问题（距离、角度、三角形）变成了一个纯屏幕空间的局部测量**——只要知道自己和邻居的 UV，别的什么都不用知道。

### 硬件基础：2×2 像素块

但这里有个微妙之处：单个像素算不出"我和邻居的 UV 差"——它需要邻居的数据，而逐像素计算的设定是"每个像素独立执行、互不可见"。怎么办？

答案是 GPU 压根就不是真正"逐像素"调度的。[[Notes/计算机图形学/GPU编程基础/GPU的并行执行模型|GPU 的并行执行模型]]讲过线程是成组调度的；在逐像素阶段，硬件还有一个更具体的约定：**以 2×2 的像素块（quad）为最小单位执行**。块内四个像素跑同一段代码、彼此紧挨，于是任意一个像素都能免费拿到"右边邻居的 UV 减去我的 UV"和"下边邻居的 UV 减去我的 UV"——这两个差值叫**屏幕空间导数**，是硬件顺手给的，一行代码都不用你写。

~={green}所以"选层"这件事的成本几乎为零：UV 插值完，差值现成，取对数，层号就有了=~。这也是"逐像素计算"这个心智模型的第一次裂缝——看似独立的像素，实际上是四个一组捆绑执行的。这个裂缝后面还会变大（4.5 的法线贴图、幕二的屏幕空间技术都建立在这四个像素的亲密关系上）。

### 一个由此而来的经典坑

2×2 块机制有一个著名的受害者：**动态分支里的查表**。如果一段查表代码被包在"每个像素真假不一"的 `if` 里，那么某些 2×2 块里四个像素会走向不同分支——走到查表这一支的像素，它的"邻居"可能在另一支里，UV 差值就是无意义的乱数，层号随之乱选，画面出现莫名的闪烁或模糊。所以查表入口除了"自动选层"版本，还备着"你直接告诉它层号"和"你直接告诉它梯度"的版本——就是为了绕开这个坑。现在只需要记住：**动态分支里的自动选层不可信**，症状出现时知道去哪查。

## 问题 3：层号 2.8，格子之间——一次完整的查询长什么样

选层机制有了，还剩两个"落在缝隙里"的问题。它们其实在 4.1 就露过面，现在收编进统一框架。

### 缝隙一：UV 落在格子之间

4.1 讲放大走样时已经给过答案的两种形态：

- **最近点（nearest）**：取最近一格。结果是一块块纯色方块——像素风游戏要的就是这个味道。
- **双线性（bilinear）**：取周围 2×2 共 4 格，按 UV 在格间的位置加权混合。颜色连续平滑，代价是一次查询读 4 个纹素。

这个取舍与金字塔无关，是"层内"的取值方式，放大、缩小场景都适用。

### 缝隙二：层号是小数

脚印 2.8 个纹素，层号 log2(2.8) ≈ 1.5。查 LOD1 还是 LOD2？

naive 做法：四舍五入，查最近的一层。后果在运动中暴露无遗——物体缓缓远去，层号从 1.4 涨到 1.6 的瞬间，整块表面"啪"地从 LOD1 跳到 LOD2，清晰度和模糊度突变。远处地平线附近这种跳变连成一圈圈肉眼可见的**模糊度分界线**，相机一动，分界线圈跟着蠕动，比闪烁好不了多少。

修法和对付"格子之间"是同一种思想：**是小数，就两边都查，按小数部分加权。**层号 1.5 就把 LOD1 和 LOD2 各查一次，结果五五混合；1.8 就二八开。层号连续变化，混合权重连续变化，分界线消失了。

### 三个独立开关，一次完整查询

到这里，"查表方式"终于可以拆解成一张完整的图。一次查询实际发生三件事：

```
输入:  UV + 屏幕空间导数（2×2 块免费提供）
        │
        ① 层号 = log2(脚印边长)，通常是小数，如 1.5
        │
        ② 在 ⌊1.5⌋=LOD1 和 ⌈1.5⌉=LOD2 两层里，
           各自做"层内取值"（最近点 或 双线性 4 格加权）
        │
        ③ 两层结果按小数部分 0.5 加权混合
        ▼
输出:  一个颜色
```

对应三个**彼此独立的开关**：

| 开关 | 管什么 | 选项 | 选错了的症状 |
|---|---|---|---|
| 放大过滤 | 一个纹素盖多个像素时怎么取 | 最近点 / 双线性 | 马赛克方块 or 糊 |
| 缩小过滤 | 一个像素盖多个纹素时查哪层 | 不用金字塔 / 用金字塔 | 远处闪烁 |
| 层间过渡 | 层号是小数时怎么办 | 取整 / 两层混合 | 模糊度分界线 |

~={green}"双线性"是②的单层版本；"三线性（trilinear）" = 两层各自双线性 + 层间混合，一次查询共接触 8 个纹素=~——它是"金字塔 + 双线性 + 层间混合"全开的组合，也是过去二十年 3D 游戏的默认配置。

值得停一下看清楚：**这三个开关是三个独立的决策，回答三个独立的问题**。新手常把"过滤模式"当成一个整体选项，于是一出毛病就乱试。拆开之后，每种症状都有唯一的归属：马赛克归①，闪烁归②，蠕动圈归③。

## 问题 4：斜着看的地面为什么还是糊？——脚印是椭圆

金字塔 + 三线性，闪烁没了，分界线没了。但如果你渲染过一条伸向远方的石板路，会发现一个新症状：**路面在中近距离很清晰，再往前突然糊掉，而且糊得比"应有的程度"厉害得多**——路缝本该依稀可辨的距离上，已经是一片灰。

这不是 bug，是 Mipmap 的结构性盲区。

### 盲区：金字塔里只有"正方形"的平均

回到脚印。正对的表面，脚印大致是正方形：横向盖 8 个纹素，纵向也盖 8 个。但斜着看的地面，透视把远端剧烈压缩：**横向盖 2 个纹素，纵向盖 64 个**——脚印是一个又窄又长的椭圆。

而金字塔是"各向同性"的：每一层只存了正方形区域的平均（4×4、8×8、16×16……），**没有任何一层存过"2×64"这种长方形的平均**。

于是选层时撞上两难：

```
椭圆脚印：横向 2 纹素，纵向 64 纹素

按短边（2）选层 → LOD1：横向清晰，
                  但纵向 64 个纹素只查了 2 格的平均 → 闪烁回来了
按长边（64）选层 → LOD6：不闪了，
                  但横向只需要 2 格平均，却被迫查了 64 格平均 → 过度模糊

金字塔里不存在"刚刚好"的那一层。
```

三线性选的是保守的那头——宁可糊，不能闪（闪烁在运动中远比模糊刺眼）。这就是斜角地面过度模糊的来历：**横向的细节被无辜地处决了，只为了给纵向的采样率不足陪葬。**

### 各向异性过滤：把椭圆拆成一串正方形

椭圆的平均算不出来（金字塔里没有），但椭圆可以**近似**：沿椭圆的长轴方向，在合适的层上多取几个点，每个点做一次普通的正方形查询，最后把这些点平均。

```
椭圆脚印（横向2、纵向64），长轴沿纵向：

在"短边决定"的层（LOD1）上，沿长轴取 8 个采样点：
    ·  ← 每个点做正常的三线性查询（正方形小脚印）
    ·      8 个点排成一列，覆盖整条长轴
    ·
   ...
    ·
8 个结果取平均 ≈ 椭圆区域的平均
```

这就是**各向异性过滤（anisotropic filtering）**：脚印有多"扁"，就沿长轴多取几倍样本。采样倍数就是它的档位——2x、4x、8x、16x，~={green}倍数 N 的意思是"长轴最多按短轴的 N 倍来补样本"=~。横 2 纵 64 的脚印，比例是 32，16x 档位取 16 个样本——比 1 个好得多，但仍未完全覆盖，所以极端斜角永远残留一点糊，这是近似算法的本分。

代价直接摆在台面上：**查询次数 ×N**。一次三线性查询接触 8 个纹素，16x 各向异性最多接触 128 个。好在它只在斜角表面真正发力——正对的表面脚印接近正方形，硬件检测到比例接近 1 就只取 1 个样本，开销自动回落。

### 工程推荐

各向异性是过去二十年性价比最高的画质选项，没有之一：

- **全局默认 4x**：几乎免费，斜角地面脱胎换骨。这是任何 3D 项目的起步配置。
- **8x 是甜点**：画质接近 16x，开销只有一半。主流 3A 的默认档位。
- **16x 收益递减**：只在极端斜角有可见提升，移动平台慎开。
- 它**依赖金字塔存在**——各向异性是在 Mipmap 的层上做多次采样，金字塔关了它也无处发力。

## 问题 5：这套机制的账单——什么时候别开金字塔

概念讲完了，诚实地算一遍账。Mipmap + 过滤不是免费的，也不是永远正确的：

**成本侧：**

- **显存 +1/3**：4.1 已算过，等比数列求和 ≈ 4/3。几百张 4K 纹理，这 1/3 就是几个 GB。
- **生成成本**：加载时现场生成要花时间；离线烘焙则把成本挪给资源管线（4.6 的推荐路线）。
- **查询带宽**：双线性读 4 纹素、三线性读 8、16x 各向异性最多 128。每一档都是实打实的显存带宽。

**收益侧（容易被忽略的）：**

- 远处像素查的是小图——小图更容易整个驻留缓存，**远处渲染反而更快**。Mipmap 不只是画质功能，也是性能功能。

**什么时候该关掉或绕开：**

- **UI 与 2D 像素游戏**：UI 元素几乎永远 1:1 显示，金字塔白占 1/3 显存；像素风要的就是最近点的硬边，双线性一开全糊。
- **装的不是"颜色"的表**：金字塔假设"平均是有意义的"。颜色可以平均，但如果表里装的是查找索引、ID、编码数据，~={red}把两个格子平均出来的是一个谁都不代表的值=~——这类表要么关金字塔，要么极其小心。法线贴图是个灰色地带：平均会让法线"变短变平"，光泽度悄悄变化——这是 4.5 的伏笔，现在先记住"金字塔的正确性依赖'表里是颜色'这个假设"。
- **负 LOD 偏置的滥用**：嫌画面糊，有人把层号故意往小调（每次选层都偏亮一层）。画面是锐了，但采样率不足被重新请回来，闪烁随之复活。锐化该由后处理做，不该靠破坏选层机制。

**默认配置结论**：3D 场景的颜色纹理——整条金字塔 + 三线性 + 各向异性 4x~8x；UI 与像素风——无金字塔 + 最近点；非颜色数据表——无金字塔，逐案判断。

## 收尾落地：这套机制在各图形后端中怎么表达

> 推导到此结束——你已经知道：金字塔 = 一次性预滤波（离线或加载时生成）、选层 = 屏幕空间导数 + 对数、查表方式 = 放大/缩小/层间三个开关 + 各向异性倍数。下面是各后端的落地，纯文字、无代码，具体实现交给 AI 生成。

- **OpenGL**：金字塔被视为纹理对象的一部分——上传完原图后一条调用让驱动自动逐级生成整条金字塔；三个过滤开关和各向异性上限作为纹理对象的参数声明。生成和采样都由驱动包办，你几乎察觉不到 2×2 块和导数的存在。
- **Vulkan**：没有"自动生成金字塔"这回事。金字塔的每一层是图像的一个独立**子资源**，要么离线烘进资源文件随表一起加载，要么你自己跑一串逐层缩小的 blit 命令生成——生成时机、显存分配全由你控制。查表方式是独立的采样器对象；各向异性是一个**设备特性**，要先查询硬件支持再显式开启。设计理由与 4.2 一脉相承：它认为"何时生成、花多少显存"是资源管线的决策，不该藏进驱动。
- **D3D12**：与 Vulkan 同路——核心 API 不提供自动金字塔生成，引擎普遍用一小段计算程序逐层生成，或直接加载自带金字塔的资源文件；查表方式同样是独立的采样器描述符。
- **Metal**：介于两者之间——提供一条"为这张纹理生成金字塔"的显式命令（在 blit 编码器上），生成仍由你发起，但不用手写逐层逻辑；采样器对象同样独立。

一句话对照：**OpenGL 把金字塔当纹理的附属品，现代 API 把金字塔当资源本身**——每一层都是要显式分配、显式填充、可以单独寻址的数据。这也再次印证 4.1 的判断："数据"和"查表方式"是两个独立决策，现代 API 只是把它摆到了明面上。学习期用 OpenGL 的一条调用最省事；做引擎时，离线烘焙金字塔进资源文件（4.6 展开）才是正路——现代 API 的"麻烦"正是在逼你走这条路。

## 总结：这篇笔记建立的核心认知

1. **金字塔生成是一次性预滤波**：每层 = 上层 2×2 平均（盒式滤波），与相机无关、与运行时解耦，用 1/3 显存买断运行时的滤波开销。
2. **选层的本质是估算像素脚印**：脚印大小 = 相邻像素的 UV 差（屏幕空间导数），硬件以 2×2 像素块为单位执行让这个差值免费可得。层号 = log2(脚印边长)，一次查询拿到近似平均。
3. **"查表方式"是三个独立开关**：放大（最近点/双线性）、缩小（是否走金字塔）、层间（取整/混合）。症状与开关一一对应：马赛克、闪烁、蠕动圈各有各的归属。三线性 = 三者全开的组合。
4. **Mipmap 的盲区是椭圆脚印**：金字塔只存正方形平均，斜角表面被迫过度模糊。各向异性过滤沿长轴多次采样来近似椭圆，代价是查询次数 ×N，4x~8x 是性价比甜点。
5. **金字塔的正确性依赖"表里是颜色"**：UI、像素风、非颜色数据表都有绕开它的理由；负 LOD 偏置的"锐化"是把闪烁请回来的歪招。

留下的缺口：查表方式还差最后一个维度——三个开关都假设 UV 落在 [0,1] 之内。可地面纹理要无限重复、UV 常常超出边界，出界之后该查什么？这就是下一篇——[[Notes/计算机图形学/纹理系统/纹理寻址与采样|纹理寻址与采样]]。

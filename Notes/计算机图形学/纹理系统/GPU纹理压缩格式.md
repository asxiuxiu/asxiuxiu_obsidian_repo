# GPU 纹理压缩格式

## 问题 0：你一直以为 PNG 的 50KB 和 GPU 里的 64MB 是同一回事——它们不是

阶段四前五篇一直在默认一件事：表到了 GPU 显存里，就是按原始 RGBA 像素数组存的——每个纹素 4 字节（R、G、B、A 各一字节），按行排列，想查哪个像素就直接跳过去读。这是最纯真的模型，也确实是"解码后的形式"。

但加载流程（4.2）里有一幕你没细想：**PNG 在磁盘上可能只有几百 KB，上传到 GPU 里变成了几十 MB。** 一张 2048×2048 的 RGBA 纹理，磁盘上压缩成 PNG 大概 500KB～2MB，到显存里就是 `2048 × 2048 × 4 = 16MB`。这还是单张；按 4.5 的材质模型，一个 PBR 材质轻松 5 张表起步——80MB 一个材质。一个场景几十种材质，加上金字塔（1.33×）——显存轻松破 GB。

你的第一反应很自然：**"为什么 GPU 不能直接读 PNG 的压缩数据来查表？那样不就省掉这 1000 倍的膨胀了吗？"**

这不是一个笨问题——恰恰相反，这个问题是理解整个 GPU 纹理压缩领域的钥匙。

答案是：**"随机访问"和"压缩"在大多数情况下是互斥的——PNG 和 JPEG 选的是"压缩率最大化"，代价是放弃了任何随机访问能力。GPU 反选了一套"固定速率随机访问"的压缩方案——压缩率没那么高，但硬件可以在一个周期内定位并解出任意像素。**

下面从"GPU 怎么查表"这个最基础的机制讲起，一步步推出为什么 PNG 不行、块压缩为什么行、BC7/ASTC 分别怎么实现。

---

## 问题 1："GPU 查一张表里的一个像素"到底在干什么——先把"随机访问"四个字讲透

GPU 在片段着色器里执行 `查(表, uv)` 时，实际发生的硬件操作是：

1. **地址计算**：根据 UV 坐标和金字塔层级，算出这个像素对应表的第几行第几列。
2. **内存寻址**：根据像素坐标算出该纹素在显存中的**字节偏移**，发出一次显存读取请求。
3. **解码**：读回来的字节如果经过压缩，硬件当场解码成 RGBA 颜色值。
4. **过滤**：如果启用了双线性/三线性，可能还需要额外读相邻的纹素。

关键就在第 2 步和第 3 步之间的隐含约束：**GPU 需要的寻址时间是恒定的。** 纹理单元是一个流水线硬件——每个时钟周期，它要能接收一个 UV 查询、算地址、读显存、解码、返回颜色。这其中"读显存"是最大瓶颈——显存带宽是所有 GPU 的稀缺资源。所以纹理单元的设计极度精简：它不需要知道"这个像素的前一个像素是什么"，它只需要知道**"这个像素的数据从显存的哪个位置开始、占多少字节"**。

**这就是"随机访问"的真正含义**：给定任意像素坐标，在 O(1) 时间内（固定的几个时钟周期）从显存的固定位置上读出它的数据并解码。不需要遍历前面的数据，不需要解码整个纹理，不需要额外的索引表。

现在，让我们看看 PNG 的压缩结构，看它能不能满足这个要求。

---

## 问题 2：PNG 为什么不能随机访问——因为"变长编码"和"固定寻址"是根本矛盾

PNG 的核心压缩算法是 DEFLATE——一种基于 LZ77 + 霍夫曼编码的通用压缩。DEFLATE 的压缩逻辑是：

- 找到重复的字节模式，用"回退 N 个字节、复制 M 个字节"的指令代替；
- 对剩下的符号用霍夫曼编码——出现频率高的符号用短码、低频率的用长码。

这套逻辑在"压缩文件整体大小"上表现优异，但它让任意位置的访问变得不可能。原因是：

> **不同的像素块（甚至不同的像素行）压缩后占据的字节数不同。你无法在不知道前面所有数据的情况下，算出"第 137 行第 289 列"这个纹素压缩后从文件的第几个字节开始。**

具体来说：

```
PNG 压缩流程：
  原始 2048×2048 RGBA → 逐行 DEFLATE 压缩 → 变长比特流
  
"查第 137 行第 289 列"需要：
  1. 解压前面 136 行的全部数据（因为 DEFLATE 的字典窗口跨行）
  2. 解压第 137 行找到第 289 列
  → 时间不可预测，且依赖前面所有行的解压结果
```

JPEG 的情况更糟：它用 DCT（离散余弦变换）把空间域（像素颜色）转成频率域（亮度 + 色度的频谱系数），再对频谱系数做霍夫曼编码。要得到一个单独像素的颜色值，你需要：
- 解码整个 8×8 MCU（最小编码单元）的 64 个频率系数；
- 对它们做逆 DCT 变换；
- 这 64 个系数本身的解码需要顺序遍历霍夫曼编码的比特流。

**结果是：PNG 和 JPEG 都不能在固定时间内定位并解码一个纹素。** 纹理单元只有两个选择：要么放弃压缩，存原始 RGBA（寻址 O(1)，但显存爆炸）；要么换一种"天生就懂随机访问"的压缩方式。GPU 选了后者——这就是**块压缩（block compression）**。

---

## 问题 3：块压缩的通用原理——4×4 像素一个固定块，每块占固定字节数

如果"压缩"和"随机访问"不能兼得的原因是"压缩后每块大小不固定"，那解法就呼之欲出了：**强制每块大小固定。** 这就是所有 GPU 块压缩格式的共同起点：

```
把纹理切成 4×4 像素的块。
每个块压缩后占固定字节数——通常是 128 位（16 字节）。
给定任意像素坐标 (x, y)：
  块地址 = (y/4) × (总列数/4) + (x/4)
  从显存中偏移 = 块地址 × 16 字节处开始读 16 字节
  → O(1) 时间定位，不依赖任何其他块。
```

**固定块大小 + 固定位数 = 直接地址映射。** 这就是 GPU 块压缩把"压缩"和"随机访问"兼得的全部秘密。就这么简单。

但问题还没完：一个 4×4 块有 16 个像素，每个像素 RGBA 各 8 位——如果不压缩就是 `16 × 4 = 64` 字节。现在压缩到 16 字节——压缩率 4×。多出来的 48 个字节去哪了？答案是：**块内的像素不是独立存储的，而是用少量"代表色"加一套"各像素选哪个代表色"的索引表来近似。**

### 块压缩的内部结构：端点 + 权重 = 插值重建

不管具体的格式是 BC 家族的哪一员、ASTC 的哪一档，所有块压缩格式内部都做同一件事：

```
一个 4×4 块 = 128 位 = 16 字节，分为两部分：

[端点色 1] [端点色 2] [16 个像素的权重索引表]
  ↑              ↑              ↑
  块内"最亮的颜色"  块内"最暗的颜色"  每个像素在 1 和 2 之间
                                       选哪个位置
```

GPU 读出一个块时：
1. 拿出两个端点色（量化后的代表色）；
2. 用它们定义一条"颜色线段"——端点 1 在一端，端点 2 在另一端；
3. 对每个像素，读它在这个块内的权重索引（0 到 N，N 由格式决定），在颜色线段上插值：权重 0 = 端点 1，权重 N = 端点 2，中间值 = 线性插值；
4. 如果格式支持多分区（partition），这个 4×4 块可以被切成 2~3 个子区域，每个区域有自己的端点对——这样一条对角线上有两个方向的颜色渐变，一个块就能近似。

```
示意图：一个 4×4 块

端点 2（亮灰）
  │  ·  ·  ·  ●     ●  = 端点色本身
  │  ·  ○  ○  ·     ○  = 两个端点之间的插值
  │  ○  ○  ·  ·     
  │  ●  ·  ·  ·     
  └──────────────→ 端点 1（暗灰）
```

块压缩不是无损的——每个像素的颜色被近似成了它所在颜色线段上的某个点。**但关键在于：GPU 从一个固定大小的块里就能独立重建出 16 个像素的颜色，不需要读任何其他块的信息。** 压缩率和随机访问兼得，代价是"每个像素的颜色是近似的"——也就是有损压缩。但实时渲染的纹理本来就充满了噪声、渐变和自然细节，人眼对这种"块级别的颜色近似"容忍度远高于"整个纹理是模糊的"或"锯齿在闪"。

到这里，"GPU 为什么不能用 PNG/JPG"这个问题的答案就完整了：

| 维度 | PNG/JPEG | GPU 块压缩（BC7/ASTC 等） |
|------|----------|--------------------------|
| 压缩粒度 | 全图 / 行 | 固定 4×4 像素块 |
| 每块位数 | 变长（不可预测） | 固定（128 位/块） |
| 随机访问 | 不支持 | O(1) 直接地址映射 |
| 解码依赖 | 需前面数据 | 0 依赖，每块独立 |
| 压缩率 | 极高（10×~100×） | 中等（4×~8×） |
| 解码开销 | 需解压大量上下文 | 硬件固定流水线，每块固定周期 |

## 问题 4：BC7 —— PC 平台的"高质量通用格式"

BC7（也叫 BPTC，Block Partitioned Texture Compression）是 DirectX 11 引入的标准，今天几乎所有 PC 独显都支持它。它是 BC 家族（BC1~BC7）里的"全能选手"——**支持最高质量的 RGBA 压缩，每像素固定 8 位（1 字节）**。

BC7 的内部比上面"两个端点 + 权重"的最简模型丰富很多：它有多达 8 种编码模式（mode 0~7），每个模式对 128 位的分配方式不同：

- **模式 0~3**：3 个分区（块内可切成 3 个子区域，各自独立端点对）+ 高精度端点；
- **模式 4~7**：2 个分区 + 更高的权重粒度或额外的 alpha 精度；
- **模式 6**：专门为 RGB（无 alpha）优化——不存储 alpha 位，把省下来的位全给颜色端点，RGB 质量在 BC7 各模式中最高。

**BC7 对"4.5 的材质多表场景"意味着什么？**

在 4.5 里，一个材质动辄 5 张表——每张表 16MB（2048×2048 RGBA8），5 张就是 80MB。换成 BC7（固定 8bpp = 1 字节/像素）：每张表变成 4MB，5 张变成 20MB。**同一个材质，显存从 80MB 降到 20MB——省出 60MB 可以放更多材质、更大分辨率。** 金字塔的 1.33× 放大因子依然适用：20MB × 1.33 ≈ 26.7MB，仍在可接受的预算内。

### BC 家族的定位（快速扫一眼，不用记）

BC7 是"终极版"，但 BC 家族还有其他成员，各有各的用武之地：

| 格式 | 每像素位数 | alpha 支持 | 典型用途 | 与 BC7 的关系 |
|------|-----------|-----------|---------|-------------|
| BC1 | 4bpp | 1 位 alpha | 漫反射贴图（不需要渐变 alpha） | BC7 比它好，但 BC1 体积只有一半 |
| BC3 | 8bpp | 完整 8 位 alpha | 带透明度渐变的标准贴图 | BC7 质量更高、同体积 |
| BC4 | 4bpp | —（单通道） | 高度图、粗糙度图、金属度图 | BC7 的单通道替代 |
| BC5 | 8bpp | —（双通道） | 法线贴图（XY 两通道，Z 推导） | BC7 也可以存法线，BC5 专门优化 |
| BC6H | 8bpp | —（HDR） | HDR 环境图（浮点格式） | BC7 不支持 HDR，BC6H 专攻 |
| BC7 | 8bpp | 完整 8 位 alpha | **最高质量通用格式** | 全能，你的 go-to option |

一条简单的默认策略：**法线贴图用 BC5（两通道专用，不浪费 alpha 位），颜色/金属/粗糙度用 BC7，HDR 环境图用 BC6H。** 如果体积比 BC7 更重要（比如移动端弱网下发），把颜色降到 BC1（不要 alpha）或 BC3（要 alpha）；但通常先跑通 BC7，体积问题交给 KTX2（问题 6）解决。

## 问题 5：ASTC —— 跨平台的"可变块大小"方案

ASTC（Adaptive Scalable Texture Compression）是由 ARM 和 AMD 联合提出的开放标准，设计目标是**一套格式覆盖从手机到桌面、从 4×4 到 12×12 的所有块大小需求**。今天的 GPU 支持情况：所有 iOS/macOS 设备（Apple GPU）、几乎所有 Android 设备（Mali、Adreno）、所有 Intel 集显、甚至部分 NVIDIA/AMD 桌面卡都支持 ASTC 的 LDR 模式。

### ASTC 与 BC7 的本质相同点

ASTC 的基础块也是 4×4（和 BC7 一样），内部也是"端点 + 权重插值 + 分区"这套模型。在 4×4 = 128 位配置下，ASTC 4×4 LDR 和 BC7 的质量在同一水平（PSNR 差不到 1dB）。

### ASTC 的独特能力：可变块大小

这才是 ASTC 真正区别于 BC7 的地方——**ASTC 不只支持 4×4，它支持 14 种标准块大小：从 4×4（8bpp）到 12×12（约 0.89bpp）。** 块越大，每像素位数越低，体积越小，质量越差：

```
ASTC 块大小 → 每像素位数 → 2048×2048 纹理的体积
  4×4   →  8.00 bpp  →  ~4 MB      （与 BC7 同级）
  6×6   →  3.56 bpp  →  ~1.8 MB    （"不错的"默认）
  8×8   →  2.00 bpp  →  ~1 MB      （"能接受"的质量）
  12×12 →  0.89 bpp  →  ~0.5 MB    （明显有损）
```

> **位数的计算**：一个块始终占 128 位。4×4 有 16 个像素 → 128/16 = 8bpp。8×8 有 64 个像素 → 128/64 = 2bpp。

### "可变块大小"的工程价值

这个能力回答了 BC7 回答不了的一个问题：**"如果这张纹理对视觉质量不重要（比如远距离地形细节、光照贴图、阴影深度图），为什么要给它 8bpp？"**

BC7 只能给 8bpp，不想要也得要（或者降级到 BC1 的 4bpp——但 BC1 没有平滑 alpha，且颜色质量显著低于 BC7）。ASTC 的 6×6 在 3.56bpp 下就能得到"肉眼分不出和 4×4 区别"的质量；8×8 在 2bpp 下适合低优先级纹理——体积是 BC7 的 1/4，质量在大多数场景下仍然可接受。

**对引擎资源管线的影响**：ASTC 让"按纹理重要性分档压缩"成为可能——资产导入时，艺术总监把核心角色皮肤设成 4×4（零妥协），地面砖块设成 6×6（性价比最优），远山天空球设成 8×8（体积优先），阴影深度图甚至可以上 12×12。同一套压缩编码器，同一个 GPU 解码器，不同的块大小——这在 BC 家族里没有等价方案。

### ASTC 的代价

1. **编码极慢**：ASTC 的编码器要做大量的搜索（端点组合 × 分区选择 × 权重分配），高质量编码一张 4K 图可能要几秒到几十秒。这是离线资产管线的事情，不影响运行时。
2. **PC 独显支持不统一**：NVIDIA 和 AMD 桌面卡直到近年才加入 ASTC 支持，老旧 PC 硬件不一定有。移动端和设备端（Apple Silicon、手机 GPU）从 2014 年前后就开始广泛支持。
3. **HDR 模式是独立的**：ASTC HDR 和 ASTC LDR 是两个不同的子格式，不是所有支持 LDR 的硬件都支持 HDR。

---

## 问题 6：一张表要跑 PC + 手机 + 网页——每一份都单独压？KTX2 的解法

至此，你已经知道 BC7 是 PC 上的首选、ASTC 是移动端和跨平台的首选。但你的游戏要跑在 Steam（PC 独显 + 集显）、App Store（Apple GPU）、Google Play（Adreno + Mali）、甚至 Web（WebGL——通常只支持 BC1/BC3/ETC 等老格式）上。每张源纹理：
- 压成 BC7 → 只有 PC 能用；
- 压成 ASTC 4×4 → PC 老硬件不支持；
- 压成 ETC2 → 只有 Android 能用，iOS 不支持。

最 naive 的做法是：**每张纹理为每个目标平台各压一份，打包时分发。** 这能跑通，但维护成本是灾难——你的纹理包体积直接乘上平台数量。而且如果将来有新硬件格式（比如未来的神经纹理编码），所有旧资产要全部重压一遍。

**KTX2（Khronos Texture 2.0）就是为消灭这个灾难而设计的。**

### KTX2 的核心思路：存一份"通用中间格式"，运行时转码到目标格式

KTX2 不是你熟悉的"又一个压缩格式"——它是一个**容器（container）**。容器里不放像素数据本身，而是放一个**通用中间编码**——一种把所有主流 GPU 格式的共性提取出来的"超级块压缩"表示。

```
传统方案（每平台一份）:
  源图 → 压 BC7  → 打进 PC 包
  源图 → 压 ASTC → 打进 iOS 包
  源图 → 压 ETC2 → 打进 Android 包
  → 3 份压缩数据，3 份维护

KTX2 方案:
  源图 → 压成通用中间格式 → 装进 .ktx2 容器 → 运行时：
    PC 独显    → 转码到 BC7  （几乎无损，快）
    Apple GPU  → 转码到 ASTC （完全无损，零计算——中间格式本身就是 ASTC 子集）
    PC 集显    → 转码到 BC3  （有损，但可接受）
    WebGL      → 转码到 ETC2 （有损，但可接受）
  → 1 份通用数据，1 份维护
```

**KTX2 的中间格式**目前最主流的是 **Basis Universal** 系统（Google/Binomial 开源），内部有两个选项：

- **ETC1S**（低~中质量，约 0.3~3 bpp）：用 ETC1 的编码子集做基础，通过自定义 LZ 无损压缩进一步瘦身。适合体积敏感的移动端下发。质量不如 BC7/ASTC 4×4，但对漫反射贴图够用。
- **UASTC**（高质量，固定 8 bpp）：用 ASTC 4×4 LDR 的一个 19 模式子集做基础。因为它是标准 ASTC 的子集——**转码到 ASTC 4×4 完全无损（直接拷贝字节，零计算）**；转码到 BC7 质量几乎无损（PSNR 差 0.75~1.5 dB）。"U" 是 Universal 的意思——UASTC 就是"通用的 ASTC"。

更进一步的，KTX2 还支持对中间数据再做一次**超级压缩（supercompression）**——用 Zstd 或 BasisLZ 对中间块数据做无损再压缩，进一步缩小容器体积。这层超级压缩在 CPU 端解码（很快），然后才把解出来的中间数据送进 GPU 转码器。**超级压缩缩小的是 .ktx2 文件大小，不影响 GPU 上的最终格式体积。**

### KTX2 的工程角色：离线编码一句命令，运行时一行转码

```
离线（资产管线）:
  源图（PNG/EXR）→ basisu 编码器 → 输出 .ktx2 文件
  参数选择: ETC1S（小）或 UASTC（高质量）
  
运行时（引擎加载）:
  读 .ktx2 → 超级压缩解压（如果用了 Zstd） → 转码器输出原生 GPU 格式
  → 调一次上传 → 挂在插槽上 → Shader 查表照旧
```

转码这个过程是纯计算——不访存、不查表。在 UASTC → ASTC 的情况下甚至**零计算**（数据本身就是合法 ASTC 块）。UASTC → BC7 的转码在每个块上做一次轻量端点映射，开销可以忽略（通常放在加载线程上做完）。**用户感知不到任何延迟差异**——一张 4K 纹理的 UASTC → BC7 转码耗时在毫秒级。

### KTX2 还解决了什么问题

1. **开发迭代速度**：你不需要每次改纹理都跑 3 种编码器——只跑一次 UASTC 编码，所有平台自动覆盖。
2. **未来兼容**：将来出了一个新 GPU 格式（比如 NVTC、神经压缩），只需要写一个新的转码器后端，所有历史 .ktx2 资产自动受益——不用重压历史纹理库。这是"存中间表示"最大的长期价值。
3. **Mipmap 链路完整**：KTX2 容器天然存储完整金字塔——每个层级作为独立数据段编码，运行时转码器逐层输出。不是"压成 KTX2 之后再算 Mipmap"——Mipmap 在编码时就已经生成好、压进去了。

## 问题 7：压缩后的纹理还能开 Mipmap 吗？——"先算金字塔再压" vs "先压再生成金字塔"

4.3 建立了金字塔的完整认知：加载纹理后生成 1/2、1/4、1/8…… 的逐级缩小版本，每级用上一级做盒式过滤。那个流程以"源图是原始 RGBA 像素数组"为前提。

但压缩格式引入了一个新问题：**如果我的纹理已经压成了 BC7——也就是"4×4 块的端点对 + 权重索引"而非"逐像素 RGBA"——还能在这个压缩域上做盒式过滤生成金字塔吗？**

答案是**不能，也不能没必要。**

### 为什么不能在压缩域上做过滤

BC7/ASTC 存储的不是逐像素的 RGBA 值，而是块级编码。用一个已经压缩的 BC7 块做缩小时——你必须先把所有涉及到的块全部解码回 RGBA 像素，才能做盒式平均。这不是"把压缩表当输入、在 Shader 里做过滤"能解决的事——压缩域里两个块之间没有直接的"两个颜色的平均值"这个概念。两个端点对之间做平均，产生另一对端点——而这对新端点在块压缩的编码空间里可能根本就没有合法表示。

### 正确的做法：金字塔在编码前生成

```
正确流程：
  源图 RGBA (2048×2048)
    ├→ 盒式过滤 → 1024×1024 → 压缩  → BC7/ASTC 块（第 1 层）
    ├→ 盒式过滤 → 512×512   → 压缩  → BC7/ASTC 块（第 2 层）
    ├→ 盒式过滤 → 256×256   → 压缩  → BC7/ASTC 块（第 3 层）
    └→ ...
    → 所有层级装进一个 .ktx2 容器
```

**每层先在 RGBA 空间做高质量盒式过滤，再独立压缩。** 这是唯一保证金字塔质量的做法。如果偷懒"先压再生成"，就只能解压→平均→重压——多了一次质量损失（压了两次）。KTX2 容器的天生结构就支持这个流程——每个金字塔层级是容器里的独立数据段，编码器生成时已经自动处理。

### 压缩后的金字塔各层还能正确采样吗？

能。每个层级都是一个合法的 BC7/ASTC 纹理——GPU 纹理单元在切换金字塔层级时，直接跳到对应层级的压缩数据区域，用同样的硬件解码器读。块的寻址公式不变（(y/4) × (层宽度/4) + (x/4) 仍然有效，只是层宽高减半了）。

但有两点值得注意：

1. **块对齐**：每一层的分辨率必须被 4 整除（否则最后一排块不满 4 像素，编码器会拒绝或补齐）。所以金字塔生成时会自动把各层分辨率向上取整到 4 的倍数。
2. **最底层（1×1）质量**：常规金字塔最后一层是 1×1 像素——但块压缩的最小单位是 4×4。所以 1×1 层实际上是一个只用了"左上角 1 个有效像素 + 其余 15 个补齐"的 4×4 块。对实时渲染来说无所谓——选到最底层时画面本来就已经缩到不可辨认。

## 问题 8：法线贴图能用 BC7 压吗？——压缩格式的信息类型适配

4.5 讲了法线贴图——表里存的不是颜色，是切线空间的方向。这个方向有两个约束：**长度应接近 1**，**两个分量（X、Y）决定法线偏离平面的方向，第三个分量（Z）可以用 `sqrt(1 - X² - Y²)` 推导**。这两个约束让法线贴图在压缩时有一些特殊考量。

### BC7 压法线贴图：能用，但浪费

BC7 支持 RGBA 四通道——但法线只需要 XY 两个通道（Z 在 Shader 里推导）。BC7 把另外两个通道的位也存了，法线不能利用"双通道"的节省空间。而且 BC7 的块内颜色线段假设"三个通道共线"（R、G、B 在同一个颜色线段上）——但法线的 X 和 Y 的变化模式完全独立（X 的凹凸块和 Y 的凹凸块不重合），强制它们共线会让端点映射效率降低。不是不能用——画面质量损失一般在可接受范围内——但**不是最优选择**。

### BC5：法线贴图的天然格式

BC5 是专门为双通道数据设计的：存 X 和 Y 各一个独立通道，每通道 8bpp（总共 8bpp）——两条独立的颜色线段，高效利用。Z 在 Shader 里做 `sqrt(1 - X² - Y²)`。BC5 压的法线贴图体积和 BC7 一样（都是 8bpp），但法线质量更高——因为两个通道的端点搜索互不干扰。

### ASTC 压法线贴图：用块大小控制取舍

ASTC 支持任意通道数的端点编码，法线贴图在 ASTC 下没有 BC5 那样"专为双通道优化"的特殊模式。但 ASTC 的解决方案更简单：**法线贴图开 4×4（8bpp）就是最高质量，如果体积紧张可以降 6×6（3.56bpp）。** 手机端项目中，因为屏幕尺寸和人眼分辨率限制，ASTC 6×6 的法线贴图在视觉上通常看不出和 4×4 的差异。

### 粗糙度/金属度/高度图：单通道贴图的处理

这些"一个通道就够"的表——粗糙度贴图只有 R 通道、金属度贴图也只有 R 通道、高度图也是——理论上 BC4（4bpp，单通道）就足够了。但工程上常把粗糙度、金属度、AO（环境光遮蔽）打包进一张表的三个独立通道（R=粗糙度、G=金属度、B=AO），这样**一张 BC7 表同时承载三个单通道语义**——体积仍是 8bpp，但省了两张表。成本是 Shader 里拆包：`roughness = packed.r; metallic = packed.g; ao = packed.b;`。**频道打包（channel packing）** 是最大化压缩比的核心技巧——它不是压缩格式本身的能力，而是"怎么用"的策略。

## 收尾落地：块压缩格式在各图形后端中怎么表达

> 推导到此结束——你已经知道：GPU 不能用 PNG/JPG 是因为变长编码与固定速率随机访问的根本矛盾；块压缩用 4×4 固定块 + 端点插值来同时兼顾压缩与随机访问；BC7 是 PC 最高质量通用格式（8bpp），ASTC 是跨平台格式的核心优势在可变块大小（4×4 到 12×12）；KTX2 用"存一份通用中间格式 → 运行时转码"解决了多平台分发的灾难。下面是各后端的落地，纯文字、无代码，具体实现交给 AI 生成。

- **OpenGL**：块压缩格式在 OpenGL 里通过扩展支持——BC7 对应 `GL_COMPRESSED_RGBA_BPTC_UNORM`（以及 sRGB 变体），BC5 对应 `GL_COMPRESSED_RG_RGTC2`，ASTC 通过 `GL_KHR_texture_compression_astc_ldr` 扩展提供一整套内部格式枚举（覆盖所有块大小）。使用方式和普通纹理完全一样——创建纹理时内部格式指定为压缩格式枚举，上传数据时直接传压缩后的字节块（`glCompressedTexImage2D`）。OpenGL 不会帮你压缩——压缩是离线做的事；它只负责接收压缩数据、让纹理单元在采样时硬件解码。

- **Vulkan**：Vulkan 把格式支持查询做得更显式——创建纹理前先调用特征查询确认设备是否支持 BC7/ASTC/BC5 等格式（通过 `VkPhysicalDeviceFeatures` 或扩展支持查询）。支持后，纹理的内部格式设为对应的 `VK_FORMAT_BC7_UNORM_BLOCK` / `VK_FORMAT_ASTC_4x4_UNORM_BLOCK` 等枚举。上传时直接填充压缩字节，每一层的每一行以块为单位计算字节偏移（行宽 = `ceil(width/4) × 16` 字节）。KTX2 容器的解析和转码有 Khronos 官方的 `ktx` 库处理——读文件、解超级压缩、调转码器输出原生格式。

- **D3D12**：BC7/BC5/BC6H 等 BC 家族格式是 D3D12 的原生格式（`DXGI_FORMAT_BC7_UNORM`），在 PC 上不需要额外查询——只要设备支持 DirectX 11 Feature Level 就保证支持。ASTC 是从 D3D12 Feature Level 12.2 开始通过扩展支持的，老旧 PC 硬件可能不支持——需要按需查询。KTX2 的微软侧支持通过 DirectXTex 库处理。

- **Metal**：Metal 支持 ASTC 全系列（所有块大小）作为一等格式，因为所有 Apple GPU 原生支持。BC7/BC5 在 macOS 上通过 `MTLPixelFormatBC7_RGBAUnorm` 等支持（Apple Silicon Mac 全部原生）。Metal 不支持 ETC2 等 Android 格式。KTX2 容器在 Metal 端同样通过 `ktx` 库转码——UASTC → ASTC 转码是零成本（数据本身就是合法 ASTC）。

一句话对照：**块压缩格式在现代 API 里都是"一等公民"——不需要手动解压，不需要 Shader 里做特殊处理，上传时传压缩字节、采样时硬件自动解码。多平台的分发问题不是靠"每个平台压一份"解决的，而是靠 KTX2 的"存中间表示、运行时转码"来解决的——这和本模块的核心洞察（"存储格式 ≠ 采样格式"）是同一条规律在资源分发层的回收。**

## 总结：这篇笔记建立的核心认知

1. **GPU 不能用 PNG/JPEG 不是因为"GPU 不会解压"，而是变长编码与固定速率随机访问的根本矛盾。** GPU 纹理单元需要 O(1) 时间从显存定位并解码任意像素；PNG 的 DEFLATE 和 JPEG 的 DCT + 霍夫曼编码都依赖顺序解码和变长比特流，无法随机访问。

2. **块压缩的解决方案——4×4 固定块 + 固定位数 + 端点插值。** 把纹理切成 4×4 像素的块，每块压缩后占固定 128 位（16 字节），块内用少量端点色加权重索引来近似 16 个像素的颜色。固定块 = 直接地址映射（O(1)）；端点插值 = 压缩率 ≈ 4×。

3. **BC7 是 PC 的最高质量通用 RGBA 格式（8bpp）。** 内部有多达 8 种编码模式，自适应选择分区数和端点精度。对 4.5 的 5 表材质：从 80MB 降到 20MB。BC5 专为法线双通道优化；BC6H 专为 HDR 浮点格式；BC4 专为单通道。

4. **ASTC 是跨平台的"可变块大小"方案——同一套编解码器，从 4×4（8bpp，质量 = BC7）到 12×12（0.89bpp，低质量高压缩）。** 可变块大小让"按纹理重要性分档压缩"成为可能——核心角色用 4×4，远山天空球用 8×8。这是 BC 家族没有的能力。

5. **KTX2 不是又一个压缩格式，是解决多平台分发的容器。** 核心思路：存一份通用中间格式（UASTC / ETC1S），运行时转码到目标 GPU 原生格式——UASTC → ASTC 完全无损（零转码，因为 UASTC 本身就是 ASTC 子集）；UASTC → BC7 几乎无损。一份 .ktx2 覆盖所有平台。

6. **金字塔在压缩前生成——每层先在 RGBA 空间做盒式过滤再独立压缩。** 不能在压缩域上直接做过滤（块编码不存在"平均两个颜色"的直接操作）。KTX2 天然存储完整金字塔链，运行时转码器逐层输出。

7. **法线贴图用 BC5 而非 BC7、粗糙度/金属度/AO 打包进一张 BC7 的三个通道——这些是"格式选择策略"而非"格式本身的能力"。** 知道每张贴图的通道语义是多少、需要哪些通道、可以接受多大质量损失，才能做出正确的格式选择。

8. **本模块把纹理在显存中的工程组织推至完整形态。** 阶段四的前五篇建立了"表数据"和"查表方式"的全部机制——从单表颜色查询到多表材质。本模块补上了最后的拼图：**表数据本身的存储格式。** 纹理不再是"解码后的原始 RGBA 像素数组"——它可以是显存中的压缩块（BC7/ASTC），采样时硬件透明解码；也可以是 KTX2 容器里的通用中间表示，加载时按需转码。表是什么、怎么查、怎么存——三个维度至此全部闭环。

# Cubemap 与纹理数组："按方向查"和"按索引查"的成组纹理

## 问题 0：单张 2D 表的模型，有一类需求注定别扭

阶段四前六篇，你一直在打磨同一个模型：**一张 2D 四边形表，给它二维坐标，它返回一个值。** 颜色表、法线表、粗糙表，全是如此。这个模型极其好用，但它的查询坐标是 `(u, v)`——一个"贴在表面上、由顶点插值而来"的位置坐标。

现在请你想象一个简单到荒谬的需求：**画一个天空。** 相机往前看是蓝天白云，往上看是更高的天，往太阳方向看是耀眼的亮。这是一个包围了相机、360° 无死角的背景。如果你只用普通的 2D 表，会怎么做？

你把一张长方形的天空图"贴"到一个巨大的球或立方体内部表面上——就像把图片贴到任何物体表面那样。这当然能画出来，但你会立刻撞上一个**方向不对**的别扭：查询这张表，需要一个 UV，而 UV 是"贴在表面上某个位置"的坐标，是由顶点带来的。对天空来说，我们心里真正想说的是"**相机往东偏上 30° 看，那一片是什么颜色**"——这是一个**方向**，不是一个表面位置。

> **本质问题一：有一类查询，输入的天然形态是"方向"而不是"表面上的位置"。如果每画一个方向都要先把方向换算成某个表面的 UV，这个换算本身就是错的杂音——为什么不能直接拿着方向去查？**

这个别扭，就是 Cubemap 登场的入口。

---

## 问题 1：怎么让"拿方向查"成为一个自然的操作？——把六张表粘成一只盒子

先别急着想 API。站在"信息结构"的角度问：**如果我要支持"给我一个方向，返回颜色"，我需要一张什么样的表？**

方向是一个三维向量——从相机出发、往东偏上 30°，就是一个 `(dx, dy, dz)`。任何一个方向都逃不出六个大类：基本朝 +x、−x、+y、−y、+z、−z。于是最自然的破法出现了：

**把方向按其最接近的坐标轴，归入六个大类之一；每一类对应一张普通的 2D 表。** 这样一来，"方向"这个三维输入被拆成两步：**先选面，再在面上查二维位置。**

想象一只空心立方体，你站在它的正中心。你往六个方向看，前、后、左、右、上、下——看到的就是六个面，每个面你用一张 2D 图把它铺满。现在你随便指一个方向，这条视线自然会射中立方体的某个面、射中那个面上的某个点——所以"方向"和"六个面各自的一个点"是一一对应的。**这只立方体贴图的六个面，就构成了一张全新的表：输入一个方向向量，输出那个方向的颜色。** 这就是 **Cubemap（立方体贴图）**——名字很直白，它真的就是"贴成一只立方体的地图"。

```
查询逻辑（Cubemap，思想层面）：

输入：一个方向向量 d = (dx, dy, dz)

步骤1  选面：看 d 的哪个分量的绝对值最大。
        |dx| 最大且 dx>0 → +x 面；dx<0 → −x 面
        |dy| 最大且 dy>0 → +y 面（天顶面）…
      （即 d 更朝向哪一面）

步骤2  定坐标：把方向"压"到选中那面上，得到面上的二维坐标 (u, v)。

输出：查那个面上的 2D 表，取 (u, v) 处的颜色。
```

> 步骤 2 里"把方向压到面上"的细节（面内坐标怎么从 d 的两个横向分量算出来、六面各自的朝向约定）是一套约定俗成的 2D→方向映射，GPU 硬件直接按这套约定做。你不需要记那套坐标换算——**只需抓住它做了什么：方向向量 → 选面 + 面上二维坐标 → 查表。** 这套换算正是 Cubemap 专属的"查表方式"，和过滤、寻址、金字塔一样，是可以独立决策的那个维度。

回想 4.1 的一个关键结论：**纹理 = 数据 + 查表方式。** 对 Cubemap，"数据"是六个面的 2D 表；"查表方式"不再只是过滤/选层/寻址，而是多了一个**"按方向选面并定坐标"**的前置步骤。这是它和普通 2D 表唯一的本质差别——除此之外的一切（过滤、Mipmap、压缩）都照旧，只是每个面各自是一张表、各自有自己的金字塔。

> **值得停下来确认的一点**：Cubemap 本质上还是"一组 2D 表"——六个面。但它不是"六张独立表"，而是"一只逻辑上不可分割的盒子"。为什么？因为**它的查询语义（拿方向去查）是建立在"六个面粘成一只立方体"这个**整体**之上的**——把六个面拆开各自单独用，就失去了"选面"这个机制，也就不再是 Cubemap 了。这个"粘成整体才有语义"的点，等一下对比纹理数组时会再次出现，是理解"成组纹理"的关键。

## 问题 2：天空盒——Cubemap 的第一个、也是最直观的用途

有了 Cubemap，"画天空"就变成了一件四两拨千斤的事。

你要的不是"把一张图贴到某个物体表面"，而是"让背景等于 Cubemap 在每个像素方向上返回的颜色"。

- 相机锥裁剪体内部有一片永远不移动的"远背景"——它贴着相机走，相机转头它也转头（因为背景是无穷远的）。
- 每个像素该显示什么颜色？**取"从相机出发、穿过这个像素的方向向量"，拿它去查 Cubemap。** 像素在屏幕左上角，对应相机往左上方看的方向，查出来就是那一片天空。

于是"画背景"和"画任何物体"分开了：你只需要画一个**足够大、完全包住相机的立方体（或球）**，对它的每个像素，你不去管它表面本来该算个啥，而是直接**用它的位置（当作方向向量）去查这张 Cubemap**。

```
天空盒（思想层面）：

把一只大立方体放在相机位置，六面贴成 Cubemap。
对立方体表面的每个像素：
  它的"位置"在立方体顶点阶段就带着一个方向语义（相对盒子中心的方向）
  片段阶段 → 拿这个方向查 Cubemap → 直接作为像素颜色输出（通常不参与光照）

相机在盒子里 → 盒子包裹住整个视野 → 像素颜色 = 对应方向的天
```

这里有一个常被初学者绕晕的细节，值得点破：**"天空盒"和"Cubemap"是两回事。**

- **Cubemap 是一张表**（数据 + 查法），它这个"按方向查"的能力，可以服务任何需要"按方向取环境"的场合。
- **天空盒是 Cubemap 的一个用法**——用一只盒子+贴它的 Cubemap，把无穷远背景填充出来。天空盒是"消费 Cubemap 的一个对象"，不是 Cubemap 本身。

为什么非要区分？因为**同一个 Cubemap 后面还会被别的消费者用**。一张装着"傍晚天空"的 Cubemap，既能被天空盒用来当背景，又能在未来被当作环境光（阶段九：把整张天当成光源，漫反射辐照度、高光预滤波都要从 Cubemap 采样）、被点光源阴影使用（阶段八：从光源向六个面各渲一张深度，正是六面 Cubemap）。**Cubemap 是个数据；它"是谁的背景"是别的东西决定的。** 分清数据与消费者，是工程上不写死资产的关键。

> 一个小坑，知道即可：天空盒用的"立方体顶点位置当方向"这个把戏，依赖盒子以相机为中心——所以画天空时通常不套相机的模型变换，只套视图和投影，保证盒子永远罩在相机上，不会跟着场景缩放平移而穿帮。这就是 4.1 里"接缝要藏、计算要对齐坐标系"那种资产/几何一致性问题，不是新的概念。

## 问题 3：另一类别扭——一大批贴图各用一个插槽，draw call 成堆

Cubemap 解决了"方向查询"。现在看第二种成组的需求，它来自反方向的生活经验。

想象你在做粒子系统：屏幕上同时有 100 种不同贴图的粒子（火花的火星、烟雾的团、光尘的颗粒、花瓣的瓣……）。4.5 已经告诉你：**每张表占一个插槽，插槽有 16~32 个上限。** 100 种贴图，插槽一下子就爆了。

退一步，就算插槽够——问题是 **draw call**。一段逐像素程序（一个材质）对应一组绑定好的插槽。你想让 100 种粒子在一帧里都画出来，而每种粒子贴图不同，你就得：画火花 → 换挂火花贴图 → 画烟雾 → 换挂烟雾贴图 → 画光尘……**每换一次贴图，往往就是一次新的绘制命令**。100 种粒子 = 至少 100 次绘制命令。而粒子、贴花、草地这类对象，单次绘制工作量极小，CPU 端提交命令反而成了瓶颈。这正是引擎 5.6 渲染队列要解决的"按材质分组、减少换挂"难题在粒子上的爆发。

> 这里的本质问题和 4.5 一样：**插槽有限、换挂有代价。** 但 4.5 的答案是"按材质分组、尽量少换"，而粒子/贴花这类"上千个对象、各自不同贴图"的场景，靠"分组"救不回来——组还是太多了。

于是问题浮出来：~={red}**能不能让"一批不同的贴图"成为一个整体，用**一次绑定、一条绘制命令**，同时让着色器想拿哪张就拿哪张？**=~

## 问题 4：两种"成组统一"的路线——拼图（图集）与叠层（纹理数组）

"把多张表变成一个整体、一次绑上去"这个需求，有两套古老而截然不同的思路。它们的差别，正好对应你心里那个"别扭"的本质。

### 路线 A：图集（atlas）——把很多小图"拼"进一张大 2D 表

最直觉的思路：**把 100 张 128×128 的小图，离线拼成一张 1024×1280 的大图。** 画的时候只绑这一张大表，每个粒子用自己那块区域：给每个对象多带一个"这块区域在哪"的偏移，采样时换算成在大表里的坐标。

```
图集（思想层面）：

把 100 张小图拼成 1 张大表：
┌────┬────┬────┬─...─┐
│ 火花│烟雾│光尘│ 花瓣│ ...（每格是一张 128×128）
└────┴────┴────┴─...─┘

每个对象带一个"格号"（这块区域在大表里的偏移）
采样：UV' = 基准坐标 × 格范围 + 大表里的格起点
```

这个方案的好处非常现实：**它没有引入任何新的 GPU 机制**——还是一张普通 2D 表，还是原来那套查表方式，只是"拼"在了离线。对不支持新特性的老平台（比如老手机 GPU），这是唯一能跑通的路线。

但它有代价，而且不止一个：

1. **所有小图被迫尺寸一致**（否则拼不齐、浪费或需要对不齐），但工程里粒子的贴图尺寸千奇百怪；
2. **边界串色**：图与图之间只有缝没有缓冲，采样过滤或选金字塔层时，边缘会"吸"到隔壁格子的颜色，必须离线加一圈 padding 来防；
3. **整张表只有一份金字塔**：离远看时整张表一起缩小，你无法对每一格单独控制 mipmap 层级；
4. **格式被平均化**：压缩时一张大表只能用一种格式和一种质量策略，没法让主角的清晰、远景的省显存各取所需。

### 路线 B：纹理数组（texture array）——把多张表"叠"成一个新维度

另一条路更彻底：**不说"拼成一张大表"，而是说"这些表本来就是一组平行的 2D 表"。** 让 GPU 支持一个"数组纹理"——它像一个 2D 表的书架，每层是一张完整的 2D 表，你查表时除了给二维坐标，**再给一个"第几层"**。

```
纹理数组（思想层面）：

一个"层叠的 2D 表"：
层0: [火花图 128×128]
层1: [烟雾图 128×128]
层2: [光尘图 128×128]
  ...
每层是一张完整的 2D 表，所有层共享同一份"查表方式"配置。

查询：坐标 (u, v) + 层号 index
      ↓ ↓        ↓
输出：第 index 层、坐标 (u,v) 处的颜色
```

每个对象照样带一个"层号"（我就是第 3 层火花），但这次它不是"偏移换算"，而是**查询坐标本身多了一个维度**——从二维 `(u,v)` 变成了 `(u,v,index)`。

对比一张"大拼图"，纹理数组的查询语义其实是**更诚实**的：你说的本来就是"100 张独立的小表"，不是吗？图集是"我把它们硬塞进一张大表凑合一下"，纹理数组是"GPU 天生把 100 张表当成一个整体管理"。这是两个不同层面的答案——一个靠改变数据摆放（拼图）、一个靠改变查询坐标的结构（加维度）。

## 问题 5：两个方案到底怎么选？——"尺寸一致性"与"整组共享一套查法"是纹理数组的命门

到此不该再罗列两条路的镜像了。真正值得你停下来想清楚的是：**任何一个方案都是"给什么、换什么"，纹理数组把什么换掉了？**

先说它拿来的好处，它天生解决图集的四个痛点：

1. **每层可以是任意独立分辨率**（虽然通常仍建议一致，但不受拼图对齐的强迫）；
2. **层与层天然隔离、不会串色**——没有"拼"这个动作，也就没有边界问题；
3. **每层都有自己的金字塔**，离远某层该选几层级，是独立、正确计算的；
4. **每层 / 整组可以正常走压缩**，质量策略比"一张大表统一"更灵活。

那它拿走的、付出的代价是什么？这才是选型的核心：

**代价一：所有层共享同一套"查表方式"配置。** 数组纹理把"一组表"当成一个对象，意味着过滤、寻址、金字塔这些查表参数是对**整组**生效的，不能给第 0 层一个采样参数、第 3 层另一个。对"都是粒子贴图、查法本来就该一致"的场合，这是合理的约束；但对"混装各种性质的表"就束手束脚。

**代价二：限制了"每层尺寸不同"的自由度，换来的是统一管理。** 工业界实际几乎总是要求每层尺寸相同——这不是强制的，而是因为我们想让数组同时支持 Mipmap 的整齐层级，以及让硬件批处理更规整。结果就是：**想要"一组大小一致的表 + 统一查法 + 一起走索引查"，用数组；想要"大小乱、性质杂"的拼盘，用图集或单独的合成技术。**

**代价三（最容易被忽略）：纹理数组没有解决"插槽"问题，它解决的是"一条绘制命令里换表"的问题。** 一张数组纹理仍然只占 *一个* 插槽——但它把"100 张表"浓缩进这一个插槽。你不再需要"画一种粒子就换一张表"，而是"一次绑定这个数组，然后给每个对象发一个层号"。**这是把"换表"从"配置切换"降级成了"一个普通数据"**——层号可以像颜色、大小一样作为每个粒子的普通属性走起来，这让"上千个不同贴图的粒子一次画完"成为可能。这就是它和合批、GPU-Driven 产生化学反应的根源。

> 一句话把两套方案钉死在各自的适用域：
>
> - **图集**：离线拼好、机制零新增、老平台兼容——但它牺牲了"每张独立"（尺寸、金字塔、格式、查法全被平均化）。
> - **纹理数组**：GPU 原生支持"一组表 + 索引查"——但它要求"尺寸一致 + 共享查法"，用"整组统一"换"每张独立"。
>
> 工业界（尤其 3D 场景里不拆的材质、粒子、贴图池）普遍**优先纹理数组**，因为它把"选哪张表"变成数据、能支撑合批与 GPU-Driven；图集则作为"老平台、跨平台兼容、尺寸杂乱素材"的兜底。**两者不是谁取代谁，而是针对"素材是否规整、目标平台是否现代"的两个答案。**

在你心里把这套权衡和 4.2 的插槽模型接上：插槽上限是"同时能挂多少组表"的硬约束，纹理数组是把"一组表"当成"一张表"来用、从而塞进*一个*插槽——它是 4.5"插槽不够怎么办"的直接延伸，也是通往阶段十二合批（DrawCall 合并）和 GPU-Driven（把"画哪个"的决定也搬去 GPU）的必经之路。

## 问题 6：Cubemap 与纹理数组的距离——以及"采样时的层级选择"为什么在这里一起讲

Cubemap 和纹理数组，一个是"方向查面"，一个是"索引查层"，看起来八竿子打不着。为什么阶段四把它俩放在同一篇？因为有一个共同的、而且这俩恰好互补的逻辑你没漏看：

**它们都在给"2D 查询表"增加一个组织维度。**

- 普通 2D 表：2D 坐标 `(u,v)` 查一个值。
- Cubemap：3D 方向先选面、再查面上的 2D 坐标——本质是"**把 3D 方向折叠成 (面, u, v)**"。
- 纹理数组：2D 坐标 + 一个"层号"——本质是"**(u, v) + index**"。

而**层级选择（选金字塔第几层、采样时按什么距离挑 LOD）**，在这两类"成组纹理"上会遇到一个 4.3 单表时代没有的新问题：

**单张表时，选层级只取决于"一个像素盖几个纹素"**（4.3 的脚印）。而数组纹理按层查，`(u,v)` 落在不同层上、那个层各自的纹素密度不同，该选哪层级就*独立*由这一层自己算——好在 GPU 对数组纹理也是这么做的：每一层都能有自己的可分离金字塔选择。**Cubemap 则更特殊一点**：它不光要有二维的金字塔，还有个独特的"过滤次序"问题——在面上过滤、还是在面与面的**接缝**上过滤也一样要平滑。因为 Cubemap 是六张表拼成一只盒子，采样到盒子棱上时会横跨两个面，硬件要保证跨面的双线性过滤也是连续的。这个"跨面的连续性"是 Cubemap 采样器专门处理的一部分"查表方式"。

> 一句话：**成组之后，"选哪一层"不再是"整张表统一一个脚印"来决定，而是由"所选的那个面/那层"自己的金字塔独立决定；Cubemap 还多了"跨面过滤要连续"这一层要处理的查表方式。** 概念上不新，但这是把 4.3 的查表方式模型搬到"成组"后的完整形态，所以放这一篇讲。

## 收尾落地：这两类"成组纹理"在各图形后端中怎么表达

> 推导到此结束——你已经知道：Cubemap 是一组 6 张 2D 表、以"按方向选面再查"为查表方式的数据；天空盒只是它的一种消费方式；纹理数组是把"一组尺寸一致的 2D 表 + 索引"做成一个对象的机制，靠"把换表降级成数据"支撑合批。下面是各后端的落地，纯文字、无代码，具体实现交给 AI 生成。

- **OpenGL**：Cubemap 是一个纹理对象，创建时声明它有 6 个面；普通采样靠方向向量，skybox 效果通常在顶点阶段传盒子位置当方向给片段采样。纹理数组是另一个纹理类型（一维或二维数组），创建时声明层数，采样坐标里多一个层号分量。两者都只是"一个纹理对象 + 一个多维坐标"，和 4.2 的插槽模型完全兼容。
- **Vulkan**：数据侧是 `VkImage`（声明 `cube` 或 `arrayLayers`），"怎么读"由 `VkImageView` 决定——同一个数据可以只当普通 2D 看、也可以按 6 面 Cubemap 看、也可以按数组看；`VkSampler` 负责查表方式（含跨面过滤、各层金字塔）。这和 4.1 说过的"数据 / 怎么看 / 怎么查"三分离完全一致——成组只是在这些维度上各加了一个选项。
- **D3D12**：Texture2DArray 与 TextureCube 是资源维度的类型，配 SRV 描述符声明维度与层数解析方式、Sampler 描述符声明查法。层次/面数在资源创建和描述符里各出现一次，结构同样是"数据 + 怎么看 + 怎么查"。
- **Metal**：`MTLTexture` 有 `textureType`（如 `typeCube`、`type2DArray`）声明类型，采样时用配合的方向/层坐标。分离思路与现代 API 一致。

一句话对照：**Cubemap / 纹理数组不是新的"资源种类"，而是"同一套表资源在'数据维度'上加了一个组织选项"——OpenGL 用类型把"成组"打包进一个纹理对象，现代 API 则在数据（怎么存）与视图/描述符（怎么看）、采样器（怎么查）上分别体现这个"成组"**，因为现代 API 想让"存的是什么""按几面看""怎么过滤"能各自独立决策。对学习阶段的你，记一个心智就够：**`Cubemap ≈ (6 面 2D) + 方向查法`、`纹理数组 ≈ (N 层 2D) + 索引查法`，其余全部复用阶段四已有的模型。**

## 总结：这篇笔记建立的核心认知

1. **Cubemap 的本质是"按方向查"的表**：输入方向向量，先按最大分量选六个面之一，再在面上查二维坐标。它与普通 2D 表的唯一本质差别是查询坐标从"表面位置"变成了"方向"；过滤/寻址/金字塔仍各有独立的一份（只是多处理"跨面连续"）。**Cubemap 是六张表粘成一只逻辑整体才有语义**——拆开就失去"选面"机制。

2. **天空盒 ≠ Cubemap**：天空盒是"消费 Cubemap当背景"的一个用法（大盒子 + 用位置当方向查）；同一张 Cubemap 未来还能当环境光（阶段九 IBL）、点光源阴影（阶段八）来用。分清"数据"与"消费者"，资产才不会写死。

3. **图集 vs 纹理数组，是"改数据摆放" vs "改查询坐标结构"**：图集把 100 张小图离线拼进一张大表，机制零新增、兼容老平台，但尺寸/金字塔/格式/查法全被平均化，还有边界串色；纹理数组让 GPU 原生管理"N 层平行 2D 表"，每层独立金字塔、不串色、可压缩，但要求尺寸一致 + 整组共享查法。

4. **纹理数组把"换表"降级成"传一个值"**：一个数组只占一个插槽，选择"第几张"变成每个对象的普通属性——这正是它成为合批与 GPU-Driven 地基的原因（阶段十二）。选型口诀：素材规整且平台现代用数组，素材杂乱/老平台用图集。

5. **成组纹理改变了"层级选择"的答案**：选哪层由"所选那个面/那层"自己的金字塔独立决定；Cubemap 还得保证采样跨面时过滤连续。

6. **它是"单 2D 表 → 给表加组织维度"的收尾**：普通表 2D 坐标；Cubemap 加"方向折叠成面"；数组加"层号"。阶段四至此，你从一张颜色表的"查表方式四维度"，升级到了"表可以成群、成群后的查询坐标会变"——这个"改变坐标结构"的觉知，是幕二（后处理、阴影读别的像素）和阶段十二（合批、GPU-Driven）多次要重复用到的思路。

留下一个自然的衔接：纹理带来了 alpha 通道——像素不只有颜色，还有"不透明度"。一旦像素半透明，深度缓冲"谁在前挡住谁"的简单假设就崩了：先画谁、后画谁，结果完全不同。这就是阶段五——单 Pass 世界的边界——即将崩塌的开始。

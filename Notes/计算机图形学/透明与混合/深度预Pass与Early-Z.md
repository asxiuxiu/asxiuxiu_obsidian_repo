# 深度预 Pass 与 Early-Z

## 开场：物体没多几个，帧率为什么掉得这么狠？

你在 5.1 里已经能把不透明物体和透明玻璃画对了。现在往场景里加东西：一面墙、几棵树、一堆箱子，最后把整条走廊的地面铺满。

结果：帧率掉得吓人。但奇怪的是，屏幕上的可见几何并没有增加多少——从相机看过去，还是一面墙、几棵树。

问题不在"画了几个物体"，而在**每个像素被画了几次**。屏幕上的像素数固定（比如 1920×1080 约 200 万个），但一帧里片段着色器实际执行的次数，可能是像素数的好几倍：远处的箱子先画，像素算了光照写进画面；近处的墙后画，深度测试通过，把箱子的颜色覆盖掉——**箱子那几百万次着色计算，最终一个像素都没留下，全是白算。**

"一个像素在最终定稿前被反复着色、只有最后一次能看见"——这件事有个名字，叫 **overdraw（过度绘制）**。它的量级因场景而异：简单场景平均每像素画 1.5~2 次，复杂场景 3~5 次，极端情况（大量透明叠加）超过 10 次。在"往画面里写像素的速度"（填充率）受限的硬件——尤其是移动端——上，overdraw 直接决定帧率。

> 核心矛盾：**深度测试能保证"画对"，但保证不了"不浪费"。** 本篇要解决的，就是"浪费"。

---

## 问题 1：被挡住的像素，能不能干脆不算？——Early-Z

先看现在的不透明物体是怎么画的。回想 [[Notes/计算机图形学/GPU编程基础/用Shader表达逐像素计算|用 Shader 表达逐像素计算]]：片段着色器为每个像素算颜色，算完再决定写不写。结合深度测试，完整流程是：

```
传统流程（深度测试在着色之后）：
for 每个被光栅化的像素：
    片段着色器执行——算光照、采样纹理，输出颜色   ← 贵
    深度测试：这个像素比缓冲里已有的深度更远？
        是 → 丢弃（白算了上面的着色！）
        否 → 写入颜色 + 深度
```

注意顺序：**先着色，后测试**。也就是说，一个明明会被遮挡的像素，也要先跑完整个片段着色器，再在最后一步被扔进垃圾桶。overdraw 的全部浪费，就发生在这里。

硬件厂商早就看到了这个问题，解决方案是在硬件里把顺序换一下：

```
Early-Z（深度测试提前到着色之前）：
for 每个被光栅化的像素：
    深度测试：这个像素比缓冲里已有的深度更远？
        是 → 直接丢弃（片段着色器根本不执行）
        否 → 片段着色器执行
            写入颜色 + 深度
```

关键差别：被挡的像素**从头到尾没有启动片段着色器**。这个"跳过"比想象中更值钱——着色器执行前，GPU 要为它分配线程资源、加载上下文、调度到计算单元，这串启动链路本身就有固定开销。哪怕你在着色器第一行写个"被挡就返回"，启动链路也已经走完了。**Early-Z 省的是整条链路的钱，不是一次计算的钱。**

> [!warning] 但 Early-Z 有两个前提条件，缺一个就自动降级回"先着色后测试"
> 1. **片段着色器不能把像素主动扔掉**——比如纹理里完全透明的部分（树叶的镂空），如果着色器会丢弃这类像素，GPU 就不知道"这个像素最终到底写不写深度"，只能先着色再判断，Early-Z 被迫关闭。
> 2. **片段着色器不能修改深度值**——如果着色器会改写自己像素的深度，那"测试时的深度"和"写入时的深度"不是同一个数，测试就失效了。
>
> 这两条不满足时，硬件会悄悄退回传统流程——**没有任何报错，只有性能凭空变差。** 这是 Early-Z 最阴险的地方。

但 Early-Z 还有一个更隐蔽的大前提，直接引出下一篇的核心问题：**深度缓冲里得有"对"的深度可供测试。** 深度缓冲是空的呢？

## 问题 2：深度缓冲"没装满"，Early-Z 使不上劲——顺序是关键

想象一个乱序绘制的场景：远处的大山先画，近处的箱子后画。

大山画的时候，深度缓冲里还是初始值（无穷远）——大山每个像素的深度测试都**通过**，全部老老实实执行了着色器，写进深度。等箱子后画，箱子的深度比大山近，测试通过，覆盖。**大山几百万次着色，一个像素没留下**——Early-Z 呢？它在场，但帮不上忙：大山测试时，缓冲里没有更近的深度可以拒绝它。

换个顺序：箱子（近）先画，大山（远）后画。这次轮到 Early-Z 立功：大山测试时，缓冲里已有箱子的近深度，大山像素全被拒绝，着色器一个都没跑。

结论很朴素：**Early-Z 的威力，取决于"正式绘制时，深度缓冲里已经装了多少正确的深度"。** 而深度缓冲是"边画边填"的——乱序时，它大部分时间处于"只填了一半"的残废状态。

于是第一个改进是自然的：**不透明物体从前到后画**（近的先进深度缓冲，远的被 Early-Z 拒绝）。这和 5.1 透明物体"从远到近"正好相反——**不透明前到后（省算力），透明远到近（保正确）**，两套顺序服务两个完全不同的目标。

但"从前到后排序"有两个缺陷：

1. **排序是"按物体"的近似**——一个巨大的建筑横跨半个屏幕，先画它的话，它背后的所有东西都被它挡住，Early-Z 全效；但它的**内部**三角形之间照样乱序，自遮挡的部分照样白算。
2. **更致命**：即使排对了序，正式绘制开始时，深度缓冲里仍然**什么都没有**——第一个物体画的时候，Early-Z 依然是废的，只是"轮到第 N 个物体时"缓冲才越来越满。

能不能……在正式绘制开始之前，就把深度缓冲**全部装满**？

## 问题 3：把"写深度"单独抽出来先跑一遍——深度预 Pass

方案：把"写深度"这件事从正式绘制里拆出来，先单独画一遍。这一遍的片段着色器几乎不干活（不需要算颜色），只把每个像素的深度写进缓冲。画完这一遍，深度缓冲里就是**所有不透明表面的最终深度**。

```
Pass 1（深度 Pass——只写深度，不画颜色）：
for 每个不透明物体：
    顶点变换 → 光栅化 → 深度测试 → 写入深度（片段着色器不输出颜色，几乎零开销）
    # 结束条件：深度缓冲 = 所有不透明表面"离相机最近的那个"的深度，一个像素都不差

Pass 2（正式 Pass——正常画所有东西）：
for 每个物体：
    顶点变换 → 光栅化 → Early-Z 测试 ← 深度缓冲已满！被挡像素直接丢弃
        片段着色器执行（只对"最终可见"的像素执行）
        写入颜色 + 深度（深度测试仍开着，用于像素级正确性）
```

这一招有个名字：**深度预 Pass（Z-Prepass / Depth Prepass）**——"预"字说的就是"把深度准备工作提前到正式绘制之前"。对比一下两次绘制时深度缓冲的状态：

```
没有深度预 Pass：深度缓冲边画边填。第 1 个物体画时缓冲是空的，Early-Z 废掉；
                越往后缓冲越满，但每个物体都贡献过"白算"的像素。

有深度预 Pass：   Pass 1 结束时，深度缓冲已是完整状态；
                 Pass 2 从第一个物体开始，Early-Z 就满负荷工作。
```

**代价必须说清楚**（这是 trade-off，不是免费的午餐）：

| 新增开销 | 换来的收益 |
|---|---|
| 几何处理跑两遍：顶点变换 + 光栅化 ×2 | 片段着色器只对"最终可见"像素执行，overdraw 从 3~5x 降到 ~1x |
| CPU 绘制命令数量翻倍（每个不透明物体发两次） | 片段着色器的执行次数（通常是最贵的部分）大幅下降 |
| 深度缓冲的读写带宽翻倍 | 光照、纹理采样这些重活不再被浪费 |

**什么时候值，什么时候亏**——判断标准就一句话：**省下的着色成本，能否盖过多付的几何成本。**

- ✅ **值**：复杂光照 + 高 overdraw 场景（室内、植被密集、移动端带宽敏感）。此时片段着色器每执行一次都很贵，能被 Early-Z 挡掉一半以上，血赚。
- ❌ **亏**：顶点极其密集的模型（细分曲面、布料网格）+ 着色很轻（纯色）。此时多跑一遍顶点变换和光栅化的钱，比省下的着色钱还多；更糟的是 CPU 命令翻倍，可能撞上 CPU 提交瓶颈。
- ❓ **拿不准**：用抓帧工具（[[Notes/计算机图形学/光照与数据流/Shader调试工具链|Shader 调试工具链]]）看 overdraw 热力图——如果大部分像素只被画了 1 次，深度预 Pass 纯粹是浪费；如果大面积 3 次以上，值得加。

> [!tip] 进阶技巧（了解即可）
> 深度预 Pass 后，正式 Pass 的深度比较可以设为"**深度相等才画**"：既然 Pass 1 已经把正确深度写好了，正式 Pass 只画"深度恰好等于缓冲里那个值"的像素——也就是自己表面。这样 Early-Z 完全生效，还能顺手关掉正式 Pass 的深度写入。代价是深度精度必须两次绘制完全一致（用同一套投影矩阵），深度压缩或偏移会破坏"相等"判断。UE 和 Unity URP 的默认不透明流程就是这么干的。

## 问题 4：深度预 Pass 怎么顺带帮到透明？——排序变得更简单了

5.1 留下的透明排序有个麻烦：透明物体排序时，到底要不要管"不透明物体"？

回顾 5.1 的结论：透明物体**关深度写、开深度测**。深度测试的参照物是深度缓冲——里面是已经画好的不透明物体深度。所以玻璃在墙后时，玻璃像素的深度测试失败，被丢弃，混合根本不会发生——**透明和不透明的遮挡，本来就是深度缓冲在裁决，透明排序从来不需要管不透明。**

深度预 Pass 把这件事做到了极致：

- 没有深度预 Pass：不透明物体"边画边填"深度，透明物体只能等不透明全部画完才画——此时深度缓冲才"满"。
- 有深度预 Pass：透明物体正式绘制时，面对的深度缓冲**从第一帧起就是完整的不透明深度**。透明与不透明的遮挡关系 100% 由深度缓冲裁决，透明排序退化为**只在透明物体内部比远近**——排序的集合变小、逻辑变纯粹，不需要任何"不透明物体在哪一步画"的协调。

渲染队列从 5.1 的两段变成三段，每一段的职责清晰到一眼能看懂：

```
1. 深度 Pass：   只写深度（不透明物体，任意顺序）
2. 不透明 Pass： 正常画不透明物体，Early-Z 满负荷（被挡像素直接丢弃）
3. 透明 Pass：   画透明物体，测深度、不写深度，透明内部远到近排序
```

> 一句话：**深度预 Pass 用一次廉价的"深度铺底"，同时喂饱了不透明（Early-Z）和简化了透明（排序范围收窄）。**

## 问题 5：Early-Z 什么时候悄悄失效？——失效清单

Early-Z 是硬件自动优化，**它失效时不会报错**，只能靠性能波动和抓帧工具发现。失效的常见原因，对照问题 1 的条件逐条看：

| 失效原因 | 为什么失效 | 典型场景 |
|---|---|---|
| 片段着色器主动丢弃像素 | GPU 无法预知像素最终是否写深度，必须着色后再判断 | 树叶/草地镂空贴图 |
| 片段着色器修改深度值 | 测试用的深度和写入的深度不一致 | 特殊特效、水岸线压平 |
| 深度测试被关闭 | 没有测试，自然没有提前拒绝 | 纯 2D 叠加、特殊合成 |
| 非标准深度比较模式 | 硬件对"小于通过"模式才做提前优化 | 反向深度、遮罩 |
| 半透明混合 | 混合必须所有像素都执行（它没有"被挡"概念，只有"部分挡"） | 所有透明物体 |

前两条尤其阴险：它们往往藏在"看起来很正常"的材质里。比如你用一张带 alpha 通道的贴图做树叶——镂空部分需要丢弃像素——**整棵树的 Early-Z 全部关闭**，overdraw 直线上升。这在工程里叫"透明（alpha 混合）可以靠排序，镂空（丢弃像素）会杀死 Early-Z"，是移动端植被渲染最大的坑之一。

怎么发现：用抓帧工具看 overdraw 可视化——如果某块区域被画了 5 次以上，先怀疑某个材质悄悄关闭了 Early-Z。

## 落地表达：这些机制在渲染器里怎么组织

推导到这里，方案已经完整：**早测（Early-Z）+ 预铺深度（深度预 Pass）+ 队列三段化。** 现在看它在后端和引擎里长什么样。

**Early-Z 不是 API 对象，是硬件行为**——API 能做的只是"别挡它的路"和"显式声明偏好"：

- **OpenGL** 全隐式：驱动根据当前状态（深度测试开关、比较模式、着色器行为）自动决定启用还是降级，开发者只能从性能上感知。
- **Vulkan / D3D12** 允许在管线创建时**显式声明**对"早期片段测试"的偏好（能否生效取决于硬件能力与着色器行为），把"我想要 Early-Z"从驱动猜测变成开发者意图。
- **Metal** 类似，深度状态在渲染描述里配置，着色器行为决定实际效果。

**深度预 Pass 不是 GPU 机制，是 CPU 渲染队列的组织决策**：它就是引擎 [[Notes/SelfGameEngine/渲染管线与画面/渲染队列与DrawCall组织|渲染队列与 DrawCall 组织]] 里的 Phase 拆分——`Depth → Opaque → Transparent` 三段，每段一个队列、一种排序策略。这比任何 API 层面的东西都重要：**Early-Z 是 GPU 的"免单"机制，深度预 Pass 是 CPU 的"排队"策略，两者必须配合才有意义**——没有预 Pass，Early-Z 大部分时间对着空缓冲使不上劲；没有 Early-Z，预 Pass 铺的深度没人消费。

> 移动端视角（了解即可）：Imagination/ARM 等移动 GPU 支持 **Depth Priming**——深度预 Pass 写完后，正式 Pass 直接**加载**这份深度而不是重新计算，连深度测试本身的开销都省了。移动端厂商把深度预 Pass 当作一等公民优化，这也是为什么移动端管线里它几乎是标配。

## 明确推荐：一张决策清单

给透明与不透明物体画渲染队列时，按这张清单决策：

1. **不透明物体默认前到后画**（廉价、零额外 Pass），让 Early-Z 在缓冲"边画边填"的过程中尽量多干活。
2. **着色成本高或 overdraw 严重（室内、植被、移动端）→ 上深度预 Pass**：深度 Pass 只画不透明物体（任意顺序），正式 Pass 享受满负荷 Early-Z。
3. **着色很轻、几何很重（细分网格、纯色）→ 别上深度预 Pass**：多跑一遍几何的代价超过省下的着色代价，还可能撞 CPU 提交瓶颈。
4. **先用抓帧工具看 overdraw 热力图再决策**——没有数据不优化（性能分析阶段会系统展开，现在就养这个习惯）。
5. **透明物体**：保持 5.1 方案（测深度、不写深度、远到近），深度预 Pass 只让它的排序范围收窄，不改变混合规则。
6. **排查卡顿时**，先怀疑某个材质悄悄关闭了 Early-Z（镂空贴图、修改深度的特效），再怀疑排序。

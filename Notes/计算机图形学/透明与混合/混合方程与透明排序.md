# 混合方程与透明排序

## 开场：玻璃窗后面，怎么什么都看不见了？

你现在能画带贴图、带光照的不透明场景了。往场景里加一扇玻璃窗——窗口半透明，透过它能看到窗外的树。

渲染出来，窗外一片黑。玻璃像一块木板，把后面挡得严严实实。

问题出在哪？回想一下深度缓冲的工作方式（[[Notes/计算机图形学/软光栅化与3D数学/3D光栅化与深度缓冲|3D 光栅化与深度缓冲]]）：**每个像素最终属于"离相机最近的表面"**——近的表面写颜色、写深度，远的表面被深度测试拒之门外。

这套逻辑对不透明物体完全正确：树被窗框挡住，看不见就对了。但玻璃是半透明的——它既属于"窗框"那层表面，又应该让出位置给"树"那层表面。**深度缓冲的模型是"一个像素 = 一个表面"，半透明像素同时属于多层表面，这个模型当场失效。**

更直接地说：现在的渲染器是"**换**像素"——后来的颜色把画布上的颜色整个盖掉。玻璃需要的动作是"**混**像素"——新颜色和画布上已有的旧颜色按比例合在一起。一字之差，就是整篇笔记要解决的问题。

---

## 问题 1：像素怎么"混"而不是"换"？——两个颜色按比例合在一起

假设玻璃像素已经算好：颜色是淡淡的蓝（RGB 三个分量），还带一个"不透明度"数值——它有多大程度盖住后面的东西。这个数值在纹理的第四个通道里，叫 **alpha**（阿尔法，在 [[Notes/计算机图形学/纹理系统/纹理对象与加载|纹理对象与加载]] 里见过它：表示像素有多"不透明"，当时说它"要到阶段五才派上用场"，现在就是了）。alpha 取 0~1：0 是全透明（等于没画），1 是全不透明（等于木板）。

"混合"的意思很朴素：

```
画布上这个像素现在的颜色 = 旧颜色（可能是背景，也可能是更早画上去的物体）
新算出来的颜色          = 新颜色（就是这块玻璃）
a                      = 新颜色的 alpha

最终颜色 = a × 新颜色 + (1 − a) × 旧颜色

其中"×"是对三个颜色通道（红/绿/蓝）各自乘，"+"是逐通道相加
```

逐通道看一遍就明白它在做什么：alpha 越接近 1，新颜色占的份额越大；越接近 0，旧颜色留得越多。alpha = 0.5 时，两边各占一半。

> [!example] 一张白纸，盖一张 alpha=0.3 的蓝玻璃
> 旧颜色 = 白（1, 1, 1），新颜色 = 蓝（0, 0, 1），a = 0.3
>
> 最终 = 0.3×蓝 + 0.7×白 = (0.7, 0.7, 1.0)
>
> 结果是一块"很淡的蓝"，像透过有色玻璃看白墙——玻璃的蓝色渗进来，白墙的亮度还留着 70%。如果 a=1，最终 = 纯蓝，玻璃变成了木板；如果 a=0，最终 = 白，玻璃完全不存在。

这个方程里，两个"份额"各有一个名字，后面所有讨论都要用到：

- **src 因子**：新颜色自己乘的那个数。上面例子里是 `a`。
- **dst 因子**：旧颜色乘的那个数。上面例子里是 `1 − a`。

名字不用记，记住角色就行：**src 决定"新来的颜色让多少"**，**dst 决定"画布上已有的颜色留多少"**。它们的组合不是只有 `(a, 1−a)` 一种——换成别的组合，就得到别的效果：

| 组合（src 因子, dst 因子） | 效果 | 场景 |
|---|---|---|
| (a, 1−a) | 标准的透明度混合 | 玻璃、烟雾、任何半透明材质 |
| (1, 1) | 新颜色直接加到旧颜色上，越叠越亮 | 火焰、光晕、粒子叠加 |
| (1, 0) | 旧颜色被完全扔掉 | 这就是"不换不混"，退回不透明覆盖 |

这些组合就是"混合方程"的完整内容：**先选好 src/dst 因子，再对每个像素做一次加权合并**。它发生在片段着色器算完颜色之后、把颜色写进画面之前的最后一步。

> 一句话：**混合 = 给像素写入前加一道"按比例合并"的工序。** 因子组合决定合并规则，最常用的是 `(a, 1−a)`。

## 问题 2：先画红玻璃，还是先画蓝玻璃？——顺序真的会改变结果

有了混合方程，玻璃能透出后面的东西了。但马上撞上第二个问题：**顺序**。

先想一个反直觉的问题：不透明物体为什么可以乱序画？

因为深度测试是"覆盖制"：不管谁先画，最终每个像素保留的是**最近的**那个表面。画 A 再画 B（B 近），B 覆盖 A；画 B 再画 A，还是 B 覆盖 A。结果由"谁更近"决定，与"谁先画"无关。

混合是另一回事。看问题 1 的方程：**旧颜色作为输入参与计算**。这意味着混合后的结果带着"之前画了什么"的记忆。一旦结果依赖历史，顺序就变成了决定因素。

用一个具体例子把这件事钉死。白背景上叠两块玻璃：红色玻璃（远）、蓝色玻璃（近），alpha 都是 0.5。

```
场景：白背景 B，远红玻璃 R（α=0.5），近蓝玻璃 G（α=0.5）

先画远的红玻璃 R，再画近的蓝玻璃 G：
  第 1 步：B 与 R 混合   →  0.5R + 0.5B
  第 2 步：与 G 混合      →  0.5G + 0.5×(0.5R + 0.5B)
                              = 0.5G + 0.25R + 0.25B
  近的蓝玻璃占 50%，远的红玻璃只占 25%，背景白占 25%    ✓ 符合直觉

反过来，先画近的蓝玻璃 G，再画远的红玻璃 R：
  第 1 步：B 与 G 混合   →  0.5G + 0.5B
  第 2 步：与 R 混合      →  0.5R + 0.5×(0.5G + 0.5B)
                              = 0.5R + 0.25G + 0.25B
  红玻璃反而占了 50%，近处的蓝玻璃只占 25%             ✗ 完全颠倒
```

同一个场景、同样的两块玻璃，仅仅因为绘制顺序不同，近处的玻璃在最终画面里占的份额从 50% 掉到 25%——**混合不可交换**，因为第二次混合时，"旧颜色"已经被第一次混合污染过，而每次混合都按 alpha 重新分配权重。

所以透明物体必须**从远到近**绘制：远的先画进画布，近的再叠上去，这样每次"近的盖远的"才是正确的分配。这其实就是你在阶段一学过的**画家算法**（[[Notes/计算机图形学/软光栅化与3D数学/3D光栅化与深度缓冲|3D 光栅化与深度缓冲]] 里提过：先画远的，近的覆盖）——当初深度缓冲宣布"不再需要排序"，透明一出现，排序又回来了。历史的轮回。

> 一句话：**混合是有记忆的运算，顺序决定每个表面在最终颜色里的权重。** 所以透明必须远→近，不透明可以乱序。

## 问题 3：深度测试怎么救不了透明？——"写深度"和"不写深度"的两难

你可能已经想到：能不能让深度缓冲继续干活，透明物体也"谁近谁优先"？

问题在于深度缓冲只有一个。它存的是"**这个像素目前最近的表面是谁**"。对于不透明物体，这个答案永远正确；对于透明物体，同一个像素被多层表面共享，任何一层都不该独占这个槽位。

于是透明物体面临一个两难：**写不写深度？**

```
场景：地面（不透明）→ 远玻璃（透明）→ 近玻璃（透明）

方案 A：透明物体照常写深度
  近玻璃画完，深度缓冲记下"近玻璃最近"。
  轮到远玻璃：它的深度比近玻璃远 → 深度测试失败 → 被丢弃。
  结果：远玻璃完全消失，画面里只有近玻璃。
  ✗ 近玻璃像木板，透明变不透明

方案 B：透明物体不写深度，但保留深度测试
  远玻璃画：与地面比，比地面近 → 通过 → 混合进画布，但不写深度。
  近玻璃画：与地面比，还是比地面近 → 通过 → 与画布混合。
  两块玻璃都画出来了，最终顺序对不对？取决于你画的顺序。
  ✓ 能透出多层，但顺序全靠排序保证
```

方案 A 的失败值得再说透一点：**深度写入的语义是"我挡住了后面的一切"**。半透明物体没有资格说这句话——它只是"部分挡住"。让它写深度，等于把"部分挡住"谎报成"完全挡住"。

所以标准答案是**方案 B**：透明物体**保留深度测试**（还能被不透明物体挡住——比如玻璃后面的墙，本来就该看不见），但**关闭深度写入**（不占那个"最近表面"的槽位，给更远的透明物体留位置）。代价就是问题 2 说的：正确性只能靠**排序**来保证。

至此，一套标准的单 Pass 世界透明管线浮出水面：

```
1. 先画所有不透明物体：开深度测试、开深度写入，顺序随便（从近到远画还能顺带省掉大量无效着色——这个加速机制 5.2 专门讲）
2. 再画所有透明物体：开深度测试、关深度写入，按到相机的距离从远到近排好序画
```

> 一句话：**透明 = 深度测试（挡得住）+ 深度写入关（挡不住）+ 远→近排序（算得对）**，三个条件缺一不可。

## 问题 4：从远到近排序，要付出什么代价？——CPU 排序与救不了的天花板

方案 B 看起来完整了，但排序不是免费的午餐。它有四笔账：

**账 1：每帧都要重新排。** 相机在动、物体在动，每个透明物体到相机的距离每帧都在变，上一帧的排序结果直接作废。排序是 CPU 上的活，每秒几十次，一次 O(n log n)。n 是透明物体数——几百个透明物体时这不是大开销，但它挤占了每帧宝贵的 CPU 预算。

**账 2：排序和合批打架。** 想让同材质的物体一起画（少切换状态），就得让它们挨着；想让透明正确，就得按深度排序。**同材质的物体深度往往各不相同**，两个目标互斥。引擎里通常的妥协是：按深度排顺序，代价是"一起画"的机会变少。

**账 3：排序单位是"物体"，不是"像素"。** 这是最致命的一笔。排序排的是**物体**（用它的中心点算距离），但正确的混合需要**逐像素**的顺序——同一个物体上，有的像素比另一个物体近，有的比它远。中心点排序只是个近似：

```
一个甜甜圈（圆环）侧对着你：
  环的"中心"到相机距离是一个值，但环本身有近半边、远半边。
  按中心排序 = 环内部自己排不了序 → 环的近半边和远半边交错时，
  离你近的那半边可能先画，远的后画，最后远的那半边盖在近的上面——自遮挡错乱。

两团烟雾互相穿插：
  A 的前半团在 B 前，B 的后半团在 A 前。任何"按物体"排序都是错的。
```

**账 4：排序救得了顺序，救不了浪费。** 就算排对了，后面还有一堆像素会被覆盖——那是 5.2 深度预 Pass 要解决的问题（后续笔记展开，现在只需知道：排序只管"画对"，不管"少画"）。

于是"从远到近排序"这条路的边界清清楚楚：**它只适用于"物体之间不交错、单物体不自遮挡"的近似情况**。玻璃窗、几块小玻璃——行。甜甜圈、粒子、头发丝、玻璃杯里插根吸管——不行。这正是阶段五后半两篇笔记的入口：

- 排序救不了性能浪费 → 深度预 Pass（5.2）
- 排序救不了交错正确性 → 顺序无关透明（5.3，它需要把中间结果存下来再组合，已经越过了"单 Pass"的边界——到时候你会看到，这个"边界"就是幕二"多 Pass 世界"的入场券）

> 一句话：**按物体排序是"便宜但近似"的方案，能处理日常的玻璃和烟雾；一旦物体交错或自遮挡，它救不了——那就是下两篇笔记的事。**

## 落地表达：这套规则在渲染器里怎么组织

推导到这里，读者已经知道要什么了：**每个像素写入前，做一次带权重的颜色合并（规则由 src/dst 因子定义）；透明物体按远→近排序、关深度写、开深度测**。现在看各家后端怎么表达。

**混合规则——"像素写入前最后一步"怎么配置：**

- **OpenGL** 把混合做成一个全局开关加两个因子参数，画到一半随时可以改。这是它历史包袱的体现：状态就是全局变量，改动即时生效、全局可见。
- **Vulkan / D3D12 / Metal** 把混合规则锁进"管线对象"——一次绘制用哪套因子组合，是绑定哪条管线时就已经定死的。想换混合模式就得换管线。它们认为"混合规则"属于绘制时不变的状态，必须在提交前就完整描述，好处是驱动拿到管线就能做全套验证，坏处是每种混合模式要单独一条管线。
- 不管哪种后端，混合都在**片段着色器之后、写像素之前**由固定硬件完成——它不在 Shader 的可编程区域里。

**排序——根本不在 GPU 上：** 从远到近排序是 CPU 在"决定先画谁"时做的事，属于渲染队列的组织逻辑。自研引擎里就是：渲染队列把透明物体单独排一个队列，按深度从远到近画。这正对应引擎 [[Notes/SelfGameEngine/渲染管线与画面/渲染队列与DrawCall组织|渲染队列与 DrawCall 组织]] 里"不透明分箱、透明排序"的设计。

## 明确推荐：一张决策清单

画透明物体时，按这张清单检查，能防住 90% 的经典 bug：

1. **不透明与透明分开两个阶段画**：先不透明（写深度 + 测深度），后透明（测深度 + 不写深度）。
2. **透明物体从远到近排序**，用相机空间深度做排序键，远的排前面。
3. **选好混合因子**：默认 `(a, 1−a)`；发光/粒子叠加用 `(1, 1)`；做遮罩用 `(1, 0)`。
4. **承认近似**：物体交错、自遮挡场景，物体级排序会错——不要试图用"更聪明的排序"硬扛，那是 5.3 的领域。
5. **性能预期**：排序是每帧的 CPU 开销且与合批互斥；透明物体多到影响帧率时，优先做 5.2 的深度预 Pass。

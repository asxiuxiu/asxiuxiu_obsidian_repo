# CPU 怎么向 GPU 发命令

## 问题 0：CPU 到底会向 GPU 发什么东西？

从上一篇笔记你知道了：软渲染器里那个 `for(y) for(x)` 的逐像素循环，在 GPU 上被一整套固定硬件 + 可编程 Shader 替代。CPU 不会也不可能把"每个像素是什么颜色"一五一十地发给 GPU。

那它发什么？

把所有 CPU 丢给 GPU 的东西分成三大类，后面很多问题都会变清楚：

| 类别 | 本质 | 例子 |
|---|---|---|
| **命令** | "请 GPU 做什么" | draw call、状态切换、同步信号 |
| **数据** | "GPU 做这件事需要读什么" | 顶点数据、索引数据、颜色数据、全局常量 |
| **程序** | "按什么规则处理每个顶点 / 每个像素" | 顶点着色器、片段着色器、计算着色器 |

可以把这个关系想象成工厂里的生产工单：

- **命令** = 工单本身："加工这批零件"
- **数据** = 零件原料："这批零件在 3 号货架"
- **程序** = 加工工艺卡："用 3 号机床程序，按这个流程加工"

CPU 发出去的绝大多数"渲染相关"信息，都可以归到这三类里。后续笔记会逐步展开：数据怎么放到 GPU 上、格式怎么描述、程序怎么写、状态怎么管理。但现在只需要有这三类的框架。

> [!info] 最重要的命令：draw call
> 在这三类里，**draw call** 是最常见、最核心的命令。它是 CPU 告诉 GPU"开始一次绘制"的那句话。下一节专门讲它是什么。

---

## 问题 1：什么是 draw call？

在软渲染器里，你写了一个外层循环：

```cpp
for (每个三角形) {
    // 顶点变换
    // 光栅化
    // 着色
    // 写入帧缓冲
}
```

这个循环在 CPU 上执行，你的 C++ 程序显式遍历每个三角形。

在 GPU 上，CPU 不能自己跑这个循环。CPU 能做的，是对 GPU 喊一句话：

> "GPU，这里有一批顶点（已经放到你能访问的显存里了），按三角形方式组装，用这套着色器和绘制状态，把它们画出来。"

这一句话，就是一个 **draw call**。

### draw call 里具体有什么？

一条 draw call 至少要告诉 GPU 三件事：

1. **画什么**
   - 顶点数据在哪里（已经上传到 GPU 能访问的显存）
   - 有没有索引数据（用来复用顶点）
   - 要画多少个顶点 / 多少个图元

2. **怎么画**
   - 图元类型：三角形、线、点
   - 当前**绘制状态**：深度测试开不开、混合模式是什么、正面朝向是哪个方向

   **什么是绘制状态？** 它不是你 C++ 程序里的变量状态，也不是 GPU 内部的寄存器状态。它是一组**控制 GPU 如何解释当前 draw call 的配置开关**。比如：
   - 深度测试是开启还是关闭？（决定像素是否可能被已有像素挡住）
   - 混合模式是什么？（决定新像素和旧像素如何叠加）
   - 正面朝向是哪个方向？（决定哪些三角形要被剔除）
   - 当前用哪套 shader 程序？

   这些配置不会每个像素单独变，而是在一个 draw call 期间保持生效。所以 draw call 必须引用"当前生效的绘制状态"。

3. **用什么程序画**
   - 顶点着色器 + 片段着色器（以及其他可能的可编程阶段）

### draw call 和 shader 是什么关系？

**shader 不是 draw call 的一部分，但 draw call 必须引用 shader。**

- **shader** 是一段提前编译好、放到 GPU 上的小程序。它回答"每个顶点怎么算、每个像素怎么着色"。
- **draw call** 是一次命令，它说"现在用这套 shader，画这批三角形"。

同一个 shader 可以被多个 draw call 使用。比如同一个材质画 10 个物体，就是 10 次 draw call，但它们共享同一套 shader 和绘制状态。

> [!important] 一个 draw call 只能绑定一套绘制状态
> 如果 10 个物体用的 shader 不同，或者深度测试设置不同，你就必须发 10 次 draw call。这是理解"合批"和"渲染状态排序"的起点，但那是阶段七的内容。现在只需要知道：draw call 是 CPU 让 GPU 干活的"原子命令单位"。

### 一个 draw call 的完整信息流

```
CPU 端：
  1. 把顶点数据上传到 GPU 能访问的显存
  2. 编译并绑定 shader 程序
  3. 设置绘制状态（深度测试、混合、剔除等）
  4. 调用 DrawCall（顶点数 / 索引数）

GPU 端收到 DrawCall 后：
  → 图元装配：按顶点拉出三角形
  → 顶点着色器：处理每个顶点
  → 光栅化：生成片段
  → 片段着色器：处理每个像素
  → 输出合并：深度测试 + 颜色写入
```

所以 draw call 本身只是一条命令，但它会触发 GPU 一整条固定流水线的工作。

## 问题 2：为什么这三类东西不能直发给 GPU？

现在你知道 CPU 发的是"命令 + 数据 + 程序"。下一个自然的问题是：为什么不能直接把这些东西塞进 GPU？为什么还要图形后端、驱动、PCIe、交换链？

因为 GPU 和 CPU 是两个完全独立的处理器，它们之间有一道真实的"墙"。

### 墙 1：不同的指令集和内存布局

NVIDIA、AMD、Intel、Apple 的 GPU，各自的指令集、显存格式、对齐要求、颜色空间转换规则都不一样。你不可能为每款显卡分别写一份"draw call 二进制格式"。

### 墙 2：CPU 和 GPU 不共享内存

CPU 内存（RAM）和 GPU 内存（VRAM）是两块物理上分开的内存。CPU 不能直接读写 GPU 的显存，GPU 也不能直接读 CPU 的内存。它们之间通过 **PCIe 总线** 连接。

> **PCIe 是什么？** 你可以把它理解为 CPU 和 GPU 之间的"高速公路"。它有带宽上限，也有延迟。数据要从 CPU 侧搬到 GPU 侧，必须走这条路。
>
> 这意味着：如果你想像软渲染器那样"每算一个像素就通过 PCIe 写一次显存"，这条高速公路会立刻堵死。软渲染器每帧要访问几百万次像素，这种逐个像素写显存的方式完全不可行。

### 墙 3：程序需要重新编译

你在 CPU 上写 C++，编译成 x86/ARM 机器码。但 GPU 有自己的指令集。你写的 shader（GLSL/HLSL/MSL）必须被驱动编译成当前这张显卡能懂的机器码。

### 墙 4：CPU 和 GPU 是异步的

CPU 发完命令后不会停下来等 GPU。GPU 可能正在画上一帧，CPU 已经在准备下一帧。如果两者不同步，会出现**画面撕裂**——显示器上半部分显示旧帧，下半部分显示新帧。

### 结论

正因为有这四堵墙，所以不能直接对 GPU 说"画这个像素"，而是需要一套中间层来：

- 把统一的命令翻译成不同 GPU 能懂的指令
- 把数据从 CPU 内存搬到 GPU 显存，并整理成 GPU 能读的格式
- 把 shader 编译成 GPU 机器码
- 管理 CPU 和 GPU 之间的同步

这套中间层就是**图形后端 / 图形 API**。

## 问题 3：图形后端 / 图形 API 解决什么问题？

图形后端（Graphics Backend）向上提供统一的"让 GPU 做事情"的接口，向下屏蔽不同 GPU 驱动的差异。

> [!info] 术语说明
> 在这篇笔记里，**"图形后端"和"图形 API"基本同义**，指 OpenGL、Vulkan、D3D12、Metal 这类标准接口。
>
> 它们由两部分组成：
> - **API 规范**：定义你能调用哪些函数（如 Khronos 定义 Vulkan，Microsoft 定义 D3D12）。
> - **驱动实现**：GPU 厂商根据规范写的驱动，负责把 API 调用翻译成自家 GPU 能懂的指令。
>
> 在引擎语境里，你还会遇到 **RHI（Rendering Hardware Interface）**。RHI 是引擎自己封装的抽象层，下面是 OpenGL/Vulkan/D3D12 这些具体"图形后端实现"。注意区分这两个"后端"的用法。

图形后端的核心职责只有三件：

1. **申请渲染上下文（Render Context）**
   - 告诉操作系统和 GPU："这个窗口/这个程序要用来渲染。"

2. **管理交换链（Swap Chain）**
   - 解决画面撕裂。GPU 维护两个帧缓冲：前台缓冲（正在显示）和后台缓冲（正在画）。画完后交换角色。

3. **翻译命令并驱动 GPU**
   - 把 draw call、状态设置、数据上传这些上层操作，翻译成 GPU 能执行的指令序列。

## 问题 4：渲染上下文、窗口表面、交换链分别是什么？

这三个概念经常出现，但它们的职责很容易被混淆。它们分别解决"在哪里画"、"画到哪里"、"怎么不撕裂"三个不同问题。

### 渲染上下文（Render Context）

"渲染上下文"这个词很抽象。把它拆开，它是你的 C++ 程序在 GPU 上获得的一个**工作空间**，包含四样东西：

1. **一个渲染目标**：窗口表面或交换链，GPU 画完的东西最终显示到哪里。
2. **一个 GPU 设备连接**：你的程序在用哪张显卡、哪个计算队列。
3. **一组当前绘制状态**：即当前生效的配置集合（深度测试、混合、当前使用的 shader 等）。这是 GPU 解释 draw call 的依据。
4. **一个命令提交通道**：CPU 把绘制命令交给 GPU 的管道。

可以这样类比：渲染上下文就像工厂里的一个**工位**——你有工位许可证、固定工作台、当前调好的工具，以及把任务递给工人的窗口。

在 OpenGL 里：
```cpp
glfwCreateWindow(...)           // 创建窗口 + 上下文
glfwMakeContextCurrent(...)     // 把当前线程和上下文绑定
```

在 Vulkan 里，同样的目的被拆成显式链条：
```cpp
VkInstance → VkPhysicalDevice → VkDevice → VkSurfaceKHR
```

**不是做的事情变多了，而是原本隐藏起来的上下文细节被暴露出来了。**

### 窗口表面（Surface）

窗口表面不是窗口本身。窗口由操作系统管理（位置、大小、边框）；窗口表面是操作系统和 GPU 之间的**交接约定**：

> "这个窗口的这块矩形区域，专门用来显示 GPU 渲染出来的图像。"

```
GPU 显存里的帧缓冲  ← GPU 在这里画画
        ↓
   交换链（Swap Chain）  ← 管理"前台缓冲 / 后台缓冲"的切换
        ↓
   窗口表面（Surface）    ← 窗口和 GPU 的交接区
        ↓
   屏幕上的窗口（Window） ← 用户最终看到的东西
```

窗口表面本身**不存放像素**，它只是声明"这个窗口可以接收 GPU 输出"。真正的像素数据存放在帧缓冲里。

OpenGL 通过 GLFW 把 Surface 创建藏在 `glfwCreateWindow` 里。Vulkan 则要求你显式创建 `VkSurfaceKHR`，并提供平台相关的窗口句柄（Windows 上是 `HWND`，Linux 上是 X11 窗口 ID，macOS 上是 `CALayer`）。

### 交换链（Swap Chain）和双缓冲

如果没有双缓冲，GPU 一边画新帧，显示器一边读旧帧，就会出现撕裂。

**双缓冲**：
- **前台缓冲**：当前正在显示到屏幕
- **后台缓冲**：你正在画
- 画完后**交换**两者角色

OpenGL 里，`glfwSwapBuffers()` 帮你隐式管理。Vulkan 里，你必须显式处理：
```cpp
vkAcquireNextImageKHR(...)   // 获取下一帧可画图像
// ... 记录渲染命令 ...
vkQueuePresentKHR(...)       // 呈现到屏幕
```

## 问题 5：命令缓冲 vs 立即模式：CPU 怎么把命令发给 GPU？

现在回到"发命令"这个动作本身。不同的图形 API 对"发命令"的设计差异很大，这是理解 OpenGL 和现代 API 分水岭的关键。

### 绘制状态由谁保管？

在讲具体 API 之前，先明确一个独立的概念问题：

> 一条 draw call 需要引用"当前绘制状态"。那么当 CPU 连续发多个 draw call 时，这些状态由谁来记录、由谁来修改？

本质上有两种思路：

**思路 A：驱动隐式维护一份"当前状态"**
- CPU 通过专门的 API 调用修改这份当前状态。
- 每个 draw call 发生时，GPU 就按这份当前状态来执行。
- 这就像工厂里有一个公示板，上面写着"当前机床配置"，所有工单都默认按这个配置执行。

**思路 B：开发者显式把状态打包进命令**
- 每个 draw call 自己携带它需要的完整状态配置。
- GPU 执行这个 draw call 时，不需要去问"当前状态是什么"，因为状态已经写在命令里了。
- 这就像每张工单上都印有"本工单专用配置"，不依赖公示板。

> [!important] 两种思路没有本质优劣
> 它们回答的是同一个问题：GPU 执行 draw call 时，怎么知道该用哪套配置？
>
> 注意：**两种方案下，状态值具体是多少最终都是由应用（也就是你）决定的**。OpenGL 里是你调用 `glUseProgram`、`glEnable`；现代 API 里也是你填写 Pipeline State Object 的每个字段。真正区别的是——**这些状态以什么形式存在、运行时由谁负责把它们整理成 GPU 能直接执行的命令**。
>
> - 思路 A（OpenGL）：驱动内部维护一份"当前绘制状态"。应用通过 `glUseProgram`、`glEnable` 等调用**逐个修改**这份当前状态。驱动负责跟踪这些修改、推断哪些状态真的变了、再把差异翻译成 GPU 命令。也就是说，**运行时状态追踪和命令生成的工作主要由驱动承担**。
> - 思路 B（现代 API）：应用自己把一套完整的绘制配置**预先打包**成一个对象（如 Pipeline State Object），再交给 GPU。驱动不需要在每次 draw call 前推断差异，可以一次性验证和编译。**状态预先描述和组织的工作更多由应用承担**，但运行时驱动的开销更低。

### OpenGL：驱动隐式维护当前状态

OpenGL 采用的是思路 A。它把当前绘制状态放在驱动内部的一个**全局状态集合**里，你的每次 API 调用都可能修改这个集合。

```cpp
glClear(GL_COLOR_BUFFER_BIT);
glUseProgram(shader);           // 修改"当前 shader"
glDrawArrays(GL_TRIANGLES, 0, 3); // 这条 draw call 隐含使用上面的当前 shader
```

这些调用会立即修改驱动里的当前状态。驱动在后台把它们翻译成 GPU 命令，但上层感受不到状态在哪里、什么时候被改了。

这种模型的优点是简单、学习曲线平缓；缺点是：
- 驱动要推断你的意图，做了很多隐式工作，开销大。
- 状态是全局的，多个 draw call 之间容易互相影响，100 个物体时很难追踪。
- 多线程困难，因为同一时刻只能有一个线程修改这份全局当前状态。

### Vulkan / D3D12 / Metal：状态显式打包进命令

现代 API 采用的是思路 B。你先把要执行的命令和它们依赖的状态一起记录到 Command Buffer 里，然后一次性批量提交给 GPU。

```cpp
vkBeginCommandBuffer(cmdBuf);
// 记录命令...
vkCmdClearColorImage(cmdBuf, ...);
vkCmdDraw(cmdBuf, ...);  // 这条 draw call 周围的状态在录制时已经明确
vkEndCommandBuffer(cmdBuf);

vkQueueSubmit(queue, cmdBuf, fence);  // 批量提交
```

这里的关键区别是：**命令先被记录到一个缓冲区里，然后一次性批量提交给 GPU**。更重要的是，状态不是藏在驱动里的全局变量，而是你在录制命令时显式指定的配置。

> [!info] Command Buffer 里到底装的是什么？
> Command Buffer 里装的是**命令**（command）。但要注意，命令不止 draw call 一种：
> - **绘制命令**：`vkCmdDraw`、`glDrawArrays`，触发 GPU 跑流水线。
> - **状态绑定命令**：`vkCmdBindPipeline`、`vkCmdBindVertexBuffers`，设置当前绘制状态。
> - **拷贝/传输命令**：`vkCmdCopyBuffer`、`vkCmdCopyBufferToImage`，把数据从 CPU 内存搬到 GPU 显存。
> - **同步命令**：`vkCmdPipelineBarrier`，控制命令之间的执行顺序。
>
> 那**顶点数据、索引数据、纹理像素、shader 程序本身**是不是命令？**不是**，它们是"数据"或"程序"。但把这些资源**从 CPU 上传到 GPU 显存**这个动作，在现代 API 里通常就是一条拷贝命令；OpenGL 里则被 `glBufferData` / `glTexImage2D` 这类调用隐藏起来，由驱动在后台处理。
>
> 上传完成后，这些数据就作为"资源"待在 GPU 显存里。绘制命令再去**引用**它们：
> - `vkCmdBindVertexBuffers` 说"接下来画的时候，顶点数据去这个 GPU 地址找"。
> - `vkCmdDraw` 说"用当前绑定的所有东西，画这些顶点"。
>
> 所以 Command Buffer 是 CPU 写给 GPU 的"任务清单"，清单上写的都是动作；真正的原料（数据）和工艺卡（shader）在上传完成后已经放在 GPU 的"仓库"（显存）里了。

| 特性 | OpenGL | Vulkan/D3D12/Metal |
|---|---|---|
| 命令提交方式 | 隐式，驱动实时翻译 | 显式记录到 Command Buffer，批量提交 |
| 状态存在形式 | 驱动内部维护一份可变"当前状态"，应用逐个调用修改 | 应用预先打包成完整状态对象，绑定后使用 |
| 运行时工作分配 | 驱动跟踪状态差异并生成 GPU 命令 | 驱动直接执行已验证的状态对象 |
| 多线程 | 困难（全局当前状态线程绑定） | 原生支持多线程录制 |
| 驱动开销 | 高（驱动做很多推断） | 低（开发者显式声明） |

> **为什么要批量提交？** 因为每次从 CPU 向 GPU 提交命令都有一定的固定开销。把一堆命令攒起来一次发过去，比发一百次小命令更高效。这就像我们不会每写一个字就寄一封信，而是写满一页再寄。

## 问题 6：现代 API 为什么把"描述"和"执行"分开？

在 Vulkan 这类现代 API 里，你需要先"描述"，再"执行"。

**描述阶段**：
- 渲染过程描述：有哪些输出目标、数据如何流转、子步骤之间的依赖
- 绘制状态配置：顶点格式、Shader、深度测试、混合模式

**执行阶段**：
- 绑定绘制配置、绑定资源、调用绘制命令

这样做的好处：

1. **驱动可以提前验证**：提交前就知道整套状态是否合法，而不是执行到一半才发现问题。
2. **支持多线程录制**：多个线程各自录 Command Buffer，最后批量提交。
3. **CPU 和 GPU 并行**：CPU 准备第 N+1 帧，GPU 执行第 N 帧。

OpenGL 把"描述"和"执行"混在一起，所以你写起来简单，但驱动很吃力。现代 API 把它们拆开，把运行时状态组织的控制权和工作量交给了开发者，以换取更低的驱动开销和更高的可预测性。

## 问题 7：RHI 是干什么用的？

学会了 OpenGL，为什么还要在阶段七封装 RHI？

因为直接调用 OpenGL 有三个工程陷阱：

1. **OpenGL 的隐式全局状态管理**：状态由驱动隐式维护，100 个物体时很难追踪。
2. **换 API 要重写**：所有 `gl*` 调用都要换成 `vk*` 或 `d3d*`。
3. **多线程渲染困难**：OpenGL 的当前状态是全局的，同一时刻只能有一个线程修改。

RHI 抽象层把具体 API 调用封装在统一接口后面，上层代码完全无感知。

> **阶段七才会深入讲 RHI**。现在只需要建立预期：阶段二~六写的裸 API 代码，最终会被阶段七的 RHI 层"吸收"和"替代"。

## 各 API 对"CPU 发什么"的不同表达

| 子问题 | OpenGL | Vulkan | D3D12 | Metal |
|---|---|---|---|---|
| 发"画什么"命令 | `glDrawArrays` / `glDrawElements` | `vkCmdDraw` / `vkCmdDrawIndexed` | `DrawInstanced` / `DrawIndexedInstanced` | `drawPrimitives` |
| 建立 GPU 会话 | `glfwCreateWindow` + `glfwMakeContextCurrent` | `VkInstance` → `VkDevice` | `CreateDXGIFactory` → `ID3D12Device` | `MTLCreateSystemDefaultDevice` |
| 连接窗口 | 隐式在 GLFW 里 | `VkSurfaceKHR` | `IDXGISwapChain` | `CAMetalLayer` |
| 交换链 | `glfwSwapBuffers` | `VkSwapchainKHR` | `IDXGISwapChain` | `MTLDrawable` |
| 清屏 | `glClearColor` + `glClear` | `vkCmdClearColorImage` | `ClearRenderTargetView` | `MTLRenderCommandEncoder` 的 `clearColor` |
| 记录命令 | 隐式 | `VkCommandBuffer` | `ID3D12CommandList` | `MTLCommandBuffer` |
| 提交命令 | 隐式 | `vkQueueSubmit` | `ExecuteCommandLists` | `MTLCommandBuffer.commit` |

> 这个表格不是让你背 API，而是展示同一个本质问题——"CPU 怎么让 GPU 干活"——不同 API 选择了不同的抽象粒度。OpenGL 把很多东西藏在驱动里；Vulkan/D3D12/Metal 把它们显式暴露出来，因为现代引擎需要更精确的控制。

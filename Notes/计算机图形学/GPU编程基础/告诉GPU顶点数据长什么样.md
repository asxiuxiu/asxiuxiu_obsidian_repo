# 告诉 GPU 顶点数据长什么样

## 问题 0：软渲染器怎么知道顶点格式的？

在软渲染器里，顶点格式由 C++ 结构体定义。比如一个顶点包含位置、颜色、UV：

```cpp
struct Vertex {
    Vec3 position;   // 12 字节，偏移 0
    Vec3 color;      // 12 字节，偏移 12
    Vec2 uv;         //  8 字节，偏移 24
};                   // 一个顶点共 32 字节
```

编译器根据结构体布局生成内存访问代码。CPU 读取 `vertices[i].color` 时，会自动从正确偏移取值。

现在数据被上传到 GPU 显存。GPU 没有 C++ 结构体定义，它看到的只是连续的字节流：

```
地址：  0     12    24    32    44    56    64    76
字节： [■■■■■■■■■■■■][■■■■■■■■■■■■][■■■■■■■■][■■■■■■■■■■■■]...
```

对 GPU 来说，这就是一块连续的字节流。它不知道：
- 一个顶点占多少字节；
- 一个顶点里有几个属性；
- 每个属性从哪个字节开始、占多少字节、是什么类型；
- 这些属性在着色器里对应哪个输入位置。

所以核心问题不是"数据在不在 GPU 上"，而是：**GPU 怎么像编译器理解 C++ 结构体那样，理解这块字节流？**

---

## 问题 1：如果不告诉 GPU 格式，像素会怎么错？

如果不告诉 GPU 格式，它只能 guess。可能把颜色当位置、把位置当颜色，画出来的三角形立刻变成一堆散乱的像素。

更隐蔽的错误是：你告诉 GPU"一个顶点是 6 个 float"，但实际上是 8 个 float。GPU 会按 24 字节一个顶点去解析，于是位置、颜色、UV 全部错位。画出来的三角形颜色完全不对，但形状可能还"大致"有个三角形的样子——这种 bug 最难调。

所以**格式解释不是可选优化，而是正确渲染的前提**。没有它，像素的颜色和位置都可能是错的。

---

## 问题 2：为什么每次 draw call 的顶点格式可能不一样？

既然 GPU 需要显式格式解释，那为什么不能全局设置一次就管所有绘制？答案是：**不同的 draw call 处理的顶点数据本就可能长得不一样。**

### 原因 1：不同物体用着色器不同

物体 A 用了一个只有位置和颜色的简单着色器；物体 B 用了一个需要位置、法线、UV、切线的复杂着色器。它们的顶点格式自然不同。

### 原因 2：同一物体在不同效果下需要的数据不同

很多渲染流程里，一个物体会被画不止一次：
- 某些只输出深度的绘制只需要位置；
- 正常着色时需要位置、法线、UV；
- 某些特殊效果可能又只要屏幕空间位置。

同一个 mesh，在不同绘制阶段里需要被解释成不同的格式。

### 原因 3：不同数据来源

有些顶点来自模型文件（静态数据），有些来自粒子系统（每帧更新的动态数据），有些来自程序化生成。它们的属性组合可能完全不同。

### 结论

**顶点格式解释不是一次性的全局配置，而是每个 draw call 都需要声明的局部状态。** 正因为不同 draw call 的格式可能不同，API 才必须提供一种机制来声明"我这次用的是什么格式"。

---

## 问题 3：最 naive 的想法——每次 draw call 前手动声明一遍

既然每次都要声明格式，那最直白的做法就是在每次 draw call 前都手动配置一遍。在 OpenGL 里，这对应一组 `glVertexAttribPointer` 调用：告诉 GPU 每个属性从哪读、读多长、读几个、stride 是多少。

但这样写有明显的麻烦：

1. **全局状态容易被覆盖**：OpenGL 的顶点属性配置是**全局当前状态**，不是按物体保存的。你画物体 A 时配置了一套格式，画物体 B 时又配置了另一套格式——这不是因为 GPU"记不住"物体 A 的格式，而是因为同一时刻只有一份当前状态，谁最后设置就生效。想再画物体 A，就得把物体 A 的格式重新设置一遍。

2. **重复劳动**：如果有 100 个物体，其中很多共享同一套顶点格式，每次 draw call 前都重新写一遍格式配置，代码会又臭又长。

3. **容易遗漏**：少启用一个属性，着色器里对应输入就是未定义值，像素颜色可能全黑或全白。

4. **和具体数据缓冲区绑定混在一起**：格式配置往往会引用"当前绑定的数据缓冲区"。如果配置顺序和绑定顺序搞错，属性就指向了错误的缓冲区。

于是自然引出一个问题：**既然顶点格式解释是一组可以复用的状态，能不能像打包礼物一样把它打包起来，用时直接取出？**

---

## 问题 4：把格式解释打包成状态对象

手动配置格式的问题已经清楚了：它是全局状态，容易被覆盖，而且重复劳动。改进思路很直接：**把一套完整的格式解释打包成一个可复用的对象，绘制时只要说"用这套格式"就行。**

这个对象应该记录什么？
- 每个属性从哪个数据缓冲区读取；
- 每个属性的 stride、offset、类型、分量数；
- 哪些属性被启用。

你可以把它理解为一份**格式说明书**。配置一次，之后绑定它即可恢复全部格式状态。

OpenGL 里，这个对象叫做 **VAO（Vertex Array Object）**。它的工作方式可以概括为：

```cpp
// 配置阶段：把格式说明书"录制"下来
bindFormatObject();
    bindVertexBuffer(vbo);
    setAttribute(0, position,  vec3, offset=0);
    setAttribute(1, color,     vec3, offset=12);
    setAttribute(2, uv,        vec2, offset=24);
unbindFormatObject();

// 绘制阶段：只需要绑定格式说明书
bindFormatObject();
drawTriangles(0, 3);
```

> 这里用的是伪代码。OpenGL 的具体函数是 `glBindVertexArray` / `glVertexAttribPointer` / `glEnableVertexAttribArray`，但核心思想是"录制一次、复用多次"。

### VAO 记住什么、不记住什么？

这是初学时最容易踩的坑。VAO 记住的是**格式解释**，而不是**数据缓冲区对象本身**。

具体来说，VAO 记录的是：
- 属性 0 从 binding index 0 读取，stride=32，offset=0；
- 属性 1 从 binding index 0 读取，stride=32，offset=12；
- 属性 2 从 binding index 0 读取，stride=32，offset=24。

它会在配置时把具体的数据缓冲区名字（比如 VBO 的句柄）**快照**下来。之后你再去改"当前绑定的数据缓冲区"，不会自动更新已经录制好的 VAO。

**常见误解**：
```cpp
bindFormatObject(vao);
bindVertexBuffer(anotherVbo);  // 以为这会让 VAO 改绑数据缓冲区
drawTriangles(...);
```

这样做不会修改 VAO 内部记录的数据缓冲区关联。VAO 仍然使用配置时绑定的那个缓冲区。当前数据缓冲区绑定只影响后续新的格式配置，不影响已经配置好的 VAO。

> [!warning] VAO 是格式说明书，不是数据容器
> VAO 不保存顶点数据本身，只保存"怎么读数据"的说明。顶点数据仍然保存在 VBO 里。多个 VAO 可以引用同一个 VBO 但用不同格式解释；同一个 VAO 也可以和不同的 VBO 搭配（前提是这些 VBO 的数据布局相同）。

## 问题 5：真实模型里顶点被多个三角形复用，怎么办？

到目前为止，我们画的三角形都只有 3 个顶点，每个三角形用一套独立的顶点。但真实模型里，一个立方体只有 8 个唯一点，却要画 12 个三角形（共 36 个顶点索引）。这意味着同一个角点会被多个三角形复用。

### 最 naive 的方案：把顶点复制 36 份

如果不做任何处理，我们只能把每个三角形需要的顶点都写进顶点数组。立方体 12 个三角形 × 3 个顶点 = 36 个顶点，但其中很多是重复的。

**问题**：
1. **显存浪费**：本可以只存 8 个顶点，现在存了 36 个。顶点越大（位置 + 法线 + UV + 切线），浪费越严重。
2. **CPU→GPU 上传量增加**：每加载一个模型，都要多传很多重复数据。
3. **顶点共享被破坏**：同一个角在不同面上可能需要不同的法线（硬边 vs 平滑着色），复制顶点会让你失去灵活选择的能力。

### 改进：用索引表组装三角形

**核心思想**：顶点数据只存一份唯一顶点，再用一个"索引表"告诉 GPU"每三个索引组成一个三角形"。

```cpp
// 8 个唯一点
Vertex cubeVertices[8] = { ... };

// 36 个索引，每 3 个组成一个三角形
uint32_t cubeIndices[36] = {
    4, 5, 6,   4, 6, 7,   // 前
    0, 3, 2,   0, 2, 1,   // 后
    0, 4, 7,   0, 7, 3,   // 左
    1, 2, 6,   1, 6, 5,   // 右
    3, 7, 6,   3, 6, 2,   // 顶
    0, 1, 5,   0, 5, 4    // 底
};
```

## 问题 6：用索引表组装三角形

问题 5 已经说了，解决顶点复用的思路是**顶点数据只存一份唯一顶点，再用一个"索引表"告诉 GPU"每三个索引组成一个三角形"**。这个"索引表"在 OpenGL 里叫做 **EBO（Element Buffer Object，元素缓冲对象）**，也叫 IBO。它本质上和 VBO 一样是一块 GPU 显存，只是语义不同：VBO 存顶点，EBO 存索引。

绘制时，CPU 不再说"画第 0 到第 N 个顶点"，而是说"用 EBO 里的索引来组装三角形"。GPU 会按索引表里的顺序，每三个索引拉出一个三角形。

### EBO 和数据缓冲区、格式说明书的关系

一个完整的 GPU mesh 需要三类信息：

```
┌─────────────────┐
│   顶点数据缓冲区  │  VBO：存实际顶点属性（位置、颜色、UV……）
├─────────────────┤
│   索引表         │  EBO：存哪些顶点组成三角形
├─────────────────┤
│   格式说明书      │  VAO：存怎么解释 VBO 里的字节流
└─────────────────┘
```

在 OpenGL 里，EBO 的绑定状态会被记录到当前 VAO 里。所以绘制带 EBO 的物体时，通常只需要绑定 VAO，EBO 会随 VAO 一起恢复。

### 索引该用哪种数据类型？

| 类型 | 每个索引字节数 | 最大顶点数 | 适用场景 |
|------|--------------|-----------|---------|
| 8 位无符号整数 | 1 | 255 | 极小的模型，比如粒子、调试线框 |
| 16 位无符号整数 | 2 | 65535 | 大多数中小型模型，默认推荐 |
| 32 位无符号整数 | 4 | 约 42 亿 | 大型地形、复杂角色模型 |

> **推荐**：个人项目默认用 16 位索引，除非顶点数超过 65535。

### EBO 真的"消除"了重复顶点吗？

**它只是把顶点复用的问题从 VBO 转移到了索引表。** VBO 里仍然只存唯一的 8 个顶点，但 EBO 里需要存 36 个索引。索引表本身也占用显存和带宽。

| 方案 | VBO 大小 | 索引数据大小 | 总显存 |
|------|---------|------------|-------|
| 复制顶点（无 EBO） | 36 × 24 B = 864 B | 0 | 864 B |
| EBO（8 顶点 + 36 索引） | 8 × 24 B = 192 B | 36 × 2 B = 72 B | 264 B |

对于立方体，EBO 节省了约 70% 的顶点显存。更重要的是，**EBO 让顶点共享成为可能**：
- 平滑着色时，同一个顶点被多个三角形共享，法线取周围面的平均；
- 硬边着色时，一个角在不同面上需要不同法线，就不能共享顶点。

所以 EBO 不是万能药，它解决的是"顶点可以共享"的场景。

### 最常见的三个坑

**坑 1：EBO 没绑进 VAO**

如果你在 VAO 外部绑定 EBO，它不会进入 VAO 的状态。绘制时 GPU 要么用错误的索引表，要么没有索引表。

**坑 2：先解绑 EBO，再解绑 VAO**

在 OpenGL 里，`GL_ELEMENT_ARRAY_BUFFER` 的绑定是 VAO 状态的一部分。先解绑 EBO 会把当前 VAO 的 EBO 清空。正确做法：直接解绑 VAO 即可。

**坑 3：索引越界**

如果索引表里的某个数字大于顶点缓冲区里的顶点数，GPU 会读出越界数据。OpenGL 通常不会报错，但会画出完全错误的东西。

## 问题 7：现代 API 怎么表达格式解释和索引绘制？

现代 API（Vulkan / D3D12 / Metal）不把"格式解释"打包成 VAO 这样的独立对象，而是把它作为**管线状态（Pipeline State）**的一部分。

为什么？回想 [[Notes/计算机图形学/GPU编程基础/CPU怎么向GPU发命令|CPU 怎么向 GPU 发命令]] 里讲的：现代 API 倾向于让开发者在录制命令之前就把状态预先描述清楚，这样驱动可以在创建管线时做完整验证，而不是每次 draw call 都重新推断状态差异。

### 格式解释的控制权差异

| 方面 | OpenGL | Vulkan / D3D12 / Metal |
|---|---|---|
| 格式解释存在哪里 | 独立的 VAO 对象 | 管线状态对象的一部分 |
| 运行时切换格式 | 绑定不同 VAO 即可 | 通常需要绑定不同的管线 |
| 驱动工作 | 运行时跟踪 VAO 状态变化 | 创建管线时一次性验证 |
| 多线程 | VAO 绑定是全局状态，多线程受限 | 每个 Command Buffer 独立引用管线 |

### 索引绘制的控制权差异

| 方面 | OpenGL | Vulkan / D3D12 / Metal |
|---|---|---|
| 索引缓冲绑定 | 存在 VAO 里 | 每次绘制前显式绑定 |
| 索引绘制命令 | `glDrawElements` | `vkCmdDrawIndexed` / `DrawIndexedInstanced` |

现代 API 不保存索引缓冲绑定，是因为它们希望把"顶点格式"和"具体用哪个索引缓冲"完全分离，方便同一份格式复用到多个网格。

> [!info] 不是"现代 API 没有 VAO"
> 现代 API 依然有"描述顶点格式"的机制，只是不把它做成一个可以运行时随便切换的独立对象。OpenGL 的 VAO 是为了学习曲线平缓；现代 API 把它并入 PSO，是为了运行时可控和可验证。

## 问题 8：为什么"数据"、"索引"、"格式解释"是三个独立决策？

回头看 OpenGL 的例子，你会发现 VBO、EBO、VAO 解决的是三个不同问题：

| 决策 | 含义 | 解决什么问题 | 对应对象 |
|---|---|---|---|
| **数据在哪** | 顶点缓冲区绑定到哪个槽位 | 顶点字节流实际存放在 GPU 显存的哪个 buffer | VBO |
| **哪些顶点组成三角形** | 用索引表还是直接按顺序 | 如何复用顶点、减少冗余 | EBO |
| **格式是什么** | 每个属性的 stride/offset/type | GPU 怎么把字节流拆成顶点属性 | VAO |

这种分离的意义：

1. **复用格式**：多个模型共享同一套顶点布局时，只需切换 VBO/EBO 绑定，不用重新配置格式。
2. **复用缓冲区**：同一批顶点数据可以用不同格式解释。比如某些只输出深度的绘制只需要位置属性，可以用一个只读位置的 VAO/布局来绘制，避免把颜色、UV 也读进缓存。
3. **现代 API 的管线状态**：Vulkan/D3D12 把格式解释放进 PSO，让驱动在创建管线时就能验证格式是否合法、是否与着色器输入匹配。

## 问题 9：交织布局（Interleaved）vs 分离布局（SoA）

现在你知道 GPU 按 stride/offset 读取属性。但属性在 VBO 内部的排布方式有两种基本选择。

### 交织布局（Interleaved / Array of Structures）

一个顶点所有属性连续存放：

```cpp
struct Vertex {
    Vec3 pos;    // 0
    Vec3 color;  // 12
    Vec2 uv;     // 24
};               // stride = 32
```

```
[pos0 color0 uv0][pos1 color1 uv1][pos2 color2 uv2]...
```

优点：读取一个顶点时，所有相关属性一起进入缓存，缓存命中率高。
缺点：如果某个绘制阶段只需要位置，其他属性也会被一起读入，浪费带宽。

### 分离布局（SoA / Structure of Arrays）

每个属性单独一个数组：

```
[pos0 pos1 pos2 ...][color0 color1 color2 ...][uv0 uv1 uv2 ...]
```

优点：位置绘制阶段只读位置缓冲区，节省带宽；每个属性可以独立更新。
缺点：需要多个 VBO/缓冲区绑定；读一个完整顶点时要访问多个内存位置。

### 怎么选？

- 大多数 3D 模型渲染用 **交织布局**，因为它简单且缓存友好。
- 粒子系统、大规模实例化、或某些后处理几何生成，可能用 **分离布局** 来单独更新某些属性。
- 某些只输出深度的绘制可以从交织数据中只读位置属性，但 stride 仍然是整个顶点大小，所以缓存不一定省；如果性能敏感，可以考虑单独准备一份只有位置的 buffer。

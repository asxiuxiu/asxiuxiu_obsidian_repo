# 一条绘制命令触发整条流水线

## 问题 0：软渲染器里，"启动一轮绘制"这个动作的本质是什么？

回看软渲染器的入口：

```cpp
for (每个三角形 tri : 场景) {
    Triangle t = transform(tri, mvp);          // 顶点变换
    for (每个像素 p : t 覆盖的区域) {
        if (inside_triangle(p, t)) {
            float depth = interpolate_depth(p, t);
            if (depth < zbuffer[p]) {          // 深度测试
                zbuffer[p] = depth;
                framebuffer[p] = computeColor(p, t, lights);  // 着色并写入
            }
        }
    }
}
```

表面上"启动"是这个 `for` 循环。但循环只是**执行方式**，不是本质。抽掉循环看，一轮绘制真正依赖的是一组信息：

1. **画什么**：顶点数组 `场景`，以及"每 3 个顶点组成一个三角形"这个约定
2. **用什么规则变换和着色**：`transform` 和 `computeColor` 两段代码，外加它们引用的 `mvp`、`lights`
3. **画到哪**：`framebuffer` 和 `zbuffer`
4. **按什么规则测试**：深度小于旧值才覆盖

**启动一轮绘制 = 把这四组信息组织到位，然后让数据流过它们。** CPU 上我们用循环逐个像素地流；GPU 上循环不存在了，但信息需求一个都不少。

所以问题变成：如果让你给 GPU 设计一条"绘制指令"，它怎么才能把这四组信息交代清楚？

---

## 问题 1：这条指令必须回答哪几个问题？

先不看任何真实 API，纯粹从信息需求推导。GPU 拿到指令后要能独立干活，指令至少要回答：

| 指令要回答的问题 | 软渲染器里的对应物 |
|---|---|
| 图元是什么形状？（三角形/线/点） | 外层循环的步进方式（每 3 个顶点一组） |
| 顶点数据在哪？从第几个开始？取几个？ | `场景` 数组、循环的起止 |
| 顶点格式怎么解释？ | `Vertex` 结构体的内存布局 |
| 用哪段代码变换、哪段代码着色？ | `transform`、`computeColor` |
| 画到哪个帧缓冲？ | `framebuffer`、`zbuffer` |
| 测试规则是什么？ | `depth < zbuffer[p]` |

注意一个结构性的发现：**指令本身可以很"瘦"**。"画 3 个顶点组成的三角形"可能只需要几个字节就能说完；真正庞大的信息——几 MB 的顶点数据、Shader 程序、帧缓冲——都是指令**引用**的东西，而不是指令携带的东西。

这和软渲染器一模一样：`for` 循环体里也没有把顶点数组拷贝一遍，它只是拿着 `场景` 的引用。

## 问题 2：最 naive 的设计——每条指令自带全部信息——会出什么问题？

假设我们让每条绘制指令完全自包含：顶点数据、Shader、帧缓冲、测试规则全部打包在指令里发过去。

推演一下会发生什么：

- 一个模型画 60 帧，同一份顶点数据就要随指令传输 60 次——这正是 [[Notes/计算机图形学/GPU编程基础/把几何数据放到GPU能访问的地方|把几何数据放到 GPU 能访问的地方]] 里已经被否决的方案
- 一帧里画 100 个物体，Shader、测试规则这些"全场通用"的信息也要重复打包 100 次
- GPU 每收到一条指令都要重新验证一遍全部内容："这个 Shader 合法吗？这个格式和那个数据对得上吗？"

naive 方案的病根是：**它把"每帧不变的信息"和"每次绘制才变的信息"混在了一起。**

改进方案因此很自然：**状态与命令分离**。绘制之前，先把不变的信息摆到 GPU 能引用的位置上（顶点数据上显存、Shader 编译好、帧缓冲指定好）；绘制时，指令只做一件事——"用刚才摆好的那套东西，画 N 个顶点"。

这就是你在任何图形程序里都会看到的两段式结构的本质：

```cpp
// 阶段 A：摆信息（每帧或每个物体一次）
用这段 Shader
用这份顶点数据和这种格式解释
画到这个帧缓冲
测试规则设成这样

// 阶段 B：发指令（引用阶段 A 的一切）
绘制：三角形，从第 0 个顶点开始，取 3 个
```

OpenGL 用一个全局状态机表达"阶段 A 摆好的东西"；Vulkan/D3D12 把同一批信息显式打包成管线对象。表达方式的差异问题 7 再谈，这里先记住：**"draw 之前有一堆绑定调用"不是 API 繁琐，而是"指令瘦身"的必然结果**——你正在亲手把每帧不变的信息从指令里挪出去。

## 问题 3：命令到达 GPU 之后，硬件按什么顺序执行？

现在发出指令："用当前这套状态，画 3 个顶点，组成三角形"。GPU 内部展开的是一条固定的硬件流水线。先给全貌，再逐段对照软渲染器：

```
顶点获取          从显存按格式解释取出 3 个顶点
   │
顶点着色器        每个顶点并行执行一次，输出 gl_Position（裁剪空间）
   │
图元装配          3 个顶点按"三角形"规则组装成一个图元
   │
裁剪 + 透视除法   丢掉视锥外的部分，(x,y,z,w) 除以 w 得到 NDC
   │
视口变换          NDC [-1,1]² 映射到帧缓冲像素坐标
   │
光栅化            遍历三角形覆盖的像素，插值出每个像素的 vColor / 深度
   │
片段着色器        每个像素并行执行一次，输出颜色
   │
逐片段测试        深度测试、模板测试，决定这个像素是否覆盖旧值
   │
混合 + 写入       通过测试的颜色写进帧缓冲
```

逐项对照软渲染器（对照的前提是 [[Notes/计算机图形学/GPU编程基础/软渲染器到GPU管线的映射|软渲染器到 GPU 管线的映射]] 已经建立的全局地图，这里补上当时没展开的三个环节）：

| 流水线阶段 | 软渲染器对应物 | 可编程？ |
|---|---|---|
| 顶点获取 | `场景[i]` 取下标 | 否（但格式可声明） |
| 顶点着色器 | `transform(tri, mvp)` | **是** |
| 图元装配 | 外层循环"每 3 个一组" | 否 |
| 裁剪 + 透视除法 | 大多数软渲染器**偷懒跳过了** | 否 |
| 视口变换 | NDC 映射到 `width×height` | 否（但范围可设） |
| 光栅化 | `for(每个像素) inside_triangle` | 否 |
| 片段着色器 | `computeColor(...)` | **是** |
| 逐片段测试 | `if (depth < zbuffer[p])` | 否（但规则可配） |
| 混合 + 写入 | `framebuffer[p] = color` | 否（但规则可配） |

表格只是总结。真正值得注意的是两个软渲染器里大概率没有认真实现的阶段——裁剪和透视除法。它们恰恰是理解"GPU 为什么这样做"的最好入口。

## 问题 4：软渲染器没裁剪也活得好好的，GPU 为什么非要裁剪？而且为什么要在"w 还没除"的时候裁剪？

naive 想法：顶点着色器输出 `gl_Position = (x, y, z, w)`，先除以 w 得到 NDC，然后丢掉 `[-1,1]` 范围外的点不就行了？

推演这个方案会撞上的两堵墙：

**第一堵墙：w = 0 除零。** 透视投影下 w 正比于视空间深度，正好在相机平面上的点 w = 0，除法直接爆炸。

**第二堵墙更隐蔽：w < 0 的点除完会翻到错误的一侧。** 相机背后的点 w 是负的。比如一条线段从相机前方 (x=1, w=1) 连到相机正后方 (x=2, w=-1)——先除 w，两个端点变成 NDC x = 1 和 x = -2，看起来都在屏幕范围内或边缘，连接它们的线段应该横贯屏幕。但实际上这条线有一段在相机背后，根本不该出现。先除 w，几何关系被透视翻转破坏了，裁剪出的结果是错的。

出路是：**把裁剪条件改写成不需要除法的形式。**

"NDC 坐标在 [-1,1] 内"这个条件，即 `-1 ≤ x/w ≤ 1`，在 w > 0 时等价于：

$$-w \le x \le w$$

对 y、z 同理。这是一组**4D 齐次空间里的线性不等式**——不需要除法，w=0 和 w<0 的情况天然被这组不等式正确处理（w<0 时不等式无解，点被丢弃）。裁剪后的新顶点（线段与裁剪平面的交点）也在 4D 空间里线性插值生成，除法留到最后一步才做。

所以"顶点着色器输出的是裁剪空间坐标"这个设计不是随意的：**GPU 把"除以 w"这件危险的事推迟到所有几何决策（裁剪）都做完之后**，这就是 clip space 存在的全部理由。

> [!faq] 软渲染器为什么能逃过这一节？
> 如果你的软渲染器只渲染"保证在相机前方"的模型，w 恒为正且远大于 0，两堵墙都撞不上，先除 w 再裁剪也能碰巧正确。GPU 是通用硬件，必须正确处理任意顶点——包括横跨近平面、一半在相机背后的三角形。这也是"软渲染器能跑"和"工业管线正确"之间的典型差距。

裁剪完成、除完 w、映射到像素坐标之后，剩下的阶段就都是软渲染器里熟悉的环节了：光栅化替代 `inside_triangle` 循环，插值器替代手写的重心坐标插值，深度测试替代 `if (depth < zbuffer[p])`。这些在阶段一已经实现过，不再展开。

## 问题 5：回到指令本身——"画三角形，从第 0 个开始，取 3 个"，为什么恰好是这三个数字？

问题 2 说指令是"瘦"的。现在可以精确地说出它瘦到什么程度。一条顶点绘指令只需要携带：

1. **图元拓扑**：三角形 / 线段 / 点。GPU 需要它来回答问题 1 里的"每几个顶点组装成一个图元"
2. **起始位置**：从顶点流的第几个开始取
3. **顶点个数**：取几个

对照问题 2 的信息表，其余的答案（顶点在哪、格式怎么解释、用什么着色、画到哪、怎么测试）**全部在状态里**，指令一个字节都不用提。

为什么起始位置可以不是 0？因为顶点流是一块连续显存，一个场景的多组顶点可以首尾相接地存在同一块里，指令用"起始 + 个数"圈出本次要用的区间——这是"指令只引用不携带"的又一次体现。

如果用了索引（[[Notes/计算机图形学/GPU编程基础/告诉GPU顶点数据长什么样|EBO 顶点复用]]），指令语义只变一件事：**取的不是顶点序号，而是索引序号**，GPU 先查索引表再去取顶点。多了一层间接寻址，换来顶点复用，指令的"瘦"没有变。

## 问题 6：一条命令为什么能展开成上万个并行执行？顺序还保证吗？

这就是不需要写循环的最终答案。指令里"取 3 个顶点"会被 GPU 展开成 3 个并行的顶点着色器实例；光栅化产生的每个像素再展开成一个片段着色器实例。[[Notes/计算机图形学/GPU编程基础/GPU的并行执行模型|GPU 的并行执行模型]] 已经讲过这些实例如何被调度到成千上万个线程上——对开发者来说，**循环被"声明数据规模"替代了**。

但并行不是没有代价的，精确的说法是：

- **顶点之间无序**：不能假设顶点 0 比顶点 1 先执行完
- **像素之间无序**：不能假设左边的像素先着色
- **唯一保留的顺序保证**：同一条指令内，对**同一个像素位置**，深度测试和混合按固定规则串行发生——否则 Z-Buffer 就没意义了

软渲染器里循环天然串行，你从没想过"像素之间有顺序吗"。GPU 上这是一个真实的设计取舍：放弃全局顺序，换来万级并行；只在你真正需要的地方（同一像素的写入）保留串行语义。后续阶段学到的很多效果（透明混合排序）之所以麻烦，根源就在这里——混合依赖顺序，而 GPU 默认不给你顺序。

## 问题 7：CPU 发出这条命令之后，什么时候才真正执行？

`glDrawArrays`（或任何 API 的绘制调用）返回时，三角形**通常还没画**。

回到 [[Notes/计算机图形学/GPU编程基础/CPU怎么向GPU发命令|CPU 怎么向 GPU 发命令]] 建立的模型：CPU 的绘制调用只是往命令队列里**记录**了一条命令，驱动可能攒一批再翻译、再提交，GPU 则按自己的节奏消费队列。CPU 和 GPU 是两条异步的流水线：

```
CPU:  记录命令 → 记录命令 → 记录命令 → （继续跑游戏逻辑）
              ↘
命令队列:      [draw][draw][draw] ...
                          ↓
GPU:                        翻译/执行 → 执行 → 执行
```

这解释了几个直觉上奇怪的现象：

- 绘制调用几乎瞬间返回，不代表画完了
- CPU 提交得太快时会被"卡住"——那不是 GPU 慢，是命令队列满了，CPU 被迫等 GPU 消费
- 想知道 GPU 什么时候真的画完，需要额外的同步手段（这是 2.2 讲过的 fence/query 的用武之地）

所以本模块标题里"触发"这个词要精确理解：**CPU 触发的是命令的记录，GPU 的流水线是异步被触发的。**

## 问题 8：现代 API 对同一条指令的表达为什么不同？

到这里，"绘制指令"的非 API 知识结构已经完整：它是**对一组预先摆好的状态的引用 + 图元拓扑 + 起始位置 + 个数**，发出后异步执行。

各 API 的分歧只在一件事上：**"那组预先摆好的状态"，谁来保证它是一致、合法、可复用的？**

- **OpenGL**：状态散在全局状态机里，一条一条设。绘制时驱动要临时推断"当前这堆状态组合起来合法吗、要不要重新编译什么"。设计假设是"驱动比开发者聪明，能帮开发者兜底"——这是九十年代延续下来的兼容性哲学。代价是每次绘制的验证开销不可控。
- **Vulkan / D3D12**：要求开发者把"Shader + 顶点格式 + 测试规则 + 输出格式"**一次性显式打包成一个管线对象**（PSO），创建时完成全部验证，绘制时直接引用。绘制指令则先记录进命令缓冲，再整批提交。设计假设是"开发者比驱动更清楚哪些状态是一组的、什么时候录制什么时候提交"——把控制权从驱动手里拿回来，换多线程录制和可预测的低开销。
- **Metal**：同样的显式哲学（`MTLRenderPipelineState` + 命令编码器），只是按 Apple 的 API 风格组织。

对照问题 2 的结论会更清楚：状态与命令分离是**所有** API 的共同答案，分歧只在于"分离出来的状态由谁打包、何时验证"。OpenGL 让驱动在绘制时猜；现代 API 让你在创建时显式打包。这就是为什么学概念时 OpenGL 够用——它的隐式不妨碍你理解指令的本质。

## 问题 9：画一个三角形和画一万个物体，差在哪？

最后留一个通往引擎的因果伏笔。

画一个三角形：摆状态一次，发指令一次。画一万个物体：每个物体换一组状态（不同的顶点数据、不同的 Shader 参数），发一条指令——**一万次"摆状态 + 发指令"**。

问题出在每一条指令的 CPU 侧成本上。正如问题 7 所说，指令要被驱动验证、翻译、入队；这个成本是**按条计**的，和三角形多少几乎无关。画一个 3 顶点的三角形和画一个 100 万顶点的模型，CPU 侧的提交成本差不多。

于是一个反直觉的结论出现了：**一帧画一万个小物体，瓶颈往往不在 GPU 算不动，而在 CPU 来不及发一万条指令。** 这正是引擎阶段"合批"要解决的问题——把多组几何合并成一条指令能引用的形式，减少指令条数。现在不需要懂合批怎么做，只需要记住这个因果链：指令按条收费 → 条数成为瓶颈 → 减少条数是引擎渲染组织的第一要务之一。

## 概念落地：OpenGL 里的最小形态

上面所有的概念，在 OpenGL 里浓缩成这样的两段式（顶点数据上传、VAO 格式声明、Shader 编译、窗口上下文分别在前面几篇和 [[Notes/SelfGameEngine/Hello-Engine-Window/最简图形后端|最简图形后端]] 已经讲过，此处不重复）：

```cpp
// 阶段 A：摆信息（问题 2 的"状态与命令分离"）
glUseProgram(program);      // 用这段 Shader
glBindVertexArray(vao);     // 用这份顶点数据和格式解释
glViewport(0, 0, w, h);     // 视口变换的范围
// （深度测试等规则同理，此处默认）

// 阶段 B：发指令（问题 5 的三个数字）
glDrawArrays(GL_TRIANGLES,  // 图元拓扑
             0,             // 起始位置
             3);            // 顶点个数
```

每一行对应前面推导出的一个信息槽，没有一行是"为了 API 而 API"。执行后发生的事就是问题 3 的那条流水线，且如问题 7 所说，这个调用返回时像素多半还没写进帧缓冲。

# 从 OBJ 文件到第一个模型

这篇笔记**不讲新的 GPU 概念**——VBO、VAO、EBO、Shader、绘制命令在前面几篇已经讲透了。它回答的是工程问题：**数据从哪来**。

之前的三角形，顶点是你亲手写进代码的 9 个 float，你对每个字节的含义了如指掌。真实模型的顶点在文件里，是别人（建模软件）生成的几万行文本。从文件到屏幕，多出来的所有问题都在"数据的解析与整形"上——这也是引擎里 Mesh Import 链路的雏形。

## 问题 0：真实模型的顶点从哪来？

从文件。模型文件格式有很多（FBX、glTF、OBJ……），我们选 OBJ 作为第一个，因为它是**最朴素的纯文本交换格式**：

- 人眼可读，出错能直接打开文件检查；
- 几乎所有建模软件都能导出；
- 语法只有几种行，手写解析器完全可行。

一个 OBJ 文件里有四种关键行：

```obj
v  1.0 0.0 0.0     # 顶点位置（三份独立列表之一）
vt 0.5 1.0         # 纹理坐标：顶点对应图片上的哪个点（后续纹理阶段才用，先原样保留）
vn 0.0 0.0 1.0     # 顶点法线：这个顶点"面朝哪"（后续做明暗计算必需，先当成多一份属性）
f  1/1/1 2/2/1 3/3/1   # 面片：用三份列表的索引描述一个多边形
```

注意 OBJ 的设计：`v`、`vt`、`vn` 是**三份各自独立编号的列表**，面片行 `f` 用 `位置索引/UV索引/法线索引` 的形式把三份列表组合起来。这个"组合"设计正是后面问题 2 所有麻烦的根源。

> [!info] OBJ 不包含的东西
> OBJ 只描述几何和材质引用。贴图图片、材质参数在配套的另一个文件里——那是后续"用图片控制每个像素颜色"时要处理的事。现在先只把几何画出来。

## 问题 1：面片行 `f` 到底有几种写法？

最 naive 的假设：所有面片都长 `f v/vt/vn v/vt/vn v/vt/vn` 这样，三个顶点、每份索引齐全。拿这个假设去解析真实文件，**几乎必崩**。OBJ 规范允许的实际情况有四种：

```
f 5 8 11            # 只有位置：文件没有 UV 和法线
f 5/1 8/2 11/3      # 位置 + UV：没有法线
f 5//1 8//1 11//1   # 位置 + 法线：UV 位置留空（注意双斜杠）
f 5/1/1 8/2/1 11/3/1 # 三份齐全
```

还有三条容易漏掉的规则：

**规则一：索引从 1 开始，不是 0。** 这是 OBJ 的历史遗留设计，解析后必须减 1 才能当作 C++ 数组下标。忘了减 1，整个模型会顶点错位——但形状可能还"大致像个东西"，这种 bug 最难看出来。

**规则二：索引可以是负数。** 负数是**相对索引**：`-1` 表示"当前列表的最后一个"，`f -3 -2 -1` 表示"用列表末尾的倒数三个顶点"。建模软件分块导出时经常这么写。不处理负索引，解析到一半就会数组越界。

**规则三：面片不一定只有 3 个顶点。** OBJ 允许任意多边形（n-gon），`f 1/1 2/2 3/3 4/4` 是一个四边形面片。但 GPU 只画三角形，所以解析时要做**扇形三角化**：

```
四边形 (v0, v1, v2, v3)  →  三角形 (v0, v1, v2) + (v0, v2, v3)
```

> [!warning] 只取前三个顶点的后果
> 如果解析时偷懒只读每行前三个顶点，四边形面会丢掉一半——模型表面出现一个个三角形破洞。这种 bug 在复杂模型上极难靠肉眼定位。

解析规则用伪代码概括：

```
for 每一行:
    "v"  → 读 3 个 float，追加到 positions
    "vt" → 读 2 个 float，追加到 uvs
    "vn" → 读 3 个 float，追加到 normals
    "f"  → 读 N 个 "a/b/c" 三元组（b、c 可缺省；负数则加上当前列表长度转成正索引）
           全部减 1（转成 0 基）
           扇形三角化：for i in 1..N-1: 输出角点 (0, i, i+1)
```

到这里，你拿到的是一串"面角点"，每个角点是 `(posIdx, uvIdx, normalIdx)` 三个索引。下一个问题：这些角点能直接当 GPU 顶点用吗？

## 问题 2：为什么不能直接用 OBJ 的位置索引当 GPU 顶点索引？

回忆 [[Notes/计算机图形学/GPU编程基础/告诉GPU顶点数据长什么样#问题 5：真实模型里顶点被多个三角形复用，怎么办？|告诉 GPU 顶点数据长什么样]] 里的结论：顶点被多个三角形复用时，用一张索引表（EBO）让 GPU 只存一份顶点。那 OBJ 不是已经给了索引吗？`f 1/1/1` 里的 `1` 不就是顶点索引？

不是。OBJ 的三份索引表是**独立编号**的，而 GPU 的一份顶点缓冲区只能配一份索引表。矛盾在于：**"同一个几何点"不等于"同一个 GPU 顶点"。**

一个立方体的角，被三个面共享。如果三个面在这个角上的法线各不相同（硬边），这个几何点就对应**三个不同的 GPU 顶点**——位置相同，法线不同。反过来，一个光滑球面上的点被六个三角形共享且法线一致，它就应该只是**一个 GPU 顶点**。

所以 GPU 顶点的身份不是"几何位置"，而是**属性组合**。去重的键必须包含全部三份索引：

```
去重的信息结构：
    vertexCache: map<(posIdx, uvIdx, normalIdx) → 新顶点索引>
    vertices[]:  去重后的交织顶点（pos + normal + uv，见前置笔记的交织布局）
    indices[]:   EBO 用的索引序列

for 每个面角点 (p, t, n):
    if (p,t,n) 不在 vertexCache:
        vertices.push(组合 positions[p] + uvs[t] + normals[n])
        vertexCache[(p,t,n)] = 新索引
    indices.push(vertexCache[(p,t,n)])
```

### 去重的双重收益

**收益一：显存**。这在 [[Notes/计算机图形学/GPU编程基础/告诉GPU顶点数据长什么样#问题 6：用索引表组装三角形|前置笔记]]里已经算过账——立方体从 864 字节降到 264 字节。对真实模型，一个光滑网格的面角点数量大约是唯一顶点的 3~6 倍，去重直接省下一大半顶点显存和上传带宽。

**收益二：顶点着色器少跑几遍**。这一点前置笔记没展开，值得补上。GPU 在顶点着色阶段有一个硬件机制叫 **post-transform vertex cache**（变换后顶点缓存）：顶点着色器的输出按**索引**缓存，如果后续三角形引用了同一个索引，GPU 直接取缓存结果，不再重跑顶点着色器。

这带来两个推论：

- **这个缓存只在索引绘制时生效**。不用 EBO、把顶点复制 N 份的方案里，GPU 认为每个顶点都是新的，缓存完全失效——索引化除了省显存，还直接省顶点阶段的算力。
- **命中率取决于索引引用的局部性**。同一个索引被引用的时间越集中，缓存越有效。经典 GPU 是 16~32 个槽位的 FIFO 缓存；现代 GPU 机制不同（按索引把顶点分批送进线程组），但"引用局部性越好、重复着色越少"的结论不变（[OpenGL Wiki: Post Transform Cache](https://www.khronos.org/opengl/wiki/Post_Transform_Cache)、[meshoptimizer](https://meshoptimizer.org/)）。工业界甚至会专门重排三角形顺序来优化命中率（meshoptimizer 的 `meshopt_optimizeVertexCache`）——这属于进阶优化，现在只需知道：**你的去重质量直接决定 GPU 顶点阶段的效率下限**。

顺带一个实用推论：去重后顶点数大幅下降，常常让 16 位索引（上限 65535）重新变得够用——对照 [[Notes/计算机图形学/GPU编程基础/告诉GPU顶点数据长什么样#问题 6：用索引表组装三角形|前置笔记的索引位宽表]]，能省一半索引显存。

## 问题 3：如果文件里没有法线怎么办？

问题 1 说过，`f 5/1 8/2 11/3` 这种行意味着文件根本没给法线。但法线是每个顶点"面朝哪"的信息，后续做任何明暗计算都缺不了它。怎么办？

**从几何本身重建。** 三角形所在平面的朝向可以由两条边的叉积得到：

```
for 每个三角形 (a, b, c):
    faceNormal = cross(pos[b] - pos[a], pos[c] - pos[a])
    // 累加到三个顶点上
    normal[a] += faceNormal; normal[b] += faceNormal; normal[c] += faceNormal

for 每个顶点: normal[i] = normalize(normal[i])
```

这个算法有个漂亮的性质：**不需要除以三角形面积**。叉积的模长正比于三角形面积，所以大三角形对共享顶点法线的"投票"天然权重更大——这正是我们想要的面积加权平均，一步到位。

这个算法同时解释了为什么平滑和硬边不需要特殊处理：同一位置在不同面上法线差异大时，问题 2 的去重键 `(posIdx, uvIdx, normalIdx)` 本来就会把它们拆成不同顶点——重建法线时按"新顶点索引"累加，机制自然对齐。

## 问题 4：解析都对了，为什么屏幕上还是什么都没有？

这是第一个模型加载时**最高频**的"bug"：代码没错，模型只是不在你看得见的地方。

原因：**OBJ 没有任何单位和坐标约定。** 建模师可能以 `(1000, 500, -300)` 为中心建了一个跨度 5000 单位的模型，而你的相机看着原点附近 ±2 的范围。模型整个在视野之外，或者巨大到相机贴在它表面的一个三角形里。

通用对策是**包围盒归一化**——加载任何陌生模型后的第一步：

```
min = max = vertices[0].pos
for 每个顶点: 逐分量更新 min / max        # 得到 AABB（轴对齐包围盒）

center = (min + max) / 2
scale  = 目标尺寸 / max(max - min 的各分量)   # 按最长边等比缩放

for 每个顶点: pos = (pos - center) * scale    # 中心移到原点，缩放到目标尺寸
```

两步之后，任何模型都会以合理大小出现在原点，和你的相机、MVP 变换兼容。

这个 AABB 不是一次性的调试工具——它是"用一个简单体积近似一堆几何"的结构，后续判断"物体是否在相机视野内"时还会反复用到它。现在先记住：**拿到陌生几何数据，先算包围盒**。

```cpp
// 位置、UV 的配置同前置笔记；新增法线：location 1

```


## 问题 6：几万个顶点，怎么验证解析和整形是对的？

肉眼没法检查 `vector<Vertex>` 里的几万个数。思路是**让数据自己画出诊断图**——用片段着色器把顶点数据可视化成颜色。

**诊断一：UV 棋盘格。** 如果 UV 解析正确且插值连续，模型表面应该呈现平滑渐变的棋盘格；UV 错乱会表现为棋盘格撕裂、跳变：

```glsl
// 片段着色器：用 UV 画棋盘格
float cx = step(0.5, fract(vUV.x * 8.0));
float cy = step(0.5, fract(vUV.y * 8.0));
float checker = abs(cx - cy);
FragColor = vec4(vec3(0.2 + 0.8 * checker), 1.0);
```

**诊断二：法线可视化。** 把法线从 `[-1,1]` 映射到 `[0,1]` 当颜色输出。朝向一致的面颜色一致，法线算错的面会突然变色：

```glsl
// 片段着色器：法线转颜色
FragColor = vec4(normalize(vNormal) * 0.5 + 0.5, 1.0);
```

**诊断三：打印统计数字。** 加载后输出一行统计，和建模软件里看到的数字对照：

```
positions=1204 uvs=980 normals=1502 → 面角点=3468 去重后顶点=892 三角形=1156
去重率 = 3468 / 892 ≈ 3.9   （光滑网格典型值 3~6，偏离太多说明去重键有问题）
```

三个诊断手段覆盖了三类数据源（UV、法线、拓扑）。养成习惯：**每加一个数据通道，先写它的诊断可视化，再写正式效果。**

## 常见错误（OBJ 特有）

1. **索引忘减 1**：OBJ 索引从 1 开始。
2. **没处理负索引**：相对索引要加上当前列表长度再减 1。
3. **去重键只用位置索引**：必须是 `(posIdx, uvIdx, normalIdx)` 三元组，否则硬边被错误平滑、UV 接缝被撕裂。
4. **n-gon 没三角化**：只读前三个顶点会丢面，必须扇形三角化。
5. **模型没归一化**：屏幕上"什么都没有"时先怀疑模型在视野外，先算包围盒。
6. **法线累加后忘归一化**：面积加权靠叉积模长是对的，但最终使用时必须是单位向量。

EBO 没绑进 VAO、`glVertexAttribPointer` 捕获错误 VBO 这类 GPU 侧的坑，[[Notes/计算机图形学/GPU编程基础/告诉GPU顶点数据长什么样#问题 6：用索引表组装三角形|前置笔记的"最常见的三个坑"]]已经讲过，不再重复。

## 工程视角：手写解析只是第一步

学习阶段手写解析器的价值在于：你被迫理解了"文件里的索引组合 → GPU 的顶点+索引"的每一步整形。

工程实践中要替换掉其中两环：

- **解析**：用成熟库（如 tinyobjloader，单头文件），边界情况（负索引、n-gon、缺省字段）都已处理。
- **格式**：OBJ 是交换格式，不是运行时格式。文本解析慢、体积大、还要在加载时去重。引擎通常**离线**把模型转成自定义二进制格式——顶点已去重、布局已交织、直接映射进内存上传 GPU。这正是引擎"资源导入管线"要解决的问题，后续引擎阶段会展开。

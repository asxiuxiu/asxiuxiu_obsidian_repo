# GPU 的并行执行模型

## 问题 0：软渲染器那么慢，瓶颈到底在哪？

回顾一下软渲染器的核心循环：

```cpp
for (int y = minY; y <= maxY; y++) {
    for (int x = minX; x <= maxX; x++) {
        // 1. 判断像素是否在三角形内（边缘函数）
        // 2. 计算重心坐标
        // 3. 透视校正插值
        // 4. Z-Buffer 深度测试
        // 5. 写入颜色缓冲
    }
}
```

一个 1920×1080 的屏幕约 200 万个像素，一个复杂场景有几十万个三角形。CPU 串行执行时，这个循环要执行几十万次。

### 最 naive 的想法：用多线程加速

"CPU 有 8 个核心，我让 8 个线程同时处理不同的像素行不就行了？"

立刻发现的问题：

1. **并行度不够**：8 个线程远远不够，复杂场景需要同时处理成千上万个像素。
2. **内存带宽瓶颈**：所有线程竞争访问同一个颜色缓冲区和 Z-Buffer，产生大量**伪共享（False Sharing）**。
3. **分支发散**：不同像素执行路径不同——有的在三角形内，有的在外。CPU 分支预测器对这种不规则模式束手无策。
4. **延迟暴露**：CPU 做浮点运算需要等待结果，缓存未命中时要等上百个周期，核心在"发呆"。

多线程 CPU 渲染确实比单线程快几倍，但离"实时 3D 游戏"的帧率还差几个数量级。

## 问题 1：渲染任务的计算模式有什么特殊之处？

CPU 擅长：复杂控制流、分支跳转、操作系统调度、数据库查询——每个任务的计算路径都不同。

GPU 面临的事情：对于屏幕上被同一个三角形覆盖的数千个像素，计算路径**几乎完全相同**——

- 都执行同样的边缘函数判断
- 都执行同样的重心坐标插值
- 都执行同样的光照公式
- 都访问同样的纹理

只有输入数据不同：每个像素的位置、深度、UV 坐标不一样。

**这就是数据并行（Data Parallelism）**，也叫 **SIMD（Single Instruction, Multiple Data，单指令多数据）**。

```
CPU 模式（8个复杂核心）：
┌─────────┐ ┌─────────┐ ┌─────────┐
│ 任务A   │ │ 任务B   │ │ 任务C   │   ← 完全不同的事情
│ 解析JSON│ │ 编译Shader│ │ 物理模拟│
└─────────┘ └─────────┘ └─────────┘

GPU 模式（数千个简单核心）：
┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐
│P1 │ │P2 │ │P3 │ │P4 │ │P5 │ │P6 │   ← 做同一件事：着色
│红 │ │绿 │ │蓝 │ │红 │ │绿 │ │蓝 │   ← 只是数据不同
└───┘ └───┘ └───┘ └───┘ └───┘ └───┘
```

## 问题 2：GPU 是怎么设计的？

### 核心思想：用大量简单核心换吞吐量

CPU：每个核心都很"聪明"——复杂分支预测、乱序执行、大容量缓存，追求**单线程性能**。

GPU：每个核心都很"笨"——没有复杂分支预测，缓存很小，但数量极多，追求**总体吞吐量**。

> **比喻**：CPU 像是 8 个大学教授，每个人能独立解决复杂问题；GPU 像是 10000 个小学生，每个人只会做简单加减乘除，但 10000 人同时做，总吞吐量惊人。

### GPU 的层级结构

```
GPU 芯片
├── Streaming Multiprocessor (SM) × 80~140个
│   └── CUDA Core / Shader Core × 128~256个
│   └── Shared Memory（高速共享内存）
│   └── 寄存器文件（海量寄存器）
├── L2 Cache（全局缓存）
└── 显存（GDDR6/HBM，高带宽）
```

- **SM（Streaming Multiprocessor）**：GPU 的"调度车间"。每个 SM 同时管理几十组线程，核心职责是**延迟隐藏**——当一组线程去显存取数据卡住了，SM 立刻把另一组准备好的线程顶上来。
- **CUDA Core / Shader Core**：执行乘加运算的小核心。
- **Shared Memory**：每个 SM 内部的一块超高速小内存，同一个 SM 里的线程可以通过它快速共享数据。
- **寄存器文件**：每个线程私有的临时变量空间。GPU 配备海量寄存器，这是 SM 能实现零成本 Warp 切换的前提。

**关键数字对比**：

| 特性 | 高端 CPU (i9) | 高端 GPU (RTX 4090) |
|---|---|---|
| 核心数 | 24 核 | 16384 个 CUDA 核 |
| 内存带宽 | ~100 GB/s | ~1000 GB/s |
| 单线程性能 | 极高 | 较低 |
| 适合的任务 | 串行、复杂分支 | 并行、相同计算 |

## 问题 3：Warp / Wavefront 是什么？

GPU 里的线程不是单独调度的，而是**成群调度**。

- **NVIDIA**：32 个线程组成一个 **Warp**
- **AMD**：64 个线程组成一个 **Wavefront**
- **Intel**：通常是 16 或 32 个线程一组

一个 Warp 内的线程共享同一个程序计数器（PC），执行**完全相同的指令**，只是操作不同的数据。

```
Warp = 32个线程

时钟周期 1：所有32个线程同时执行"加载顶点位置"
时钟周期 2：所有32个线程同时执行"矩阵乘法"
时钟周期 3：所有32个线程同时执行"写回结果"

32个线程 × 32个核心 = 一步处理32个顶点/像素
```

为什么偏偏是 32 个？这是 NVIDIA 硬件的固定宽度，就像 CPU 缓存行固定是 64 字节一样，属于硬件设计约定。

## 问题 4：延迟隐藏是怎么工作的？

GPU 的核心虽然简单，但有一个绝妙的机制：**当一个 Warp 在等待内存数据时，马上切换到另一个 Warp 执行**。

```
Warp A：执行 → 请求纹理采样（等待100个周期）→ 挂起
  ↓ 切换（零开销）
Warp B：执行 → 请求内存读取（等待200个周期）→ 挂起
  ↓ 切换
Warp C：执行 → ...
```

每个 SM 可以同时管理几十个 Warp。只要有足够的 Warp 在"排队"，GPU 的核心就永远不会空闲。

**Little's Law**：并行度 = 吞吐量 × 延迟。如果一次内存访问要等 100 个周期，而每个周期都想完成 1 个操作，那至少要有 100 个操作在同时"飞行"才能把延迟盖住。GPU 正是通过海量线程提供这个并行度。

## 问题 5：分支发散对 GPU 有什么影响？

Warp 里的 32 个线程共享一个 PC，所以它们必须执行相同的指令。

如果代码里有分支：
```glsl
if (uv.x > 0.5) {
    color = red;
} else {
    color = blue;
}
```

Warp 里有些线程走 `if` 分支，有些走 `else` 分支。GPU 不能同时执行两个分支，只能：
1. 先让走 `if` 分支的线程执行，`else` 分支的线程被屏蔽（不写入结果）
2. 再让走 `else` 分支的线程执行，`if` 分支的线程被屏蔽

这叫做**分支发散（Branch Divergence）**。最坏情况下，一个 Warp 要串行执行所有分支路径。

**对 Shader 代码的启示**：
- 尽量减少 Warp 内线程走不同分支的情况
- 同一 Warp 内的相邻像素最好执行相同路径

## 问题 6：为什么三角形是 GPU 的基本图元？

你可能会问：既然 GPU 这么擅长并行，为什么不用四边形、多边形，偏偏是三角形？

**第一，三角形天然保证平面性。** 三个点一定共面，四边形四个顶点可能不在同一平面上，渲染时容易出现裂缝。

**第二，判断像素是否在三角形内非常简单。** 边缘函数本质上是叉乘，硬件实现非常高效。

**第三，任何多边形都能拆成三角形。**

```
四边形 → 2个三角形
五边形 → 3个三角形
复杂模型 → 几千个三角形
```

**第四，GPU 的光栅化器是固定功能硬件。** 它并行计算三条边的边缘函数、并行插值深度/颜色/纹理坐标、硬件做 Z-Test——这些单元从设计之初就假设输入是三角形。

## 问题 7：那软渲染器的代码对应 GPU 的什么？

| 软渲染器（CPU 代码） | GPU 对应物 | 是否可编程 |
|---|---|---|
| `for(每个顶点)` + MVP 矩阵乘法 | **顶点着色器** | ✅ |
| 三角形组装、裁剪、透视除法 | **图元装配** | ❌ |
| `for(每个像素)` + 边缘函数 | **光栅化器** | ❌ |
| 透视校正插值 | **插值器** | ❌ |
| `computeColor()` + Blinn-Phong | **片段着色器** | ✅ |
| Z-Buffer 深度测试 | **深度测试单元** | ⚠️ |
| 写入颜色缓冲 | **ROP** | ⚠️ |

**核心洞察**：你在软渲染器里写的所有代码，在 GPU 上被拆成两半——
- **可编程部分**：顶点着色器、片段着色器
- **固定硬件部分**：光栅化、深度测试、输出合并

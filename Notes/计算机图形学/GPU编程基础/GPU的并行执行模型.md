# GPU 的并行执行模型

## 问题 0：软渲染器的双重 `for` 循环，为什么不能直接搬到 GPU 上？

在 [[Notes/计算机图形学/软光栅化与3D数学/3D光栅化与深度缓冲|3D光栅化与深度缓冲]] 里，你的软渲染器核心逻辑大概是这个形状：

```cpp
for (int y = minY; y <= maxY; y++) {
    for (int x = minX; x <= maxX; x++) {
        // 1. 判断像素是否在三角形内（边缘函数）
        // 2. 计算重心坐标
        // 3. 透视校正插值
        // 4. Z-Buffer 深度测试
        // 5. 写入颜色缓冲
    }
}
```

一个 1920×1080 的画面约 200 万个像素，复杂场景有几十万个三角形。CPU 串行执行时，这个循环要跑很多很多次，所以软渲染器通常每秒只能渲染几帧。

### 最 naive 的想法：用多线程加速

"CPU 有 8 个核心，我让 8 个线程同时处理不同的像素行不就行了？"

立刻会发现几个天花板：

1. **并行度不够**：8 个线程远远不够。复杂场景需要同时处理成千上万个像素，而 CPU 核心数只有个位数到几十。
2. **内存带宽瓶颈**：所有线程都在读同一个颜色缓冲和 Z-Buffer。CPU 缓存行只有 64 字节，多个核心反复争夺同一块缓存，会产生大量 [[Notes/C++编程/对象内存模型与底层机制/缓存行、false sharing 与内存布局|伪共享]]（False Sharing）。
3. **分支发散**：不同像素的执行路径不同——有的在三角形内（要着色），有的在外（跳过）。这个判断结果完全取决于像素位置，没有固定规律，CPU 的分支预测器会频繁猜错，导致流水线清空。
4. **延迟暴露**：CPU 做浮点运算要等结果，缓存未命中时要等上百个周期，这段时间核心只能"发呆"。

多线程 CPU 渲染确实比单线程快几倍，但离"实时 3D 游戏"还差几个数量级。这说明问题不是"核心不够多"，而是**CPU 的架构不适合这种计算模式**。

## 问题 1：渲染任务的计算模式有什么特殊之处？

CPU 擅长的事：复杂控制流、分支跳转、操作系统调度、数据库查询——这些场景的特点是**不同任务走完全不同的代码路径**，而且分支结果通常有规律可循（比如循环、状态机、缓存命中模式），CPU 的分支预测器能很好地利用这些规律。

GPU 面临的事：对于屏幕上被同一个三角形覆盖的几千个像素，它们的计算路径**几乎完全相同**——

- 都执行同样的边缘函数判断；
- 都执行同样的重心坐标插值；
- 都执行同样的光照公式；
- 都访问同样的纹理。

只有输入数据不同：每个像素的位置、深度、UV 坐标不一样。

**这就是数据并行（Data Parallelism）**：同一个程序，跑在不同数据上。CPU 的 [[Notes/操作系统/CPU与内存架构/计算机体系结构速览：CPU、内存与总线#SIMD 与图形管线|SIMD]]（Single Instruction, Multiple Data，单指令多数据）也是这个思想，只不过 GPU 把它推到了极致。

```
CPU 模式（8 个复杂核心）：
┌─────────┐ ┌─────────┐ ┌─────────┐
│ 任务 A  │ │ 任务 B  │ │ 任务 C  │   ← 完全不同的事情
│ 解析 JSON│ │ 编译 Shader│ │ 物理模拟│
└─────────┘ └─────────┘ └─────────┘

GPU 模式（数千个简单核心）：
┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐
│P1 │ │P2 │ │P3 │ │P4 │ │P5 │ │P6 │   ← 做同一件事：着色
│红 │ │绿 │ │蓝 │ │红 │ │绿 │ │蓝 │   ← 只是数据不同
└───┘ └───┘ └───┘ └───┘ └───┘ └───┘
```

> **比喻**：CPU 像是 8 个大学教授，每个人能独立解决复杂问题；GPU 像是 10000 个小学生，每个人只会做简单加减乘除，但 10000 人同时做，总吞吐量惊人。

这个比喻有个重要限制：如果 10000 个小学生要做的题不一样，GPU 就会非常难受。后面讲分支发散时我们会回到这个限制。

## 问题 2：GPU 为什么要设计成"很多简单核心"？

CPU 的设计哲学：每个核心都很"聪明"——复杂分支预测、乱序执行、大容量缓存，追求**单线程性能**。

GPU 的设计哲学：每个核心都很"笨"——没有复杂分支预测，缓存很小，但数量极多，追求**总体吞吐量**。

### GPU 的层级结构（简化版）

以 NVIDIA GPU 为例，一颗芯片内部大致长这样：

```
GPU 芯片
├── Streaming Multiprocessor (SM) × 几十个到一百多个
│   └── CUDA Core / Shader Core × 上百个
│   └── Shared Memory（每个 SM 内的高速小内存）
│   └── 寄存器文件（海量寄存器）
├── L2 Cache（全局缓存）
└── 显存（GDDR6/HBM，高带宽但高延迟）
```

不要被缩写吓到，每一层都有明确分工：

- **SM（Streaming Multiprocessor）**：GPU 的"调度车间"。每个 SM 同时管理几十组线程，核心职责是**延迟隐藏**——当一组线程去显存取数据卡住了，SM 立刻把另一组准备好的线程顶上来。
- **CUDA Core / Shader Core**：真正执行乘加运算的小核心。它们没有复杂分支预测，只会按统一指令做同样计算，但数量极多。
- **Shared Memory**：每个 SM 内部的一块超高速小内存，比显存快几十倍，但通常只有几十到几百 KB。同一个 SM 里的线程可以通过它快速共享数据。
- **寄存器文件**：每个线程私有的临时变量空间。GPU 为了同时维护几千个活跃线程，配备了海量寄存器——这是 SM 能实现零成本 Warp 切换的硬件前提。
- **L2 Cache / 显存**：L2 是整颗芯片共享的缓存；显存容量大、带宽高，但 SM 去显存取数要等上百个时钟周期，这正是延迟隐藏机制存在的原因。

> **关键数字对比**：
>
> | 特性 | 高端 CPU (i9) | 高端 GPU (RTX 4090) |
> |---|---|---|
> | 核心数 | 24 核 | 16384 个 CUDA 核 |
> | 内存带宽 | ~100 GB/s | ~1000 GB/s |
> | 单线程性能 | 极高 | 较低 |
> | 适合的任务 | 串行、复杂分支 | 并行、相同计算 |
>
> 这个表格只是帮你建立数量级直觉，不必背数字。

### 为什么 GPU 能放这么多核心？

因为 GPU 核心**简单**。它们共享指令解码器、共享控制逻辑。一组核心（通常是 32 个）执行**完全相同的指令**，只是操作不同的数据。

**代价**：如果同一组核心里，有的要走分支 A，有的要走分支 B，它们不能同时执行两个分支——必须串行执行。这就是后面要说的**分支发散**。

## 问题 3：Warp / Wavefront 是什么？为什么 32 个线程绑在一起？

GPU 里的线程不是单独调度的，而是**成群调度**。

- **NVIDIA**：32 个线程组成一个 **Warp**。
- **AMD**：64 个线程组成一个 **Wavefront**。
- **Intel**：通常是 16 或 32 个线程一组。

一个 Warp 内的线程共享同一个程序计数器（PC），执行**完全相同的指令**，只是操作不同的数据。

```
Warp = 32 个线程

时钟周期 1：所有 32 个线程同时执行"加载顶点位置"
时钟周期 2：所有 32 个线程同时执行"矩阵乘法"
时钟周期 3：所有 32 个线程同时执行"写回结果"
```

> **比喻**：Warp 就像一辆载了 32 名工人的班车。司机（SM）给每个人发同一张操作清单，同一时刻所有人执行同一步骤，只是各自处理自己手里的零件（数据）。

为什么偏偏是 32？这是 NVIDIA 硬件的固定宽度，就像 CPU 缓存行固定是 64 字节一样，属于硬件设计约定。你只要知道"Warp 是 GPU 调度的最小车队"就够了。

这种执行模型叫做 **SIMT（Single Instruction, Multiple Threads，单指令多线程）**。它和 SIMD 的核心区别是：SIMD 需要你手动把数据打包成向量；SIMT 让你写"每个线程单独做什么"的程序，硬件自动把 32 个线程打包成 Warp 执行。

## 问题 4：延迟隐藏是怎么让 GPU 不"发呆"的？

GPU 的核心虽然简单，但有一个绝妙的机制：**当一个 Warp 在等待 GPU 显存（或 L2 / 纹理缓存）中的数据时，SM 马上切换到另一个 Warp 执行**。

```
Warp A：执行 → 请求纹理采样（等待 100 个周期）→ 挂起
  ↓ 切换（零开销）
Warp B：执行 → 请求内存读取（等待 200 个周期）→ 挂起
  ↓ 切换
Warp C：执行 → ...
```

每个 SM 可以同时管理几十个 Warp。只要有足够的 Warp 在"排队"，GPU 的核心就永远不会空闲。

> **注意**：Warp 等待的是 **GPU 自己的显存**。Shader 运行前，顶点、纹理、uniform 等数据通常已经通过命令通道从 CPU 内存上传到 GPU 显存；正在执行的 Warp 不会直接访问 CPU 内存。如果数据还在 CPU 那边，先发生的是一次 CPU→GPU 上传，而不是 Warp 空等。

**Little's Law**：并行度 = 吞吐量 × 延迟。如果一次内存访问要等 100 个周期，而每个周期都想完成 1 个操作，那至少要有 100 个操作在同时"飞行"才能把延迟盖住。GPU 正是通过海量线程提供这个并行度。

> **代价**：每个线程用的寄存器越多，同时能驻留的 Warp 就越少，延迟隐藏能力就越差。所以 Shader 写得太复杂（临时变量太多）反而会让 GPU 变慢——这是写 Shader 时第一个反直觉的地方。

## 问题 5：分支发散对 GPU 有什么影响？

Warp 里的 32 个线程共享一个 PC，所以它们必须执行相同的指令。

如果 Shader 里有分支：

```glsl
if (uv.x > 0.5) {
    color = red;
} else {
    color = blue;
}
```

一个 Warp 里有些线程走 `if` 分支，有些走 `else` 分支。GPU 不能同时执行两个分支，只能：

1. 先让走 `if` 分支的线程执行，`else` 分支的线程被屏蔽（不写入结果）；
2. 再让走 `else` 分支的线程执行，`if` 分支的线程被屏蔽。

这叫做**分支发散（Branch Divergence）**。最坏情况下，一个 Warp 要串行执行所有分支路径。

> **比喻**：班车走到一个岔路口，一半工人要左转，一半要右转。司机只有一张地图，于是先让左转的人下车走一段，右转的人在车上等着；再让右转的人走，左转的人等着。整个车队的总时间 = 左转时间 + 右转时间。

**对 Shader 代码的启示**：

- 尽量减少 Warp 内线程走不同分支的情况。
- 同一 Warp 内的相邻像素最好执行相同路径。
- 如果分支条件对同一个 draw call 里的所有像素都一样（比如由 uniform 控制），就不会发散。

这个约束你现在记住就行，后续写光照、材质、后处理 Shader 时会反复遇到。

## 问题 6：这些硬件特性，对写 Shader 有什么实际约束？

把前面的内容收束一下，GPU 的并行模型对 Shader 代码有三条主要约束：

1. **同 Warp 内像素尽量走相同分支**
   - 否则分支发散会让 GPU 串行执行多条路径。
   - 典型反例：在片段着色器里按 `materialID` 分支。

2. **尽量减少显存随机访问和纹理采样次数**
   - GPU 显存带宽高，但延迟也高；随机访问会让 Warp 频繁挂起。
   - 纹理采样虽然会被缓存，但采样次数过多仍然是性能瓶颈。

3. **控制 Shader 的复杂度和寄存器用量**
   - Shader 越复杂，每个线程用的寄存器越多，同时驻留的 Warp 越少，延迟隐藏能力下降。
   - 这不是说"Shader 越简单越好"，而是说"在实现效果的前提下，别让 GPU 的核心闲着"。

> **核心认知**：GPU 不是"更快的 CPU"，而是"另一种处理器"。你在软渲染器里写的代码不能直接搬到 GPU 上；你必须把计算拆成"每个顶点都一样"和"每个像素都一样"的两段小程序，并遵守 Warp 的约束。

## 问题 7：那软渲染器的代码对应 GPU 的什么？

把软渲染器的逻辑映射到 GPU 管线，能帮你带着并行视角重新理解 [[Notes/计算机图形学/GPU编程基础/软渲染器到GPU管线的映射|软渲染器到 GPU 管线的映射]] 那张表：

| 软渲染器代码 | GPU 对应物 | 并行方式 | 是否可编程 |
|---|---|---|---|
| `for(每个顶点)` + MVP 矩阵乘法 | **顶点着色器** | 每个顶点一个线程 | ✅ |
| 三角形组装、裁剪、透视除法 | **图元装配** | 固定硬件 | ❌ |
| `for(y) for(x)` + 边缘函数 | **光栅化器** | 每个三角形并行生成片段 | ❌ |
| 重心坐标插值颜色 / UV / 深度 | **插值器** | 固定硬件 | ❌ |
| `computeColor()` + 光照 | **片段着色器** | 每个像素一个线程 | ✅ |
| `if (z >= zbuffer) continue;` | **深度测试** | 固定硬件 | ⚠️ 可配置 |
| `framebuffer[x,y] = color;` | **ROP / 颜色混合** | 固定硬件 | ⚠️ 可配置 |

> 符号说明：✅ 可编程；❌ 固定硬件；⚠️ 固定硬件但可配置行为。

**关键洞察**：你在软渲染器里写的所有代码，在 GPU 上被拆成两半——

- **可编程部分**：顶点着色器、片段着色器（你写 Shader 代码）。
- **固定硬件部分**：光栅化、深度测试、输出合并（GPU 自动做，你无法改算法）。

可编程的部分之所以能被并行执行，是因为 GPU 用 Warp 把成千上万个顶点/像素打包成一组，让它们共享指令、各用各的数据。

# 蒙皮矩阵：从骨骼姿势到顶点变形

> [!todo] 本篇核心问题
> `skin matrix` 怎么由骨骼姿势与 bind pose 推导出来？为什么必须乘上 `Bind⁻¹`？

> [!tip] 先回答一个更实际的问题：需要懂多深？
> 调动画时你对蒙皮矩阵的全部需求是：
> 1. **知道它是"这根骨骼相对绑定姿势的位移量"**——不是"骨骼现在在哪"。
> 2. **知道 `BoneCurrent × BoneBind⁻¹` 里那个 `⁻¹` 的存在理由**——它负责把顶点从"模型空间"搬进"骨骼自己的空间"。
> 3. **知道 `BoneBind⁻¹` 是加载时算一次、缓存起来的常量**——运行时每帧做的只有一次矩阵乘法。
>
> 至于矩阵怎么展开（3×4 里的 12 个数各是什么）、四元数怎么转成矩阵，属于内部机制，本篇不展开。

## 为什么需要解决这个问题

前两篇 [[Notes/动画系统/角色资产与骨骼基础/骨骼的本质：从骨架到 Skeleton 资产|《骨骼的本质》]] 和 [[Notes/动画系统/角色资产与骨骼基础/骨骼网格与蒙皮：顶点怎么绑到骨骼上#线性混合蒙皮：加权求和|《骨骼网格与蒙皮》]] 一路推到这样一句话：**一个顶点由几根骨骼按权重"拽着"**——这里的"拽"是一种比喻说法，机制上还没有任何一根骨骼真的去搬动顶点；权重只是一个 0~1 的数，表示"这根骨骼对顶点的影响占几成"。比如膝盖附近那个顶点，绑了 70% 给小腿、30% 给大腿，所以弯膝时它会走到一个"折中位置"，皮肤看起来才像是弯的。

但还剩最后一环没交代：每根骨骼手上的这份影响力，到底**按什么公式把顶点搬到新位置**？（这篇讲单根骨骼怎么算，多根怎么合在最后一节。）

最直觉的做法是：骨骼现在在哪，就把顶点搬到哪。结果是灾难——**整块模型会"跳"到骨骼身上去**。原因很朴素：顶点记录的位置是**模型空间**的坐标（"模型空间"就是以角色模型自己的原点为原点的那套坐标系），比如"在模型原点上方 1.05 米、正前方 3 厘米"，而骨骼的世界位置是**世界空间**的坐标（以场景原点为原点），可能是"距离场景原点 40 厘米、抬到 1.3 米高"。两者根本不在一个坐标系里。直接把顶点设成骨骼的世界坐标，等于宣布"这块皮肤长在骨骼的原点上"——模型会缩成一堆挤在骨头尖上的碎块。

真正需要的东西比"骨骼在哪"更绕一层，也比它更有用：不问骨骼**现在在哪**，而是问它**离开了绑定位之后动了多少**——骨骼不动，顶点就不动；骨骼动多少，顶点跟着动多少。这个"相对量"就是整篇的出发点。

## 直观理解：橡皮筋与钉子

把场景缩到二维，拿一根真实的小臂来看。

绑定姿势（**bind pose**，也叫参考姿势：建模时角色摆的那个标准姿势，通常就是双臂平举的 T-Pose；它在数据里长什么样，见 [[Notes/动画系统/角色资产与骨骼基础/骨骼的本质：从骨架到 Skeleton 资产#Skeleton 资产里到底存了什么|《骨骼的本质》]]）下，有一条皮肤——比如手肘到手腕那段前臂的表面。这条皮肤上的每一个点，在**模型空间**里都有一个确定的坐标，这是建模时量出来的。同时，小臂骨也在这段皮肤的正中央，它在这个姿势下也有一个确定的**世界变换**，记作 `BoneWorld_bind`。

现在，往这段皮肤和小臂骨之间拉一根橡皮筋。**绑定的那一刻，橡皮筋松紧正好——皮肤老老实实贴在小臂上。**

接下来动画跑起来了。小臂骨抬起来、转过去，跑到了新的位置 `BoneWorld_current`。这时候你会希望皮肤怎么动？当然是**跟着小臂一起被带过去**——而且带的是"小臂走了多远、转了多大角度"，不是"小臂现在在哪"。

这就是橡皮筋那笔账的全部内容：

- 橡皮筋记下来的不是钉子在哪，而是**钉子从绑定时移动了多少**；
- 皮肤在绑定那一刻已经贴好了，它只需要照着这笔位移**整体挪过去**；
- 所以皮肤最终的形态 = **绑定姿势 + 骨骼的位移量**，而不是"骨骼的当前位置"。

把这笔账写成公式时会冒出一个**逆矩阵**，下一节就来看它是从哪儿来的。

## 核心机制

### 数据流位置：蒙皮是姿势数据的终点站

```mermaid
graph LR
    A["动画资源<br>关键帧"] --> B["采样 + 混合<br>得到骨骼姿势"]
    B --> C["姿势 = 每根骨骼的世界变换"]
    C --> D["蒙皮矩阵<br>当前世界 × 绑定世界⁻¹"]
    D --> E["顶点变形<br>加权求和"]
    E --> F["渲染"]
```

输入：一张**姿势（Pose）**——这个词在动画系统里指"某一时刻，每根骨骼各自处于什么变换"这样一份整体快照。本篇要的姿势是"每根骨骼当前的世界变换"（它怎么来的，见 [[Notes/动画系统/旋转与变换基础/变换层级与复合变换|变换层级与复合变换]] 里的层级连乘）。输出：每根骨骼一个**蒙皮矩阵**，交给顶点变形用。

注意交接方式：**蒙皮只用姿势里的世界变换，完全不知道这些旋转值是从关键帧采样来的、还是混合出来的、还是 IK 掰出来的。** 这就是为什么动画和蒙皮可以彻底解耦——你换了整套动画系统，蒙皮那一段代码一行都不用改。

### BindInverse：把顶点搬进"骨骼自己的空间"

先补一个前置概念（[[Notes/动画系统/角色资产与骨骼基础/骨骼的本质：从骨架到 Skeleton 资产#直观理解：骨骼是一个"关节坐标架"，不是一个物件|《骨骼的本质》]] 讲过，这里只取用到的那点）：骨骼是一个坐标架，而**骨骼空间**指的是"以这根骨骼的原点为原点、以它的朝向为坐标轴"的那个坐标系。同一个世界位置，换一根骨骼来量，坐标完全不同——这正是"在我左手前方 10 厘米"这句话必须绑定到具体哪根骨骼才成立的原因。

现在看顶点。顶点在模型空间里的位置是 `v`——"相对模型原点，我在哪儿"。这个小臂骨想知道的是另一件事：**"相对我自己的原点，这个顶点在哪儿？"** 也就是"它在我前方 3 厘米、上方 5 厘米"。

这个换算就是一次**反向求解**：把"外部坐标"翻译成"内部坐标"，用的正是变换的逆。而这恰好是 [[Notes/动画系统/旋转与变换基础/变换层级与复合变换|变换层级与复合变换]] 里那套层级推导的**倒着走**——那里讲"局部变换怎么一级级连乘出世界变换"，这里要的是"世界变换怎么反解回局部"。IK 和重定向也在用同一个操作。

```cpp
// flags: -O0 -g
#include <cmath>

// 3×4 仿射矩阵：3×3 旋转/缩放 + 一列平移（蒙皮用的是齐次矩阵的紧凑形式）
struct Mat34 {
    float m[3][4];
    Vec3 TransformPoint(const Vec3& v) const;
    static Mat34 FromTransform(const Transform& t);  // T·R·S 组装
    static Mat34 Identity();
};

// 绑定姿势：整棵骨架在标准姿势下的世界变换，每根骨骼一份，加载时算好
struct BindPose {
    std::vector<Mat34> BoneWorldBind;      // BoneWorld_bind
    std::vector<Mat34> BoneWorldBindInv;   // BoneWorld_bind⁻¹ ← 全篇的 `BindInverse`
};

// 加载时算一次，之后每帧只读——这就是"每帧不用求逆矩阵"的原因
void BuildBindInverse(Mat34* outInv, const std::vector<Transform>& bindPoseWorld,
                      int boneCount) {
    for (int i = 0; i < boneCount; ++i)
        outInv[i] = Inverse(bindPoseWorld[i]);   // 每根骨骼只算这一次
}
```

### 蒙皮矩阵的推导：两站接力

把上一节的直觉写成可执行的句子，只有两站：

**第一站：顶点 → 骨骼空间（用 `BoneWorld_bind⁻¹`）。**

拿绑定时这根骨骼的世界变换**求逆**，去乘顶点位置，得到 `v_bone`——"这个顶点，在**绑定姿势下**这根骨骼自己的坐标系里，位于哪里"。这一步把顶点从共享的模型空间，搬进了这根骨骼的私人空间。之后哪怕世界翻天覆地，这个坐标始终有意义。

**第二站：骨骼空间 → 当前世界（用 `BoneWorld_current`）。**

骨骼现在跑到哪、朝哪，用它的当前世界变换，把 `v_bone` 搬出去。同一个"前方 3 厘米、上方 5 厘米"，在骨骼转身 90° 之后，落到世界里的位置就完全不同了——这正是我们要的"皮肤跟着骨骼转"。

用橡皮筋那套说法收一遍：**第一站是"把这根皮筋在钉子出发位置上的长度量清楚、记下来"，第二站是"拿现在这颗钉子把同一段皮筋重新拉出去"。** 重点是第二站拽的是**皮筋的长度**，不是钉子的位置——否则钉子一挪，皮筋就会先弹回原长再重拉，皮肤在半路上跳一下。

两站串起来：

$$
v' = \text{BoneWorld}_{current} \times \text{BoneWorld}_{bind}^{-1} \times v
$$

括号里那一坨，就是**蒙皮矩阵**：

$$
\text{SkinMatrix} = \text{BoneWorld}_{current} \times \text{BoneWorld}_{bind}^{-1}
$$

```cpp
// flags: -O0 -g

// 每帧、每根骨骼：一次矩阵乘（BindInverse 是加载时缓存好的常量）
Mat34 BuildSkinMatrix(const Mat34& boneWorldCurrent, const Mat34& boneWorldBindInv) {
    return Multiply(boneWorldCurrent, boneWorldBindInv);
}
```

读代码抓两个点：① 右边那个 `boneWorldBindInv` 是**常量**，它在整个运行期不会变；② 左边的 `boneWorldCurrent` 每帧都在换——所以每帧的工作量是"一次 3×4 矩阵乘"，不是"求一次逆"。

### 一句话直觉 + 一次自检

蒙皮矩阵是什么？

> **它是"从绑定姿势到当前姿势，这根骨骼跑了多远"。**

注意措辞——不是"骨骼现在在哪"，是"跑了多远"：它是一个**位移量**。后面所有现象都能由这一点推出来。

怎么验证这个理解没跑偏？做一次自检：**让动画停在绑定姿势下**。

此时 `BoneWorld_current` 和 `BoneWorld_bind` 是同一个矩阵。代入公式：

$$
\text{SkinMatrix} = \text{BoneWorld}_{bind} \times \text{BoneWorld}_{bind}^{-1} = I
$$

**蒙皮矩阵退化成单位矩阵，顶点一动不动。**

这个结果对不对？当然对——绑定的时候模型本来就该是静止的，它此刻的形态就是美术做好时看到的那个形态。**如果模型在绑定姿势下还发生了变形，那一定是蒙皮算错了。** 这条自检在引擎里也是真实的调试手段：把角色强制回到参考姿势看它是否正常，是排查"绑定炸了"的标准第一步。

反过来看也成立：任何一根骨骼，只要相对于绑定时没动过（世界变换和绑定时一模一样），它的蒙皮矩阵就是单位矩阵——**这根骨骼不给它影响的顶点带来任何变形**。注意这只是"不影响顶点位置"，每帧那次矩阵乘一样省不掉；但引擎普遍会做一层优化：把整帧没动的骨骼整支跳过，连矩阵乘都不做。

### 多骨骼加权：加权求和，不是依次作用

到这里只解决了"一个顶点跟一根骨骼"的情形。但前面说过，关节处的顶点由好几根骨骼共同拽着。多根怎么合？很简单：

$$
v' = \sum_i w_i \cdot (\text{SkinMatrix}_i \times v)
$$

读这个式子要抓住一个关键差别：**是"每个骨骼各自算一遍、再按权重加总"，不是"一个接一个地接力作用"**。

为什么这点值得单独说？因为它意味着两件事：

- **顺序无关**。每个 `SkinMatrix_i × v` 都从**同一个原始顶点位置** `v` 出发（注意式子里右边都是 `v`，不是上一项的产物），所以先算哪根骨骼都一样。这就是它叫**线性**混合蒙皮（Linear Blend Skinning，LBS）的原因——每一步都是线性的，可以随意重排。顺带一个实际后果：**同一根骨骼的受影响的顶点可以并行算**，各家算各家，不需要互相等——这也是 GPU 适合干这件事的原因（见文末性能一节）。
- **代价是"平均"，而平均会把关节压塌**。因为这里平均的对象是**位置**，不是旋转——所以弯肘角度一大，关节内侧就会往里缩。这是 LBS 的固有缺陷，机制与表现见上一篇 [[Notes/动画系统/角色资产与骨骼基础/骨骼网格与蒙皮：顶点怎么绑到骨骼上#LBS 的经典缺陷：弯肘时塌陷|LBS 的经典缺陷]]，下一篇 [[Notes/动画系统/蒙皮与骨骼网格/顶点权重与蒙皮算法|顶点权重与蒙皮算法]] 讲怎么缓解——本篇只需要知道它从这个式子里来。

```cpp
// flags: -O0 -g

// 顶点变形：每根影响骨骼各自算一遍，再按权重加总
// 注意每一项的起点都是原始顶点 v，不是上一项的结果——所以顺序无关
Vec3 SkinVertex(const Vec3& v, const BoneInfluence* influences, int count) {
    Vec3 sum = { 0, 0, 0 };
    for (int i = 0; i < count; ++i)
        sum += influences[i].Weight * influences[i].SkinMatrix.TransformPoint(v);
    return sum;
}
```

### "每帧都在求逆矩阵"是个误解

最后一次澄清，因为它直接影响你对性能的判断。

`BoneWorld_bind⁻¹` 里那个"逆"，**每根骨骼在整个运行期只算一次**——绑定姿势是资产的一部分，不会变。所以引擎在**加载骨骼网格**的时候就把它算好、存成一份数组（通常和骨骼索引一一对应），运行时只读。

于是每帧的真实开销是：

$$
\text{每帧每根骨骼} = 1 \text{ 次矩阵乘法（3×4）}
$$

而不是"求逆 + 乘法"。这个区别有多大？求逆要算行列式、伴随矩阵、除法……成本是矩阵乘的好几倍。如果真按"每帧求逆"来写，你会在几百根骨骼上白白多烧掉数倍的时间，而且这个开销**看不出任何视觉收益**——它纯粹是白花的。

### 性能事实：为什么蒙皮要丢给 GPU

> **知道即可**，不影响你怎么用，但解释了一件你迟早会好奇的事。

蒙皮矩阵是 3×4 的（含平移，其中 3×3 那块管旋转和缩放、最后一列管平移），每个顶点要做 N 次矩阵-向量乘（N = 影响它的骨骼数，通常 4）。看起来不多，但**顶点数是骨骼数的几十倍**——拿个具体量级：一个角色两三百根骨骼、几万个顶点，一帧下来就是几十万次矩阵乘。所以这是整条动画管线里最贵的环节之一，也是为什么行业做法是**把蒙皮矩阵整批传给 GPU，让顶点着色器去算**（GPU 天然擅长这种"大量顶点各自独立做同一种算术"的活，那句"顺序无关"正是它成立的前提）。CPU 端则退化成"准备一张矩阵表"。

## 边界与坑

- **换了模型但绑定姿势不同 → 整体歪一个角度**。同一套骨骼做了两个网格，一个按 T-Pose 绑、一个按 A-Pose 绑，同一段动画播到这两个模型上，一个正常、另一个**整体歪掉一个固定角度**（手臂长期垂着、或者长期架着）。因为两者对"绑定姿势"的定义就不一样，"相对绑定姿势的位移量"自然也算不到一块去。跨骨架复用动画时这是高频事故，属于**重定向**要处理的问题（见 [[Notes/动画系统/动画数据与采样/动画重定向：一套动画复用到不同骨架|动画重定向]]）。

- **骨骼动了但 BindInverse 没更新 → 模型直接崩掉**。在编辑器里改了绑定姿势（挪了一根骨骼、重新摆了一次姿势），却**没有对网格重新绑定**（re-bind / re-skin），缓存下来的 `BindInverse` 还是旧的。此时蒙皮矩阵不再等于单位矩阵，模型会**整体错位、扭曲成一团**——而且是在绑定姿势下就错，一眼就能看出。**改绑定时必须重新绑定网格**，这是资产流程里的硬要求。

- **权重和不为 1 → 模型整体缩放**。三条影响权重加起来等于 1.2，顶点会被多拽 20%——表现在模型上就是**整块区域发胖**；加起来只有 0.8 则**缩水**。顺带划清一件事：蒙皮矩阵本身是刚性的（只有旋转和平移），**"胖"和"缩"只可能来自权重，不会来自那个矩阵**——查到模型发胖，先去看权重表，别怀疑公式。所以导入流程里通常有一道"权重归一化"（把每个顶点的权重重新除以它们的和），专治美术笔刷刷过头。这是上一篇 [[Notes/动画系统/角色资产与骨骼基础/骨骼网格与蒙皮：顶点怎么绑到骨骼上#边界与坑|《骨骼网格与蒙皮》的边界与坑]] 里讲过的问题在这里的复现。

- **权重为 0 或骨骼缺失 → 顶点留在原地**。某根骨骼的权重为 0，它对应的那一项贡献为零，顶点完全不受它影响——看起来"没反应"，不是崩了。如果权重标签指向的骨骼在网格里根本不存在，顶点会**卡在模型空间的原位不动**，也就是**挂在角色身后的空中**，不管动画怎么跑。排查"有一小撮顶点不动"时，先查权重表里的骨骼名。

- **绑定姿势下发生变形 → 一定是算错了**。回到前面的自检：`BoneWorld_bind × BoneWorld_bind⁻¹` 必须是单位矩阵。这个式子只在**两侧用的是同一份数据**时成立——一旦 `current` 里混进了别的姿势、或者两侧的骨骼索引对不上，退化就不成立，绑定姿势下模型就会走形。

- **零缩放**：绑定姿势里某根骨骼带着 0 缩放时，它的 `BoneWorld_bind` 是奇异的，**逆矩阵根本不存在**（除以零）。实际表现是那根骨骼影响的顶点全部塌成一个点、或者算出 NaN 让整块模型消失。同样是 [[Notes/动画系统/旋转与变换基础/变换层级与复合变换|变换层级与复合变换]] 里"骨骼 Scale 保持 (1,1,1)"那条规矩的延伸。

- **骨骼的缩放被逐帧写坏 → 越播越胖**。有些管线的做法是每帧从动画通道里解算骨骼变换；如果这一步漏掉了"把缩放复位成 1"，上一帧算出来的缩放会被当成基准一路累积下去。表现和"权重和为 1.2"很像——模型**越播越胖，而且是渐进地胖**，播久了才看出不对。区别在于：权重问题一进去就不对，缩放累积是"跑上几百帧以后突然发现角色圆了一圈"。

## 一句话总结

蒙皮矩阵 = **骨骼的当前世界变换 × 绑定姿势下世界变换的逆**——它描述的是"这根骨骼相对绑定姿势跑了多远"，所以绑定姿势下它退化成单位矩阵、顶点一动不动；那个逆矩阵把顶点搬进骨骼自己的空间，是加载时算一次的常量，于是每帧每根骨骼只剩一次矩阵乘法。顶点最终位置的算法则简单到只有一句：每根影响它的骨骼各算一遍，再按权重**加权求和**。

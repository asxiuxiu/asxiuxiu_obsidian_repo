# 混合空间：布局与插值

> [!todo] 本篇核心问题
> BlendSpace 的 1D/2D 布局、采样点，双线性与三角形插值权重怎么算

> [!tip] 需要懂多深
> 这篇不讲怎么用编辑器摆点，你只需要拿捏两件事：
> 1. **一次混合到底动用几段动画？**（一维与二维的答案不同，且与样本点总数无关）
> 2. **摆样本点有什么规矩？**（一维和二维的规矩不一样）
>
> 另外还要记住一条交付规范：**同一张图里所有样本动画的时长和循环相位必须对齐**。这条为什么重要、怎么查，正文「边界与坑」里讲。

## 为什么需要解决这个问题

一个最常见的对抗场景：角色在场景里移动，玩家推摇杆的手劲有大有小。

如果动画只按状态机切，你手上只有两个资源——一段"走路"、一段"跑步"。可实际速度是**连续的**：轻轻推是 100 单位/秒，推满是 512 单位/秒，中间还夹着 250、380、以及每个玩家手指造成的无数个中间值。而状态机只会给出**离散的几个状态**：要么在走，要么在跑。

那怎么办？两条路都不通：

- **为每个速度都做一段动画**——美术做不过来（速度组合是无穷的），打包进内存也放不下。
- **用状态机硬切**——角色会在 249 单位/秒时突然"啪"地跳成跑步姿势，脚底下瞬移一截，肉眼能看出穿帮。玩家推摇杆时速度是缓缓升上去的，动画却是一格一格跳的，手感就是"这东西在打嗝"。

于是需要第三种做法：**美术只做几个典型速度的动画（比如 100、250、512 各一段），中间的速度由引擎实时把相邻几段混出来**——速度 380 时，就是"250 那段占四成、512 那段占六成"。

这就是**混合空间**（BlendSpace；Unity 里叫 **Blend Tree**，混合树）。它要回答的问题听起来简单——"中间那段动画怎么混出来"——但真到动手时会有两个绕不开的坎：

1. **参数不止一个**。八向移动要同时看速度和方向，不是一根轴上的事。于是很自然的想法是"两根轴不就成了"——把每个参数各配一根轴，摆成一个表格（走路×朝前、走路×朝右、跑步×朝前……）。**表格确实能做出来，但它默认这些格子是"能摆满"的**，而美术手上从来只有零星几段动画，中间一大片格子是空的。这就是本篇后半段要处理的核心麻烦。
2. **权重从哪来**。姿势混合的机制早就有了（[[Notes/动画系统/动画播放与混合/姿势混合：加权与跨渐变|姿势混合：加权与跨渐变]]），但那里的权重是状态机给的 α；现在权重得**由输入参数在样本点之间的位置现算出来**。

本篇只回答第二件事——**输入落到采样点之间的哪个位置，权重怎么分**。至于"速度这个参数从哪来、要不要平滑"，那是下一篇 [[Notes/动画系统/混合空间与Additive/数据驱动动画：参数到姿势|数据驱动动画：参数到姿势]] 的事。

## 直观理解：一张被样本点铺满的图，输入落在哪个格子里

把混合空间想成**一张摊开的图纸**（所以它才叫"空间"）。

- 图纸上的**每一个坐标点**，代表参数的一个取值组合。一维的情况下，这张图纸退化成**一条数轴**（比如速度轴）；二维的情况下，它是一张**平面**（横轴速度、纵轴方向）——横纵各是一个参数，两个参数**各占一根轴**，这正对应上面那个"表格"的直觉。
- 美术在图上**钉钉子**：每钉一颗钉子，就放一段动画（比如"朝右前方小跑"），并交代"这段动画代表图纸上的哪个位置"。这颗钉子就是**样本点**（Sample）。
- 运行时收到一组参数（比如"速度 380、方向 45°"），相当于在图纸上标出一个**输入点**。接下来做的事只有一件：**看这个输入点离哪几颗钉子近，按"近的多分、远的少分"给每颗钉子派一个权重，再把这些钉子的动画混起来。**

"离得近就多分一点"这句话，就是这一整篇笔记的全部内容。真正需要动脑的地方在于：**"哪几颗钉子"和"多近算多近"，在一维和二维下的答案完全不同。**

```mermaid
graph LR
    A["输入参数<br/>速度 380"] --> B["在图纸上定位<br/>找到周围的样本点"]
    B --> C["按几何位置算权重<br/>Σw = 1"]
    C --> D["多个姿势加权混合"]
    D --> E["输出姿势"]
```

数据流位置：本篇处在动画链路「采样 → 混合 → 蒙皮」的**混合站的入口**——比 [[Notes/动画系统/动画播放与混合/姿势混合：加权与跨渐变|姿势混合]] 更靠上游一站。姿势混合回答"给定几个权重，怎么把几段动画混起来"；本篇回答"这几个权重**从哪来**"。它的输入是一组连续参数（速度、方向角）和一段**当前时间**（每颗钉子的动画都要按各自的时间轴取到当前帧姿势），输出是一组权重（外加被选中的样本动画），下游直接交给姿势混合去执行。

## 核心机制

### 数据结构：样本点 = 一段动画 + 一个坐标

一张混合空间的资产，剥到最里面就是一串样本点：

```cpp
// flags: -O0 -g

// 一颗钉子：某段动画代表图纸上的哪个位置
struct BlendSample {
    AnimationRef Anim;      // 指向一段循环动画资产
    Vec2         Position;  // 它在图纸上的坐标（1D 时只用 X）
    float        RateScale; // 可选：这段动画的播放速率修正
};

// 一张混合空间（2D）：图纸的范围 + 钉在上面的钉子
struct BlendSpace {
    Vec2                      Min, Max;   // 图纸边界，也是参数的钳制范围
    std::vector<BlendSample>  Samples;
    // 编辑器预先算好的三角网（下一节解释为什么需要它）
    std::vector<Triangle>     Triangles;
};
```

混合空间资产的本质就是**这张图纸本身**——它是离线数据，运行时不会被改。运行时的产物是另一份数据：**当前输入点该给每颗钉子分多少权重**。

### 1D 混合空间：一根轴上的线性插值

先从最简单的情况入手，因为它几乎是"理所当然"的。

一维混合空间只有一根轴（速度轴），钉子钉在轴上：100 处一段走、250 处一段小跑、512 处一段冲刺。**摆钉子有一条硬规矩：必须按坐标从小到大排好**——因为后面找区间靠的是"相邻两颗"，顺序一乱，相邻关系就没了。输入点是轴上的一个数值，它必然落在**某个区间**里，比如 380 落在 `[250, 512]` 之间。

顺序摆错会是什么后果？假设美术把表里的顺序录成了 100、**512**、250。输入 380 时，程序找到的是 512 和 250 这一对"相邻"钉子——**输入点离它们都很远，却仍按距离硬分权重**，于是角色在 380 的速度下，姿势里混进了一大半冲刺。表现是**角色以小跑的速度跑着，动作却快得像冲刺，脚底疯狂打滑**。这类问题不会有任何报错，只能靠肉眼在跑动时发现——所以"检查样本点是不是按坐标排序"值得写进美术交付规范。

这时说什么"离哪几颗钉子近"？答案很干脆：**只有两颗钉子跟它有关系**——区间左端和右端的那两颗。剩下的钉子离得更远，直接不参与。权重则按"离左端多远、离右端多远"来分：

```cpp
// flags: -O0 -g

// 1D：找输入点所在区间，按距离线性加权
// 权重公式与 Lerp 里那个 t 是同一个东西，只是这里反过来解出 t
bool UpdateBlend1D(const BlendSpace1D& bs, float Input, std::vector<SampleWeight>& Out) {
    // 输入超出图纸范围：钳到边界（不外推，理由见「参数范围与钳制」）
    const float Pos = std::clamp(Input, bs.Min.X, bs.Max.X);

    // 找到 Position 小于等于 Pos 的最后一个样本，作为区间左端
    int L = -1;
    for (int i = 0; i < (int)bs.Samples.size(); ++i)
        if (bs.Samples[i].Position.X <= Pos) L = i;

    if (L < 0)                      { Out = { { 0, 1.f } }; return true; }  // 全在左边：直接用第 0 个
    if (L == (int)bs.Samples.size()-1) { Out = { { L, 1.f } }; return true; } // 全在右边：直接用最后一个

    const float A = bs.Samples[L].Position.X;
    const float B = bs.Samples[L + 1].Position.X;

    // 两颗钉子坐标重合：分母为 0 会除出 inf/NaN，退回单样本（美术摆错了，见「边界与坑」）
    if (B - A <= 1e-6f) { Out = { { L, 1.f } }; return true; }

    const float wB = (Pos - A) / (B - A);   // 离右端越近，右端权重越大
    Out = { { L, 1.f - wB }, { L + 1, wB } };
    return true;
}
```

读这段代码，抓两个点：

1. **最多两颗钉子参与**。一维混合空间无论钉了多少钉子，每次只有相邻的两颗有非零权重——这是它便宜的根源。
2. **权重就是"离端点有多近"的比例**。`wB = (Pos - A) / (B - A)`：输入正好在中点时两颗各 0.5；贴着左端时左端拿满 1.0。

**关键认知：一维混合空间里没有任何新机制。** 它做的是姿势混合的加权平均，只不过权重不再是手工拖滑块给的 α，而是**由输入参数在一根轴上的位置算出来的**。

### 2D 混合空间（一）：朴素的双线性插值

多一个参数，直觉上就是"把两根轴摆成一张表格"——行是速度、列是方向，格子里放动画。这个想法本身没错，问题出在下一步。

二维的情形是八向移动：横轴速度、纵轴方向（0° / 45° / 90° …），美术在平面上钉了几颗钉子。

"离哪几颗钉子近"这个问题，在平面上不再有唯一答案。最朴素的接法是：**把平面切成矩形格子**——钉子理论上排成规则网格，输入点必然落进某个格子里，那就用**包围这个格子的四颗钉子**，按"上下比例 × 左右比例"加权：

> **为什么只有两颗变成四颗？** 一维时输入点被左右两边夹住，帮手是 2 个；二维时它被上下左右四个方向夹住，帮手自然是 4 个。**夹住它的"邻居"有几个，就要混几段动画**——这条规律在三角形那一节会以"3"的形式再出现一次。

```cpp
// flags: -O0 -g

// 双线性（Bilinear）：先按 X 在左右两列间插值，再按 Y 在上下两行间插值
// 前提：样本点排成了规则网格（每行每列都在同一组坐标上）
void UpdateBlendBilinear(const BlendGrid& g, Vec2 Input, std::vector<SampleWeight>& Out) {
    const int cx = FindCellX(g, Input.X);   // 输入落在第几列
    const int cy = FindCellY(g, Input.Y);   // 输入落在第几行

    const float tx = (Input.X - g.X[cx]) / (g.X[cx+1] - g.X[cx]);
    const float ty = (Input.Y - g.Y[cy]) / (g.Y[cy+1] - g.Y[cy]);

    Out = {
        { g.At(cx,     cy    ), (1-tx) * (1-ty) },  // 左下
        { g.At(cx + 1, cy    ), (    tx) * (1-ty) },  // 右下
        { g.At(cx,     cy + 1), (1-tx) * (    ty) },  // 左上
        { g.At(cx + 1, cy + 1), (    tx) * (    ty) },  // 右上
    };
}
```

它为什么不太行？两个原因，都是动过手就会撞上的：

- **它对样本点的摆放提了硬要求**。要形成"格子"，钉子必须排成整齐的网格：要么四颗齐（第 3 行只有 2 颗、第 4 行有 4 颗，网格就散了）。而美术摆点的现实是**随手**——"这个方向我只想插一段持枪跑，别的方向不需要"。图一旦不规整，双线性就无处下口。
- **它会请进离得很远的钉子**。假设输入点贴着左下角那颗钉子，但那个格子的右上角钉着一颗位于图纸另一头的动画。双线性照样按 `tx * ty` 给这颗远处的钉子分一份权重——**输入点明明离它很远，它却硬挤进了混合**。表现为：角色本该是纯粹的"走"，姿势里却偷偷混进了"冲刺"的痕迹，出现**莫名其妙的扭动或滑步**。

### 2D 混合空间（二）：三角剖分 + 重心坐标

既然问题的根源是"格子里那四颗钉子的关系是人为指定的"，那就换一个更贴合几何的解：**让图纸上的钉子两两自然连成三角形，输入点落进哪个三角形，就只跟这个三角形的三颗钉子发生关系**。

这一步"把散点连成三角网"由编辑器离线完成，用的典型算法叫 **Delaunay 三角剖分**——它的选边原则可以一句话概括：**避免出现又瘦又长的尖三角形，尽量让每个三角形接近等边**。为什么在意这个？因为三角形的形状直接决定权重的手感：

- **歪得离谱的三角形：输入点轻轻一动，某颗钉子的权重就"啪"地甩到另一个极端**。你可以把三颗钉子看成夹住输入点的三个人，三角形越细长，输入点越过"中分线"时受力变化越剧烈——那一颗的权重从接近 1 陡然掉到 0，混出来的姿势**肉眼可见地抖一下**，角色会像被电了一下似的抽动；
- **接近等边的三角形：三个权重平滑连续地增减**，混出来的动画也就平滑，输入点从一端移到另一端时姿势是**匀速过渡**的，没有突变。

形状直接决定手感，这就是 Delaunay 存在的全部理由：它让每个三角形的形状**尽可能归一化**，从而保证权重曲线平滑、抖动最小。

剖分结果会作为**资产数据的一部分烘进文件**，运行时不必现算（只在需要时按当前参数做一次快速定位）。

现在只剩最后一块拼图：输入点落在某个三角形里，**三颗钉子各分多少权重**？答案是**重心坐标（barycentric coordinates）**。

不要被名字吓到，它的直觉很朴素：**站在三角形内部的一个点上，看自己离三个顶点各有多近——离谁近，谁的权重就大；三个权重加起来正好是 1。** 几个能验证直觉的特例：

- 输入点正好压在顶点 A 上 → A 拿 1.0，另外两个拿 0——**整个动画就是 A 那段，一根头发都不混**。
- 输入点坐在 A、B 的正中间、远离 C → A 和 B 各 0.5，C 拿 0。
- 输入点坐在三角形正中心 → 三个各拿 1/3。

**几何上，重心坐标就是"输入点被三颗钉子以质量为 1:1:1 平衡住时的受力分配"**：把三颗钉子当成三个等重的砝码，把输入点当成那个恰好被平衡住的支点，支点底下三根柱子各自承担多少重量，就是三个权重。

```cpp
// flags: -O0 -g

// 2D 核心：定位输入点所在的三角形，用重心坐标算三颗钉子的权重
// 输入：编辑器烘好的三角网；输出：三角形三顶点 + 三个权重（和为 1）
void UpdateBlend2D(const BlendSpace& bs, Vec2 Input, std::vector<SampleWeight>& Out) {
    const Vec2 Pos = ClampToRange(Input, bs.Min, bs.Max);   // 先钳制

    const Triangle* T = nullptr;
    for (const Triangle& Tri : bs.Triangles) {
        if (Contains(Tri, Pos)) { T = &Tri; break; }        // 落在哪个三角形里
    }

    // 退化：输入点落在三角网之外（图有洞、或样本点少于 3 颗）
    //        兜底为"离得最近的单颗钉子"，否则会出现权重和为 0 的非法姿势
    if (!T) { Out = { { NearestSample(bs, Pos), 1.f } }; return; }

    // 重心坐标：Pos = wA*A + wB*B + wC*C，且 wA + wB + wC = 1
    // 只记直觉：离哪个顶点近，哪个权重就大
    float wA, wB, wC;
    Barycentric(Pos, T->A, T->B, T->C, wA, wB, wC);

    Out = { { T->iA, wA }, { T->iB, wB }, { T->iC, wC } };
}
```

所以"BlendSpace 用几个采样点"这个问题有了准确答案：**一个三角形 = 3 个采样点**。一维时是 2 个（区间两端），二维时是 3 个（包围三角形的三个顶点）。这个数字是固定的，跟美术钉了多少颗钉子无关。

对比一下两种做法的差别，就明白为什么工业界都选后者：

| 做法 | 每次参与的样本数 | 对样本点摆放的要求 | 输入点贴着某颗钉子时的权重分布 |
| :--- | :--- | :--- | :--- |
| 双线性（网格） | 4 | 必须排成规则网格 | 远处那颗仍有非零权重，混进不该有的姿势 |
| 三角网 + 重心坐标 | 3 | 任意摆放，编辑器自动剖分 | 只有包围它的 3 颗参与，远处的钉子权重天然为 0 |

> [!note]- 想深究：重心坐标的具体公式
> 实现上用的是面积比：把输入点和三角形的三条边分别组成三个小三角形，某个顶点的权重就是"它对面的那个小三角形面积 ÷ 大三角形面积"。写成行列式或叉积都能算出来。
> **不读不影响调动画**——"权重是什么、三个权重为什么加起来是 1"这两件事，上面的直觉已经说清楚了；这条只是给要自己写一份求解器的人留的入口。

### 参数范围与钳制：图纸边界就是硬边界

混合空间的图纸有一个有限范围（`Min` ~ `Max`），它由最外围的样本点决定。当输入参数超出这个范围时，引擎**不会外推，而是钳到边界**：

```cpp
// flags: -O0 -g
// 输入参数超界时的钳制：图纸外没有动画可混，只能贴边
const float Clamped = std::clamp(InputSpeed, bs.Min.X, bs.Max.X);
```

理由很直白：图纸外面**没有钉子**。想"外推"就得回头找某颗钉子，把它的动画加速播放——那是另一类技术（动画速率缩放），不是混合空间该干的事，也容易做出"跑了 2 倍速但步幅不变"这种明显的滑步。

**这是设计如此，不是 bug。** 玩家会看到的表现是：**速度再往上加，角色的腿也不再迈得更快了**——最快的那段冲刺动画被拉满，就到此为止。实际项目里，做法是让游戏逻辑把速度"封顶"控制在这个范围附近，再靠别的机制（比如加速镜头特效、加大位移）去补偿"速度感"。

钳制这条规则在 1D 和 2D 下"长"得不太一样：**一维那两行 `L < 0` / `L == size-1` 的判断，就是钳制的落地**——输入点跑到最左/最右之外时找不到可夹住它的区间，只能整体压给最边上那颗钉子（相当于 `w` 被钳成 0 或 1）。二维的三角网天然围住了整个参数范围，所以代码里那句 `ClampToRange` 更多是双保险。**两条路径最后落在同一件事上：参数超界时，用边界上的样本，不外推。**

## 边界与坑

- **只有一个样本点**：混合空间直接退化成"无条件播放这一段动画"，输入参数完全被忽略。调试时出现"参数怎么改都没反应"，先看图纸上是不是只有一颗钉子。
- **两颗样本点坐标重合**（美术手滑摆到一起了）：1D 的 `B - A` 为 0，`(Pos - A) / 0` 会算出 `inf` 或 `NaN`，权重直接污染成非法值——**表现是模型在特定速度下突然糊成一团、四肢被拉出屏幕**。这是必须自己兜底的除零（代码里的 `<= 1e-6f` 那行），因为它是美术操作失误，不是理论边界。
- **一维样本点没按坐标排序**：症状与后果见「1D 混合空间」一节。这里只补一条前面没说过的：**这个坑不报错，只能靠跑动时肉眼发现**，所以摆点规则要提前交代给美术。
- **样本动画的时长不一致 → 脚滑**：走路那段 1.0 秒、跑步那段 0.6 秒，混合时两段都以自己的时间轴播放，混出来的腿**既不是走也不是跑，是一种频率错乱的蠕动**，脚底在地面上打滑。这是混合空间**最高频的实战坑**——判定与修法（相位同步／速率缩放）见 [[Notes/动画系统/动画状态机与动画图/动画同步：过渡时机与步伐对齐|动画同步：过渡时机与步伐对齐]]。
- **样本动画的循环相位不同 → 鬼步**：时长对上了，但一段从左脚落地开始、另一段从右脚落地开始。两段混起来时，**左右腿的动作互相打架**——明明是往前跑的姿势，腿部看起来却在原地高频抖动。规则很硬：**同一张混合空间里的所有样本，循环相位必须对齐**。这条要在美术交付时立成规范，事后再查非常痛苦。
- **权重归一化**：所有路径算出的权重必须满足 `Σw = 1`，否则姿势会被整体放大或缩小（表现为模型发胖／缩水）。三角网兜底路径（没找到三角形时退回单颗钉子）就是为了堵住"权重和为 0"这个口子。
- **坐标轴含义必须是"实际参数"，不是"归一化数值"**：进度条上位置是 0~1，但蓝图/代码喂进来的速度常常是 cm/s（几百上千）。两边对不上，输入点就**永远贴在图纸的某个角落**——表现是"不管跑多快，动画永远是走路"。摆点前先确认量纲。（参数从哪来、怎么喂，是下一篇的事：[[Notes/动画系统/混合空间与Additive/数据驱动动画：参数到姿势|数据驱动动画：参数到姿势]]。）

## 变体：Aim Offset 与极坐标布局

前面讲的都是"用一个平面装速度 × 方向"。实际项目里还有两种常见变体，**知道它们存在、知道什么时候会用到就够了**，机制完全复用本篇。

- **想做"站着不动、只转上半身瞄准"**：参数不该是速度，而该是**朝向偏移量**——身体朝向与瞄准方向的夹角（偏航＋俯仰）。这就是 **Aim Offset**（瞄准偏移），它本质上就是一张 2D 混合空间，钉子换成"身体朝前 / 朝左上 45° / 朝右上 45°"这些纯上身姿势。它常和 Additive 结合使用（只叠加上半身的偏差，不动腿部），见 [[Notes/动画系统/混合空间与Additive/Additive动画：叠加与增量姿势|Additive 动画：叠加与增量姿势]]。
- **八向移动只想给每个方向挂几段专门动画**：有人会把参数换成**角度 + 速度**的极坐标形式（角度绕一圈、速度当半径）。好处是"方向"这个维度天然是环绕的；代价是靠近原点（速度接近 0）时角度会剧烈抖动，需要额外地处理。

> [!note]- 想深究：Delaunay 剖分算法本身
> 它是计算几何里的经典算法（分治、增量插点、扫描线等多种实现），负责把散点连成"尽量等边"的三角网。
> **不用学**。引擎的编辑器在你点保存时已经算好了，运行时只是查表。你唯一需要知道的是"它存在，且它的产物会被烘进资产文件"——这解释了为什么**挪动一颗样本点会导致资产重新保存**，也解释了为什么运行时定位非常快。

## 一句话总结

混合空间是一张被样本动画钉满的图纸：输入参数在图纸上的位置决定权重怎么分——一维时是相邻两颗钉子按距离线性分配，二维时先用编辑器烘好的三角网定位到**一颗**由 3 个采样点构成的三角形，再用重心坐标按"离三个顶点各有多近"分配权重；参数超出图纸就钳到边界，而真正的实战杀手不是数学，是所有样本动画的**时长与循环相位必须对齐**。

# 数据驱动动画：参数到姿势

> [!todo] 本篇核心问题
> 速度/方向等参数怎么实时选出与混合出一段自然的动画？

> [!tip] 需要懂多深
> 调一个角色的移动动画，你真正要拿捏的只有三件事：
> 1. **参数有唯一的统一入口**——所有驱动动画的数据先集中收集到一处，节点只读不自己去问要。**调试动画的第一步永远是「把参数打出来看」。**
> 2. **区分「想」和「实际」**：输入（摇杆推了多少）和速度（角色现在跑多快）是两回事。
> 3. **参数必须先平滑再驱动动画**，且平滑系数要按 dt 算。
>
> 每一条的后果与修法都展开在正文对应小节，这里只列清单。至于参数该分几个、平滑该用哪种滤波，收在「知道即可」里，知道有这回事就行。

## 为什么需要解决这个问题

先说清楚下面要反复用的两个字，不然整篇都无从谈起。

**动画数据**（俗称"一段动画"，也就是资源文件里的东西）本质上是一串**带时间戳的姿势快照**：角色在 0.00 秒是什么姿态、0.03 秒是什么姿态……一路排到这段动作的结尾。这里的**姿势**（Pose），指的是一整副骨架在这一瞬间的完整形态——每根骨头转到什么角度、抬到什么位置，全部合起来才是一个姿势。而**"播动画"这个动作**，就是从这串快照里按当前时间把对应那一帧取出来（相邻两帧之间还要做个插值过渡），得到"此刻该摆成什么样"，再让角色的模型照着摆出来。这一套的细节在 [[Notes/动画系统/动画数据与采样/动画数据的本质：关键帧与采样|动画数据的本质：关键帧与采样]]，这里只要抓住一件事就够：

> **一段动画 = 一条固定的姿势序列。播它，就是按时间往前挪。**

先看一个反例：**如果把角色当成「播一段动画」来处理**，会撞上什么。

玩家按下 W。这时候世界里同时存在的数字有：摇杆倾斜量 0.7、角色当前速度 320、正在爬坡（坡度 12°）、举着枪所以后坐力累积到了某个值、刚落地 0.1 秒。这些数字没有一个长得像"姿势"，可你却希望屏幕上的人**正好是"在坡上小跑"那个样子**。

如果让"播哪段动画"这个决策直接去读这些数字，问题马上就来了：读速度的代码在移动组件里，读坡度的在角色物理里，读后坐力的在武器系统里。**动画成了最下游、却要伸手到上游各个系统里去捞数据的东西**。捞出来的后果有三个，每一个都会在项目里真实发生：

- **同一帧读到的不是同一份数据**。节点 A 在求值时读速度，读到 300；节点 B 晚了几微秒再读，移动组件已经把它改成 280。于是同一个角色、同一帧，腿上用的是 300 的动画、上半身用的是 280 的动画——**身体上下半身的行为对不上**。
- **不知道该在什么时候读**。动画求值常常被丢到工作线程去跑（主线程要留着做游戏逻辑）。工作线程去读主线程正在写的角色属性，就是数据竞争——轻则读到撕开的半份数据，重则崩。
- **出错时无处可查**。动画表现不对，你得挨个系统去问"你到底给了动画什么值"，或者在各处临时插打印。这恰恰是"动画调了半天没效果"最常见的处境。

所以动画系统需要一样东西：**一个明确的上游边界**。在这条边界之外，游戏逻辑爱怎么写怎么写；跨过这条边界，进入动画侧的数据就定型了、只读的、可见的。这条边界上的东西，就是本篇的主角——**动画参数**（编译期/资源里通常叫 **Anim Parameters**，运行时通常叫**动画实例** Anim Instance）。

## 直观理解：海图室与固定的出航簿

用一个贯穿全篇的比喻。

一艘船上，各路人马都在忙自己的事：瞭望员看风向、机舱看航速、舵手看航向、水手长看吃水深度。这些人**不会**在船长要定航线的那一刻被挨个喊过来现场汇报——那样船长每次问完，数字都已经过时了。

船上的做法是：**海图室**里挂着一块**出航簿**，上面按固定栏目记着"这一时刻的风向、航速、航向、吃水"。各路人马各自把数字**誊到簿子上**（这一步发生在一个固定的时间点，一天一次）；船长定航线时，只看簿子——**他看到的永远是同一时刻的完整快照**，不会出现"风向是两小时前的、航速是十分钟前的"这种拼接。

这套机制对应动画侧的三件事：

- **出航簿 = 动画实例里的参数集**：它是一份**结构化的数据**（速度、方向、是否在空中、坡度……），不是散落各处的 getter。
- **誊写的那一次 = 每帧一次的参数收集**：所有游戏状态在这一刻被翻译成动画侧看得懂的数字，之后动画侧**只读不写**。
- **船长看簿子 = 动画图节点读参数**：状态机、混合空间节点全都从这份快照里读数，于是同一帧内**人人看到的是同一份世界**。

数据流位置：本篇站在**动画链路的入口站**，比采样还靠前。它不产生姿势，它决定**上游的哪一份世界状态会被用来产生姿势**：

```mermaid
graph LR
    A["玩家输入"] --> B["移动组件<br>解算速度 / 朝向"]
    B --> C["游戏逻辑<br>是否落地 / 是否攻击中"]
    C --> D["动画实例参数集<br>本帧唯一快照"]
    D --> E["动画图节点<br>状态机 / 混合空间"]
    E --> F["姿势"]
```

这头再往上游是游戏逻辑，那头再往下游就是 [[Notes/动画系统/动画状态机与动画图/动画图：节点与求值序#求值序：从唯一的出口往上拉|动画图的求值]]——节点怎么从下游往上游把姿势一路拉出来。

## 核心机制

### 参数家族：四类数字，各自回答什么问题

参数不是一个速度、一个方向就完了。按"它回答什么问题"分，日常打交道的就四类：

**运动类——角色现在在怎么动。** 速度（**大小**和**方向**要分开存：大小决定跑步动画播多快，方向决定朝哪个方向的动画被选中）、加速度、是不是在移动、是不是在转向。这一类的特点是**连续量**，天生适合喂给连续插值。

**状态类——角色现在处在什么情境。** 是否在空中、是否刚落地、是否蹲下、是否举枪。这一类的特点是**离散量**，天生适合当状态机的转移条件。

**输入类——玩家想让它怎么动。** 摇杆推了多少、键盘按下了哪个方向。**这一类必须和运动类分开存**，原因见下一节——它是动画手感 bug 的高频来源。

**环境类——角色脚下的世界长什么样。** 地面坡度、脚下材质（冰面/草地/水）、是否在浅水中。这一类最容易被漏掉，因为物理系统本来就有这些数据，只是没人想到要接给动画。漏掉之后有两种都不好看的画面：**上坡时角色宁可不出脚**——因为美术做的是平地走路，脚是水平的，坡度一大前脚掌就扎进土里、后脚跟翘在半空，看起来像在刨地；**下坡时脚又像踩在隐形台阶上**，每一步都悬空一小截。材质也一样：走冰面该是小心翼翼的小碎步，漏了这个参数，角色就还是大步流星地走出去。

> [!note]- 想深究：参数能不能不集中，改成"节点需要时现查"
> 在小项目里，"每个节点自己去 `GetOwner()->GetVelocity()`"确实能跑起来，代价是每处调用都可能读到不同时刻的值，而且工作线程下不安全。集中收集的代价是多了一次数据拷贝和一个明确的结构定义。
> 什么时候可以不集中：单机原型、动画还在主线程串行求值、角色只有一个——此时省下的样板代码确实划算。判断依据是**有没有第二种"读取时刻"**：一旦存在工作线程、或者同一帧有多个节点读同一份数据，就该回到集中收集。

### 输入不是速度：一个手感 bug 的解剖

这是本篇**最有决策价值**的一条，因为它解释了一类反复出现的 bug。

先说清楚这一节的前提。如果角色速度是由玩家输入直接赋值出来的（推满摇杆就是 400），那"输入"和"速度"永远是同一个数，也就没有必要分。**两者之所以会分家，是因为中间隔了一层移动解算**：移动组件按加速度一点点把速度推上去，还要受摩擦力、转向速率、地形坡度、碰撞等制约。推满摇杆是"我要求 400"，而这一帧真的跑多快，得解算完才知道。下面这张表里的速度就是这么来的。

先看一个具体场景：玩家从静止开始按 W。

| 时刻 | 输入（摇杆/按键） | 实际速度 | 如果拿**输入**驱动动画 | 如果拿**速度**驱动动画 |
| :--- | :--- | :--- | :--- | :--- |
| t+0ms | 1.0（瞬间拉满） | 0 | 立刻切到全速跑步 | 仍是待机/起步 |
| t+150ms | 1.0 | 180 | 全速跑步 | 慢跑 |
| t+400ms | 1.0 | 400 | 全速跑步 | 全速跑步 |

这里藏着**两个互不相容的要求**，它们正好把输入和速度各推给了一边：

- **动画必须"跟手"**（要求 1）。玩家一按键，屏幕上的人就该立刻起势——不能让角色原地杵半秒才抬腿。做到这一点，动画读的就必须是**输入**，因为只有它是瞬变的。
- **动画必须"贴地"**（要求 2）。上半身和腿摆动得跟角色真实的移动合拍，脚才能踩实地面。做到这一点，动画读的就必须是**实际速度**，因为那才是角色这一帧真正在用的速度。

真正的选项因此只有三个，而不是"要不要用输入"：

1. **只用输入**：跟手，但角色还没动腿已经在跑（下表第三列的那种穿帮）。
2. **只用速度**：贴地，但起步和刹车都有迟滞——"松手了人还往前蹭两步"。
3. **两个都接，但分工**（多数项目的结果）：**连续量（混哪段跑步动画、步频多快）用速度**，保证贴地；**离散量（现在算待机/起步/奔跑/停止）用输入**，保证跟手。

看第三列：**输入是瞬变的，角色动作却不是**。玩家按下的那一瞬间，角色速度还是 0，位置还在原地，但动画已经"啪"地切成了全力奔跑——这就是玩家嘴里那句"**角色还没动，腿已经在跑了**"，看起来像脚滑（foot sliding）的另一种形态。

反过来，只用速度驱动也有代价：**停止时**速度是逐渐降到 0 的，动画会慢慢退到起步动画、再退到待机，看起来"松手了人还往前蹭两步"。想要干脆的刹车，就得参考输入——输入已经归零了，可以让动画提前开始往待机过渡。

**实践结论**：两个都要，但要分清谁负责什么。

- **状态切换**（待机 / 起步 / 奔跑 / 停止）主要看**速度**，因为状态切换是"已经发生了的事"的宣告。
- **"玩家是否还在推"**（决定停止动画什么时候开始起播、决定转向前是否先出那个"急停"）主要看**输入**，因为它表达意图。
- 想让角色"跟手"，可以给位移也加上根据输入做的前馈/加速度——但那属于移动组件的调参，**不是动画能单方面解决的**。

> [!warning] 「动画改了半天没效果」通常不是动画的问题
> 动画永远是这条链的**下游**：它被动消费游戏状态，不会反过来修正游戏状态。所以当你把混合空间的门槛改了又改、方案换了又换，动作还是不对时，先回头查两件事——**速度这个参数这一帧真的更新了吗？落地标志清了吗？** 最常见的真相是：上游某个系统根本没在写这个参数，或者写了但时序在你读之后。

### 参数怎么变成姿势：三种映射

参数到手了，接下来是"映射"——它和前面几篇正好接上：

**阈值式**：参数越过某个阈值就触发一次状态转移（`Speed > 300` 就从走路切到跑步）。特点是**离散**，结果只有"切了/没切"。这就是 [[Notes/动画系统/动画状态机与动画图/动画状态机：状态与转移|状态机]] 干的事。

**连续插值式**：参数本身直接当作坐标，喂给混合空间。速度 320 落在"慢跑"和"奔跑"两个采样点之间，就按距离加权混出中间姿势。特点是无跳变，但**只能表达参数空间内已有的形状**。这就是 [[Notes/动画系统/混合空间与Additive/混合空间：布局与插值|混合空间]] 干的事（本篇不重复它的插值规则）。

**混合式**，也就是真实项目的常态：用速度**大小**这一维驱动一个混合空间（待机/走/跑/冲刺的连续过渡），同时用阈值判断"要不要切到跳跃状态"；用速度**方向**驱动另一个混合空间（左/前/右/后的朝向）；转身、落地、受击则完全交给状态机。同一份参数集，被三种消费者各取所需——这也正是"参数必须集中"的第二个理由：**消费者一多，各自去捞数据就必然对不齐时刻**。

这里还有一件事值得点破：不论喂进来的是"输入"还是"速度"，只要有东西在持续驱动，最后都能得到一段连续变化的动画。**真正不可替代的是参数这一层本身**——它把"上游有哪些数字、它们是什么语义"固定成了一份清单，前面那几类坑能被定位，靠的都是这份清单（怎么用这份清单排查，见「边界与坑」末尾）。

写下来大概是这样一份结构（表达结构，不求可运行）：

```cpp
// flags: -O0 -g

// 动画参数集：本帧唯一的一份快照
// 所有字段都要求在同一个时间点被填好，之后整个动画求值过程只读
struct AnimParams {
    // 运动类：连续量，喂给混合空间的坐标
    float Speed;              // 水平速度大小，决定"跑多快"的动画
    float Direction;          // 相对角色正面的朝向角（-180~180），决定"朝哪跑"
    bool  bIsMoving;          // 速度大小超过某个死区，避免原地待机时抖

    // 状态类：离散量，当作状态机的转移条件
    bool  bIsFalling;
    bool  bIsCrouching;
    bool  bIsArmed;

    // 输入类：表达"玩家想干什么"，与 Speed 严格区分
    // 用于决定起步/停止动画何时起播，以及转向前的预动作
    Vec2  MoveInput;          // 摇杆原始值（已归一化）

    // 环境类：角色脚下的世界
    float GroundSlopeDeg;     // 地面坡度，决定走坡时是否换一套姿势
};
```

读这份结构抓到一点就够：**每个字段都标注了"它属于哪一类、会被哪一类消费者消费"**。参数表的设计问题基本都可以归结为"某个字段被两种不同语义的消费者同时用了"——比如 `MoveInput` 被拿去当混合空间坐标，就是这个 bug 的雏形。

### 参数平滑：为什么不能直接驱动动画

到这里，参数已经能决定姿势了。但直接接上去，手感会很糟，原因和"输入 vs 速度"那条是同一个：

**输入是突变的**——键盘按下去就是从 0 到 1，中间没有过渡。**角色动作不该突变**——真人的启动有个加速过程，动画的姿势也应该有个爬升过程。所以参数在驱动动画之前，通常要**先过一道平滑**：不要"这一帧速度是 0，下一帧就是 400"，而是**让参数花几十毫秒爬到目标值**。

平滑的对象通常是**连续量**（速度大小、方向、坡度），状态类的布尔量一般不平滑——它要么真要么假，中间态没有意义（硬要平滑就成了"半蹲"这种没法定义的姿势）。方向有个例外：**角度必须走最短弧**，从 170° 平滑到 -170° 应该走 20°，而不是绕 340°——这和 [[Notes/动画系统/旋转与变换基础/四元数插值：Slerp与归一化|Slerp 与归一化]] 里"点积选最短路径"是同一回事，只是这次发生在**参数**上，而不是骨骼旋转上。

这里的取舍必须讲清楚，因为它是**纯手感调优**、也是"动画手感"最核心的几个旋钮之一：

| 平滑程度 | 行为 | 玩家的感受 |
| :--- | :--- | :--- |
| 太少（系数接近 1） | 参数紧跟原始值 | 动作抖动、动画在待机和跑步之间闪烁切换 |
| 刚好 | 参数几十毫秒爬到位 | 动作有重量感、过渡自然 |
| 太多（系数接近 0） | 参数远远落在后面 | **操作迟滞**——按了键，角色半天才动 |

而实现这个平滑时，有一个**会真实发生的跨设备差异**：

```cpp
// flags: -O0 -g
#include <cmath>

// ❌ 错误写法：每帧插值固定比例
// 30fps 时 1 秒插 30 次，144fps 时插 144 次
// → 同一份代码，高帧率机器上参数爬得更快、动作更跟手
void TickWrong(float dt, float target, float& value) {
    value += (target - value) * 0.1f;
}

// ✅ 正确写法：把"每秒的比例"换算到这一帧
// 先给一个与帧率无关的基准：每秒把差距追掉 99.8%（剩下 0.2% 交给下一秒继续追），
// 再按 dt 折算这一帧该推进多少。这样无论一秒被切成 30 份还是 144 份，结果都一样。
void TickRight(float dt, float target, float& value) {
    const float kPerSecond = 0.998f;           // 基准：每秒追掉 99.8% 的剩余差距
    const float k          = 1.f - std::pow(1.f - kPerSecond, dt);
    value += (target - value) * k;
}
```

两种写法的差别是数量级的，不算不知道：144fps 下一秒钟要插值 144 次，就算每次只挪 10%，一秒后也会挪到目标的 **99.99997%**；而 30fps 下只插 30 次，同样一秒后只到 **95.76%**（`0.9³⁰`）。差距还在继续拉：30fps 下要追到 99.8% 需要 **58 帧、约 1.9 秒**，高帧率那边不到 **0.4 秒**就追完了。

**这就是"必须懂"级别的坑**：它不是一个数学洁癖，而是一个会实际发货出去的体验差异。写错的那份代码在开发机（144Hz）上调出来的手感，到了家用机 30fps 上会**明显变钝**；玩家在低配机器上骂"这游戏操作不跟手"，而你本地完全复现不出来。

平滑本身属于哪个环节？它是**参数的事，不是姿势的事**：平滑的是那个数字（速度从 180 爬到 320），不是混出来的骨骼旋转。

## 边界与坑

- **参数未初始化**：角色刚生成、或刚切进新的动画实例时，参数集里还是一堆 0。速度 0 通常问题不大（正好是待机），但**布尔量默认为 false** 会让"在空中"判断失效——角色在出生点悬空的那一帧会摆出站立姿势。所有布尔参数要有**明确的默认值**，别依赖零值。
- **参数为 0 的退化**：方向参数为 0 不一定是"朝前"，可能只是"还没算"——在混合空间里它落在坐标原点，会把角色拉向前方那组采样点。用方向之前先确认"这一帧方向真的算过了"。
- **输入 vs 实际速度混用**：解剖见上文「输入不是速度」。这里只留判据：**这个数字是"想"还是"是"**。
- **参数更新频率与动画求值频率不一致**：参数按游戏帧更新，动画却可能因为 LOD 降频（远处的角色隔帧甚至隔几帧才求值一次）。此时参数是被**跳帧采样**的——表现为远处的角色动画偶发抖动、或者转身时突然转一大截。排查方法是在调试面板里看参数曲线是否连续。
- **多个系统写同一个参数**：两个组件都往"速度"上写、技能系统和移动系统都在改"是否在攻击"，最终值取决于执行顺序。**表现是"偶尔动画不对，但是复现不了"**——因为复现条件依赖那一帧两个系统的先后。一个参数只能有**一个写入方**，其他系统想影响它，要通过明确的接口，而不是直接赋值。
- **同时写多个参数但不一致**：`Speed = 0` 但 `bIsMoving = true`，或 `bIsFalling = true` 但同时 `bIsOnGround = true`。这种自相矛盾的组合会把动画图推进"逻辑上不该存在"的分支，表现为姿势卡在某个奇怪的中间态。**同一批参数应该在同一个函数里一次性写全**，不要分散在多个 tick 里。
- **平滑系数用了帧率相关的写法**：展开见上文「参数平滑」一节；结论是跨设备手感不一致，修法就是把系数按 dt 折算。
- **平滑用在布尔量上**：给"是否在空中"做了插值，于是它变成 0.5。节点拿它当开关用的时候就看不懂了——有的按"非零即真"处理，角色在起跳那一帧仍被判成在跑；有的按"大于 0.5 才算真"，于整个上升段都被判成"不在空中"。两种表现都很糟，但原因和修法完全不同：**布尔量不平滑。**

> [!tip] 调试动画的第一步永远是「把参数打出来看」
> 上面这些坑里，绝大多数在视觉上是**同一个症状**：动画不对。**只盯着姿势看，永远分不出是"参数错了"还是"节点配错了"**。所以标准动作是先把这一帧的参数值显示在屏幕上或者打印出来——速度多少、方向多少、落地标志真假——然后才去看动画图。步骤反了，你会在动画图上白折腾半天。
>
> 这也是"参数集中收集"最实用的一条回报：**有一个确定的、完整的参数表可以打**。

## 一句话总结

动画不是"播一段"，而是**被一组游戏参数驱动**出来的：所有上游状态（速度、方向、是否落地、坡度）必须先集中收集成一份**本帧唯一的参数快照**，节点只读不自己去捞——这样才有确定的时序、一次同步点和可调试性；参数落到姿势有阈值、连续、混合三种映射方式，但落到姿势之前**必须先按 dt 平滑**（否则要么抖、要么迟滞、要么在不同帧率的机器上手感不一样），且**永远区分"玩家想怎样"和"角色现在怎样"**。

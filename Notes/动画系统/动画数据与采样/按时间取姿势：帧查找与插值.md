# 按时间取姿势：帧查找与插值

> [!todo] 本篇核心问题
> 给定任意时间点，怎么高效取出一帧姿势？

## 为什么需要解决这个问题

先看一个具体的画面：角色正在跑，`t = 2.37` 秒。

这个 `2.37` 是**连续**的——渲染帧间隔是多少，它就以那个步长往前走一点（60fps 就是每帧 +0.0167s）。但美术在 DCC 里做动画时，只会在**几个时间点**上摆姿势、"咔嚓"存一下，这些存下来的姿势叫**关键帧（Keyframe）**；中间那 2.30s ~ 2.40s 之间的 2.37s，磁盘上根本没有。

于是每一帧都要现场做同一件事：**拿连续的时间 `t`，去离散的关键帧里翻出附近的两张，按比例把中间的姿势算出来**。这个动作叫**采样（Sampling）**。

它必须很快，因为它是全链路里被调用次数最多的操作：一个角色身上有上百根骨骼——这里的"骨骼"不是骨头，而是一个**没有长度、只标定位置和朝向的坐标架**（见 [[Notes/动画系统/角色资产与骨骼基础/骨骼的本质：从骨架到 Skeleton 资产|骨骼的本质]]），每根骨骼都有一串随时间变化的位置采样点和一串旋转采样点（也就是上一篇说的**轨道**，一条轨道 = 一根骨骼的一个分量沿时间轴铺开的一串采样点，见 [[Notes/动画系统/动画数据与采样/动画数据的本质：关键帧与采样#数据结构：一条轨道 + 一组轨道|轨道与关键帧]]），一条轨道就要跑一趟采样。

采样的产物是一份**姿势（Pose）**——当下这一刻，整个骨架每根骨骼分别转到了什么角度、挪到了哪里。而这一整套还要乘以"同时在场上的角色数"——大世界里几十个角色同时在动是常态。

所以这篇里的每个设计选择，最后都是在回答同一句话：**能不能再省掉一次查找、一次三角函数。**

本篇处理数据流里的哪一站：

```mermaid
graph LR
    A[动画资源<br>离散关键帧] --> B["采样站（本篇）<br>连续 t → 一份姿势"]
    B --> C[混合 / 状态机]
    C --> D[IK 等后处理]
    D --> E[蒙皮矩阵]
    E --> F[渲染]
```

输入是一个浮点时间 + 一份关键帧轨道，输出是一份完整的骨骼姿势。

## 直观理解：在时间轴上投一根针

把一段动画的播放时间轴画成一把尺子，每一个关键帧是尺子上的一道**刻度**（关键帧自己带时间戳，从 0 开始往后排）。动画播放时，那根**指针在尺子上匀速往前滑**。

"取出一帧姿势"就是三个动作：

1. **把指针挪到正确的位置**——尺子上要有个原点、有个走得快慢可调的速率，尺子本身还有总长度。指针该落在哪，得先算出来。
2. **量出指针夹在哪两道刻度之间**——这就是帧查找。注意尺子上的刻度是**从小到大排好序**的（第 2 秒不可能排在第 1 秒前面），这是个极值钱的性质：它意味着可以**跳着找**。
3. **按"指针离左刻度多远"把这两道刻度的姿势调匀**——这就是插值。

这一步的全部难点，恰好就藏在第 1 步和第 2 步的接缝处：**指针的位置算错了，或者刻度找错了一格，插值再精确也没用**，观众看到的是动作跳帧、位置错位。

## 核心机制

### 第一步：先把"播放时间"翻译成"采样时间"

这是全篇最容易出事、又最容易被跳过的一步。原因很朴素：**动画的"时间轴"不止一条，而采样的钥匙只认其中一条。**

- **原始时间轴**：关键帧自己带时间戳，从 0 排到总时长（长度 = 2.5s 的动画，最后一帧就在 2.5s 处）。不同动画的总时长、帧率都可以不一样——走路 27 帧、跑步 21 帧都无所谓，它们的轴各自独立。
- **播放时间轴**：角色身上的播放器在推的那个 `t`。它有三个旋钮：
  - **播放速率 PlayRate**：`2.0` 表示两倍速播。动画和游戏速度对不上时（比如角色移动变慢了，脚步却还在快跑）就调它——但**调速率不改变采样精度**，它只让指针走得快慢不同。
  - **循环 Loop**：播到末尾要不要绕回开头——跑步、待机必须循环。
  - **起始偏移 StartPosition**：从动画的哪一秒开始播。它存在的理由很实际：同一段跑步动画，左腿在前和右腿在前是同一条轨道的**不同相位**（相位就是"在同一段循环里走到了哪个时间点"）——切动画时从 0.5s 起播，左右腿就不会瞬间对调。

三个旋钮都得先作用完，才能拿结果去查关键帧：

```text
采样时间 = wrap(StartPosition + 已播放时长 × PlayRate, 总时长)
```

`wrap` 是"绕回"：循环动画绕回一圈内的位置，不循环的动画超界就钳（clamp）死在两端。

### 第二步：帧查找——为什么不能从头线性扫

指针位置拿到手，接着要回答：`t` 落在哪两个关键帧之间。

最直白的写法是"从头扫"：从第 0 帧开始，一帧一帧看 `关键帧[i].time <= t < 关键帧[i+1].time`，谁成立就是谁。逻辑没错，代价却很致命——**关键帧可能有几百上千个**（一段 10 秒 30fps 的动画就是 300 个关键帧，动作细腻的更多）。

数一下这笔账（为了有个具体数，就假设这段动画有 1000 个关键帧）：扫描平均要走过一半的关键帧（500 次比较），乘上每帧的轨道数（假设 150 根骨骼 × 2 条轨道 = 300），再乘上同屏角色数（50 个），**光"找"这一件事，一帧就是 7,500,000 次比较**。这些比较全是白烧的——插值真正需要的信息只有"哪两道刻度夹住了指针"这两条。

因为**关键帧时间是单调递增的**（这是资源导出时就保证的性质），可以用**二分查找**：先跳到时间轴正中，看指针在左半边还是右半边，然后只在那一半里重复——每问一次就把候选范围砍掉一半。这就是尺子上"跳着找刻度"的正确姿势：**1000 个关键帧最多问 10 次，500 次比较塌缩成 10 次**。

```cpp
// flags: -O0 -g

// 位置轨道存 Vec3、旋转轨道存 Quat，结构相同，这里用 T 代表元素类型
template <typename T>
struct Track {
    // Times 单调递增——这是二分能成立的前提，也是资源导入时就要保证的
    // 约束：Count >= 2（只有一帧的动画在更上层就被拦掉了，见「边界与坑」）
    const float* Times;
    const T*     Values;   // 与 Times 一一对应：同一时刻的姿势分量
    int Count;

    // 找出"夹住 t 的那两个关键帧"，返回左关键帧下标
    int FindSegment(float t) const {
        // 越界先钳制住，保证返回值 i 满足 i+1 < Count
        if (t <= Times[0])            return 0;
        if (t >= Times[Count - 1])    return Count - 2;

        // 二分：维持不变式 Times[lo] <= t < Times[hi]，区间收窄到相邻两帧即停
        int lo = 0, hi = Count - 1;
        while (hi - lo > 1) {
            int mid = (lo + hi) / 2;
            if (Times[mid] <= t) lo = mid;   // 指针在右半边（含 mid）
            else                 hi = mid;   // 指针在左半边
        }
        return lo;
    }
};

// 采样一帧：先找区间，再算局部的插值比例
struct PoseKey { Vec3 Pos; Quat Rot; };

PoseKey Sample(const Track<Vec3>& posTrack, const Track<Quat>& rotTrack, float t) {
    // 两条轨道的时间戳是对齐的，所以只需查一次
    int   i     = rotTrack.FindSegment(t);
    float t0    = rotTrack.Times[i];
    float alpha = (t - t0) / (rotTrack.Times[i + 1] - t0);   // 注意这里的分母可以是 0

    Quat a = rotTrack.Values[i];
    Quat b = rotTrack.Values[i + 1];
    // 双重覆盖：两端隔了大半圈时先把 b 取负，否则姿势会绕远路翻转
    if (Dot(a, b) < 0.f) b = -b;

    PoseKey out;
    out.Pos = Lerp(posTrack.Values[i], posTrack.Values[i + 1], alpha);
    out.Rot = Nlerp(a, b, alpha);   // 旋转不能裸 Lerp；Nlerp 内部还要再归一化一次
    return out;
}
```

### 第三步：插值——把两张姿势调匀

拿到左右两个关键帧下标 `i`、`i+1` 之后，剩下的就是插值。插值的进度不能直接用 `t`，得先归一化：`alpha = (t - Times[i]) / (Times[i+1] - Times[i])`，把"离左刻度多远"折算成 0~1 的比例——`alpha = 0` 就是左关键帧本身，`alpha = 1` 就是右关键帧本身。

这里必须回指上一篇的结论：**调匀的方式取决于分量的几何性质**。位置、缩放是普通的空间量，直接按比例平均就是对的；旋转住在球面上，直接平均会离开球面（表现为角色中途**发胖**），而且两个四元数符号相反时还会**绕大半圈**。

| 姿势分量 | 插值方式 | 为什么 |
| :--- | :--- | :--- |
| 位置、缩放 | Lerp | 平面量，中间点天然合法 |
| 旋转 | Slerp（工程上多用 Nlerp） | 球面量，直接平均会离开球面（见上） |

**为什么工程上多用 Nlerp 而不是 Slerp？** 这正是采样环节的性能账。Slerp 每根骨骼每帧要算一次 `acos` 和两次 `sin`——150 根骨骼就是 450 次昂贵的三角函数调用；Nlerp 只有乘加和一次归一化，结果在小角度下和 Slerp 肉眼无差。而相邻两个关键帧之间的旋转差**天然是小角度**（美术不会让一帧跨过 90°），所以答案自然落在 Nlerp 上。这张"什么角度该用谁"的账，[[Notes/动画系统/旋转与变换基础/四元数插值：Slerp与归一化#边界与退化|Slerp 与归一化]] 的边界一节有更完整的对照。

顺便，这两个 `alpha` 有个免费的优化：**同一条轨道的所有分量共用同一个 `alpha`**（位置、旋转、缩放的采样点时间戳是对齐的），更极端的做法是**整个骨架共用一份时间到帧号的映射**——一次查找、全场复用。这也是为什么工业实现不会"每根骨骼各查各的"。

### 优化：为什么不每次二分

即便换成二分，每次采样都还是 10 次比较，而且大多数是**白查**。

原因在于播放是**单向推进**的：这一帧的 `t` 是 2.37s，下一帧是 2.387s——指针几乎不动，而且**总是往前走**。刚才找到的关键帧下标 `i`，极大概率下一帧还是 `i`，偶尔变成 `i+1`。既然如此，二分查找那 10 次比较基本是在反复重新发现一个已知答案。

于是最朴素也最有效的优化是**缓存上次的结果**：记住上一次命中的下标 `i`，下一次从 `i` 开始往后顺序查——通常第 0 步或第 1 步就命中，代价从 10 次比较降到 1 次。

这是"知道即可"的知识点：它不会改变你调动画的方式，只是解释了一句"为什么动画系统能扛住这么多骨骼"。

```cpp
// flags: -O0 -g

// 带缓存的采样：把"上次命中的下标"和轨道放在一起
struct CachedTrack {
    const Track<Quat>& track;   // 缓存只对位置/旋转中的某一类轨道生效
    int                LastIndex = 0;   // 上次命中的区段，下一次从这里起步
};

int FindSegmentCached(CachedTrack& cached, float t) {
    const Track<Quat>& track = cached.track;

    if (t < track.Times[0]) {                        // 循环回绕 / 倒放退到 0 之前
        cached.LastIndex = 0;
        return 0;
    }

    // 单向播放时，几乎总是"原地命中"或"前进一格"，顺序推进几步就撞上
    while (cached.LastIndex < track.Count - 2 &&
           t >= track.Times[cached.LastIndex + 1]) {
        ++cached.LastIndex;
    }

    // 倒放时指针往回退，缓存失效，退化成一次二分重找
    if (t < track.Times[cached.LastIndex]) {
        cached.LastIndex = track.FindSegment(t);
    }
    return cached.LastIndex;
}
```

## 边界与坑

下面每一条，最后都会在屏幕上变成一个具体的画面。排查"动画突然不对劲"时，从这几条开始查，命中率很高。

- **~={red}两个关键帧时间戳相同 → 除零 → NaN=~**：`alpha = (t - t0) / (t1 - t0)` 的分母是 `0`，`alpha` 变成 `NaN`。NaN 的蔓延性极强：只要有一个分量是 NaN，变换矩阵、蒙皮矩阵、顶点坐标会一个接一个变成 NaN，最后的表现是**模型整块消失，或者炸成一团拉长的三角形**。这是"动画突然炸掉"的高价值嫌疑点——重点怀疑导出的资源里有重复时间戳的关键帧。
- **时间超出末尾**：循环动画应当**回绕**（`t - 总时长 × 取整`），不循环动画应当**钳制**在最后一帧。搞反了不会崩，但表现很扎眼：`t` 超出后不钳制，采样会拿"最后一对关键帧 + `alpha = 3.7`"去外插，**角色会沿最后一帧的运动趋势无限漂出去**。
- **总时长为 0（只有单帧姿势）**：分母直接是 0，或者压根凑不出"两个关键帧"。单帧动画（或某些被压扁的姿势资源）必须先拦截：只有一帧时直接返回那一帧，不做插值、也不做查找。
- **负的 PlayRate（倒放）**：指针反着走，缓存优化里的"只往后找"立刻失效（每次都退到边界再兜底重找），采样会退化成每次重新二分。倒放还要注意 `wrap` 的方向——从 0 往回绕应该绕到**末尾**，不是绕到负数。
- **超长播放的浮点累积误差**：如果时间靠"每帧累加 `dt × Rate`"推进，几分钟后误差会累积到毫秒级，而循环是拿总时长做模运算的——表现为循环接缝处**越播越对不上**，一个循环比一个循环错开一点。更稳的做法是用绝对时间（播放起点 + 已播时长）来算 `t`，而不是让 `t` 自己无限累加。
- **区间长度趋近 0 + 时间精度**：两个时间戳并不完全相同、但挨得极近时，`alpha` 的除法会放大浮点误差，表现为关键帧附近的姿势出现**微小抖动**。常见的兜底是"区间长度小于某个阈值就取最近的关键帧"。

## 一个常见误判：卡顿 ≠ 插值不对

调动画时最常见的抱怨之一是"动作看起来一卡一卡的"，第一反应往往是怀疑插值写得不对。但**更常见的原因在别处：采样率与显示帧率不匹配。**

动画资源可能按 30fps 导出，而游戏跑 60fps 甚至 120fps。指针以恒定速率前进，但在 1/30 秒的窗口里它没有跨过任何关键帧区段，于是相邻两帧渲染**采到的是同一个姿势**——1/60 秒内画面完全没变，下一帧才动一下。这是**采样率的台阶**，插值完全正确。判断方法很直接：如果卡顿是**恒定节奏**的（每两帧动一次），是采样率问题；如果是**随机位置抖动或跳变**，才回头查这篇里的时间换算与帧查找。

如何缓解（对真正的采样率问题）：让美术按高于目标帧率的规格导出、或者接受这个台阶并在设计上避免慢速大幅度动作、或者用曲线插值让相近关键帧之间的过渡更平滑。这些属于资产管线的话题，这里知道判断方法就够了。

## 一句话总结

采样就是"把连续时间翻译成正确刻度、再按比例调匀两张关键帧"：时间换算错一格表现就是跳帧错位，帧查找必须靠单调性二分（而不是线性扫），插值必须按分量分开处理——位置 Lerp、旋转走四元数插值；而真正让"动画突然炸成一团"的，通常是两个关键帧时间戳相同导致的除零。

# 动画数据的本质：关键帧与采样

> [!todo] 本篇核心问题
> 一段动画在内存/磁盘里到底是什么数据结构？

## 为什么需要解决这个问题

前四篇把"旋转怎么算、怎么插值、怎么级联成世界变换"讲完了，但这些知识默认了一件事：**每秒 60 次，你手上有一整套能用的骨骼姿势。**

那套姿势是哪来的？

美术在 Maya/Blender 里 K 关键帧，导出成 `.fbx`，再导进引擎变成 `.uasset` 之类的动画资产。一个很自然的想法是："那运行时拿到的，大概就是把 DCC 里那些关键帧原封不动搬过来吧。"

如果真是这样，这段数据会大到没法用。算一笔账：**一段 30 秒的动画、60 帧/秒、100 根骨骼**——每根骨骼每帧要存平移、旋转、缩放三个变换，旋转还是 4 个浮点数。30 × 60 × 100 = **18 万个变换**，按每个 40 字节算就是 7 MB 左右，**一段普通走路动画**。一个游戏有几千段动画，光动画资产就能吃掉几十 GB。

更糟的是：其中**绝大多数数据是冗余的**。人走路时小臂和大臂的相对角度变化很慢，60 帧/秒里相邻两帧的值几乎一样；手指这种骨骼可能整段动画只动了 3 次。全存下来，99% 是在存重复信息。

所以必然会有一个问题浮出来：**运行时真正需要的，到底是什么形态的数据？** 这一篇就回答这件事——一段动画在内存/磁盘里长什么样。它是动画链路的第一站：**这一站吐出的"一组采样点"，就是后面所有环节（按时间取姿势 → 混合 → IK → 蒙皮）唯一的原料**。

## 直观理解：动画不是"一串帧"，是"一叠曲线"

用一个贯穿全篇的比喻：**一段动画不是一本翻页动画册，而是一叠叠在时间轴上铺开的折线图。**

想象打开一个股票软件：横轴是时间，纵轴是价格，每个交易日画一个点，相邻的点连成折线。看这支股票怎么走，你不需要看它每一秒的价格——**画折线的那些点就是"关键帧"**，中间的价格由折线插出来。

动画系统里同一种东西，只是横轴换成"动画时间"，纵轴换成"某个数值"，而且同时叠着**几千条这样的折线**。每条折线叫一条**动画曲线（Animation Curve）**。

**关键认知（也是新手最容易误解的一条）：关键帧 ≠ "每一帧都有值"。**

很多人以为"30fps 的动画"意味着每 1/30 秒就存了一份完整姿势。不是的。真实数据是：**每条曲线各自稀疏**，中间的值靠插值补出来。一条曲线可能只有 5 个关键帧横跨 3 秒，也可能有 200 个关键帧——完全由美术在哪一帧按了 K 键决定。

这带来一个直接好处：**美术改动画的成本 = 改几个点，而不是改几百帧**。也带来一个直接麻烦：**"这一帧的姿势"从来不是存出来的，而是算出来的**——这正是下一篇 [[Notes/动画系统/动画数据与采样/按时间取姿势：帧查找与插值|按时间取姿势：帧查找与插值]] 要做的事。

```mermaid
graph LR
    A["DCC 里的关键帧<br/>（美术 K 出来的稀疏点）"] --> B["动画资产<br/>一叠轨道 × 每轨一串采样点"]
    B --> C["按时间取姿势<br/>（下一篇）"]
    C --> D["一帧完整骨骼姿势"]
```

## 核心机制

### 最本质的形态：一根骨骼 × 一个分量 = 一串随时间的采样点

**先把"骨骼"这个词钉死**，不然后面全是空转：游戏里的骨骼**不是骨头，也不是顶点**——它是一个没有长度、没有粗细的**坐标架**，标定了"这一节肢体此刻在哪儿、朝哪边"。它唯一携带的信息，就是一个相对父级的局部变换。这个认知没建立起来，读下文"每根骨骼要存平移、旋转、缩放"会完全摸不着头脑，所以值得先花五分钟看 [[Notes/动画系统/角色资产与骨骼基础/骨骼的本质：从骨架到 Skeleton 资产#直观理解：骨骼是一个"关节坐标架"，不是一个物件|骨骼的本质：骨骼是一个坐标架]]。

再剥到什么程度都不剩：**动画曲线的最小单位，是"一根骨骼的某一个分量，沿时间轴的一串 (时间, 值)"。**

那"一个分量"又是什么？就是上面那个局部变换拆开后的每一项：它含一个平移（三个数，X/Y/Z）、一个旋转（四元数四个数，但**它不是按轴拆的**，见 [[Notes/动画系统/旋转与变换基础/四元数的几何意义与运算|四元数的几何意义与运算]]）、一个缩放（三个数，X/Y/Z）。每一项就是一个可以单独画成折线的标量：

- **平移 X** 是一条曲线，**平移 Y** 是另一条；
- **缩放 Z** 又是一条；
- **旋转**比较特殊，它不是三条曲线，而是 4 个数各自一条曲线（下面单独说）。

所以最朴素的存储方式就是：**每个分量各存一条曲线**。手腕的"平移 X"是一条曲线，"缩放 Y"是另一条，"旋转的 4 个数"则是 4 条。

> [!warning] 曲线的粒度是"标量"，但旋转那 4 条曲线不能各插各的
> 说"手腕的旋转曲线"是句方便话。实际存的是**手腕旋转的 4 个分量各自一条曲线**——而且这 4 条曲线**不能各自独立插值**。
>
> 为什么？回想 [[Notes/动画系统/旋转与变换基础/四元数插值：Slerp与归一化#旋转直接按数平均，错在哪|四元数不能直接按数平均]]：4 个数分开插值，得到的组合点**离开了单位球面**，四元数里混进缩放。副作用就是**角色在关键帧之间"发胖"再缩回去**，像橡皮人。
>
> 所以工程上有两种选择：要么存成**逐帧完整四元数**（本帧的 4 个数必须来自同一次采样，一起插），要么像某些资产格式那样，**存成欧拉角的三条独立曲线**（每轴单独插值——代价是可能在万向锁附近异常，见 [[Notes/动画系统/旋转与变换基础/旋转的三种表示：欧拉角矩阵与四元数#万向锁到底发生了什么|万向锁]]）。

### 数据结构：一条轨道 + 一组轨道

把"一根骨骼的几个分量"打包在一起，就得到动画资产的基本存储单位——**轨道（Track）**。注意 Java/C++ 这类语言通常用「通道（Channel）」指代"单个分量的一条曲线"，本篇统一说「轨道」，指的是**一根骨骼所有分量的集合**：

```cpp
// flags: -O0 -g

// 插值模式：决定"两个关键帧之间怎么走"
enum class Interp : uint8 {
    Constant,   // 阶跃：直接跳到下一个值（定格动画）
    Linear,     // 直线连接（关键帧处速度会突变）
    Cubic,      // 三次曲线，带切线（平滑，但切线能毁掉整段动作）
};

// 一条轨道 = 一根骨骼在时间轴上的采样序列
// 它是动画资产里唯一"存数据"的结构，其余都是组织与索引
struct Track {
    int32 BoneIndex;              // 指向骨架里的第几根骨骼（不是骨骼名！）
    std::vector<float> Times;     // 关键帧时间点，严格递增；三个分量共用这一份
    Interp Mode;                  // 通常整条轨道一个模式；DCC 里可以逐关键帧不同

    // 各分量的曲线。注意一个分量不是"一根曲线一个标量"：
    //   RotKeys 一个元素就是一整组四元数——4 个数绑在一起，必须整体插值
    // 没有 K 过的分量键数组为空，整个省掉（见下）
    std::vector<Vec3> PosKeys;    // 平移：每个关键帧一个 (x, y, z)
    std::vector<Quat> RotKeys;    // 旋转：每个关键帧一个完整的四元数
    std::vector<Vec3> ScaleKeys;  // 缩放
};
```

三个字段各有一句要点：

- **`BoneIndex` 是索引，不是名字。** 这是动画资产必须和"骨架"这个独立资产绑死的原因——索引的含义由骨架定义。索引对不上，整段动画就演给别的骨头看了（见 [[Notes/动画系统/动画数据与采样/动画重定向：一套动画复用到不同骨架|动画重定向]]）。
- **`Times` 必须严格递增**，因为"取姿势"要靠它做二分查找（下一篇的主题）。有序不是可选的优化，是前提。
- **`bHasTranslation` 那类"有没有 K 过"的标记**（上面代码里体现为键数组为空）不是啰嗦：绝大多数骨骼整段动画里平移和缩放**一个关键帧都没有**，只有旋转。空数组让那些分量的键整个省掉——这就是压缩的第一个来源，细节见后面的边界段。

一段完整的动画资产，就是这些轨道的集合，外面再包一层元信息：

```cpp
// flags: -O0 -g

// 一段动画资产：轨道集合 + 让这些轨道能被正确解读的元信息
struct AnimationAsset {
    SkeletonRef     Skeleton;      // 这些 BoneIndex 是对谁说的
    float           Rate;          // 采样率（每秒多少帧），影响"帧号 ↔ 时间"换算
    float           Length;        // 总时长；循环回绕要用它取模
    bool            bLooping;      // 默认是否循环播
    std::vector<Track> Tracks;     // 只包含"真的动过"的骨骼，不是全部骨骼
};
```

注意 `Tracks` 那句注释：**轨道列表通常只包含"动过的骨骼"**。一段只有上半身挥舞的动画，下半身骨骼根本不会出现在这里——运行时没被轨道覆盖的骨骼怎么办，是本篇末尾要交代的一个坑。

### 插值模式：决定"两个关键帧之间怎么走"

到这里为止，数据只是"一串点"。真正让美术一眼看出问题的是**点与点之间那段路怎么走**——这就是插值模式。它是本篇最该讲透的一段，因为**美术报"这个动作甩得很生硬"，十次有八次是插值模式或切线被人动过**。

先看三种模式各自画出来的形状，每种都配一个能想象出来的画面。

**常量（Constant / 阶跃）**：时间没走到下一个关键帧之前，值保持不变。画出来是一串台阶。

这在游戏里不是"偷懒"，而是**正确的选择**：手指张合、武器切换、面部表情这类**离散状态**，本来就该硬切；用线性或曲线插值反而会让手指在中途出现"半张开"的废帧。

但它误用的表现非常显眼：**像定格动画**。整段动作一顿一顿地跳，帧与帧之间没有过渡。排查"这个动作怎么掉帧"时先看一眼插值模式——很可能不是性能问题，是美术不小心把模式设成了常量。

**线性（Linear）**：点和点之间用直线连。这是最符合直觉的模式，也是**默认误用的重灾区**。

它的问题在于：**速度在关键帧处会突变**。

直线段上，值随时间匀速变化；走到关键帧那一点，直接拐向下一条直线，斜率突然换了。放到旋转上，这个"斜率"就是**角速度**。角速度突变意味着什么？想象角色挥手：手臂在中间匀速转过去，到关键帧位置**"啪"地一下从匀速跳到另一个速度**——不是卡顿，是**发顿**，像有人在那一帧推了角色一把。

人做的动作几乎从来不是这样：真人的肢体会**加速、减速、越过再回拉**（想想甩鞭子、点头、呼吸）。直线连接天然做不出这些。

**三次曲线（Cubic / 贝塞尔）**：每个关键帧上除了"值"，还带两个控制手柄——**入切线和出切线**，决定曲线以什么斜率进入、以什么斜率离开这个点。两个关键帧之间的曲线，由这两组切线共同决定。

这是最像人手做的动作的模式，也是**能做坏的最多功能**：

- **切线朝同一方向且拉长** → 数值会**冲过目标再回来**（过冲）。偶尔是优点（"回弹感"），失控就是**关节反向抽搐**——膝盖在落地瞬间朝反方向弹一下。
- **两侧切线不一致** → 关键帧处出现**尖角**，本质上退化成线性，又回到"发顿"。
- **切线平行于时间轴** → 关键帧处速度归零，动作变成"到位 → 停死 → 再起步"，看起来像机器人一节节地动。

所以第三个实用结论是：**遇到"别扭/生硬/抽搐"的动作，先去看切线手柄，再怀疑别的。**

三种模式对比（这张表是给已经看懂上面故事的读者做复习用的）：

| 模式 | 中间段形状 | 关键帧处 | 典型用途 | 误用后的可见后果 |
| :--- | :--- | :--- | :--- | :--- |
| 常量 | 台阶 | 硬跳 | 手指张合、表情、武器切换等离散状态 | 整段像定格动画，一顿一顿 |
| 线性 | 直线 | **角速度突变** | 机械、UI、短促过渡 | 动作发顿，像被推了一把 |
| 三次曲线 | 带切线的平滑曲线 | 平滑（切线决定） | 人物动作、绝大多数角色动画 | 关节反向抽搐（切线过冲）、尖角、节奏被切线改掉 |

> [!tip] 一个能直接用的判断方法
> 在曲线编辑器里把某根骨骼的曲线展开看一眼：**这条曲线的形状，就是角色做这个动作时的节奏。**
> 曲线是直的 → 匀速，动作会发顿；曲线在关键帧处有尖角 → 那里有一次速度突变；曲线冲过头再回来 → 那里有一次反向抽搐；曲线在关键帧处变平 → 那里"停死"了一拍。
>
> 调动画的很多问题，本质上是"曲线形状不对"，而不是"关键帧数值不对"。

### 循环：不是插值，是把时间绕回去

"循环播放"这个需求看起来很像插值问题——"最后回到开头，中间插一下不就行了？"

**不是。循环和插值无关，它是时间轴上的取模运算。**

原因很简单：插值发生在**两个关键帧之间**，而循环发生在**时间轴的两端之外**。它们根本不在同一个维度上。循环的规则只有一条：

```text
播放时间 t 一旦超过总长 Length，就减掉 Length
```

写出来比读起来还短：

```cpp
// flags: -O0 -g

// 循环播放的全部机制：时间越界就"绕回去"
float WrapTime(float t, float Length, bool bLooping) {
    if (!bLooping) return std::clamp(t, 0.f, Length);  // 不循环：钳制在两端
    t = std::fmod(t, Length);        // 回绕：3.2 秒的动画，t=3.5 → 0.5
    return (t < 0.f) ? t + Length : t;  // 倒放时 fmod 会给负值，补一圈
}
```

> [!note]- 想深究：为什么暂停/倒放总在这几行出 bug
> `std::fmod` 对负数的结果是负的（C++ 标准如此），所以倒放时 `t = -0.3` 直接喂给下一篇的帧查找会读到非法数据。补一圈（`t + Length`）就是那行三元表达式。另外，浮点误差会让 `t` 偶尔等于或极其接近 `Length`（本该是 0），导致"循环时闪一下上一帧的姿势"。不读这段不影响理解循环机制，但自己写播放器时这两行能省你半天。

**循环最经典的坑：首尾姿势不一致，循环就会"抖一下"。**

假设一段跑步动画的第 0 帧和第 30 帧（末尾）姿势不一样——左脚在前 vs 右脚在前。循环播放时会发生什么？

播放到末尾（接近 30 帧），然后时间绕回 0，姿势**瞬间跳回开头那一帧**。于是每循环一圈，角色就**抽一下**，像被谁按了快退。

这个坑的隐蔽之处在于：**它看起来像"卡帧"或"姿势跳变"，很容易被误判成引擎的循环实现有 bug。** 实际上引擎只是老老实实执行了取模，问题在数据：**动画资产的首尾帧姿势本身就不一致。**

修法只有一个，而且是美术那边的动作：**把首尾两帧 K 成一样的姿势**。做不了完全一致时（比如跑步的左右脚交替，循环点本来就该在中间），就得靠美术调整循环区间，或者靠引擎侧的同步机制把循环点"藏"进动作里——这属于 [[Notes/动画系统/动画状态机与动画图/动画同步：过渡时机与步伐对齐|动画同步]] 的话题。

顺便一个几何上的推论：如果角色在动画里**位移过**（比如向前走 2 米），循环时它会瞬间**跳回原点**。所以循环动画要么本来就不含位移，要么把位移交给代码处理——这就是 Root Motion 的取舍，见 [[Notes/动画系统/动画播放与混合/RootMotion：动画驱动移动|Root Motion：动画驱动移动]]。

### 压缩：动画文件为什么小得"不可思议"

前面算了 7 MB，但你在引擎里见过的走路动画，往往只有几百 KB——差了十几倍。压缩这一块**知道即可**：具体的算法由引擎和资产管线在导入时离线跑完，调动画时碰不到实现细节。但知道"数据是被压过的"能解释两个现象：动画资产体积和时长不成正比；有些动作回放起来总有点"糊"，那是压缩误差。

压缩主要有三板斧（不展开）：

- **帧丢弃**：把逐帧数据先还原成密集采样，再逐帧估算"去掉这一帧后误差有多大"，误差在阈值内的帧直接删。变化慢的段落会被削掉大量帧，激烈的段落几乎不丢。
- **量化**：把 32 位浮点压成 16 位整数存。位置和缩放还能接受，**旋转对精度更敏感**——量化误差会累积成旋转漂移，所以旋转通常还需要配合"归一化重建"。
- **曲线拟合**：把一段密集采样点拟合成一条低阶多项式曲线，只存系数。

> [!note]- 想深究：压缩为什么会改变动画的"手感"
> 帧丢弃会**抹掉动作里的小起伏**——比如呼吸带动胸腔的细微起伏、肌肉的细微抖动。这些细节正是让动作"活"的东西，压缩阈值调高之后角色会显得有点"塑胶感"。
>
> 工程上的做法是**分档**：过场、特写动画用高精度，远处 NPC 用高压缩，这就是动画 LOD 的来源。知道有这么个取舍就够，不用去读压缩算法。

## 边界与坑

- **时间越界**：`t < 0` 或 `t > Length` 时有三种处理，选哪种取决于动画语义：**钳制**（停在首/尾帧，用于一次性动作播完后保持姿势）、**回绕**（循环播放）、**外推**（按曲线趋势继续算，几乎没人用，容易把姿势甩得离谱）。
- **骨骼在动画里缺失**：轨道列表只包含"动过的骨骼"。一根骨骼在整段动画里没有轨道时，它用的是**骨架的参考姿势**——也就是建模时角色摆的那个标准姿势（多半是双臂平举的 T-Pose），它是"Skeleton 里每根骨骼的局部变换"这份数据的初始值，讲透见 [[Notes/动画系统/角色资产与骨骼基础/骨骼的本质：从骨架到 Skeleton 资产#Skeleton 资产里到底存了什么|参考姿势是什么]]。这个坑的典型症状是"换一套动画后动作不完整"：不同动画资产的轨道覆盖面不一样，某根骨骼在 A 动画里被 K 过、在 B 动画里没有，切过去就**"卡"在参考姿势**——对新动作来说是错位的，但姿势本身完全合法，所以不会有任何报错。
- **首尾不一致的循环**：见上文。表现是每循环一圈抽一下，根因是数据而非引擎。
- **只有位移、没有旋转的曲线**：比如电梯、平台、一些道具。这类轨道只写平移分量，旋转保持参考姿势。角色骨骼的常态恰好相反（只 K 旋转、不动位移）——调道具动画时突然发现"它怎么自己转了 90°"，通常就是这条被忽略了。
- **关键帧数为 1 的曲线**：等价于常量，整段动画该分量恒等于那一个值。这不是错误数据，只是"K 了一帧就忘了后面的"——表现是某个分量**从头到尾纹丝不动**，混动作时会出现"别的骨骼都在动，就它僵着"。
- **`Times` 不递增**：数值上不会崩，但二分查找会失效（下一篇的帧查找直接假设有序）。DCC 导出异常或手工合并动画时偶尔会遇到。
- **零长度动画**：`Length == 0` 时取模会除零。做"空动画占位"的资产时要显式处理。

## 一句话总结

一段动画的本质是**一叠各自稀疏的曲线**——每一条记录的是"一根骨骼的某个分量"沿时间轴的一串 `(时间, 值)` 采样点，关键帧之间靠插值模式（常量/线性/三次曲线）补出来；循环不是插值问题而是时间的取模回绕，所以首尾姿势不一致时会抽一下；真正让动画文件远小于"逐帧全存"的，是帧丢弃、量化和曲线拟合这些离线压缩。

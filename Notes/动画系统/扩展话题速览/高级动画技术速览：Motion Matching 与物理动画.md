## Motion Matching（动作匹配）

**是什么。** 这是相对"状态机 + 混合空间"路线的一种**替代方案**。

传统做法是人手工搭状态机：走路是一个状态、跑步是另一个、急停是第三个，中间用一条条转移连起来，再给每个状态配上混合空间——混合空间是一张把几个朝向、几个速度的样本动画摊成的网格，按参数插值出当前"姿势"（姿势 = 这一刻每根骨骼各自摆在哪的完整描述），见 [[Notes/动画系统/混合空间与Additive/混合空间：布局与插值|混合空间]]。人搭、人连线、人调参数。

Motion Matching 换了思路：**把一大段真人动捕数据（常常几十上百段、每段几分钟）整体当作一个"动作库"，运行时每一帧去库里搜索"哪一小段动作，最接近我现在想要的状态"，直接切到那一段去播。** 配上一小段"淡入淡出"，就得到了连续的动作。它不搭状态机、不连转移线，动作的"衔接"由搜索本身保证。

**它在补哪个洞。** 传统状态机方案有两个刀口：

1. **过渡的观感**。手工 Crossfade 出来的过渡，是"两个动作叠一叠"的产物——脚会在地上滑一下、上半身和下半身的节奏对不上、急停时总要"多迈半步才停住"。这些都是人眼一眼能看出来的。
2. **工时**。一个 3A 动作游戏的主角，状态机可能有几十个状态、上百条转移，光"走 → 跑 → 转向 → 急停 → 上下坡 → 落地"这一套，美术和 TA 要磨几个月。**每加一种位移节奏，就要新增状态、新增混合空间、新增转移。**

Motion Matching 把这份手工劳动换成了"数据 + 搜索"：**摇杆一推，角色就自然动起来**——8 方向移动、急停、急转、上下坡，一套数据全包。因为每一帧都是从真实动捕里挑出来的，过渡天然连贯。这份人力省下来，就是它最大的卖点。

**代价。** 这是取舍，不是免费升级：

- **数据成本**：必须有一份量足质高的动捕库。没有动捕设备或预算的小团队，直接出局。
- **内存与搜索开销**：动捕库很大，而且每帧都要搜一遍。工程上的对策是**把"我现在是什么状态"编码成一个特征向量**（当前速度、朝向、未来几帧的轨迹、若干关键骨骼的位置），把库里的每个片段也预先编码成同样的向量，再用**特征匹配（最近邻搜索）**找最像的那一帧；配合降维和分层搜索把开销压下来。这些都是引擎内部的事，使用时不必管。
- **可控性**：搜索是"尽量像"，不是"必须播"。遇到**明确要求播某个动作**的场合（受击、处决、开宝箱、任何需要精确对位的动作），还得把它交回状态机。所以实际项目里 Motion Matching 和状态机是**共存**的——自由移动交给搜索，确定性动作交给状态机。

**什么项目才需要它。** 需要**自然、连续、高质量的移动**表现，并且**有动捕预算和成规模的团队**——典型是 3A 动作／体育／写实类。反过来说，小项目、风格化卡通、移动端，用状态机 + 混合空间通常就交付了：这些项目要么动作数量少，要么本来就不追求写实连贯，上 Motion Matching 反而是拿数据成本和调参成本换一个用户看不出的提升。

## 布娃娃（Ragdoll）与物理动画融合

**是什么。** 先说清"骨骼"这个词——游戏里的骨骼**不是那根有粗细的骨头，而是一个没有长度的坐标架**，标定某一节肢体此刻在哪儿、朝哪边（这条地基由 [[Notes/动画系统/角色资产与骨骼基础/骨骼的本质：从骨架到 Skeleton 资产|骨骼的本质：从骨架到 Skeleton 资产]] 打好，这里只取用到的那点）。正常状态下，每根这样的坐标架由动画数据来写。

**布娃娃（Ragdoll）**就是把这个写法换掉：给角色身上那一串坐标架挂上一套**物理刚体 + 关节约束**——每个坐标架变成一个会受重力、会撞墙的"胶囊/盒子"，相邻两个之间用铰链式的约束拴住，让角色能"软软地倒下去"，而不是整个模型当一块木头飞出去。

它的本质是**把骨骼姿势的来源从"动画驱动"换成"物理驱动"**。对照 [[Notes/动画系统/蒙皮与骨骼网格/蒙皮矩阵：从骨骼姿势到顶点变形|蒙皮矩阵]]：无论姿势从哪儿来，到了蒙皮那一步都是"拿骨骼的世界变换去拉顶点"，这一步完全没变——变的只是上游是谁在写这些变换。

**它在补哪个洞。** 死亡、被击飞、被爆炸掀翻，这类表现**没法预先做好**：倒的方向、力度、脚下的地形、当时身体是什么姿势，每局都不一样。手工做进动画里（也就是美术逐帧摆姿势的"K 帧"）只能覆盖有限几种情况，多出来的一律露馅。物理驱动的好处是**每次结果都不重样，而且天然符合直觉**——倒下去会被台阶卡住、会被栏杆弹开，玩家觉得"物理是真的"。

**代价与工程要点。** 纯布娃娃有三个老问题：**卡在墙里**、**关节抖动**、**穿模**（角色表面互相插进去——手臂穿进躯干、斗篷穿过腿），而且**动画和物理的接缝很难看**——上一秒还在播"被击中"的动画，下一秒整条身体瘫成物理软体，中间那一下非常出戏。

所以实践中主流不是"全布娃娃"，而是**物理动画混合（Physical Animation / Active Ragdoll）**：**保持动画驱动为主，物理只提供一个"外力／修正"**。角色被车撞了一下，动画继续控制他跑，物理只是把他上半身往旁边推一把，于是表现为"踉跄一下还能站住"，而不是直接瘫倒。这样既有物理的即时反馈，又保住了角色的可控性。反过来，从布娃娃"爬起来回到动画"也需要一个过渡期——这段时间角色是没法受控的。

**什么项目才需要它。** 需要**受击／死亡表现**的动作类项目（近战、射击、体育对抗）。反过来说，没有战斗、或者死亡只是一个"倒地消失"的过场的项目，用现成动画就够——布娃娃在这里没有任何额外收益。这里的关键取舍是：

| 方案 | 成本 | 效果与可控性 |
| :--- | :--- | :--- |
| 纯物理布娃娃 | 最低（挂上资产即可） | 表现最不可控——会卡墙、会穿模、会抖，好看程度通常不达标 |
| 物理-动画混合 | 需要大量调试（每根骨骼的物理强度、关节限制、回归动画的过渡期都要调） | 表现最好，但要投入人力，且调不好会变成"果冻人" |
| 预先做好的受击动画 + 少量物理点缀 | 最低（美术多摆几套方向） | 完全可控、出片稳定，代价是重复感 |

很多项目就停在第三行——**这是最省事也最稳的选择**，不是妥协。

## 程序化抖动与次级运动

**是什么。** **次级运动（Secondary Motion）**指的是**身体的附属部位因为主体运动而产生的滞后摆动**：跑起来尾巴甩、转身时长发扫、斗篷下摆飘、肚子随步伐起伏、触手拖在后面。它和"主体动作"的区别在于：主体动作是主动的、有意图的；次级运动是**被动的、被主体带着走的**。

这类运动逐个手工做进动画里极不划算——角色速度不一样、转向快慢不一样，尾巴该怎么甩都不一样，你不可能为每个动作都单做一套。所以改用**程序化（Procedural，算法自动生成）**的方式，这就是"程序化次级运动"。

**它在补哪个洞。**

1. **省美术工时**：不用为每个动作单独做尾巴／头发动画，一套算法自动跟着所有动作走。
2. **自适应**：角色这次转身快、上次转身慢，摆动幅度自动跟着变，不用你调。
3. **可叠加**：它是叠在任意基础动画之上的——**这和 [[Notes/动画系统/混合空间与Additive/Additive动画：叠加与增量姿势|Additive 动画]] 是同一个思路**：都在基础姿势上叠一个偏差，只不过 Additive 的偏差是美术做进资源里存好的，程序化次级运动的偏差是**当场算出来的**。

**常见做法（知道即可，不展开）。** 主流是**弹簧-阻尼（Spring Damper）/ 跟随延迟**：让尾巴尖那根骨骼去朝向"几帧之前它上一节骨骼的朝向"，滞后就自然出现了；再加阻尼和角度上限，避免它越甩越大。整套东西的调参手感很像"给骨头绑了一根橡皮筋"。

**代价。** 三个典型翻车：**穿模**（头发飘进胸口、斗篷穿过腿）、**过冲**（甩得比主运动还夸张，看着像在水里）、**帧率不稳定**（弹簧按帧推进，帧率一变表现就变，同一角色在高配机和低配手机上甩得不一样）。所以角度限制、阻尼、最大速度这几个参数必须调，且要调到位。

**什么项目才需要它。** 有**明显附属部位**的角色——尾巴、长发、披风、触手、动物、带辫子的角色。反过来说，机器人、短发角色、盔甲硬质部件通常**完全用不上**，硬加反而会让人觉得"这盔甲怎么是软的"。另外注意开销：单个角色的弹簧链很便宜，但场景里几百个 NPC 各自跑一条时就要单独评估了。

## 参考实现（UE）

| 技术 | 对应模块／数据结构 | 具体体现 |
| :--- | :--- | :--- |
| Motion Matching | UE5 的 Pose Search 系统 | 搜索数据库（`PoseSearchDatabase`）＋ 特征定义（`PoseSearchSchema`）＋ 运行时从数据库里取最匹配片段的节点，见 [[Notes/UE/第四阶段-客户端运行时层/UE-Engine-源码解析：IK、Motion Matching 与 RootMotion\|UE IK / Motion Matching / RootMotion]] |
| 布娃娃与物理动画融合 | `PhysicsAsset`（骨骼网格的物理资产）／ `FAnimNode_RigidBody` | `PhysicsAsset` 定义每根骨骼的刚体与关节约束；`FAnimNode_RigidBody` 是插进动画图里的"物理驱动"节点，可只驱动部分骨骼，从而做出动画为主、物理为辅的混合效果（底层走 Chaos 物理），见 [[Notes/UE/第四阶段-客户端运行时层/UE-Engine-源码解析：IK、Motion Matching 与 RootMotion\|UE IK / Motion Matching / RootMotion]] |
| 程序化次级运动 | `FAnimNode_SpringBone` / AnimDynamics（`FAnimNode_AnimDynamics`） | `FAnimNode_SpringBone` 是"跟随延迟型"弹簧骨骼，常用于尾巴／辫子；AnimDynamics 是带完整物理模拟的骨骼链，用于斗篷、飘带等更长的附属链；两者都挂在动画图里，作为基础姿势之上的后处理，见 [[Notes/UE/第四阶段-客户端运行时层/UE-Engine-源码解析：IK、Motion Matching 与 RootMotion\|UE IK / Motion Matching / RootMotion]] |

三个都落在"动画图里的后处理节点"这个位置——**基础动画照常求值，它们在结果姿势之上再动手**，这正是前面说的"叠加而非替换"。

## 一句话总结

Motion Matching 用"动捕库 + 每帧搜索"替换手工状态机，换来自然的移动表现，代价是数据与可控性；布娃娃把骨骼交给物理以换取无法预演的死亡／击飞，代价是难控，于是主流退回到"动画为主、物理为辅"；程序化次级运动用弹簧延迟算法替代逐帧手做附属部位，代价是穿模、过冲与调参——三者都不是升级，而是三张明码标价的取舍单。

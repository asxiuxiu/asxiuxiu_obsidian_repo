# 旋转的三种表示：欧拉角矩阵与四元数

> [!todo] 本篇核心问题
> 同一个旋转为什么有欧拉角、矩阵、四元数三种表达？各自付出什么代价、分别适合哪个环节？

## 为什么需要解决这个问题

动画系统最底层的动作是**让一根骨骼从此刻的姿态转到下一个姿态**——转头、弯膝、抬手，本质上都是「旋转随时间发生变化」。所以动画的一切计算都建立在同一个前提上：**我们得有一种可靠的方式，把一个旋转存下来、算起来**。

这听起来是件小事，但真的动手做时你会发现「存旋转」有一堆隐形的坑。想象你要在代码里给角色写一句「转身看向 +X 方向」：你打算用一个数、三个数还是九个数来描述这个旋转？选错了，轻则调起来别扭，重则模型在某个特定角度突然**猛地翻滚一下**、或者同一个旋转怎么调都对不上。欧拉角、旋转矩阵、四元数——这三者都能描述同一个旋转，但它们的「人话程度」「插值手感」「运算成本」完全不同。弄清楚各自代价，才能知道动画系统的每一站该用谁。

## 直观理解

先想清楚「一个旋转」的几何本质：**绕某根能固定住的轴，转过一个确定的角度**。就好比拧一个螺丝——螺丝的杆是轴，拧了多少圈是角度。这个「轴 + 角」的直觉，三种表示都是它的某种变体，只是把信息塞进了不同的容器里。

用一句贯穿本篇的话来记：

> **欧拉角负责「给人调」，四元数负责「在机器里跑」，矩阵负责「交给 GPU 画」。**

把这句话对应到动画数据流的最上游。旋转是一切姿势的基本单位——后面阶段的采样、混合、蒙皮都是在一堆「旋转」上做运算，所以这篇是在整条管线的源头选好「地基」：


## 核心机制

动画对「旋转表示」主要有三个诉求，恰好对应三种工具。我们从最直觉的那个讲起。

### 诉求一：要直观可读 → 欧拉角（Euler Angles）

**欧拉角**的手法最符合人的直觉：把一个旋转拆成「绕三个互相垂直的固定轴，各转多少度」三个数字。像调节一个三轴云台——横滚（roll）、俯仰（pitch）、偏航（yaw）各一个旋钮。美术想「让角色往左偏 30°」，直接改 yaw 那一个数字就行，清清楚楚，而且只占 3 个数字的内存（两个 `float` 都不到）。

但便宜没好货。它有两个致命缺陷，都会在动画里造成**肉眼可见**的翻车：

1. **顺序敏感**：三个轴先转哪个、后转哪个结果完全不同。你写 `先转X再转Y` 和 `先转Y再转X`，得到的是两个不同的姿态。为了统一，引擎必须绑定死一种顺序（比如先 X 再 Y 再 Z），一旦美术的直觉和这个顺序不符就会对不上。
2. **万向锁（Gimbal Lock）**：三个云台环是有嵌套的。当中间那环转到 ±90° 时，最外层和最内层的转轴会**重合到同一条线上**——这时两个旋钮控制的是同一个自由度，第三个自由度凭空消失了。表现就是：角色在这个特定角度附近怎么调都转不利索，姿势会突然像被"锁住"、再强行调就会猛地跳一段。后面会专门展开。

### 诉求二：要能平滑插值、不锁死 → 四元数（Quaternion）

动画天然需要「**把姿势 A 平滑地变成姿势 B**」——转头要连贯，不能 A 到 B 之间闪一下就跳过去。用欧拉角做插值，差值是三个数字各自线性挪动，但旋转不是线性量，挪中间结果会走歪路（再叠加万向锁，插值点上是乱的）。这是个数学上的硬伤。

**四元数**替掉了这个硬伤。它是「复数」思想在三维的推广——复数用一个「实部 + 虚部」描述平面上的旋转，四元数用一个实部加三个虚部（`w + x·i + y·j + z·k`，共 4 个数）描述空间旋转，且本质上就是「轴 + 角」：

$$
q = \left(\cos\frac{\theta}{2},\;\; \hat{n}\sin\frac{\theta}{2}\right)
$$

一个单位四元数就装着一根轴 $\hat n$ 和一个角 $\theta$。它有两个欧拉角给不了的好处：

- **没有万向锁**：四元数绕的是「任意一根斜轴」而不是固定三轴，不存在三环重合的问题。
- **插值天然平顺**：沿球面在两个姿态间走最短弧线（即 Slerp），无论从哪到哪都不会乱翻。

代价是它不「人话」——给美术看 `(0.7071, 0.7071, 0, 0)` 没人懂这是什么朝向；而且它多了一个冗余约束：**必须保持模长为 1**，数值误差会让它悄悄偏离单位长度，得时不时归一化。四元数的几何与运算细节是下一站，本篇先记住"它负责平滑"即可。

### 诉求三：要能高效复合、喂给 GPU → 矩阵（Matrix）

最终数据要交给显卡去变换顶点，而实时渲染就是一连串「位置(x,y,z) × 变换」的流水线运算。**矩阵**是这种运算的原生形态——回顾 [[Notes/数学基础/线性代数的本质/矩阵与线性变换#3.4 常见线性变换|旋转矩阵]]会发现，旋转矩阵就是「把坐标系的基向量转到新位置」的记录，GPU 拿到它直接做乘法和点积，快且没有任何抽象理解成本。

但矩阵为速度牺牲了一切「几何意义」：一个 3×3 旋转矩阵要 9 个数字（存位移和透视后是 4×4 共 16 个），冗余严重；连续旋转多次相乘后数值会慢慢漂移走形（不再严格正交）；更致命的是——**矩阵之间没有自然的插值**，你不能把两个矩阵"各取一半"，这在动画里是硬伤。所以矩阵适合**末端出口**，不适合在中途频繁插值。

### 三种表示的分工

看，三个诉求恰好对应三种工具，没有谁全面胜出：

| 表示 | 核心方式 | 强项 | 代价 |
| :--- | :--- | :--- | :--- |
| 欧拉角 | 3 个数，绕三个固定轴各转角度 | 直观可读、内存最小、可逐轴限制 | 顺序敏感、**万向锁**、插值会跳变 |
| 四元数 | 4 个数，轴 + 角 | 无万向锁、插值平滑、省内存 | 不直观、需保持单位模长、冗余约束 |
| 矩阵 | 9~16 个数，基向量变换记录 | 复合/渲染高效、GPU 原生 | 冗余、数值会漂移、无法插值 |

工程上最顺的做法就是**分工**：编辑器里给美术/策划用欧拉角调数，存进资源后在运行时统一转成四元数来存储和插值，最后提交渲染时再一次性转成矩阵。这样每种表示只干自己最擅长的活。

### 万向锁到底发生了什么

这是欧拉角最"看得见"的坑，单独展开。万向锁源自嵌套的三环结构（这就是为什么它叫 **Gimbal Lock**，Gimbal 就是云台上的万向支架）：

```text
       最外环(Y 轴)
      /              \
     |   中环(X 轴)    |
     |      /            \
     |     |  内环(Z 轴)   |
     |     |    (物体)     |
     |      \            /
     |        \________/
      \              /
        \__________/
```

当**中环转到 ±90°** 时，最外环的转轴会和中环的转轴（此时已横过来）指向同一条线——两个环套在同一个转轴上，其中一个的自由度就"并"进来了。表现在角色身上：原本「转头」「点头」「歪头」三个独立动作里的两个突然合二为一，你想让角色歪一下头，却发现转的是脖子——方向错乱、怎么调都对不上。这正是古老的航空航天「陀螺仪锁定」问题在骨骼旋转上的复现。

### 一个可运行的验证

下面这段用矩阵和四元数**各自**绕 X 轴转 90°，作用到同一个向量 `(0,1,0)` 上，验证它们确实描述了同一个旋转：

```cpp
// flags: -O0 -g
#include <cmath>
#include <cstdio>

struct Vec3  { float x, y, z; };
struct Mat3  { float m[3][3]; };
struct Quat  { float w, x, y, z; };

// 绕 X 轴旋转 90° 的矩阵：[[1,0,0],[0,0,-1],[0,1,0]]
Vec3 mat_rotate(const Mat3& M, const Vec3& v) {
    return { M.m[0][0]*v.x + M.m[0][1]*v.y + M.m[0][2]*v.z,
             M.m[1][0]*v.x + M.m[1][1]*v.y + M.m[1][2]*v.z,
             M.m[2][0]*v.x + M.m[2][1]*v.y + M.m[2][2]*v.z };
}

// 单位四元数旋转向量：v' = v + 2w(Q×v) + 2(Q×(Q×v))
Vec3 quat_rotate(const Quat& q, const Vec3& v) {
    Vec3 qv{q.x, q.y, q.z};
    auto cross = [](Vec3 a, Vec3 b) {
        return Vec3{ a.y*b.z - a.z*b.y, a.z*b.x - a.x*b.z, a.x*b.y - a.y*b.x };
    };
    Vec3 t  = cross(qv, v);
    Vec3 tt = cross(qv, t);
    return { v.x + 2*q.w*t.x + 2*tt.x,
             v.y + 2*q.w*t.y + 2*tt.y,
             v.z + 2*q.w*t.z + 2*tt.z };
}

int main() {
    // 绕 X 轴 90°：欧拉角 roll=90°；矩阵；四元数轴(1,0,0)角90°
    Mat3 M = {{{1,0,0},{0,0,-1},{0,1,0}}};
    Quat q{ std::cos(M_PI/4), std::sin(M_PI/4), 0.f, 0.f };   // (√2/2, √2/2, 0, 0)
    Vec3 v{0,1,0};

    Vec3 a = mat_rotate(M, v);
    Vec3 b = quat_rotate(q, v);
    std::printf("matrix   : v' = (%.3f, %.3f, %.3f)\n", a.x, a.y, a.z);
    std::printf("quat     : v' = (%.3f, %.3f, %.3f)\n", b.x, b.y, b.z);
    std::printf("max diff : %.3f\n",
        std::max({std::fabs(a.x-b.x), std::fabs(a.y-b.y), std::fabs(a.z-b.z)}));
    return 0;
}
```

预期输出是两种方式都把 `(0,1,0)` 转到 `(0,0,1)`，最大差值近似 0——证明欧拉角、矩阵、四元数在这件事上是**同一个旋转的三种说法**，可以互相转换、互相验证。

## 引擎落地（UE）

UE 把三种表示都做进了核心数学库，并严格按「分工」来用，见 [[Notes/UE/第二阶段-基础层/UE-Core-源码解析：数学库与 SIMD|UE Core 数学库与 SIMD]]：

| 引擎 | 对应模块/数据结构 | 具体体现 |
| :--- | :--- | :--- |
| UE | `FQuat`（`Quat.h`） | 运行时旋转的**主导载体**：骨骼姿势、IK、约束、动画求值大量直接用四元数运算（如 `FQuat::FindBetweenNormals`） |
| UE | `FRotator`（`Rotator.h`） | 编辑器里读给美术/策划看的**直观角**；约束与控制里用它做逐轴插值和限制，见 [[Notes/UE/第四阶段-客户端运行时层/UE-AnimationCore-源码解析：动画系统总览#2.5 专用变换类型：FEulerTransform 与 FTransformNoScale|AnimationCore 的 FEulerTransform]] |
| UE | `FTransform`（`Transform.h`） | 骨骼参考姿势以 `TArray<FTransform>` 存储（见 [[Notes/UE/第四阶段-客户端运行时层/UE-Engine-源码解析：骨骼与重定向|UE 骨骼与重定向]]），其中旋转分量 `Rotation` 就是 `FQuat`——数据在内部永远走四元数 |
| UE | `FMatrix` / 提交渲染时 | 所有四元数在组织好最终姿势后，才一次性转成矩阵交给 GPU 做顶点变换 |

一句话概括 UE 的做法：**FRotator 只出现在人类需要看的入口，FQuat 贯穿整个动画求值内部，FMatrix 是最终送给渲染器的打包形态**——恰好对应本篇「给人调、机器里跑、交 GPU 画」的分工。

## 一句话总结

同一个旋转可以用欧拉角（直观但会万向锁、插值乱跳）、矩阵（渲染快但无法插值）、四元数（平滑无锁但难读）三种方式表达，动画工程的分工是：编辑用欧拉角、内部存储与插值用四元数、提交渲染转矩阵。

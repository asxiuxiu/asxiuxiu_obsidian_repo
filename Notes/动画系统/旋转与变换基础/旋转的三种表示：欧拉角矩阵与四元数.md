# 旋转的三种表示：欧拉角矩阵与四元数

> [!todo] 本篇核心问题
> 同一个旋转为什么有欧拉角、矩阵、四元数三种表达？各自付出什么代价、分别适合哪个环节？

## 为什么需要解决这个问题

动画系统最底层的动作是**让一根骨骼从此刻的姿态转到下一个姿态**——转头、弯膝、抬手，本质上都是「旋转随时间发生变化」。所以动画的一切计算都建立在同一个前提上：**我们得有一种可靠的方式，把一个旋转存下来、算起来**。

> 这里的「骨骼」不是现实里那根有粗细、有长度的骨头，而是角色身体上一个**没有大小的坐标架**——它只回答「这个部位在哪、朝哪个方向」。骨骼连同它记录的那份朝向，构成了角色的「姿态（Pose）」。如果你对这个词还陌生，先看 [[Notes/动画系统/角色资产与骨骼基础/骨骼的本质：从骨架到 Skeleton 资产|骨骼的本质：从骨架到 Skeleton 资产]]，它讲清了骨骼为什么必须是坐标架；本篇不重复，只专注于坐标架里那个「朝哪」的分量。

这听起来是件小事，但真的动手做时你会发现「存旋转」有一堆隐形的坑。想象你要在代码里给角色写一句「转身看向 +X 方向」：你打算用一个数、三个数还是九个数来描述这个旋转？选错了，轻则调起来别扭，重则模型在某个特定角度突然**猛地翻滚一下**、或者同一个旋转怎么调都对不上。

顺带交代本篇的边界：骨骼的「姿态」由**位置 + 旋转 + 缩放**三部分拼成，但位置就是三个数线性挪动、缩放同理，几乎没有计算上的坑；**旋转是唯一一个「存储方式跟人的直觉差得远、处理不当就会翻车」的分量**。跑步时角色整体向前位移也是变换的一部分，只是简单到不值得专门讨论——本篇只把旋转挖出来放大看。

## 直观理解

先想清楚「一个旋转」的几何本质：**绕某根能固定住的轴，转过一个确定的角度**。就好比拧一个螺丝——螺丝的杆是轴，拧了多少圈是角度。这个「轴 + 角」的直觉，三种表示都是它的某种变体，只是把信息塞进了不同的容器里。

用一句贯穿本篇的话来记：

> **欧拉角负责「给人调」，四元数负责「在机器里跑」，矩阵负责「交给 GPU 画」。**

后面三节各自展开它的一角，这里只立起来、不解释。

数据流位置：这是动画链路**最上游的一次选型**——采样、混合、蒙皮各站的运算都落在「旋转」这个分量上，所以先在这里选好容器：

```mermaid

    B --> C[提交给 GPU<br>转成矩阵]
```

## 核心机制

动画对「旋转表示」主要有三个诉求，恰好对应三种工具。我们从最直觉的那个讲起。

### 诉求一：要直观可读 → 欧拉角（Euler Angles）

**欧拉角**的手法最符合人的直觉：把一个旋转拆成「绕三个互相垂直的固定轴，各转多少度」三个数字。像调节一个三轴云台（Gimbal，摄影棚里托住相机、能分别绕三个方向转动的支架）——横滚（roll）、俯仰（pitch）、偏航（yaw）各一个旋钮。美术想「让角色往左偏 30°」，直接改 yaw 那一个数字就行，清清楚楚，而且只占 3 个数字的内存（3 个 `float`，共 12 字节）。

但便宜没好货。它有两个致命缺陷，都会在动画里造成**肉眼可见**的翻车：

1. **顺序敏感**：三个轴先转哪个、后转哪个结果完全不同。你写「先转 X 再转 Y」和「先转 Y 再转 X」，得到的是两个不同的姿态。这不是理论上的吹毛求疵——**低头 90° 再向右转 90°，和先向右转 90° 再低头 90°，头最终朝着完全不同的方向**：前者是头歪向一侧、脸朝上，后者是脸朝侧面、头是正的。为了统一，引擎必须绑定死一种顺序（比如先 X 再 Y 再 Z），一旦美术的直觉和这个顺序不符，他在面板上转旋钮看到的就不是自己预期的效果，只能靠试错凑。
2. **万向锁（Gimbal Lock）**：当云台的中间那环转到 ±90° 时，两个旋钮会控制同一个自由度，第三个自由度凭空消失——角色在这个特定角度附近怎么调都转不利索，姿势会突然像被"锁住"。**这是本篇唯一展开推导的部分，见下面 [[#万向锁到底发生了什么]]。**

### 诉求二：要能平滑插值、不锁死 → 四元数（Quaternion）

动画天然需要「**把姿势 A 平滑地变成姿势 B**」——转头要连贯，不能 A 到 B 之间闪一下就跳过去。用欧拉角做插值，差值是三个数字各自线性挪动，但旋转不是线性量，挪中间结果会走歪路（再叠加万向锁，插值点上是乱的）。结果是角色转身时**转得忽快忽慢、中途还可能猛地绕一大圈**——这在走路切跑步这种一两百毫秒的过渡里格外刺眼。这是个数学上的硬伤（为什么硬伤，[[Notes/动画系统/旋转与变换基础/四元数插值：Slerp与归一化|四元数插值：Slerp 与归一化]] 会把原因刨到底，本篇只需记住结论）。

**四元数**替掉了这个硬伤。它是「复数」思想在三维的推广——复数用一个「实部 + 虚部」描述平面上的旋转，四元数用一个实部加三个虚部（`w + x·i + y·j + z·k`，共 4 个数）描述空间旋转，且本质上就是「轴 + 角」：

$$
q = \left(\cos\frac{\theta}{2},\;\; \hat{n}\sin\frac{\theta}{2}\right)
$$

一个单位四元数就装着一根轴 $\hat n$ 和一个角 $\theta$。它有两个欧拉角给不了的好处：

- **没有万向锁**：四元数绕的是「任意一根斜轴」而不是固定三轴，不存在三环重合的问题。
- **插值天然平顺**：沿球面在两个姿态间走最短弧线（这就是 **Slerp**，Spherical Linear Interpolation，球面线性插值），无论从哪到哪都不会乱翻。

代价是它不「人话」——给美术看 `(0.7071, 0.7071, 0, 0)` 没人懂这是什么朝向；而且它多了一个冗余约束：**必须保持模长为 1**（这里说的「模长」就是这四个数的平方和开根号，等价于「这个四元数是纯旋转、没有偷偷混进缩放」），数值误差会让它悄悄偏离单位长度，得时不时归一化，否则角色会越动越「发胖」。四元数的几何与运算细节是下一站 [[Notes/动画系统/旋转与变换基础/四元数的几何意义与运算|四元数的几何意义与运算]]，本篇先记住"它负责平滑"即可。

### 诉求三：要能高效复合、喂给 GPU → 矩阵（Matrix）

最终数据要交给显卡去变换顶点，而实时渲染就是一连串「位置(x,y,z) × 变换」的流水线运算。**矩阵**是这种运算的原生形态——回顾 [[Notes/数学基础/线性代数的本质/矩阵与线性变换#3.4 常见线性变换|旋转矩阵]]会发现，旋转矩阵就是「把坐标系的基向量转到新位置」的记录，GPU 拿到它直接做乘法和点积，快且没有任何抽象理解成本。

但矩阵为速度牺牲了一切「几何意义」：一个 3×3 旋转矩阵要 9 个数字（存位移和透视后是 4×4 共 16 个），冗余严重；连续旋转多次相乘后数值会慢慢漂移走形（不再严格正交）；更致命的是——**矩阵之间没有自然的插值**，你不能把两个矩阵"各取一半"，这在动画里是硬伤。所以矩阵适合**末端出口**，不适合在中途频繁插值。

### 三种表示的分工

三个诉求恰好对应三种工具，没有谁全面胜出。把前面三节各自付的代价并排放在一起看：

| 表示 | 核心方式 | 强项 | 代价 |
| :--- | :--- | :--- | :--- |
| 欧拉角 | 3 个数，绕三个固定轴各转角度 | 直观可读、最省内存、可逐轴限制 | 顺序敏感、**万向锁**、插值会跳变 |
| 四元数 | 4 个数，轴 + 角 | 无万向锁、插值平滑、体积小 | 不直观、需保持单位模长 |
| 矩阵 | 9~16 个数，基向量变换记录 | 复合/渲染高效、GPU 原生 | 冗余、数值会漂移、无法插值 |

所以工程上的做法就是开头那句话：**编辑器里给美术/策划用欧拉角调数，存进资源后在运行时统一转成四元数来存储和插值，最后提交渲染时再一次性转成矩阵。** 换个容器的能力本身就是这套方案的前提，而旋转在这三种形式之间来回倒腾，正是后面 [[Notes/动画系统/旋转与变换基础/变换层级与复合变换|变换层级与复合变换]] 要处理的日常。

### 万向锁到底发生了什么

这是欧拉角最"看得见"的坑，单独展开。万向锁源自嵌套的三环结构（这就是为什么它叫 **Gimbal Lock**，Gimbal 就是云台上的万向支架）：

```text
       最外环(Y 轴)
      /              \
     |   中环(X 轴)    |
     |      /            \
     |     |  内环(Z 轴)   |
     |     |    (物体)     |
     |      \            /
     |        \________/
      \              /
        \__________/
```

当**中环转到 ±90°** 时，内环的转轴被中环带着横了过来，恰好与最外环的转轴指向同一条线——注意中环自己的转轴是不动的（轴不会跟着自己转），重合的是**内外两环**。两个旋钮从此套在同一个转轴上，其中一个的自由度就"并"进来了。表现在角色身上：原本「转头」「点头」「歪头」三个独立动作里的两个突然合二为一，你想让角色歪一下头，却发现转的是脖子——方向错乱、怎么调都对不上。这个问题最早是航空航天领域踩到的：飞行姿态也用三个角描述，飞机俯仰到 ±90°（机头直指天空）时就会撞上同一个坑。

#### 最容易想岔的地方：局部坐标系不是一直正交吗？

第一次听说万向锁，几乎所有人都会卡在同一个疑问上：物体的局部坐标系被刚体旋转带着走，三根轴**永远**互相垂直，哪来的"锁"？这个直觉对了一半——刚体旋转确实保正交，物体最终的局部坐标系从头到尾完好无损。但万向锁说的根本不是它。这里要分清两组轴：

- **物体最终的局部轴**（X'、Y'、Z'）：永远正交，永远不会坏；
- **三个旋钮的"瞬时控制轴"**：此刻拧 yaw 旋钮物体绕哪根线转、拧 pitch 绕哪根线、拧 roll 绕哪根线。

锁说的是**第二组里有两根重合了**，这跟第一组毫无矛盾——姿态本身没有任何毛病，坏掉的是「用这三个旋钮把姿态调往任意方向」的**操控能力**：有一个方向，从这个位形出发谁都够不着。

#### 为什么三个旋钮是嵌套链，而不是平权的三兄弟

直觉上 yaw/pitch/roll 像是绕局部轴的三次平权旋转——"三根轴都跟物体走，各转各的不就行了"。但只要你把姿态**存成三个数**，就必须回答"这三个数怎么还原出姿态"；而旋转不能同时施加，只能一个接一个地复合，链条就必然有先有后：pitch 旋钮的轴在哪取决于 yaw 转了多少，roll 旋钮的轴在哪取决于 yaw 和 pitch 各转了多少。链里必须有人排第一，而第一个动手时还没有"当前姿态"可跟，它的轴只能**钉死在世界里**——这就是外环。

所以"沿局部轴旋转"不但不是云台的替代方案，它**就是**云台：绕当前局部轴依次旋转（内旋）与绕世界固定轴按相反顺序旋转（外旋）在数学上完全等价，而"每转一次带着后面的轴一起走"正是三环嵌套的机械结构本身。三个旋钮里只有最内层"完全跟物体走"，最外层"完全不走"。

#### 走查一遍：机头竖直朝天时，三个旋钮各在干什么

前面用的是飞机的例子，因为它最好想象。把 pitch 拉到 90°，机头直指天空：

- 拧 **yaw**（钉死的世界竖直轴）→ 飞机绕竖直轴打转；
- 拧 **pitch**（机翼横轴，现在是水平的）→ 把机头压回水平或继续后翻，这个旋钮还正常；
- 拧 **roll**（机头纵轴）→ 机头正指着天，纵轴**就是**世界竖直轴——和 yaw 旋钮撞了车。

此刻你真正想做的动作往往是"机头保持朝天、绕机体自己的竖直轴横扫"——抱歉，三个旋钮谁都不提供它，它恰好是被"并"掉的那个自由度。真实飞机蹬舵就能做到（舵面绕的是机体轴），但面板上存成三个数的姿态做不到。

**回到角色身上，这就是同一个坑。** 角色把头仰到 90°（对应 pitch 到极限）时，再想让他「保持仰头、把脸从左边甩到右边」，三个欧拉角旋钮同样给不出这个动作：你会发现在这个位形下改 yaw 和改 roll 转的是同一个方向，脖子僵在半空、脸要么甩不过去要么突然翻过去。**只要骨骼转到那 90° 附近，美术在编辑器里就会立刻撞上这个现象**——这也是为什么限制骨骼旋转范围时，要避开这个奇异角度。

#### 锁不住物体，锁的是"三个数的地图"

更深一层看，万向锁不是欧拉角的设计失误，而是数学必然：三维旋转的全貌铺不平成三个独立数字，就像任何一张平面地图都画不好整个地球——总有一个点（北极点）上"经度"失去意义。锁不在物体上，也不在局部坐标系上，而在「用三个数描述姿态」这张**地图**上。

**这对工作的意义很直接**：既然"锁"只在"把姿态拆成三个数"时发生，那么只要**不拆**，就永远遇不上它——姿态存在四元数里，每次改动都是绕当前轴乘上一个小增量旋转，永远不需要拆回三个全局角度。~={green}编辑器面板上显示给美术看的 yaw/pitch/roll 只是从四元数**反解出来的读数**，不是存储本身、也不是控制源——所以角色在渲染和插值时不会因为面板上那几个角度而中招。=~

这也解释了为什么欧拉角**可以继续在编辑器里用**：它不是被淘汰的旧方案，只是被限制在了"给人读数、给人调参"这个安全的位置上，不参与运行时的旋转运算——这正是开头那句分工话的下半句。

### 代码表达：矩阵与四元数，同一次旋转

下面这段用矩阵和四元数**各自**绕 X 轴转 90°，作用到同一个向量 `(0,1,0)` 上——代码不是用来跑数值的，只用来表达两种表示在「结构上怎么描述同一件事」：

```cpp
// flags: -O0 -g
struct Vec3  { float x, y, z; };
struct Mat3  { float m[3][3]; };
struct Quat  { float w, x, y, z; };

// 绕 X 轴旋转 90° 的矩阵：[[1,0,0],[0,0,-1],[0,1,0]]
Vec3 mat_rotate(const Mat3& M, const Vec3& v) {
    return { M.m[0][0]*v.x + M.m[0][1]*v.y + M.m[0][2]*v.z,
             M.m[1][0]*v.x + M.m[1][1]*v.y + M.m[1][2]*v.z,
             M.m[2][0]*v.x + M.m[2][1]*v.y + M.m[2][2]*v.z };
}

// 单位四元数旋转向量：v' = v + 2w(Q×v) + 2(Q×(Q×v))
Vec3 quat_rotate(const Quat& q, const Vec3& v) {
    Vec3 qv{q.x, q.y, q.z};
    auto cross = [](Vec3 a, Vec3 b) {
        return Vec3{ a.y*b.z - a.z*b.y, a.z*b.x - a.x*b.z, a.x*b.y - a.y*b.x };
    };
    Vec3 t  = cross(qv, v);
    Vec3 tt = cross(qv, t);
    return { v.x + 2*q.w*t.x + 2*tt.x,
             v.y + 2*q.w*t.y + 2*tt.y,
             v.z + 2*q.w*t.z + 2*tt.z };
}
```

矩阵的乘法是 9 个系数与 3 个坐标的线性组合，四元数则是叉积链的复合——两种结构都编码了同一个旋转，只是表达方式不同。**实际工作中你几乎不会手写这两个函数**，但看懂它们的结构差异能让你明白：为什么"把矩阵转成四元数"是**有损的近似**（矩阵里那 9 个数并不总能干净地折回 4 个数，数值漂移过的矩阵尤其如此）。

| UE | `FQuat`（`Quat.h`） | 运行时旋转的**主导载体**：骨骼姿势、IK、约束、动画求值大量直接用四元数运算（如 `FQuat::FindBetweenNormals`） |
| UE | `FRotator`（`Rotator.h`） | 编辑器里读给美术/策划看的**直观角**；约束与控制里用它做逐轴插值和限制，见 [[Notes/UE/第四阶段-客户端运行时层/UE-AnimationCore-源码解析：动画系统总览#2.5 专用变换类型：FEulerTransform 与 FTransformNoScale|AnimationCore 的 FEulerTransform]] |
| UE | `FTransform`（`Transform.h`） | 骨骼参考姿势以 `TArray<FTransform>` 存储（见 [[Notes/UE/第四阶段-客户端运行时层/UE-Engine-源码解析：骨骼与重定向|UE 骨骼与重定向]]），其中旋转分量 `Rotation` 就是 `FQuat`——数据在内部永远走四元数 |
| UE | `FMatrix` / 提交渲染时 | 所有四元数在组织好最终姿势后，才一次性转成矩阵交给 GPU 做顶点变换 |

## 一句话总结

三种表示是同一个旋转的三副面孔：欧拉角给人读、四元数给机器算、矩阵给 GPU 画；选用哪个，看那一步最缺的是「好调」「好插」还是「好算」。

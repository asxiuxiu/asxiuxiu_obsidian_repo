# 动画同步：过渡时机与步伐对齐

> [!todo] 本篇核心问题
> 走路切跑步、起跳切落地时，怎么保证脚不滑、步频对得上？

## 为什么需要解决这个问题

先把本篇反复要用的两个词交代清楚（一句话版本，细节见链接）：

- **姿势（Pose）**：角色某一瞬间的**完整样子**——所有骨骼此刻各自是什么变换，一份快照。走路的一帧是一个姿势，跑步的一帧是另一个姿势。见 [[Notes/动画系统/动画播放与混合/姿势混合：加权与跨渐变|姿势混合：加权与跨渐变]]。
- **骨骼**：游戏里的"骨骼"不是那根看得见的骨头，而是一个**没有长度的坐标架**，标定某一节肢体此刻在哪儿、朝哪边。所谓"相位对齐"，对齐的就是每根骨骼在循环上各自走到了哪一步。见 [[Notes/动画系统/角色资产与骨骼基础/骨骼的本质：从骨架到 Skeleton 资产|骨骼的本质：从骨架到 Skeleton 资产]]。

角色在走，玩家按下 Shift，[[Notes/动画系统/动画状态机与动画图/动画状态机：状态与转移|状态机]] 把「走路」切到「跑步」。两个动画各自都在漂漂亮亮地循环，混合曲线也拉得平滑——**但屏幕上角色的两只脚同时在往地上踩，或者一只脚突然在半空里往前窜了一下。**

这个现象业内叫**鬼步**（foot sliding / foot skating / ghost step）。它不"卡"、不"跳"，混合得很顺滑，却**一眼就让人看出这个游戏的动作品质很差**——玩家说不出哪里错了，只会说"感觉很廉价、像漂着走"。

对照一下另一个失败方式：**过渡本身没做平滑**。所谓过渡，就是在一两百毫秒里把两段动画的姿势按权重揉在一起——如果这个过程没做好（比如直接把权重从 0 跳到 1，中间不经过任何中间值），角色的姿势会"啪"地跳变——那是个**看得到的跳变**，容易定位。鬼步的问题在于它**隐藏在平滑里**：数字一切正常，每一帧的姿势都是合法的，只是**脚下的世界不认这个姿势**。

先看清它为什么必然发生，机制就顺理成章了。

**每个动画的「播到哪儿了」是彼此独立的。** 走路动画总长 1 秒，跑步总长 0.6 秒。当两者都播到 `t = 0.3s` 时：

- 走路播了 30%，正是**左脚触地那一瞬**；
- 跑步播了 50%，正是**右脚离地、荡到半空**。

如果"同步"的办法是**把两者的播放时间都设成 0.3 秒**，那么混合出来的姿势就是"左脚落地"和"右脚荡在半空"的平均——**一个人类做不出来的姿势**。而"两只脚同时落地"，正是这个不存在的姿势在屏幕上的样子。

所以本篇要回答的核心问题是：**两段动画要"对得上"，对的到底是什么？**

## 直观理解：两段音乐同时播放

用一个贯穿全篇的比喻。

**每段循环动画是一张唱片**，唱针的位置就是"播到哪儿了"。走路这张唱片转一圈 1 秒，跑步这张 0.6 秒。

现在要把两张唱片**同时放着、并且混在一起听**（姿势混合就是"同时听"——把两份完整姿势按权重合成一份）。最直觉的办法是"让两张唱片的唱针位置一样"——都放到 0.3 秒处。但这在音乐上立刻是错的：**同样的秒数，落在两首曲子的不同小节上**。一首在副歌、一首在前奏，叠起来是噪音。

音乐人不会用秒数对齐两首曲子，他们会用**拍子**——"都在第 2 拍的第 3 个八分音符上"。不管曲子几分钟长，**"第 2 拍"这件事是对得上的**。

这个"拍子位置"就是动画里的**相位（Phase）**：它不看秒数，只看"**播到循环的百分之几**"。走路的 0.5 秒（半圈）= 相位 0.5，跑步的 0.3 秒（半圈）= 相位 0.5——**秒数不同，拍子相同，所以它们该在同一时刻混合。**

把比喻再推一步，就能看到本篇最容易被搞混的那个区分：

| 对齐方式 | 比喻 | 动画里的结果 |
| :--- | :--- | :--- |
| 对齐**秒数**（都播 0.3s） | 两首曲子都放到第 0.3 秒 | 走路的 30% 撞上跑步的 50%：**一个左脚落地、一个右脚荡空** |
| 对齐**相位**（都到 50%） | 两首曲子都跳到第 2 拍 | 两者都是"循环一半"那个姿势，**混出来的东西人做得出来** |

**这就是本篇的核心答案：同步对齐的是相位，不是时间。** 时间相同恰恰是错的。

数据流位置：本篇机制坐在「[[Notes/动画系统/动画数据与采样/按时间取姿势：帧查找与插值|采样]] → **选段与对齐** → 混合」这一站，属于状态机与混合之间的**调度层**——上游是 [[Notes/动画系统/动画状态机与动画图/动画状态机：状态与转移|状态机]] 决定"这一帧该播哪几段"，下游是采样器按时间把姿势取出来，本篇插在中间，负责把时间算对。它不产生姿势，也不修改姿势——它决定**每段动画这一帧该播到哪一时刻**，把时间喂给采样器。输入端是状态机的转移决策与当前的移动速度，输出端是每段动画的播放位置（一个秒数）。和它紧挨着的下一站是 [[Notes/动画系统/动画播放与混合/姿势混合：加权与跨渐变|姿势混合]]：本篇保证"参与混合的几段动画姿势对得上"，那一站负责"把它们按权重揉成一个"。

## 核心机制

### 相位：与时长无关的进度

一个循环动画的**相位（Phase）**，就是**当前播到循环的第几个百分比**，取值 0~1：

$$
\text{phase} = \frac{t \bmod \text{length}}{\text{length}}
$$

它是**归一化时间**（Normalized Time）的另一种叫法，强调它代表"循环周期上的位置"而不是"过了多久"。

相位之所以有用，全靠一个约定：**同类动作的动画，会在相同的相位上做相同的事**。美术做走路和跑步时，都习惯把"左脚落地"放在循环的开头附近、"右脚落地"放在一半附近——**这个约定就是相位能对齐的全部前提**。

> [!tip] 相位是资产约定的产物，不是数学必然
> 引擎算不出"左脚落地发生在相位的几分之几"——它只知道你给的曲线和关键帧。**相位对齐要成立，得美术在制作时把两段动画的姿势在循环上摆到一致的位置**；摆不一致时，靠下一节的「同步标记点」来补救——那是一种**人手动打在时间轴上的命名旗子**，用来告诉引擎"这里发生了什么"，下文细讲。

### 同步组：让一组动画共享同一相位

有了相位的定义，机制就只剩一句话：**把该一起混合的几段动画标记成"同组"，让它们共享同一个相位**。

```cpp
// flags: -O0 -g

// 同步组：一组"拍子对得上"的动画共享相位
// 主控（leader）通常是在播的、权重最大的那一段；其余是跟随者（follower）
struct SyncGroup {
    // 主控的归一化相位（0~1），本帧由主控自己的播放推进得出
    float LeadingPhase;

    // 把每个跟随者按相位换算到自己的时间轴上
    // 关键：分母是"自己的时长"，不是主控的时长
    static float PhaseToTime(float phase, float ownLength) {
        return phase * ownLength;   // 同一个相位，各自的秒数
    }
};

// 反过来：任意一段动画当前的自有时间 → 它自己的相位
float GetPhase(float time, float length) {
    if (length <= 0.f) return 0.f;              // 零时长守卫（见"边界与坑"）
    float t = std::fmod(time, length);
    if (t < 0.f) t += length;                   // 播放速率为负时 fmod 会返回负数
    return t / length;
}
```

读这段代码只抓一件事：**相位与秒数之间的换算，分母永远是"那一段动画自己的时长"**。

把三个情景并排看一遍，这个区分就刻进去了：

| 情景 | 主控播放时间 | 主控相位 | 跟随者时长 | 跟随者该播到 |
| :--- | :--- | :--- | :--- | :--- |
| 走路（1.0s）主控，跑到一半 | 0.5 s | 0.50 | 0.6 s | **0.30 s** |
| 走路主控，刚起步 | 0.25 s | 0.25 | 0.6 s | **0.15 s** |
| 走路主控，播完一圈 | 1.0 s | 0.00 | 0.6 s | **0.00 s**（回绕，见坑） |

**这样对齐之后，两只脚就同时落在"同一个动作事件"上了**——走路在 0.5 相位（左脚落地），跑步也被推到它自己的 0.5 相位（也是左脚落地）。混合出来的姿势，是同一个动作在两个速度下的插值，人做得出来，脚不滑。

### 对齐什么时候做、谁说了算

机制的第二半是"时机"。

**同步不是每帧强行扯平。** 如果每帧都把跟随者硬拽到主控的相位上，那么跟随者的播放时间就完全由主控决定了——它自己的播放速率形同虚设（跟随者的时间轴会瞬间跳跃）。正确的分工是：

- **过渡开始的那一刻对齐一次**——让两段动画从同一个相位起步；
- **过渡期间各播各的**——各自按自己的播放速率推进，只是让**速率**保持比例（下一节）。这样两段动画的相位会**一起**向前走，混合全程都对得上。

**谁当主控（leader）？** 两种常见选择：

- **以目标状态为主控**：过渡到跑步时，以跑步的相位为准，把走路拽过来对齐。因为过渡结束后留下来的是跑步，让它从"自然的位置"继续播更合理。
- **以权重更大的一方为主控**：过渡进行到一半之后自动换手，避免刚过 50% 时相位跳一下。

选错的后果很具体：**过渡结束后步频对不上**——走路的相位虽然在混合期间被拉到了跑步的节奏上，但过渡一结束走路被丢掉、跑步从自己被拽过的位置继续播，如果对齐过程有跳变，就会看到"过渡完成的一瞬间脚步节奏乱了一拍"。手感上表现为"切跑步之后先乱两步再顺"。

### 镜像问题：只对相位会把左右脚对反

前面各节都隐含了一个假设：**走路和跑步把同一条腿的落地放在循环的同一相位上**。这个假设**经常不成立**。

美术做动画时，同一条腿在循环里的位置可能完全相反：走路是**左脚起步**（左脚落地在 0.25），跑步做成了**右脚起步**（右脚落地在 0.25，左脚落地在 0.75）。两段动画各自都很标准，但它们**在循环上的事件位置是错开的**。

此时如果仍然"裸相位对齐"，会发生什么：

- 走路的 0.25 相位（**左脚落地**）被对到跑步的 0.25 相位（**右脚落地**）；
- 混合出来的姿势里，两条腿的相位差了半拍——**两只脚打架**：一只往前迈的同时另一只也在往前迈，看起来像"两条腿同时抢着走"，比单纯的鬼步更刺眼。

解法是让资产自己交代"循环上都有哪些关键事件"：在做动画的时候，**在时间轴上的某些时刻打上带名字的标记**——比如在"左脚落地"那一帧打一个叫 `LeftFootDown` 的标记，在"右脚落地"那一帧打一个叫 `RightFootDown` 的标记。这个标记就是「**同步标记点**」（Sync Marker）：**它是打在某一段动画时间轴上的一个"命名时刻"，不带任何变形数据，纯粹是一句备注**——"播放到这里的时候，左脚落地了"。同步时：

1. 取主控**当前所在的、或最近经过的**标记点；
2. 在跟随者里**找同名的标记点**；
3. 把跟随者的时间轴对齐到那个同名标记点上，而不是对齐裸相位。

**这就是"为什么动画资产里要标 sync marker"的答案**——它把"左右脚"这个语义补给了引擎。引擎自己只看得见数字，看不见哪只脚。

对齐路径上还有两个必须处理的细节，都属于"没处理就会出现可见抽动"的范畴：

- **回绕（相位从 1 回到 0）**。如果主控刚跨过循环末尾、相位回到 0.02，而跟随者还停在 0.95，对齐算法要**沿前进方向**走（让跟随者 0.95 → 1.0 → 0.02），而不是倒着从 0.95 退回 0.02。方向算错，跟随者会在过渡瞬间**倒退一大截**——屏幕上就是那条腿"抽"一下。
- **跨越标记点过渡时的配对方向**。同理，配的应该是"下一个同类标记点"，而不是"最近的那一个"。

### 步频与速度绑定：脚滑的另一半原因

相位对齐解决的是"**过渡期间**脚不滑"。还有一半脚滑发生在**稳态下**，而且更常被玩家看到：**角色移动速度变了，动画播放速率没变。**

角色从 200cm/s 加速到 400cm/s，走路动画还是 1 秒一圈——**动画里的步幅是固定的（一步 100cm）**，一秒走完一圈本来应该前进 200cm，现在角色一秒被推出去 400cm。多出来的 200cm，只能靠**脚在地上擦过去**补——这就是持续性的脚滑。

这里的物理关系其实很简单：**动画的"步幅"是固定量，想让脚不滑，动画的播放频率必须与移动速度成正比。**

$$
\text{PlayRate} = \frac{\text{角色当前速度}}{\text{该动画在 PlayRate=1 时对应的速度}}
$$

分母那个数就是"这段走路动画画的是多人快"——它通常是美术做动画时的参考速度，或者从 **Root Motion** 的位移量反推出来（这一段见 [[Notes/动画系统/动画播放与混合/RootMotion：动画驱动移动|Root Motion：动画驱动移动]]：Root Motion 恰好提供了"这段动画播完一圈，角色在世界里该走多远"这个权威答案）。

**这里有取舍，不能无脑按比例缩。** 比例缩放的幅度一大，动画就会**快得不像人**：极慢的速度会把走路拉成"太空漫步"（每一帧都在原地缓缓挪），极快则变成鬼畜抽搐。工程上的两条常见约束：

- **给 PlayRate 加上下限**（如 clamp 到 `[0.5, 1.5]`），超出范围时接受一点脚滑，换取可接受的动画节奏；
- **在两端换动画而不是继续加速**：走得慢就切到"走"、快了就切到"跑"，靠**切换不同动画**来覆盖速度区间，而不是把一段动画拉到极限。这也正是 [[Notes/动画系统/混合空间与Additive/混合空间：布局与插值|混合空间（BlendSpace）]] 存在的意义——它是"用速度选动画"的自动化版本。

### 过渡时机：响应性还是观感

最后一块拼图是"**什么时候发起过渡**"。相位对齐保证过渡**过程中**对得上，但"在哪一帧按下切换"本身也影响观感。两条策略：

- **条件满足立即切**：玩家按下 Shift 的下一帧就切过去。**响应快**，但可能切在"半步中间"——脚还抬在半空，跑步动画已经接管，画面像被剪了一刀。
- **等合适的相位再切**（如"等这只脚落地后再切"）：观感干净，因为新动画是从一个语义明确的事件点（脚落地）接管的。代价是**有延迟**——玩家按下按键后，角色可能还要等 200~300 毫秒才真的加速，**输入没有立刻被回应**。

这是一个**纯手感决策，没有正确答案**：多数动作游戏对响应性更敏感（宁可突兀也不能延迟，玩家会觉得按键失灵），而写实向、注重画面连续性的作品可以等相位。实际项目里常见的折中是**不等相位、但把过渡时长压短**——用快一点的混合掩盖切入点的突兀。

## 边界与坑

- **同步组里只有一段动画**：什么也不会发生。同步的全部意义在于"多段之间对齐"，只有自己一段时对齐恒等——安全，不需要特判。
- **时长差异过大**：1 秒的动画和 0.2 秒的动画强行同步，跟随者相当于被强制缩放 5 倍播放——**动作会完全变形**（该有的过渡姿势全被跳过去，看起来像快放）。这种情况下同步带来的收益小于畸形播放的损失，**不该配成同步组**。经验上，两段动画时长在一倍以内时同步才有意义（走 ↔ 跑、走 ↔ 后退走都合适）。
- **标记点缺失**：资产没标 sync marker 时，机制退化成裸相位对齐——**左右脚错开就没人管了**，表现为过渡瞬间两条腿打架。这也是接手别人项目时"动画切得怪"的一个高频原因：不是配置错，是资产里压根没打标记。
- **相位回绕**：相位从 0.98 跨到 0.02 时，如果按"数值差"计算插值方向，会得到"往后倒 0.96"——**腿在过渡时抽一下**。对齐必须按前进方向计算跨越量。
- **Loop 与 One-shot 混进同一组**：One-shot 指的是**一次性动作**——播放一遍就结束、不循环，比如起跳、落地、挥刀。它没有循环概念，相位对它无意义（"播到循环的百分之几"这句话对一段不循环的动画无从谈起）。把它和循环动画塞进同一个同步组，只会得到"起跳动画被拉到走路的三分之一处"这类随机结果。**别这么配**——起跳/落地这类过渡应该用相位采样点或独立处理（起跳接下落时，做的是"从起跳的某一点开始播下落"，而不是同步一个相位）。
- **零时长动画**：时长 ≤ 0 的资产算相位会除零，必须守卫（返回 0），否则整组的时间轴会变成 `NaN` 并污染整个姿势。
- **播放速率为负（倒放）**：此时求余运算可能返回负数，相位需要补一个周期拉回正数，否则对齐结果落在 `[0,1)` 之外。

## 参考实现（UE）

| 引擎 | 对应模块/数据结构 | 具体体现 |
| :--- | :--- | :--- |
| UE | 同步组配置挂在**资产播放器节点**上：`GroupName`（组名）+ `GroupRole`（该节点在组里的角色，`EAnimGroupRole`）+ `Method`（`EAnimSyncMethod`，决定按组还是按标记点同步） | 给同一组里的节点填同一个 `GroupName` 就完成了"同组"声明，角色决定谁当主控（`CanBeLeader` / `AlwaysLeader` / `AlwaysFollower` 等）；实际对齐在 Update 阶段由 Sync Group 完成，见 [[Notes/UE/第四阶段-客户端运行时层/UE-AnimGraphRuntime-源码解析：动画图与BlendSpace\|UE 动画图与 BlendSpace]] |

一句话点评：UE 把**"拍子"（sync marker，逐段动画各自记录、可镜像）** 和 **"组"（Sync Group，在 Update 阶段对齐）** 这两件事分开处理——这正是本篇讲的两层机制：标记点负责语义（哪只脚），组负责调度（何时对齐谁）。

## 一句话总结

两段动画要一起混合，对的是**相位**（播到循环的百分之几）而不是秒数——时间是各自的时间，拍子是共同的拍子；靠同步组在过渡开始时对齐一次、靠同步标记点解决"左右脚对反"、靠 PlayRate 正比于速度解决稳态脚滑，而"立即切还是等相位切"是一道纯粹的手感取舍题。
